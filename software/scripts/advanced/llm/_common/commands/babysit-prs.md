[Sy] Run `/sy-babysit-pr` on EVERY open PR in scope. This command is a fan-out wrapper — it resolves a list of target PRs (from `$ARGUMENTS`), ranks them by how much work they are owed, and dispatches them **all at once, in parallel background jobs**, each in its own git worktree. One job per PR while job slots last; past that, PRs are **assigned** to the running slots rather than queued behind them, so every resolved PR is serviced in the same run.

**Recommended order.** Run `/sy-review-prs` first (verdict pass), then `/sy-babysit-prs` (this command). Reversing wastes babysit cycles on PRs that would be requested-changes anyway.

**This is the command for "sync all my PRs with main, babysit them, address comments — all at once, in the background, with worktrees."** Every part of that ask is already in scope: the branch sync is `/sy-babysit-pr` Step 5, which delegates to `/sy-sync-pr-branch` (default branch + the whole ancestor chain on a stack); comment remediation is Steps 6–7; background + worktree + all-at-once is Step 4 below. Route any plain-English phrasing of that request here — do not hand-roll a loop, and do not call `/sy-sync-pr-branch` yourself first; every job already runs it.

Argument: $ARGUMENTS (optional — selects scope; the first token decides the mode, no mixing).

- **Empty** — babysit every open PR authored by `@me` for git repos at or below cwd, two levels deep (see Repo discovery). (Default behavior.)
- **PWD keyword** — first token (case-insensitive, trimmed) is one of the PWD keyword set defined in `/sy-list-prs`. Scan repos up to 2 child levels below cwd and babysit `@me` open PRs in those repos only.
- **Explicit PR refs** — one or more whitespace-separated PR refs. Each ref is one of:
  - full URL: `https://github.com/<owner>/<repo>/pull/<n>`
  - shorthand: `<owner>/<repo>#<n>`
  - bare `#<n>` or bare digits `<n>` — only valid when the current working directory is a git repo with a GitHub `origin`; resolve `<owner>/<repo>` via `git remote get-url origin`, never from the folder name (see Repo Identification).

## Steps

1. **Resolve target PR list from `$ARGUMENTS`.** Pick exactly one branch:

   a. **Empty `$ARGUMENTS` or PWD keyword** — delegate to `/sy-list-prs short pwd` (scope = pwd, format = short). Parse the emitted URLs (one full PR URL per line, grouped under `##` headings). **Do not pre-filter the READY TO MERGE group, or any other group** — a green PR still gets a slot and still gets its passes, and `/sy-babysit-pr` Step 4's early exit is what turns each of those passes into a cheap documented no-op. Pre-filtering here is how a PR ends the run with zero passes, which is exactly what Step 3b exists to make impossible; it also assumes "green right now" means "green in 90 minutes", which a fan-out this long routinely disproves. If zero PRs resolved, report it and stop.

   b. **Explicit PR refs** (any other `$ARGUMENTS` — treat as whitespace-separated tokens):
   - For each token, normalize to a full PR URL:
     - Full URL → use as-is.
     - `<owner>/<repo>#<n>` → expand to `https://github.com/<owner>/<repo>/pull/<n>`.
     - `#<n>` or bare digits → require cwd to be a git repo; resolve `<owner>/<repo>` via `git remote get-url origin` (never from the folder name), then expand. If cwd is not a git repo, error out naming the unresolvable token and ask the user to use a fully-qualified ref.
     - Anything else (not a URL, shorthand, `#<n>`, or digits) → error out, name the bad token, do NOT silently skip.
   - For each resolved URL, fetch metadata to match the search-result shape used downstream:
     `gh pr view <url> --json number,title,headRefName,baseRefName,isDraft,url,createdAt,updatedAt,author`. **`gh pr view` has no `repository` field** (see the `gh` field traps in `/sy-list-prs`) — the owning `<owner>/<repo>` is the one you already resolved from the ref itself.
   - De-duplicate by URL.

2. **Announce:** Tell the user which scope mode was resolved (`pwd scan of <N> repos` for empty/PWD args, or `explicit list of <N> PRs`), how many PRs were resolved, and list them (repo, PR number, title). If any resolved PR is authored by someone other than you (`gh api user --jq .login`), include the author on every listed PR and call the split out explicitly — explicit-ref mode does not filter by author, so babysitting someone else's PR is easy to do by accident.

   **Also announce the stacks.** Stack detection needs `headRefName` + `baseRefName`, and **the PWD path does not have them yet** — `/sy-list-prs short` deliberately skips the per-PR branch fetch (see its Fetch PR data notes), so only the explicit-refs path of Step 1b has them already. Fill the gap the same way `/sy-review-prs` does: one `gh pr view <url> --json headRefName,baseRefName` per resolved PR, which is also the call whose result the worktree path depends on. Then detect stacks from the set itself: any PR whose `baseRefName` equals another PR's `headRefName` is stacked on it. Chain those links and print each stack bottom-up (`<root link> ← <child link> ← <grandchild link>`), noting that they merge in that order. This is display only — it does not change dispatch (Step 3b still assigns every PR before anything launches) and it never makes one job wait on another.

3. **Render the resolved PR set as a table** so the user sees exactly what is about to be babysat. Delegate to `/sy-list-prs table <same-scope-token>` — `/sy-list-prs` accepts the same scope vocabulary as this command (empty / PWD keyword / explicit refs), so pass the same scope `$ARGUMENTS` (prefixed with `table`) and let it render. Single source of truth for the table layout lives in `/sy-list-prs`.

3a. **Open the ping-pong pulse — emit the FIRST one before dispatching anything.** Render `/sy-list-prs pingpong <same-scope-token>` with every Agent cell at `⚪ NOT STARTED`. This is the baseline the user compares every later pulse against; a fan-out that goes quiet for an hour before its first status line is the exact failure this exists to prevent. Layout lives in `/sy-list-prs` — do not hand-roll it.

Start the **agent ledger** here: one row per resolved PR holding job state, loop number, **slot number and position within that slot**, first dispatch time, last pass start / end, next pass ETA, **that PR's latest `## State` block verbatim** (the round counter, per-check attempt counters, `automerge_decision`, and workspace path + kind + ownership that `/sy-babysit-pr` hands back after every `pass=single` pass), and the **last rendered pulse snapshot** (Status color emoji, component lines, counters strip). The state block is not bookkeeping trivia — it is the only copy of what a re-invoked per-PR job cannot remember, so the next round's prompt is built from it and a replacement job for a dead slot is seeded from it. A ledger without it makes every round a first round. The snapshot is what `/sy-list-prs pingpong` diffs to pick the `Δ` / `▫️` / `🆕` change marker and write the `Δ` line — overwrite it with what was just printed after every pulse, so each pulse compares against the one immediately before it. Record the slot number and position for every PR at assignment (Step 3b), including the ones sitting at position 2+: the pulse groups its board by feature set and prints `🌊 slot <N>` on every row, and a missing slot silently degrades that row to an ungrouped one. Record every timestamp the moment it happens (dispatch, pass start, pass end, next-pass ETA) — the pulse's `started 17:12 · running 22m` clock is read straight from this ledger and cannot be reconstructed after the fact. Never snapshot the elapsed duration itself; it is recomputed at render time and is deliberately excluded from the diff. The ledger is this command's bookkeeping; `/sy-list-prs` only renders it.

3b. **Rank every PR, then assign every PR to a slot — before anything launches.** The harness caps how many background jobs can run at once. With more PRs than slots, the naive fan-out services the first `S` and silently strands the rest; this step is what makes "EVERY open PR in scope" true rather than aspirational.

- **Resolve `S`, the concurrency cap.** Default to **8**. It is a property of the harness, not of this command, so treat it as a parameter: a `cap=<positive-int>` token in `$ARGUMENTS` wins over the default, as does the user naming a cap in prose. Reject anything that is not a positive integer — fall back to the default and say so, because `S = 0` makes `i mod slot_count` a division by zero and `S < 0` makes the whole assignment meaningless. **Strip the `cap=` token from `$ARGUMENTS` before any scope parsing**, and never forward it to `/sy-list-prs`; left in place it is read as a PR ref by Step 1 and as a scope token by every delegated render. Say which value you used and where it came from.
- **If the launch is partially rejected, cancel and relaunch — never inject the rejects into a running slot.** Slot prompts are immutable and self-contained by design (Step 4), which is exactly why a live slot cannot be handed extra PRs; the dead-slot rule forbids the same mutation for the same reason. When only `k` of `slot_count` jobs actually start:
  - **`k == 0` is a launch failure, not a cap discovery.** Report it and stop — do not set `S = 0`, which makes `i mod slot_count` a division by zero and would "recover" into launching nothing at all.
  - **Cancel the `k` that started and confirm each one is actually terminated before relaunching.** Two jobs on one PR is worse than a stranded PR: they push over each other, double-comment, and race on the same worktree.
  - **Collect what the cancelled jobs already did.** A first pass is short but not empty — a job may already have pushed a fix, posted a comment, or enabled automerge. Take each PR's `## State` block from the ledger (jobs report ownership changes the moment they happen, precisely for this) and seed the relaunched slots with it, so previously-enabled automerge is not misread as `pre_existing` and already-done work is not repeated.
  - Then set `S = k`, re-deal the **entire** ranked list round-robin into `k` slots, and launch that set in one message. These jobs are sleep-dominated, so cancelling a partial first pass costs almost nothing. Report the discovered cap and the re-deal, since the new slot map supersedes the one already announced.
- **Rank all `N` resolved PRs by the work-owed ranking, read through the AUTHOR lens** (the default) — the canonical tier list lives in `/sy-list-prs` (`## Work-owed ranking`): P0 unshipped work → P1 someone waiting on a reply → P2 broken and ours to fix → P3 stale against base → P4 bot nits only → P5 waiting on someone else → P6 nothing owed, ties broken on oldest `updatedAt`. Do not restate or re-derive the tiers here; read them there. Babysitting acts for the PR's author, so the tiers apply in their listed order — `/sy-review-prs` is the one that reorders them. Say which lens you used when reporting the slot map. Ranking decides **order only** — it never removes a PR from the set.
- **Open `slot_count = min(N, S)` slots and deal the ranked list round-robin**, not in chunks: ranked PR `i` (0-based) goes to slot `i mod slot_count`. Dealing beats chunking because it puts the top `slot_count` PRs each at the **head of their own slot** — every one of them gets serviced in round 1. Chunking would pile the four most urgent PRs into slot 1 and make three of them wait behind the first.
- **Every PR has a slot before the first job launches.** There is no queue and no "wave 2". A resolved PR with no slot assignment is a bug in this step, not a backlog — go back and assign it.
- **Report the slot map at dispatch** — one line per slot listing its PRs in service order with each one's tier (`slot 3: github.com/acme/api/pull/51 (P1) → github.com/acme/web/pull/7 (P5)`). This is the artifact that proves nothing was stranded, and it is the first thing to check when a PR looks ignored.
- **Warn — do not refuse — when a slot holds more than 3 PRs.** `N > 3 × S` means each round costs three-plus passes of wall time before the shared sleep, so the run stretches. Say so, name the number, and carry on; servicing all of them slowly beats servicing `S` of them and abandoning the rest.

4. **Fan out one background job per SLOT — all at once, in parallel.** Do NOT walk the list sequentially.

   **Dispatch mechanics — this is the step agents get wrong.** "In parallel" is a hard requirement, not a hint:
   - **Emit every slot job in ONE assistant message with `slot_count` tool calls in that same message.** One sub-agent / Task / background-shell invocation per slot, all in a single block. A second message per slot is a sequential loop wearing a parallel costume — that is the failure mode this section exists to prevent.
   - **Never** `for pr in ...; do ...; done`, never "start job 1, wait, start job 2", never a staggered launch. Every slot starts at the same instant.
   - **One slot = one job = one lane. When `N ≤ S`, one slot holds exactly one PR** and this is the classic one-job-per-PR fan-out. A slot only holds several PRs because there were more PRs than slots — that is the carve-out to the "never a single job that iterates the PR list" rule, and it is the _only_ one: a slot iterates **its own assigned PRs**, never the whole list, and never a list it chose itself.
   - **Jobs share nothing** — no cwd, no branch, no state file, no conversation. A slot job must never read another slot's result or wait on it. Within a slot, each PR still gets its own worktree; the slot switches between them, it does not merge them.
   - **Each slot job's prompt is self-contained.** Pass, explicitly: its **ordered list of assigned PRs** with each one's tier, and for every one of them the full PR URL, the resolved `<owner>/<repo>` (from `git remote get-url origin`, never the folder name), the PR number, the canonical worktree path `$HOME/.worktrees/<owner>/<repo>/<repo>__pr-<number>` (what `git create-worktree "$BR" <number>` produces), **the full list of every other PR URL in the whole dispatched set** — all slots, not just this one (its batch siblings, needed by `/sy-babysit-pr` Step 2a's companion check so a docs PR does not merge ahead of the code), and **the stack position from Step 2 when that PR is in one** (its ancestor PR links bottom-up and its children, so the job knows it must not merge before its parent). Sub-agents start with a fresh context — anything you don't pass, they don't have.
   - **Do not pre-create worktrees from the dispatcher.** Each job owns the worktree lifecycle of every PR it holds (`/sy-babysit-pr` Step 5a create/reuse and cleanup). The dispatcher never runs `git worktree add`, never `cd`s anywhere, and never touches the user's primary checkout.
   - **A cancelled fan-out leaves live worktrees — re-running resumes them, it does not start over.** Jobs killed mid-flight (session ended, run cancelled, machine slept) leave dirty worktrees and unpushed commits at the canonical paths. That is recoverable state, not garbage: `/sy-babysit-pr` Step 5a picks each one back up, and the Step 3b ranking scores exactly that state as **P0**, so a resumed run services it first. Never pre-clean `$HOME/.worktrees` before a fan-out, and never pass jobs an instruction to reset or re-clone.
   - **Report the fan-out the moment it's launched** — the slot map from Step 3b, with every PR's job and worktree path — so the user can see the whole set covered, not a prefix of it.

   **What a slot job does — interleave rounds, never run one PR to completion first.** This is the make-or-break rule of a multi-PR slot. A slot that ran the full `/sy-babysit-pr` loop for PR A (≥3 passes, ~1.5h) before touching PR B has simply moved the starvation somewhere less visible. **The slot owns the cadence:**
   - **One round = one pass on each PR the slot holds, in its assigned order, then ONE shared 30-minute sleep.** Invoke `/sy-babysit-pr <PR-URL> pass=single round=<n>/<total>` per PR, **and paste that PR's `## State` block from the previous round into the job's prompt under a `## Prior state` heading** (omit the heading entirely on round 1). `pass=single` makes the per-PR command run one pass and return instead of sleeping and looping itself; `round=` tells it whether this is the last round, which is what defers workspace cleanup; the prior-state block is what keeps its counters, automerge decision, and workspace ownership from resetting to zero every round. Dropping any of the three silently turns a 3-round slot into three disconnected first passes.
   - **Run at least 3 rounds**, so every PR in the slot still gets its ≥3 passes, 30 minutes apart — the floor from `/sy-babysit-pr` Step 12, honored by the slot instead of by the per-PR job. A slot holding one PR is behaviorally identical to plain `/sy-babysit-pr`.
   - **Re-rank the slot's own PRs at the top of every round** using the same work-owed ranking, so a PR that just picked up a `CHANGES_REQUESTED` moves ahead of one that is idle. **Re-ranking sets the order within the round — never whether a PR gets a pass in that round.** Every PR the slot still holds gets exactly one pass per round regardless of its tier, so a PR that ranks last forever is serviced last forever, not skipped. Re-rank within the slot only — never steal a PR from another slot mid-run.
   - **A PR that reaches a terminal state drops out of the slot's rotation** (merged, closed, or escalated to a human). Report it, stop passing it, and let the remaining PRs have the round to themselves.
   - The 30-minute sleep is per round, not per PR — that is what makes packing a slot nearly free. These jobs are sleep-dominated: a pass bursts a handful of `gh` calls and then waits, so three PRs in one lane cost three passes of work and **one** sleep, not three sleeps.

   - Expect long runtimes: every PR gets **at least 3 passes 30 minutes apart**, so a run takes 1h+ by design, longer as slots fill. That is the point — do not shorten it, and do not poll the jobs in a busy loop. Collect each result when its job reports back.
   - If one job fails or escalates, the others keep running; never abort the whole fan-out for a single PR. **If a whole slot job dies, relaunch that slot — do not fold its PRs into a live one.** A dying slot frees exactly the capacity it was using, so a replacement job fits without exceeding `S`, and pushing its PRs into a neighbour would both silently double that lane's round length and violate the "a slot's assignment never changes mid-run" rule. Launch the replacement with the dead slot's **remaining** PRs (drop the ones that already reached a terminal state) plus a checkpoint of what it got through — each PR's last `## State` block from the dispatcher's ledger.
   - **Resume per PR from its own `completed_round + 1`, not from a single slot-wide round number.** A slot almost never dies on a round boundary: it dies after PR A finished round 2 and before PR B started it. Restarting the whole slot at round 2 gives A a second round-2 pass minutes after its first, breaking the 30-minute spacing that is the entire point of the cadence; restarting at round 3 silently robs B of round 2. So the replacement first services only the PRs still owing the interrupted round, takes the one shared sleep, and from the next round on runs the full rotation again — the slot re-unifies naturally once every PR is level. This is exactly why the state block carries `completed_round` per PR rather than a round counter per slot.
   - If the slot died with no capacity to relaunch into (the whole run is being torn down), report its PRs as partially serviced with their per-PR round counts, so the next invocation picks them up as P0.
   - **Parallelism is safe because every PR gets its own git worktree** at a rigid, collision-free path — **`$HOME/.worktrees/<owner>/<repo>/<repo>__pr-<number>`**, created by `git create-worktree` (see One rigid worktree path). The PR number keys the path, so no two PRs share a working tree — across slots or within one — and none of them touch your primary checkout. Never let a job `git checkout` in the main repo.
   - The per-PR command owns the pass. This wrapper owns only which PRs run in which lane and when — if the per-PR flow needs to change, edit `/sy-babysit-pr`.

4a. **Ping-pong every 10 minutes until every job reports.** The fan-out runs an hour-plus by design (≥3 passes, 30 min apart), so the dispatcher's job while it waits is to keep a pulse on the wall — not to sit silent, and not to busy-poll the jobs.

- **Cadence: one pulse every 10 minutes**, from dispatch until the last job reports. Three pulses per babysit pass, so a sleeping job still shows a live heartbeat with its next-loop ETA.
- **Render with `/sy-list-prs pingpong <same-scope-token>`, passing the current agent ledger.** Same scope token as Steps 3 and 3a, so every pulse covers exactly the dispatched set. Never hand-roll the board.
- **Refresh the Status column from GitHub, not from the jobs.** Re-run the cheap `gh pr view` status calls `/sy-list-prs` already uses. **Never `write_agent` / message / interrupt a running job to ask how it's doing** — that wakes a sleeping pass and corrupts its 30-minute cadence (see the busy-poll rule in Step 4). Read job state only from results the jobs have already reported.
- **Update the ledger from reports as they land** — a job finishing pass N on a PR moves that row to `⏸️ WAITING (loop N/3)` with `next loop <ETA>`; a job's final report for a PR moves it to `✅ COMPLETED` / `⚠️ ESCALATED` / `❌ FAILED`. A PR sitting at position 2+ of a slot whose earlier PRs are still mid-pass stays `⚪ NOT STARTED` with its position and the link it is behind. Between reports, derive `IN PROGRESS` vs `WAITING` and the next-loop ETA from the known cadence (round end + 30 min) rather than leaving the cell blank.
- **A pulse is display-only.** It never dispatches, retries, cancels, merges, comments, or re-assigns a slot. If a pulse shows a job wedged, say so in that row and let the human decide. A pulse that notices a **dead** slot reports it and nothing more — the relaunch is Step 4's job, taken outside the pulse, and it relaunches the dead slot rather than moving its PRs anywhere.
- Stop pulsing when every row is terminal (`✅ COMPLETED` / `⏭️ SKIPPED` / `⚠️ ESCALATED` / `❌ FAILED`), then go to Step 5. **`⏸️ WAITING_AFTER_SKIP` is not terminal** — that PR still has passes scheduled, so the pulse keeps running.

5. **Final report:** emit the **closing ping-pong** — one last `/sy-list-prs pingpong <same-scope-token>` with the final ledger and `Next ping-pong: — (final)` — followed by one `/sy-list-prs table <same-scope-token>` render and a short summary of which PRs were skipped (already green), which were processed, and which need human attention. Include each PR's pass count (`<N>/3`), its slot, and its worktree path (reused vs created), and note any worktrees left behind because they pre-existed. **State explicitly that every resolved PR was serviced** — count the rows and compare against the Step 1 resolved count; a mismatch is the failure this command's slot assignment exists to prevent, so name any PR that got zero passes and why. The run therefore always brackets itself: pulse at the start (Step 3a), pulse every 10 min (Step 4a), pulse at the end.

## Rules

- This command is a dispatcher. The per-PR loop lives in `/sy-babysit-pr` — do not re-implement it here.
- **Prose-only PRs in a fan-out do NOT self-merge — they wait for their batch.** `/sy-babysit-pr` Step 2a only enables `--auto` on a _standalone_ docs / comment / whitespace PR, and every PR in this dispatched set counts as a companion of every other. So a docs PR inside a fan-out is deferred until its siblings merge or close, then self-merges on a later pass. That is what keeps documentation from landing ahead of the code it describes. A fan-out of exactly one PR is standalone by definition and may self-merge immediately. Say which docs PRs are deferred in the Step 2 announce; the dispatcher itself never enables or disables automerge.
- **Base-branch sync is already included — never bolt it on.** Each job's `/sy-babysit-pr` Step 5 delegates to `/sy-sync-pr-branch`, which merges the default branch and, on a stacked PR, every ancestor branch up the chain — before the job does anything else. Do not call `/sy-sync-pr-branch` from the dispatcher, do not `git merge origin/main` here, and do not add a "sync pass": the same sync would run twice and race the jobs' own worktrees.
- **Parallel means one message, `slot_count` tool calls — not `N` (Step 4 Dispatch mechanics).** The job count is `min(N, S)`, never the PR count: launching one job per PR past the cap is what strands the tail. If the transcript shows the slot jobs starting one message at a time, the fan-out was sequential and must be relaunched. Self-contained prompt per slot, no shared state.
- **Every resolved PR is assigned before anything launches — never queue, never drop (Step 3b).** One job per PR while slots last; past the concurrency cap, the surplus PRs are dealt round-robin into the running slots and serviced there. There is no "wave 2", nothing waits for a freed slot, and a PR that ends the run with zero passes is a bug in this command, not an acceptable outcome. Slots are **sleep-dominated** — a pass bursts a few `gh` calls and then waits 30 minutes — so packing a lane costs extra passes, not extra sleeps, which is what makes total assignment affordable.
- **Order comes from the work-owed ranking, defined once in `/sy-list-prs`.** Do not restate the tiers here, do not invent a second ranking, and never use it to skip a PR — it sets service order only. Re-rank inside a slot each round; never move a PR between slots mid-run.
- **A slot with several PRs interleaves rounds — it never finishes one PR before starting the next (Step 4).** One pass per held PR, then one shared 30-minute sleep, at least 3 rounds, via `/sy-babysit-pr <url> pass=single`. Running PR A's full 3-pass loop before touching PR B is the same starvation this design removes, just hidden inside a job.
- **Babysit all resolved PRs in parallel background jobs — never a sequential for-loop** (see Fan out multi-PR work in parallel). One worktree per PR at `$HOME/.worktrees/<owner>/<repo>/<repo>__pr-<number>` via `git create-worktree` (`/sy-babysit-pr` Step 5a) is what makes this safe: the PR number keys the path, so PRs can't collide across slots or within one, nothing is shared, and the user's primary checkout is never touched.
- **A fan-out run is long by design.** Every PR gets ≥3 passes 30 minutes apart, so budget an hour-plus, more as slots fill. Don't truncate jobs, don't busy-poll them, and don't declare the fan-out done until every PR has reported.
- **Ping-pong is mandatory, not optional (Steps 3a / 4a / 5).** Every run pulses before dispatch, every 10 minutes while jobs run, and once at the end. A long async fan-out with no heartbeat is indistinguishable from a hung one. The pulse is read-only — it refreshes PR status from `gh` and reads already-reported job results; it never messages, wakes, or interrupts a running job, and it never acts on what it finds.
- **Ping-pong layout is owned by `/sy-list-prs pingpong`.** This command owns the agent ledger (job state, loop number, slot number and position, pass timestamps, next-loop ETA, last rendered pulse snapshot) and passes it in; `/sy-list-prs` owns the three columns, the icons, the change marker, the feature-set grouping, and the sort. Do not hand-roll a different board.
- **Table output is owned by `/sy-list-prs`.** Both the pre-flight render (Step 3) and the final report (Step 5) reuse its `table` format. Pass the same scope `$ARGUMENTS` to `/sy-list-prs table` so the rendered set matches the resolved PR set exactly. Do not hand-roll a different table layout.
- **First token of `$ARGUMENTS` decides the mode — no mixing.** PWD-keyword + explicit refs in the same call is an error; pick one. Empty and PWD-keyword modes both scan cwd + nested repos; explicit-list mode does not filter by author (you asked for those specific PRs).
- **Surface authors when the resolved set isn't all yours** (see Show PR authors). Explicit-ref mode is author-agnostic, so it can silently pull in someone else's PR — name the author on every row and in the summary whenever the set is mixed. The `/sy-list-prs table` renders (Steps 3 and 5) already add an `Author` column in that case.
- **Always resolve `<owner>/<repo>` via `git remote get-url origin`, never from the folder name (see Repo Identification).** Applies to PWD scan (delegated to `/sy-list-prs`) and to bare-`#<n>` ref expansion.
- **Stacked PRs still fan out in parallel — do NOT serialize them, and do NOT sync them from the dispatcher.** A stack (PR B based on PR A's branch, C based on B) is safe to dispatch all at once because every job merges **downhill only** — each job's delegated `/sy-sync-pr-branch` walks that PR's own ancestor chain and merges floor-then-ancestors into its own branch, and no job ever pushes a branch it doesn't own. Two jobs therefore never write the same ref. Ordering falls out of the ≥3-pass loop instead of a dependency graph: a child whose pass ran before its parent pushed picks that up on the next pass, 30 minutes later. Never make a child job wait on its parent job, never `write_agent` a job to ask whether it has pushed, and never merge or retarget an ancestor from the dispatcher.
- **Stacks land bottom-up, and only the human lands them.** A stacked PR that goes green + approved is reported as blocked on its parent (`/sy-babysit-pr` Step 4) — no job merges it, and no job enables automerge on it. When a parent does merge, GitHub retargets its children automatically and the children's next pass re-resolves the chain. Say which dispatched PRs are stacked, and on what, in the Step 2 announce so the merge order is visible before the run starts.

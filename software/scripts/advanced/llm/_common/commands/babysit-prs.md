[Sy] Babysit YOUR OWN open pull requests to the merge line — you act as the **author**, not a reviewer. Runs `/sy-babysit-pr` on every open PR in scope: syncs each branch with its base, addresses reviewer comments with real code changes, fixes failing CI, and keeps at it until the PR is green and mergeable. Resolves the target PRs (from `$ARGUMENTS`), ranks them by how much work they are owed, and dispatches them **all at once, in parallel background jobs**, each in its own git worktree. One job per PR while job slots last; past that, PRs are **assigned** to the running slots rather than queued behind them, so every resolved PR is serviced in the same run.

**Whose PRs, and what this does to them — the one distinction to get right.** This command works on **PRs you authored**, and it **changes them**: it pushes commits, merges the base branch in, replies to review threads, and can enable automerge. That is why the default scope is `@me` and why it must never be pointed at a teammate's PR — pushing to someone else's branch rewrites work you do not own, and answering their reviewers speaks for them. The sibling `/sy-review-prs` is the opposite: it reviews **other people's** PRs and only ever leaves feedback. If the ask is "review the team's PRs / give a verdict / leave comments", that is `/sy-review-prs`, not this. Someone else's PR belongs here only when they explicitly hand it over — say whose it is and what you pushed.

**This is the command for "sync all my PRs with main, babysit them, address comments — all at once, in the background, with worktrees."** Every part of that ask is already in scope: the branch sync is `/sy-babysit-pr` Step 5, which delegates to `/sy-sync-pr-branch` (default branch + the whole ancestor chain on a stack); comment remediation is Steps 6–7; background + worktree + all-at-once is Step 4 below. Route any plain-English phrasing of that request here — do not hand-roll a loop, and do not call `/sy-sync-pr-branch` yourself first; every job already runs it.

**Recommended order.** Run `/sy-review-prs` first (verdict pass), then `/sy-babysit-prs` (this command). Reversing wastes babysit cycles on PRs that would be requested-changes anyway.

Argument: $ARGUMENTS (optional — selects scope; the first token decides the mode, no mixing). Every mode below stays scoped to **your own** PRs unless a PR is named explicitly.

- **Empty** — babysit every open PR authored by `@me` for git repos at or below cwd, two levels deep (see Repo discovery). (Default behavior.)
- **PWD keyword** — first token (case-insensitive, trimmed) is one of the PWD keyword set defined in `/sy-list-prs`. Scan repos up to 2 child levels below cwd and babysit `@me` open PRs in those repos only.
- **Explicit PR refs** — one or more whitespace-separated PR refs. Each ref is one of:
  - full URL: `https://github.com/<owner>/<repo>/pull/<n>`
  - shorthand: `<owner>/<repo>#<n>`
  - bare `#<n>` or bare digits `<n>` — only valid when the current working directory is a git repo with a GitHub `origin`; resolve `<owner>/<repo>` via `git remote get-url origin`, never from the folder name (see Repo Identification).

## Execution mode

Background agents are default. Resolve, sort, announce, and assign the complete PR set first, then dispatch the existing slot jobs in parallel and return while they run. Explicit foreground signals are `foreground`, `fg`, `inline`, `blocking`, `synchronous`, `sync`, or `wait`; strip that token, keep the same author-lens ranking and round-robin slot assignment, then execute assigned PRs inline in slot order without background agents. Never change scope, sorting, assignment, worktree reuse, state checkpoints, or pass cadence based on mode.

## Steps

1. **Resolve target PR list from `$ARGUMENTS`.** Pick exactly one branch:

   a. **Empty `$ARGUMENTS` or PWD keyword** — delegate to `/sy-list-prs short pwd` (scope = pwd, format = short). Parse the emitted URLs (one full PR URL per line, grouped under `##` headings). **Do not pre-filter the READY TO MERGE group, or any other group** — a green PR still gets a slot and still gets its passes, and `/sy-babysit-pr` Step 4's early exit is what turns each of those passes into a cheap documented no-op. Pre-filtering here is how a PR ends the run with zero passes, which is exactly what Step 3b exists to make impossible; it also assumes "green right now" means "green in 90 minutes", which a fan-out this long routinely disproves. If zero PRs resolved, report it and stop.

   b. **Explicit PR refs** (any other `$ARGUMENTS` — treat as whitespace-separated tokens):
   - For each token, normalize to a full PR URL:
     - Full URL → use as-is.
     - `<owner>/<repo>#<n>` → expand to `https://github.com/<owner>/<repo>/pull/<n>`.
     - `#<n>` or bare digits → require cwd to be a git repo; resolve `<owner>/<repo>` via `git remote get-url origin` (never from the folder name), then expand. If cwd is not a git repo, error out naming the unresolvable token and ask the user to use a fully-qualified ref.
     - Anything else (not a URL, shorthand, `#<n>`, or digits) → error out, name the bad token, do NOT silently skip.
   - For each resolved URL, fetch metadata to match the search-result shape used downstream:
     `gh pr view <url> --json number,title,headRefName,baseRefName,isDraft,url,createdAt,updatedAt,author`. **`gh pr view` has no `repository` field** (see the `gh` field traps in `/sy-list-prs`) — the owning `<owner>/<repo>` is the one you already resolved from the ref itself.
   - De-duplicate by URL.

2. **Announce:** Tell the user which scope mode was resolved (`pwd scan of <N> repos` for empty/PWD args, or `explicit list of <N> PRs`), how many PRs were resolved, and list them (repo, PR number, title). If any resolved PR is authored by someone other than you (`gh api user --jq .login`), include the author on every listed PR and call the split out explicitly — explicit-ref mode does not filter by author, so babysitting someone else's PR is easy to do by accident.

   **Also announce the stacks.** Stack detection needs `headRefName` + `baseRefName`, and **the PWD path does not have them yet** — `/sy-list-prs short` deliberately skips the per-PR branch fetch (see its Fetch PR data notes), so only the explicit-refs path of Step 1b has them already. Fill the gap the same way `/sy-review-prs` does: one `gh pr view <url> --json headRefName,baseRefName` per resolved PR, which is also the call whose result the worktree path depends on. Then detect stacks from the set itself: any PR whose `baseRefName` equals another PR's `headRefName` is stacked on it. Chain those links and print each stack bottom-up (`<root link> ← <child link> ← <grandchild link>`), noting that they merge in that order. This is display only — it does not change dispatch (Step 3b still assigns every PR before anything launches) and it never makes one job wait on another.

   **Also announce the waves.** A wave is a merge barrier, not a branch parent (see the _Hard dependencies phase into waves_ rule), so it is invisible to the stack detection above — every wave PR targets the default branch. Read each resolved PR's body (`gh pr view <url> --json body,isDraft,title`) for a `## Blocked on` section or dependency prose (`depends on <link>`, `blocked by <link>`, `part of <link>`), and resolve each named blocker's real state. Print the waves in merge order with each blocked PR's parked shape (`wave 2: github.com/acme/web/pull/7 (draft, WIP prefix) — blocked on github.com/acme/api/pull/40`). **When the set carries `wave <W> - pr <i>/<N>` titles, check `<i>` against the wave graph you just resolved and report any that disagree** — a number below a lower wave's, a duplicate, or a stale `<N>` means the titles encode creation order rather than merge order (see the _A sequence number in a title is MERGE order_ rule). Report the corrected positions; the retitle itself is the per-PR job's, on its own pass. **Re-run this check on every pulse, not only at dispatch** — the set is re-resolved each time, and a PR that appeared mid-run (a new slice, or a follow-up a reviewer asked for) changes the ordering and `<N>` for everyone. Place it by its dependencies rather than at the end, re-derive the whole order, and name every PR whose position moved. **Hand every blocked PR's blocker links down to its worker** (Step 4) — that context is what `/sy-babysit-pr` Step 4a promotes on, and a job that was never told cannot see a wave from its own branch. The dispatcher itself never edits a title, never undrafts, and never rewrites a body: promotion is the per-PR job's, on its own pass.

3. **Render the resolved PR set as a table** so the user sees exactly what is about to be babysat. Delegate to `/sy-list-prs table <same-scope-token>` — `/sy-list-prs` accepts the same scope vocabulary as this command (empty / PWD keyword / explicit refs), so pass the same scope `$ARGUMENTS` (prefixed with `table`) and let it render. Single source of truth for the table layout lives in `/sy-list-prs`.

3a. **Open the ping-pong pulse — emit the FIRST one before dispatching anything.** Render `/sy-list-prs pingpong <same-scope-token>` with every Agent cell at `⚪ NOT STARTED`. This is the baseline the user compares every later pulse against; a fan-out that goes quiet for an hour before its first status line is the exact failure this exists to prevent. Layout lives in `/sy-list-prs` — do not hand-roll it. **This includes the baseline.** Emit the full four-column board (`PR | Description | Status | Agent`) — the PR cell carrying nothing but the linked path, the Description cell carrying author, head branch, title, and auto-merge state ` · `-separated in their own markdown spans with full `github.com/<owner>/<repo>/pull/<number>` paths, exactly as `/sy-list-prs pingpong` specifies — never a condensed stand-in with elided paths, invented columns, or a bespoke header, and never `<br>` inside a cell. A baseline in a different shape than the pulses that follow it cannot be diffed against them, which is the only reason it is printed first.

Start the **agent ledger** here: one row per resolved PR holding its **stable job key (`sy-babysit-pr:<owner>/<repo>#<number>`) and the handle of the live job that currently owns it** — the pair every later turn matches on before it dispatches anything, so a re-invocation, a requeue, or a recovery adopts the running job instead of spawning a second one onto the same PR — plus its ledger state (`active` / `queued` / `watching` / `terminal`), pass count, **slot number when active and queue position when queued**, first dispatch time, last pass start / end, next pass ETA, **that PR's latest `## State` block verbatim** (the round counter, per-check attempt counters, `automerge_decision`, and workspace path + kind + ownership that `/sy-babysit-pr` hands back after every `pass=single` pass), and the **last rendered pulse snapshot** (Status change marker, color emoji, and fragments, plus the Agent counters). The state block is not bookkeeping trivia — it is the only copy of what a re-invoked per-PR job cannot remember, so the next round's prompt is built from it and a replacement job for a dead slot is seeded from it. A ledger without it makes every pass a first pass. The snapshot is what `/sy-list-prs pingpong` diffs to pick the `Δ` / `▫️` / `🆕` change marker and write the `Δ` line — overwrite it with what was just printed after every pulse, so each pulse compares against the one immediately before it. Record the ledger state and slot for every PR from enrollment onward (Step 3b), queued and watching ones included: the pulse groups its board by feature set and prints `🌊 slot <N>` on every active row, and a missing state silently degrades that row to an ungrouped one. Record every timestamp the moment it happens (dispatch, pass start, pass end, next-pass ETA) — the pulse's `started 17:12 · running 22m` clock is read straight from this ledger and cannot be reconstructed after the fact. Never snapshot the elapsed duration itself; it is recomputed at render time and is deliberately excluded from the diff. The ledger is this command's bookkeeping; `/sy-list-prs` only renders it.

3b. **Enroll every PR, rank them, then fill the worker slots from the top of the queue.** The harness caps how many background jobs can run **at once**; it does not cap how many PRs the run covers. Every resolved PR is enrolled in the ledger before anything launches, and `S` limits only how many are being **actively worked** at the same moment — a PR that is merely being polled holds no slot. This is what makes "EVERY open PR in scope" true rather than aspirational, without stranding anything behind a lane.

- **Resolve `S`, the concurrency cap.** It is a property of the harness, never of this command, so this command names no number. Resolve in this order: a `cap=<positive-int>` token in `$ARGUMENTS` or the user naming a cap in prose wins; otherwise the **harness concurrency cap** declared in your harness's own instructions, if it declares one; otherwise there is no cap and `S = N`, one job per PR. Reject anything that is not a positive integer — fall back to the next source down and say so, because `S = 0` makes `i mod slot_count` a division by zero and `S < 0` makes the whole assignment meaningless. **Strip the `cap=` token from `$ARGUMENTS` before any scope parsing**, and never forward it to `/sy-list-prs`; left in place it is read as a PR ref by Step 1 and as a scope token by every delegated render. Say which value you used and where it came from.
- **If the launch is partially rejected, cancel and relaunch — never inject the rejects into a running slot.** Slot prompts are immutable and self-contained by design (Step 4), which is exactly why a live slot cannot be handed extra PRs; the dead-slot rule forbids the same mutation for the same reason. When only `k` of `slot_count` jobs actually start:
  - **`k == 0` is a launch failure, not a cap discovery.** Report it and stop — do not set `S = 0`, which makes `i mod slot_count` a division by zero and would "recover" into launching nothing at all.
  - **Cancel the `k` that started and confirm each one is actually terminated before relaunching.** Two jobs on one PR is worse than a stranded PR: they push over each other, double-comment, and race on the same worktree.
  - **Collect what the cancelled jobs already did.** A first pass is short but not empty — a job may already have pushed a fix, posted a comment, or enabled automerge. Take each PR's `## State` block from the ledger (jobs report ownership changes the moment they happen, precisely for this) and seed the relaunched slots with it, so previously-enabled automerge is not misread as `pre_existing` and already-done work is not repeated.
  - Then set `S = k`, refill from the top of the ranked queue, and launch that set in one message. A cancelled first pass costs almost nothing. Report the discovered cap and the refill, since the new ledger supersedes the one already announced.
- **Rank all `N` resolved PRs by the work-owed ranking, read through the AUTHOR lens** (the default) — the canonical tier list lives in `/sy-list-prs` (`## Work-owed ranking`): P0 unshipped work → P1 someone waiting on a reply → P2 broken and ours to fix → P3 stale against base → P4 bot nits only → P5 waiting on someone else → P6 nothing owed, ties broken on oldest `updatedAt`. Do not restate or re-derive the tiers here; read them there. Babysitting acts for the PR's author, so the tiers apply in their listed order — `/sy-review-prs` is the one that reorders them. Say which lens you used when reporting the ledger. Ranking decides **order only** — it never removes a PR from the set.
- **Every enrolled PR is in exactly one of four states, and only one of them costs a slot:** `active` (a worker is running a full pass on it — consumes a slot), `queued` (owed a full pass, waiting for a free slot — costs nothing), `watching` (nothing actionable; the dispatcher polls its fingerprint from the pulse — costs nothing), `terminal` (merged, closed, or handed to the human). A PR moves between them freely; nothing is ever dropped from the ledger.
- **Launch `min(N, S)` workers from the top of the ranked queue, all at once.** The highest-ranked PRs each get their own worker, so every one of them is serviced immediately. When a worker finishes a pass, its PR moves to `watching` or back to `queued`, the slot frees, and the next PR by rank takes it.
- **Every PR is enrolled before the first job launches.** A resolved PR missing from the ledger is a bug in this step, not a backlog — go back and enroll it. `queued` is not stranded: it is next in line, and the ledger says so.
- **Report the ledger at dispatch** — every PR with its tier and starting state (`github.com/acme/api/pull/51 (P1) active — slot 1`, `github.com/acme/web/pull/7 (P5) queued`). This is the artifact that proves nothing was stranded, and it is the first thing to check when a PR looks ignored.
- **Warn — do not refuse — when the queue is more than 3× the slot count.** `N > 3 × S` means a PR can wait through several passes before its first, so the run stretches. Say so, name the number, and carry on; servicing all of them slowly beats servicing `S` of them and abandoning the rest.

3c. **Concurrent-migration cross-check — run it BEFORE dispatching anything, over EVERY open PR in each repo, not just the ones being babysat.** Once the fan-out is in flight the jobs run concurrently and cannot be handed shared context, and a per-PR job only ever sees its own branch. Merge ordering across a shared migration DAG is a property of the whole set, so the dispatcher is the only thing positioned to compute it.

- **Scope is every open PR in every repo the resolved set touches** — `gh pr list --repo <owner/repo> --state open --json number,url,title,headRefName,author,autoMergeRequest --limit 100` per repo. Deliberately wider than the babysit set: a migration PR nobody asked you to babysit still collides with one you are, and a PR with automerge already on can land mid-run without any job watching. Filtering to babysat PRs, or to automerge-on PRs, would hide exactly the collisions that break the default branch.
- **Keep the ones that add a migration file** (detection table: `/sy-sync-pr-branch` Step 7 — do not restate it). `gh pr diff <n> --repo <owner/repo> --name-only` per candidate. Zero or one hit across the repo → nothing to coordinate; say so in one line and move on.
- **Record the floor head once, at dispatch,** and hand it to every job: the current migration head on each repo's default branch. A job that knows the head as of dispatch can tell "I was always stale" from "the head moved under me mid-run", which is the difference between re-parenting once and re-parenting every pass.
- **Two or more migration PRs in one repo → compute a merge order and pass it down.** Rank them by whichever must land first (ready-to-merge and automerge-on first — those land without a human), then hand each job its position plus the full pairing. Whichever lands second re-parents; that is the job's own Step 4 override doing the work, not something the dispatcher fixes. **Never re-parent, push, or reorder anything from here** — the dispatcher coordinates and never touches a branch.
- **Name the pairs in the announcement and in the Step 5 final report,** with each PR's automerge state. An unattended `--auto` PR sitting behind another migration is the single highest-risk row in the set, and the user should see it before an hour of passes starts, not after.

4. **Fan out one background job per SLOT — all at once, in parallel.** Do NOT walk the list sequentially.

   **Dispatch mechanics — this is the step agents get wrong.** "In parallel" is a hard requirement, not a hint:
   - **Emit every slot job in ONE assistant message with `slot_count` tool calls in that same message.** One sub-agent / Task / background-shell invocation per slot, all in a single block. A second message per slot is a sequential loop wearing a parallel costume — that is the failure mode this section exists to prevent.
   - **Never** `for pr in ...; do ...; done`, never "start job 1, wait, start job 2", never a staggered launch. Every slot starts at the same instant.
   - **One slot = one job = one lane. When `N ≤ S`, one slot holds exactly one PR** and this is the classic one-job-per-PR fan-out. A slot only holds several PRs because there were more PRs than slots — that is the carve-out to the "never a single job that iterates the PR list" rule, and it is the _only_ one: a slot iterates **its own assigned PRs**, never the whole list, and never a list it chose itself.
   - **Jobs share nothing** — no cwd, no branch, no state file, no conversation. A slot job must never read another slot's result or wait on it. Within a slot, each PR still gets its own worktree; the slot switches between them, it does not merge them.
   - **Give every job an identifying label, and a PR-specialized worker when one exists.** Where the environment lets a dispatched job carry a short label, set it to `<PR number> - <head branch> - <author>` for the PR that job starts on (drop the author when every PR in the set is yours). Where the environment offers a worker specialized for babysitting a pull request, dispatch to that one rather than the generic default. Both are cosmetic-only: a run that can do neither is not degraded, and neither ever changes scope, ranking, assignment, or cadence. They exist because a board of identically-named workers is unreadable the moment a fan-out exceeds two slots — the operator cannot tell which lane stalled.
   - **Each slot job's prompt is self-contained.** Pass, explicitly: its **ordered list of assigned PRs** with each one's tier, and for every one of them the full PR URL, the resolved `<owner>/<repo>` (from `git remote get-url origin`, never the folder name), the PR number, the head branch, the canonical worktree path `$HOME/.worktrees/<owner>/<repo>/<sanitized-branch>` (what `worktree_create "$BR"` produces), **the full list of every other PR URL in the whole dispatched set** — all slots, not just this one (its batch siblings, needed by `/sy-babysit-pr` Step 2a's companion check so a docs PR does not merge ahead of the code), and **the stack position from Step 2 when that PR is in one** (its ancestor PR links bottom-up and its children, so the job knows it must not merge before its parent), and **its migration coordination context from Step 3c when that PR adds a migration** (the floor's migration head as of dispatch, the other open migration PRs in that repo with their automerge state, and this PR's position in the computed merge order — a job cannot see any of that from its own branch). Sub-agents start with a fresh context — anything you don't pass, they don't have.
   - **Do not pre-create worktrees from the dispatcher.** Each job owns the worktree lifecycle of every PR it holds (`/sy-babysit-pr` Step 5a create/reuse and cleanup). The dispatcher never runs `git worktree add`, never `cd`s anywhere, and never touches the user's primary checkout.
   - **A cancelled fan-out leaves live worktrees — re-running resumes them, it does not start over.** Jobs killed mid-flight (session ended, run cancelled, machine slept) leave dirty worktrees and unpushed commits at the canonical paths. That is recoverable state, not garbage: `/sy-babysit-pr` Step 5a picks each one back up, and the Step 3b ranking scores exactly that state as **P0**, so a resumed run services it first. Never pre-clean `$HOME/.worktrees` before a fan-out, and never pass jobs an instruction to reset or re-clone.
   - **Report the fan-out the moment it's launched** — the ledger from Step 3b, with every PR's state, job, and worktree path — so the user can see the whole set covered, not a prefix of it.

   **Adopt before you dispatch — a slot is a long-lived job, not a per-round spawn.** Every slot job carries the stable key `sy-babysit-prs:slot<i>`, and every PR it holds carries `sy-babysit-pr:<owner>/<repo>#<number>` (see _A job is addressed by a stable key_). **Match those keys against the jobs already live before launching anything**: a slot whose key already has a running owner is left alone, an idle one is handed its next round as a follow-up turn, and only a key with no live owner gets a new job. **Record the resume handle each dispatch hands back into the ledger the moment it returns** — it is the only thing that can address that job on a later round, and it cannot be reconstructed afterwards. This is what makes re-invoking `/sy-babysit-prs` mid-fan-out re-attach to the running slots instead of doubling every lane and double-pushing every branch. A PR found under two live jobs is resolved by keeping the older and cancelling the newer, reported explicitly.

   **What a worker does — one pass per round, inside the job that already owns the slot.** A slot job is dispatched **once** and then resumed for each subsequent round; the **PR assignment** rotates through it, the job itself does not end and is not re-spawned (see _A pass that runs inside a job runs in that job_). A worker still runs exactly one pass per PR per round and reports, so it never sits on a slot waiting for a sleep to elapse — the dispatcher owns the sleeping.
   - **Run every round inside the slot job it belongs to — never dispatch a fresh agent per PR per round.** Resuming a slot for round N+1 is a follow-up turn against a warm context that still holds its worktrees, the comment threads it has read, and its counters. Re-dispatching instead produces `PRs × rounds` agents — 10 PRs over 3 rounds is 30 cold agents rather than 10 warm ones, each re-fetching the same diff and re-walking the same threads. A round number in a job's label (`3217 r2`, `3217 r3`) beside a fresh session is the visible symptom that this rule was skipped.
   - **Invoke `/sy-babysit-pr <PR-URL> pass=single round=<n>` per pass**, adding `last=true` on the pass you know is the final one for that PR, **and paste that PR's `## State` block from the previous pass into the job's prompt under a `## Prior state` heading** (omit the heading entirely on the first pass; a resumed job that still holds the prior round in its own context needs it only as a cross-check). `pass=single` makes the per-PR command run one pass and return instead of owning the clock itself; `last=true` is what releases workspace cleanup; the prior-state block is what keeps its counters, automerge decision, workspace ownership, and fingerprint from resetting to zero. Dropping any of the three silently turns a long run into a series of disconnected first passes.
   - **Await every job dispatched or resumed in a turn before that turn ends** (see _Never end a turn with a dispatched job still in flight_). A child's completion status is written by this dispatcher when the child returns, so a round left open when the turn stops freezes those jobs at "running" permanently — the workers exited, the board just cannot say so. Never issue a round the run has no time left to await: on the deadline, finish the round in flight and report, rather than starting one more.
   - **The dispatcher owns the clock — the run budget is `<SY_PR_RUN_BUDGET_SECONDS>` seconds** from launch, shared by the whole set. Within it, a PR gets a full pass when its fingerprint moves, when it has never had one, or on its keepalive (at least every `<SY_PR_KEEPALIVE_INTERVAL_SECONDS>` seconds), plus one final pass before the deadline. There is no per-PR pass quota; a busy PR gets many passes and a quiet one few, and both are correct.
   - **Re-rank the queue every pulse** using the same work-owed ranking, so a PR that just picked up a `CHANGES_REQUESTED` jumps ahead of an idle one. **Ranking sets which queued PR takes the next free slot — never whether a PR is serviced at all.** Age the queue: a PR waiting more than a few pulses is promoted, so a permanently low-ranked PR is serviced late, never never.
   - **A PR that reaches a terminal state leaves the ledger's rotation** (merged, closed, or handed to the human). Report it and stop scheduling it.
   - **Never preempt a running pass.** When new inbound work lands on a PR that is `active`, mark it `dirty_after_pass` and re-queue it the moment its worker returns — it goes to the head of the queue, not the back. Cancelling a pass mid-edit is how a half-applied fix, a stale reply, or a duplicate comment happens.
   - **Report each PR's fingerprint and `externally_blocked` back with its `## State` block, every pass.** That is what lets the dispatcher move it to `watching` and stop paying a worker for it (Step 4b). A worker never decides to park itself — it reports state; the dispatcher schedules.

   - Expect long runtimes: the run works its full budget by design. That is the point — do not shorten it, and do not busy-poll the jobs. Collect each result when its job reports back.
   - If one job fails or escalates, the others keep running; never abort the whole fan-out for a single PR. **If a whole slot job dies, relaunch that slot — do not fold its PRs into a live one.** A dying slot frees exactly the capacity it was using, so a replacement job fits without exceeding `S`, and pushing its PRs into a neighbour would both silently double that lane's round length and violate the "a slot's assignment never changes mid-run" rule. **Confirm it is dead before replacing it** — a job that finished its turn is _idle_, not dead, and an idle slot is resumed with a follow-up turn carrying its next round, which keeps its worktrees, its read comment history, and its counters intact (see _Resume an idle job; relaunch only a dead one_). Only a job that is failed, cancelled, or gone gets a replacement, launched with the dead slot's **remaining** PRs (drop the ones that already reached a terminal state) plus a checkpoint of what it got through — each PR's last `## State` block from the dispatcher's ledger, which exists precisely because a replacement cannot inherit what the live job still held.
   - **Resume per PR from its own `completed_round + 1`.** A worker that died mid-pass leaves that PR owing the pass it was on, not the next one; re-queue it at the head with its last `## State` block, and let every other PR keep its own counter. This is exactly why the state block carries `completed_round` per PR rather than a single run-wide round number.
   - If the slot died with no capacity to relaunch into (the whole run is being torn down), report its PRs as partially serviced with their per-PR round counts, so the next invocation picks them up as P0.
   - **Parallelism is safe because every PR gets its own git worktree** at a rigid path — **`$HOME/.worktrees/<owner>/<repo>/<sanitized-branch>`**, created by `worktree_create` (see One rigid worktree path). The sanitized branch key keeps branches separated, and none of them touch your primary checkout. Never let a job `git checkout` in the main repo.
   - The per-PR command owns the pass. This wrapper owns only which PRs run in which lane and when — if the per-PR flow needs to change, edit `/sy-babysit-pr`.

4a. **Ping-pong every 10 minutes until the run ends.** The fan-out works its full `<SY_PR_RUN_BUDGET_SECONDS>`-second budget by design, so the dispatcher's job while it waits is to keep a pulse on the wall — not to sit silent, and not to busy-poll the jobs. The pulse is also where the Step 4b fingerprint probes ride, on the `<SY_PR_POLL_INTERVAL_SECONDS>`-second cadence.

- **Cadence: one pulse every 10 minutes**, from dispatch until the last job reports. Three pulses per babysit pass, so a sleeping job still shows a live heartbeat with its next-loop ETA.
- **Render with `/sy-list-prs pingpong <same-scope-token>`, passing the current agent ledger.** Same scope token as Steps 3 and 3a, so every pulse covers exactly the dispatched set. Never hand-roll the board.
- **Refresh the Status column from GitHub, not from the jobs.** Re-run the cheap `gh pr view` status calls `/sy-list-prs` already uses. **Never `write_agent` / message / interrupt a running job to ask how it's doing** — that wakes a running pass and corrupts its cadence (see the busy-poll rule in Step 4). Read job state only from results the jobs have already reported.
- **Update the ledger from reports as they land** — a worker finishing pass N on a PR moves that row to `🔍 WATCHING` or back to `⏸️ WAITING` with its next-check ETA; a final report moves it to `✅ COMPLETED` / `⚠️ ESCALATED` / `❌ FAILED`. A queued PR with no pass yet stays `⚪ NOT STARTED` with its queue position. Between reports, derive `IN PROGRESS` vs `WAITING` and the next-check ETA from the poll cadence rather than leaving the cell blank.
- **A pulse is display-only.** It never dispatches, retries, cancels, merges, comments, or re-assigns a slot. If a pulse shows a job wedged, say so in that row and let the human decide. A pulse that notices a **dead** slot reports it and nothing more — the relaunch is Step 4's job, taken outside the pulse, and it relaunches the dead slot rather than moving its PRs anywhere.
- Stop pulsing when every row is terminal (`✅ COMPLETED` / `⏭️ SKIPPED` / `⚠️ ESCALATED` / `❌ FAILED`), then go to Step 5. **`⏸️ WAITING_AFTER_SKIP` is not terminal** — that PR still has passes scheduled, so the pulse keeps running. **`🔍 WATCHING` is not terminal either** (Step 4b).

4b. **Watching — a PR with nothing actionable is polled by the dispatcher and holds no worker.** This is the fan-out's biggest waste: three PRs all sitting on a human approval gate means three workers waking worktrees, re-reading diffs, re-walking the same comments, and reporting the same no-op — while a fourth PR with a fresh review comment waits for a slot. Nothing an agent can do moves any of them; only a person clicking, or another PR merging, does. So the dispatcher stops paying workers it does not need and pays two `gh` calls per PR instead — and the freed slot goes to the PR that actually has work.

- **Move a PR to `watching` when its last `## State` block came back `externally_blocked`** — the enumerated set in `/sy-babysit-pr` Step 12a, which the per-PR job decides and this command never second-guesses. Watching is per PR, not per lane: one blocked PR frees its slot immediately, whatever the rest of the set is doing.
- **Never move a PR to `watching` mid-pass, and never one whose state records unpushed commits or a dirty workspace** — that PR has work outstanding and cannot be externally blocked in the first place. Let its worker finish and report first.
- **Prefer an idle, addressable job over a terminated one.** An idle job still holds its worktrees, the comment threads it has read, and its counters, so resuming it is a follow-up turn rather than a fresh agent re-deriving all of it from a pasted summary (see _Resume an idle job; relaunch only a dead one_). An idle job holds no slot. Terminate only when the harness cannot hold an idle job, and say so when you do — the ledger requirement (Step 3a) is what makes that fallback safe.
- **The watch runs inside the pulse's existing fetch.** Step 4a already re-runs the cheap `gh pr view` status calls for every row, so the fingerprint costs one extra `gh api .../pulls/<n>/comments?per_page=1&sort=updated&direction=desc` line per watched PR and nothing else. Compute the digest exactly as `/sy-babysit-pr` Step 12a defines it — same two commands, same string comparison. Do not invent a second fingerprint here.
- **The pulse itself stays display-only.** It renders; it never dispatches. This step schedules, it happens to reuse the pulse's fetch, and the only thing it may launch is a worker for a PR **it moved to `watching` itself**. It never relaunches a dead job (Step 4 owns that) and never merges, comments, or pushes.
- **Any fingerprint change re-queues that PR immediately, at the head of the queue.** Resume its idle job with a follow-up turn when it is still addressable; replace it only when it is gone, seeded from the ledger's `## State` block. Report which PR moved and which field flipped (`github.com/acme/api/pull/51 — Owner Approval cleared (reviewDecision none→APPROVED) — requeued, slot 2`).
- **A merged wave blocker is a fingerprint change, and the requeued pass is what promotes.** The probe already checks every named blocker's state (`/sy-babysit-pr` Step 12a), so `OPEN → MERGED` on a blocker fires a full pass, and that pass runs `/sy-babysit-pr` Step 4a: sync, CI green, `gh pr ready`, drop the `WIP: DO NOT MERGE — ` prefix, rewrite the `## Blocked on` section. This is the whole reason a wave-blocked PR stays enrolled instead of being written off — a watched wave-2 PR that never wakes ends the run unpromoted, which is the failure the fingerprint exists to prevent. The dispatcher notices; it never promotes anything itself.
- **A watched PR still owes its keepalive.** Give it a full pass at least every `<SY_PR_KEEPALIVE_INTERVAL_SECONDS>` seconds and always once before the deadline, honored here by the dispatcher because a watched PR has no job to honor it itself. A run that ends on an unverified probe has not finished.
- **Say what it saved.** The pulse shows watched rows as `🔍 WATCHING` with the blocker and the next check time, and the Step 5 report names every watched PR, how long it spent watching, what it was waiting on, and how many worker dispatches that avoided. Watching is a reported state, never silence.

4d. **A worker's stop-and-ask is surfaced to the operator, and revalidated before it is repeated.** A PR handed back with `needs_user` in its `## State` block leaves the rotation for this run — but the operator is the one who has to see it, and a sub-agent's report scrolls past. Carry the block into the ledger verbatim, mark that row `NEEDS_USER`, and repeat it in **every** pulse and in the final report: the reason, the exact message, and its `Next:` line. Never open a prompt, never block the run waiting on an answer, and never express it on GitHub — no label, no status, no review, no comment posted purely to record it. Other PRs keep running; when every enrolled PR is terminal or `NEEDS_USER`, print all the outstanding questions together and stop.

- **Revalidate before repeating a claim from an earlier run.** A `needs_user` block read out of a journal at startup is a hypothesis: dispatch that PR's next pass with the block pasted in, let `/sy-babysit-pr` Step 2b re-fetch the source and resolve `current` / `cleared` / `changed` / `conflicted` / `stale_unknown`, and render that verdict — never the stale claim on its own. A `cleared` verdict re-queues the PR normally and names the comment that cleared it.
- **`NEEDS_USER` is a local pause, not a GitHub state.** The PR may be green, approved, and mergeable to everyone else; only this run is holding off on it. Render it distinctly from `⚠️ ESCALATED` (a job that stopped on its own error) and never as `⏭️ SKIPPED`.

4c. **Stop the run on the deadline, on a fully terminal ledger, or on an unreachable service.** The run ends when every enrolled PR is `terminal`, when the `<SY_PR_RUN_BUDGET_SECONDS>` budget expires (after a final full pass on anything not already terminal), or when GitHub or the model service stays unreachable for `<SY_PR_RETRY_MAX_FAILURES>` consecutive attempts `<SY_PR_RETRY_INTERVAL_SECONDS>` seconds apart. On the unreachable stop, report `"GitHub or model service unreachable — stopping with resumable state"`, never a local network cause you cannot verify. On **every** stop, write the ledger — each PR's state, its last `## State` block, its fingerprint, and the queue order — to the durable journals, so a fresh invocation resumes instead of restarting.

5. **Final report:** emit the **closing ping-pong** — one last `/sy-list-prs pingpong <same-scope-token>` with the final ledger and `Next ping-pong: — (final)` — followed by one `/sy-list-prs table <same-scope-token>` render and a short summary of which PRs were skipped (already green), which were processed, and which need human attention. Include each PR's pass count, its final ledger state, its worktree path (reused vs created), and **every PR that spent time watching** (`github.com/acme/api/pull/51 watched 3h12m — blocked on Owner Approval; 41 probes, 0 worker dispatches, requeued once when <link> merged`), and note any worktrees left behind because they pre-existed. **Name every wave promotion** (`github.com/acme/web/pull/7 promoted on round 6 — blocker github.com/acme/api/pull/40 merged → synced, undrafted, WIP prefix dropped`) and every wave PR still watching, with the blocker it is still waiting on — a run that left a promotable PR unpromoted is a reportable miss, not a silent one. **Report agent reuse too**: which jobs were adopted or resumed rather than freshly dispatched, and any duplicate job cancelled. **State explicitly that every resolved PR was serviced** — count the rows and compare against the Step 1 resolved count; a mismatch is the failure this command's enrollment rule exists to prevent, so name any PR that got zero passes and why. A watched PR is a serviced PR: report it as one, never as skipped or missing. The run therefore always brackets itself: pulse at the start (Step 3a), pulse every 10 min (Step 4a), pulse at the end.

## Rules

- This command is a dispatcher. The per-PR loop lives in `/sy-babysit-pr` — do not re-implement it here.
- **A slot is a long-lived job that is adopted, resumed, and reused — never re-spawned per round (Step 4).** Every slot and every PR carries a stable job key; enumerate live jobs and match on it before dispatching anything, so re-invoking this command mid-fan-out re-attaches to the running slots instead of doubling every lane, and so no PR is ever serviced by two jobs at once. A job that finished its turn is **idle, not dead**: resume it with a follow-up turn, replace it only when it is failed, cancelled, or gone. And a pass runs **inside** the slot job — `pass=single` and "already inside a dispatched job" each force `/sy-babysit-pr` inline, because a slot that spawns a child agent per PR per round creates `PRs × rounds` agents to do work one job already holds the context for. The canonical rules are _A job is addressed by a stable key_, _Resume an idle job; relaunch only a dead one_, and _A pass that runs inside a job runs in that job_.
- **Wave promotion is detected here and performed there.** The dispatcher sees the whole set, so it resolves the wave graph at announce time (Step 2) and hands every blocked PR its blocker links down to its slot job; the fingerprint then makes a blocker's `OPEN → MERGED` flip requeue that PR on the next probe (Step 4b). The promotion itself — sync, CI green, `gh pr ready`, drop the `WIP: DO NOT MERGE — ` prefix, rewrite `## Blocked on` — is `/sy-babysit-pr` Step 4a, on that PR's own pass. **The dispatcher never edits a title, never undrafts, and never rewrites a body.** A wave-2 PR that ends the run unpromoted while its wave-1 blocker merged hours earlier is the failure both halves of this exist to prevent.
- **Prose-only PRs in a fan-out do NOT self-merge — they wait for their batch.** `/sy-babysit-pr` Step 2a only enables `--auto` on a _standalone_ docs / comment / whitespace PR, and every PR in this dispatched set counts as a companion of every other. So a docs PR inside a fan-out is deferred until its siblings merge or close, then self-merges on a later pass. That is what keeps documentation from landing ahead of the code it describes. A fan-out of exactly one PR is standalone by definition and may self-merge immediately. Say which docs PRs are deferred in the Step 2 announce; the dispatcher itself never enables or disables automerge.
- **Migration collisions are the dispatcher's to see and the jobs' to fix (Step 3c).** Scan **every** open PR in each repo — not just the babysat set, not just the automerge-on ones — because a per-PR job only ever sees its own branch, and the PR that breaks the default branch is routinely one nobody asked you to babysit. Compute the merge order, record the floor's migration head at dispatch, and hand both to every affected job. The dispatcher never re-parents, never pushes, and never reorders a merge itself: whichever PR lands second re-parents via its own `/sy-babysit-pr` Step 4 override.
- **Base-branch sync is already included — never bolt it on.** Each job's `/sy-babysit-pr` Step 5 delegates to `/sy-sync-pr-branch`, which merges the default branch and, on a stacked PR, every ancestor branch up the chain — before the job does anything else. Do not call `/sy-sync-pr-branch` from the dispatcher, do not `git merge origin/main` here, and do not add a "sync pass": the same sync would run twice and race the jobs' own worktrees.
- **Parallel means one message, `slot_count` tool calls — not `N` (Step 4 Dispatch mechanics).** The job count is `min(N, S)`, never the PR count: launching one job per PR past the cap is what strands the tail. If the transcript shows the slot jobs starting one message at a time, the fan-out was sequential and must be relaunched. Self-contained prompt per slot, no shared state.
- **An idle set is a reason to sleep, not to stop.** Every wait is a real blocking `sleep` command (`sleep 1500` per slot round, `sleep 600` per pulse), the in-scope PR set is re-resolved at the top of every round so PRs opened mid-run are picked up, and the run never ends with a question to the user. A dispatcher whose harness has no detached jobs runs the rounds inline with real sleeps instead of cancelling them; stopping with rounds still owed is a failed run.
- **Every resolved PR is enrolled before anything launches — never dropped (Step 3b).** One worker per PR while slots last; past the concurrency cap the surplus is `queued` by rank and takes the next slot a worker releases. A slot is held only by a pass actually running: a `watching` or `queued` PR costs nothing, which is what makes covering the whole set affordable. A PR that ends the run with zero passes is a bug in this command, not an acceptable outcome.
- **Order comes from the work-owed ranking, defined once in `/sy-list-prs`.** Do not restate the tiers here, do not invent a second ranking, and never use it to skip a PR — it sets service order only. Re-rank inside a slot each round; never move a PR between slots mid-run.
- **A worker runs one pass per round and hands the slot to the next PR — the job it runs in is not re-spawned (Step 4).** Every pass goes through `/sy-babysit-pr <url> pass=single` with the prior state block pasted in, run **inside** the slot job that already owns that lane; round N+1 resumes that job rather than dispatching a new one. A worker that sleeps out a cadence while holding a slot is the starvation this design removes, just hidden inside a job — and a fresh agent per PR per round is the agent explosion it removes, just hidden behind a round number in the label.
- **Babysit all resolved PRs in parallel background jobs — never a sequential for-loop** (see Fan out multi-PR work in parallel). One worktree per branch at `$HOME/.worktrees/<owner>/<repo>/<sanitized-branch>` via `worktree_create` (`/sy-babysit-pr` Step 5a) is what makes this safe: the sanitized branch key keeps PRs from colliding across slots or within one, nothing is shared, and the user's primary checkout is never touched.
- **A fan-out run is long by design.** It works the full `<SY_PR_RUN_BUDGET_SECONDS>`-second budget unless every PR goes terminal first. Don't truncate jobs, don't busy-poll them, and don't declare the fan-out done until every PR has reported.
- **An externally blocked PR is watched by the dispatcher and holds no worker (Step 4b).** A PR waiting on a human approval click costs two read-only `gh` calls per probe, folded into the pulse's existing fetch, and its slot goes to a PR that actually has work. It is requeued at the head the instant its fingerprint moves, and still gets a keepalive pass at least every `<SY_PR_KEEPALIVE_INTERVAL_SECONDS>` seconds plus one before the deadline. Never move a PR to watching mid-pass, and never report a watched PR as skipped. The mechanism and the fingerprint are defined once in `/sy-babysit-pr` Step 12a; the externally-blocked call belongs to the per-PR job, the scheduling to this one.
- **Ping-pong is mandatory, not optional (Steps 3a / 4a / 5).** Every run pulses before dispatch, every 10 minutes while jobs run, and once at the end. A long async fan-out with no heartbeat is indistinguishable from a hung one. The pulse is read-only — it refreshes PR status from `gh` and reads already-reported job results; it never messages, wakes, or interrupts a running job, and it never acts on what it finds.
- **Ping-pong layout is owned by `/sy-list-prs pingpong`.** This command owns the agent ledger (job state, loop number, slot number and position, pass timestamps, next-loop ETA, last rendered pulse snapshot) and passes it in; `/sy-list-prs` owns the four columns, the icons, the change marker, the feature-set grouping, and the sort. Do not hand-roll a different board.
- **Table output is owned by `/sy-list-prs`.** Both the pre-flight render (Step 3) and the final report (Step 5) reuse its `table` format. Pass the same scope `$ARGUMENTS` to `/sy-list-prs table` so the rendered set matches the resolved PR set exactly. Do not hand-roll a different table layout.
- **First token of `$ARGUMENTS` decides the mode — no mixing.** PWD-keyword + explicit refs in the same call is an error; pick one. Empty and PWD-keyword modes both scan cwd + nested repos; explicit-list mode does not filter by author (you asked for those specific PRs).
- **Surface authors when the resolved set isn't all yours** (see Show PR authors). Explicit-ref mode is author-agnostic, so it can silently pull in someone else's PR — name the author on every row and in the summary whenever the set is mixed. The `/sy-list-prs table` renders (Steps 3 and 5) already add an `Author` column in that case.
- **Always resolve `<owner>/<repo>` via `git remote get-url origin`, never from the folder name (see Repo Identification).** Applies to PWD scan (delegated to `/sy-list-prs`) and to bare-`#<n>` ref expansion.
- **Stacked PRs still fan out in parallel — do NOT serialize them, and do NOT sync them from the dispatcher.** Stacks should never have been created in the first place (see the "Every PR branches off the default branch" rule) — this rule is containment for ones that already exist, not a reason to keep making them. A stack (PR B based on PR A's branch, C based on B) is safe to dispatch all at once because every job merges **downhill only** — each job's delegated `/sy-sync-pr-branch` walks that PR's own ancestor chain and merges floor-then-ancestors into its own branch, and no job ever pushes a branch it doesn't own. Two jobs therefore never write the same ref. Ordering falls out of the polling loop instead of a dependency graph: a child whose pass ran before its parent pushed picks that up on the next probe. Never make a child job wait on its parent job, never `write_agent` a job to ask whether it has pushed, and never merge or retarget an ancestor from the dispatcher. - **Stacks land bottom-up, and only the human lands them.** A stacked PR that goes green + approved is reported as blocked on its parent (`/sy-babysit-pr` Step 4) — no job merges it, and no job enables automerge on it. When a parent does merge, GitHub retargets its children automatically and the children's next pass re-resolves the chain. Say which dispatched PRs are stacked, and on what, in the Step 2 announce so the merge order is visible before the run starts.

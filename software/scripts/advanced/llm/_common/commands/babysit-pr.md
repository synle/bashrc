[Sy] Babysit a single pull request **you authored** to the merge line — you act as the author, not a reviewer. Syncs the branch (delegated to `/sy-sync-pr-branch`, which merges the default branch plus every ancestor branch when the PR is stacked), addresses review comments with real code changes, runs local checks, fixes failing builds, and waits until CI passes. All git work runs in a **dedicated worktree** (never your primary checkout), and the loop keeps working for a fixed run budget, polling the PR cheaply between passes and reacting the moment its state moves. A standalone prose-only PR (docs / comments / whitespace) gets automerge enabled on the first pass; one with companion PRs still open waits for them, and anything with an executable line does not.

**Scope.** This command **changes the PR** — it pushes commits, merges the base in, replies to review threads, and can arm automerge. That is why it belongs to PRs you own: pushing to someone else's branch rewrites work that is not yours, and answering their reviewers speaks for them. To leave a verdict on **someone else's** PR without touching it, use `/sy-review-pr`. Take a PR authored by someone else only when it is explicitly handed to you — then say whose it is and exactly what you pushed.

Argument: $ARGUMENTS (optional — a PR URL or PR number. If empty, use the current branch's PR. A caller dispatching a batch, e.g. `/sy-babysit-prs`, may also pass the full list of sibling PR URLs in that batch; Step 2a's companion check treats them as companions. A slot driver holding several PRs may pass `pass=single` — see the Step 12 loop gate.)

## Execution mode

Background agent is default **for a top-level invocation only.** Dispatch one self-contained background agent with the resolved PR URL and return its handle immediately; the agent owns workspace reuse, recovery, the whole run budget, the poll cadence, pushes, and final report. **Before dispatching, check whether a live job already owns this PR** — key `sy-babysit-pr:<owner>/<repo>#<number>`, recorded in the job prompt and in the PR journal (see _A job is addressed by a stable key_). A running owner is left alone and its handle reported back; an idle owner is handed the next round as a follow-up turn; only an unowned PR gets a new agent. Two live jobs on one PR double-push and double-comment, so a duplicate is resolved by keeping the older and cancelling the newer. **Two conditions force this flow inline instead, either one sufficient: a `pass=single` token on the invocation, or already executing inside a dispatched job** — a round is one pass of work, and dispatching a child agent per pass is what turns a 3-PR slot into 30 agents (see _A pass that runs inside a job runs in that job_). Explicit foreground signals are `foreground`, `fg`, `inline`, `blocking`, `synchronous`, `sync`, or `wait`; strip that token, then run this same flow inline. Mode changes only execution placement — keep PR resolution, worktree ownership, interrupted-run recovery, sync delegation, comment handling, checks, and pass order unchanged. `foreground`, `fg`, `inline`, `blocking`, `synchronous`, `sync`, or `wait`; strip that token, then run this same flow inline. ## Steps

1. **Determine which PR to babysit:**
   - If `$ARGUMENTS` is provided (a PR URL like `https://github.com/org/repo/pull/123` or a PR number), use that.
   - If `$ARGUMENTS` is empty, detect from the current working directory:
     - `git remote get-url origin` to determine the repo.
     - `git branch --show-current` to get the current branch.
     - `gh pr view --json number,title,url,headRefName,baseRefName` to find the PR for the current branch.
     - If no PR exists for the current branch, tell the user and stop.

2. **Announce:** Tell the user which repo and PR you are babysitting (repo name, PR number, title, URL).

2a. **Prose-only automerge gate — runs on the first pass, before the CI check.** A standalone docs / comment PR should not wait on a human to click merge, so babysit flips `--auto` on itself the moment it picks one up. It runs here, ahead of Step 3, because enabling automerge is safe while CI is still running — `--auto` is a queued instruction, not a merge. The one branch that re-runs on later passes is the deferred-companion case below.

    Fetch: `gh pr view <number> --repo <owner/repo> --json state,isDraft,title,body,author,autoMergeRequest,headRefName,baseRefName`.

    - **Skip the gate entirely** (report why once, never re-check) when any of: `state != "OPEN"`; `isDraft` is true; the title contains `WIP` or `DO NOT MERGE` (case-insensitive); `author.login` is not you (`gh api user --jq .login`); or `autoMergeRequest != null` (already enabled — someone else's call, leave it alone). **"Never re-check" has exactly one exception: a Step 4a wave promotion.** Draft state and a WIP title are the two skip reasons promotion actively removes, so a promoted PR gets this gate re-run once, on the pass that promoted it — otherwise a wave-2 prose-only PR is disqualified by a condition that stopped being true hours earlier and is never reconsidered.
    - **Classify the diff** — `gh pr diff <number> --repo <owner/repo>`, and read every changed line, not just the file list. **Prose-only** means every `+`/`-` line is a line in a docs file (`*.md`, `*.mdx`, `*.rst`, `*.txt`, `docs/**`, `README*`, `CHANGELOG*`, `LICENSE*`), a comment line in a source file, a docstring / JSDoc block, or pure whitespace (see the Automerge is opt-in rule). A single executable line — code, config, schema, lockfile, CI workflow, test — disqualifies the whole PR, however small. A file-name check alone is not enough in either direction: a `.md` file can hold an executed snippet the repo tests, and a `.py` file can hold a comment-only fix.
    - **Companion check — only a STANDALONE prose-only PR self-merges.** Merging docs before the code they describe is the failure this prevents, so a prose-only PR that belongs to a set waits for that set. Gather companions from all four signals, then keep only those still `OPEN`:
      - **Batch siblings** — if the dispatcher passed a sibling PR list (`/sy-babysit-prs` Step 4 hands each job the full dispatched set), every other PR in it is a companion. This is the strongest signal and needs no API call.
      - **Branch group** — read `headRefName`. If it has three or more segments (`<username>/<group-slug>/<feature>`), the group prefix is the first two. Same repo: `gh pr list --repo <owner/repo> --state open --json number,url,title,headRefName,author --limit 100`, keep rows whose `headRefName` starts with `<username>/<group-slug>/`. Other repos (best effort — `gh search prs --json` exposes no `headRefName`, so match on text): `gh search prs --author @me --state open --json number,repository,url,title --limit 50 "<group-slug>"`.
      - **Explicit references** — read the title and body for another PR path (`.../pull/<n>`), or the words "depends on", "part of", "stacked on", or a shared plan slug. Resolve each and keep the open ones.
      - **Stacked** — `baseRefName` is another open PR's head branch.
    - **Prose-only AND standalone → enable it:** `gh pr merge <number> --squash --auto`, then report `"Standalone prose-only diff (<n> files, docs/comments only) — automerge enabled; CI and any required approval still gate the merge."` Then continue the normal loop at Step 3 — babysit still syncs, still fixes CI, still handles comments; automerge only removes the final click.
    - **Prose-only but NOT standalone → defer, and re-check every later pass.** Leave `--auto` off and report `"Prose-only diff, but <n> companion PR(s) still open — automerge deferred so the docs don't land before the code: <full PR links>."` This is the one gate decision that is **not** final: what blocks is a companion still being open, not the PR being grouped. On every later pass, re-resolve the companion list; the moment all of them are `MERGED` or `CLOSED`, enable `--auto` then and report `"Last companion (<link>) landed — automerge enabled on the prose-only PR."` If any companion is still open when babysit finishes its passes, say so in the Step 13 report and leave the merge to the human.
    - **Not prose-only → leave it off,** report `"Diff touches <what> — automerge stays off until you say otherwise."`, and do not reconsider on later passes. Automerge is opt-in everywhere except a standalone prose-only diff.
    - **If `gh` rejects `--auto`** (repo has auto-merge disabled, squash not an allowed method, branch protection missing a required check), report the exact error once and carry on with the loop. Never fall back to a bare `gh pr merge` without `--auto` — that would merge on the spot — and never retry on later passes.
    - **Revoke it if the PR stops qualifying.** Babysit pushes its own commits (Steps 5–10), and a CI fix or a new test turns a docs PR into a code PR; separately, a companion PR can open after this gate already enabled `--auto`. On every later pass, if automerge is on **because this gate enabled it**, re-check both conditions:
      - The diff now contains an executable line → `gh pr merge <number> --disable-auto`, report `"PR is no longer prose-only (<what changed>) — automerge disabled; merge is yours again."`, and treat it as opt-in from then on.
      - A companion PR has since opened (re-run the companion check) → `gh pr merge <number> --disable-auto`, report `"A companion PR opened since automerge was enabled (<link>) — automerge revoked so the docs don't land first; it will be re-enabled once that PR merges or closes."`, and fall back to the deferred branch above.

      Never revoke automerge the user or `/sy-create-pr` enabled — only what this gate turned on.

3. **Skip if a BUILD is currently running — a pending human review gate is not a build.** Before any other check, fetch state:
`gh pr view <number> --repo <owner/repo> --json statusCheckRollup`

- **Classify every non-`COMPLETED` entry before deciding anything.** A pending entry is a `CheckRun` whose `status` is `IN_PROGRESS` / `QUEUED` / `WAITING` / `PENDING` / `REQUESTED`, or a `StatusContext` whose `state` is `PENDING` / `EXPECTED`. Sort each one into exactly one bucket:
  - **Blocking — a self-resolving build.** A job is executing and will reach a conclusion on its own: test, lint, type-check, build, scan, deploy. Pushing into it wastes CI cycles and merging into it is unsafe, so it ends the pass.
  - **Non-blocking — a human gate, or a stalled entry.** A check that cannot finish without a person clicking something never resolves on a timer, so "wait for CI" means wait forever. Mark an entry non-blocking when ANY of:
    1.  Its display name matches a review-gate pattern, case-insensitive: `approv`, `review`, `sign-?off`, `codeowner`, `resolution`, `ack`, `attestation`, `waiver`. The name is `name` (+ `workflowName`) on a `CheckRun` and `context` on a `StatusContext` — `gh pr view --json statusCheckRollup` emits those two and no `description`, so match on what it actually returns. Apps report approval gates as checks that sit `IN_PROGRESS` **by design** until a human acts.
    2.  It is a `StatusContext` in `PENDING` with no `targetUrl` — nothing is executing behind it.
    3.  **Staleness backstop** — it has been pending longer than **60 minutes**. Age comes from `startedAt`, which `gh` emits for **both** node types (the underlying GraphQL field on a `StatusContext` is `createdAt`; `gh` renames it — do not look for `createdAt` in `gh` output). Babysit's whole window is one bounded run, so a check that has not moved in an hour cannot be waited out; treating it as blocking makes every remaining round a no-op. Name it in the report as `"stalled check treated as non-blocking"` so a genuinely slow build is visible rather than silently stepped over.
- **End the pass ONLY if the blocking bucket is non-empty.** Report `"PR build is currently running (<blocking check names>) — skipping this pass"` and take no other action: do not merge, do not address comments, do not push. Then fall through to the **Step 12 loop gate** (sleep 30 min, re-enter at Step 3) instead of exiting babysit.
- **If every pending entry is non-blocking, DO NOT end the pass.** Report `"<n> check(s) pending on a human gate (<names>) — not a build; continuing the pass"` and go to Step 4. A review gate blocks the _merge_, not the sync, the comment triage, or the tests — and those are exactly the work the reviewer is waiting on. Aborting the pass here is how requested changes go unaddressed for an entire run.
- Carry the non-blocking list forward for the rest of the pass: Step 4 reads "all CI checks passing" as _all blocking checks passing_, Step 11 stops polling once only non-blocking entries remain, and Step 13 names every gate still pending.
- CI is fully idle only when every entry is `COMPLETED` (or there are no checks). A non-blocking gate means "proceed", never "green".

4. **Early-exit check.** Fetch state:
   `gh pr view <number> --repo <owner/repo> --json statusCheckRollup,reviews,reviewDecision,mergeable,state,autoMergeRequest,baseRefName,headRefName`
   - If `state == "MERGED"`: PR already landed — report the merge SHA, **reap the leftovers** (the merged branch and its worktree are now dead: run `git clean-worktree` then `git clean-stale-branches`, remove a skipped detached-HEAD worktree with `git worktree remove <path>` after confirming it is clean, and **keep the journal** — see the _A merged PR gets cleaned up_ rule). **Do NOT trigger a release** — release is expensive and stays a manual `/sy-release` the user invokes; never auto-dispatch it after a merge. Stop babysit entirely — merged is the one terminal state that skips the remaining Step 12 passes. A worktree carrying unpushed commits or a dirty tree is never reaped silently: report the path and leave it for the human.
   - **Merge-conflict override — check `mergeable` BEFORE either early-exit branch below.** A PR with conflicts against its base branch is NEVER "done", even when CI is green and reviewers have approved.
     - If `mergeable == "CONFLICTING"` (or any non-`MERGEABLE`, non-`UNKNOWN` value indicating a base-branch conflict): report `"PR is green + approved BUT conflicts with <baseRefName> — falling through to Step 5 to resolve"` and continue to **Step 5**. Step 5 will perform the actual merge + conflict resolution; the rest of the loop (tests, local checks, CI monitor) handles the rebuild.
     - If `mergeable == "UNKNOWN"`: GitHub is still computing mergeability. Wait 5s and re-fetch — **cap at 6 retries (~30s total)**. If still `UNKNOWN` after the cap, treat as `CONFLICTING` and fall through to **Step 5** (the merge attempt will surface the real state). Never treat `UNKNOWN` as `MERGEABLE`.
   - **Migration-head override — check this BEFORE the green + approved early-exit below, and re-check it EVERY pass.** Same shape as the merge-conflict override above and for the same reason: a PR whose migration is parented on a superseded head is NEVER "done", however green CI is and however many reviewers approved. This is the one failure mode where every signal the early-exit reads says "ready" and merging still breaks the default branch — the migration DAG is not a git conflict (sibling revisions are different files, so `mergeable` stays `MERGEABLE`), and CI on this branch never ran against the head that landed while the PR sat.
     - **Applies to any PR whose diff touches a migration path** (detection table: `/sy-sync-pr-branch` Step 7 — do not restate it here). No migration in the diff → skip this bullet entirely, no API calls.
     - **Cheap read-only probe first.** Compare the branch's migration parent against the current head on the floor branch without checking anything out: for Alembic, read the new revision's `down_revision` from `gh pr diff <number> --repo <owner/repo>` and the floor's head from `gh api repos/<owner>/<repo>/contents/<versions-path>?ref=<floor>`; for the rest, apply the framework's equivalent ordering check. In doubt, fall back to **"is there a migration on the floor branch that is not in this PR's history?"** — if yes, treat it as stale.
     - **Stale → do NOT early-exit.** Report `"PR is green + approved BUT its migration is parented on <old-head> and <floor> is now at <new-head> — falling through to Step 5 to re-parent"` and continue to **Step 5**. The fix is the delegated sync's Step 7 (merge the floor in, re-stamp onto its head — **never `alembic merge`**, never a rebase), exactly as the merge-conflict override delegates the merge itself. Babysit implements neither.
     - **Single head → carry on** to the wave-block check and the early-exit below, and say `migration head current (<head>)` in the report so a pass that skipped is auditable.
     - **Never re-parent an ancestor PR's migration** — the sync enforces downhill-only; on a stack, this branch's revision re-parents onto the ancestor's.

   - **Wave-block check — do this before judging CI, and do it every pass.** Read the PR body for a `## Blocked on` section (see the _Hard dependencies phase into waves_ rule). It names the PRs this later-wave branch waits on, so it decides whether this pass has any work in it at all. Resolve each named PR's real state with `gh pr view <link> --json state` rather than trusting the section, which goes stale by design.
     - **Any named PR still `OPEN`** → this branch legitimately does not contain the migration / column / field it needs, so red CI here is expected and is not yours to fix. Report `"PR is wave-blocked on <link> — CI stays red until it merges; skipping this pass"` and **end the pass** (skip Steps 5–11), exactly as a running build does. Do not push, do not attempt fixes, do not touch the Step 11 attempt counters, and do not escalate — this is a documented skip, not a terminal state, and the next pass exists precisely to catch the blocker landing.
     - **Every named PR `MERGED`** → the block is over and this pass has real work in it. Do not end the pass; carry on to **Step 4a**, which owns the promotion end to end. Do not drop the title prefix, undraft, or rewrite the body from here — one implementation, and it is Step 4a's.
     - **A named PR is `CLOSED` without merging** → stop and ask. The dependency this branch was built on is not coming, so the wave plan itself is wrong and no amount of syncing fixes it.
     - **No `## Blocked on` section** → not a wave PR; skip this bullet entirely and carry on. Most PRs are wave 1 and never mention it.
   - If **all blocking CI checks are passing** (Step 3's classification — a still-pending human gate neither passes nor fails this test; it does not hold the branch back, and it is named in the report so "green" is never claimed for a gate nobody clicked) AND `reviewDecision` is `APPROVED` AND `mergeable == "MERGEABLE"`:
     - **Do NOT enable automerge here.** The one place babysit may flip `--auto` is the Step 2a prose-only gate; by this point that decision is already made, and a green non-prose PR is the user's merge to click.
     - If `autoMergeRequest` is `null`: report `"PR is green + approved — ready for you to merge with 'gh pr merge <number> --squash' (or enable automerge if appropriate)"` and **end the pass** (skip Steps 5–11). Fall through to the **Step 12 loop gate** — a later pass catches review comments or CI reruns that land after this moment. **Exception — a Step 2a deferred prose-only PR:** re-run Step 2a's companion check first. If every companion is now `MERGED`/`CLOSED`, enable `--auto` here and follow the branch below; if any is still open, report `"green + approved, waiting on <n> companion PR(s): <links>"` instead and end the pass.
     - **Stacked PR — green + approved is not mergeable yet.** Cheap check: `gh pr list --repo <owner/repo> --head <baseRefName> --state open --json number,url,title`. A hit means this PR's base is another open PR, so merging now would land this work into the parent's branch, not the default branch. Report `"green + approved, but stacked on <parent link> — that PR merges first; this one retargets automatically when it does"`, do **not** merge, do **not** enable automerge, and end the pass. Keep running the remaining passes: the parent landing is exactly the event a later pass is there to catch.
     - If `autoMergeRequest` is NOT `null` (Step 2a's prose-only gate, or the user earlier via UI or `/sy-create-pr` Step 10): the merge will land on its own. Poll `gh pr view --json state,mergeable` every 30s until `state == "MERGED"`, then reap the leftovers (`git clean-worktree`, `git clean-stale-branches` — keep the journal, leave any dirty/unpushed worktree for the human, per the terminal-MERGED handling above) and stop. **Do NOT trigger a release** — release stays manual. If `mergeable` flips to `CONFLICTING` mid-wait (base advanced), break out and fall through to **Step 5**.
       - **On a migration PR, re-run the migration-head override on every poll cycle, not once on entry.** This wait is the single most dangerous place a stale head can sit: automerge means the PR lands with nobody watching, and the head can move between the check and the merge. A `--auto` PR is a queued instruction, so the window is exactly as long as the slowest required check. If the head goes stale mid-wait, break out of the poll and fall through to **Step 5** — same as a `CONFLICTING` flip. Do **not** revoke a `--auto` this command did not enable (`automerge_decision` other than `enabled_by_me`); pushing the re-parented migration re-triggers CI and re-queues the same automerge safely, which fixes the problem without touching someone else's decision.

4a. **Wave promotion — when the wave below lands, make THIS PR mergeable.** A later-wave PR is parked in a deliberately unmergeable shape: a `WIP: DO NOT MERGE — ` title prefix, a `## Blocked on` section, often draft state. **Nothing in GitHub undoes any of that when the blocker merges** — so without this step a wave-2 PR ends the run green, unblocked, and still unmergeable, waiting on a human to notice a state change that happened hours ago. This step is what turns "wave 1 merged" into "wave 2 is ready". Run it **every pass**, and run it **even when Step 4 ended the pass early** — "skip Steps 5–11" never skips this one, because a green + approved PR still titled `WIP` is precisely the PR that needs promoting.

- **Resolve the blocker set from all three signals**, then keep only the ones still open:
  - the `## Blocked on` section in the body — the canonical signal (see the _Hard dependencies phase into waves_ rule);
  - **wave context handed down by the dispatcher** — `/sy-babysit-prs` Step 4 passes each job the blocking PR links for every PR it holds. No API call, and it is the only signal available when the body was never annotated;
  - dependency prose in the body: `depends on <link>`, `part of <link>`, `blocked by <link>`, a shared plan slug.

  Resolve every candidate's **real** state with `gh pr view <link> --json state --jq .state`. The body goes stale by design and is never trusted — that staleness is the whole reason this step re-checks instead of reading a flag.

- **Any blocker still `OPEN` → not promotable.** Say which one and leave the PR exactly as it is: prefix, section, and draft state all stay. Same documented skip as Step 4's wave-block check.
- **A blocker `CLOSED` without merging → stop and ask** (Step 12 terminate-early). The dependency is not coming, so the wave plan itself is wrong; no promotion and no sync fixes that.
- **Every blocker `MERGED` → promote, in this order, never out of it:**
  1.  **Sync** — fall through to Step 5 so `/sy-sync-pr-branch` merges the default branch in and the branch finally _contains_ the migration / column / field it was waiting on. Nothing below may run before the code is actually there.
  2.  **CI green** — let the loop re-run checks. A red branch is never promoted; the next pass resumes the promotion where this one left off.
  3.  **Undraft** — `gh pr ready <number> --repo <owner/repo>` when `isDraft` is true. Third and not first on purpose: readying requests reviewers, and pinging a team onto a red branch is exactly what draft state existed to prevent.
  4.  **Drop the WIP prefix** — `gh pr edit <number> --repo <owner/repo> --title "<new>"`, stripping only a leading `WIP` / `DO NOT MERGE` prefix and preserving the `[<repo>] ` prefix and everything after it.
  5.  **Rewrite the body** — replace the `## Blocked on` section with a one-line note that it landed (`Blocked on <link> — merged`), and clear any `TODO —` marker that blocker owned. Every other section is left alone (_PR body tracks the branch_), and the payload goes through `--body-file` (_Every GitHub body payload uses a temporary file_).
- **Promote per reason — the other reasons are the author's call.** When the WIP prefix or the draft state has a stated reason _besides_ the wave block (an open `TODO —` marker, unfinished work named in the body, an explicit "keep this draft"), sync anyway, report that the blocker landed, and **leave the prefix and the draft state alone**. Promoting past a reason you did not resolve ships work its author called unfinished.
- **Idempotent and re-entrant.** Each pass completes only what is still outstanding, so a promotion interrupted between steps 3 and 5 finishes next pass instead of starting over — and nothing runs twice: a title with no prefix is left alone, an already-ready PR is not re-readied, a body with no `## Blocked on` section is not rewritten.
- **Re-run the Step 2a automerge gate once, on the pass that promotes.** Draft state and a WIP title are two of Step 2a's skip reasons, and promotion is the one event that makes them false — without this, a promoted prose-only PR stays disqualified by a condition that expired hours ago.
- **Report it explicitly** — which blocker landed, which of the five actions ran, and which did not and why: `promoted: blocked-on github.com/acme/api/pull/40 merged → synced, CI green, undrafted, prefix dropped, body updated`, or `blocker landed, WIP kept — 2 open TODO markers`.

5. **Set up the workspace, then DELEGATE the sync to `/sy-sync-pr-branch`.** Babysit does not implement branch syncing — the ancestor walk, the merge order, the conflict resolver, the migration-head check, and the pre-push gate all live in `/sy-sync-pr-branch`, which is the single implementation every Sy command shares. Babysit owns the workspace (Steps 6–11 keep using it) and consumes the sync's result block.
   **⚠️ MERGE ONLY — NEVER REBASE**, in this step and every later one. `git pull --rebase`, `git rebase`, and `--squash` rewrite pushed history and force `--force-with-lease` on the next push.
   a. **Resolve an isolated worktree for this PR — ALWAYS a worktree, NEVER the user's primary checkout** (see Never do PR-branch work in the primary checkout). Resolve the PR head branch first: `BR="$(gh pr view <number> --repo <owner/repo> --json headRefName --jq .headRefName)"`.
   - **Create or reuse it with one command: `WT="$(worktree_create "$BR")"; cd "$WT"`** (see One rigid worktree path). The command prints the folder on stdout and diagnostics on stderr, so that line is the entire setup. Do not hand-roll `git worktree add`, do not assemble the path yourself, do not `mkdir` anything: `worktree_create` already prunes stale admin records, reuses a linked worktree already on `$BR`, refuses to hand back the primary checkout, preserves unpushed commits, and falls back to a detached worktree when the branch is checked out in the primary checkout.
   - **Create or reuse the durable journal immediately after resolving the branch.** Call `worktree_create --path-only "$BR"` and use its exact output to create the sibling file `pr<number>-<sanitized-branch>.md` under the same `$HOME/.worktrees/<owner>/<repo>/` container. Record the request, PR URL, workspace path/kind, and pass number. This file persists across passes and re-invocations; it is not a temporary API payload.
   - **Check which case you landed in — the alias reports it on stderr — and pay what each one owes:**
     1. **`reusing worktree already on '<branch>'`** — a worktree from an earlier run (or the user's own). `git fetch origin`, then go straight to the recovery pass below. Compare the path against `worktree_create --path-only "$BR"`: if it is not that canonical path, treat it as a pre-existing noncanonical worktree (possibly user-owned or created by an older helper), report it, never migrate or delete it automatically, and stop for human input if it is dirty. The canonical `--path-only` output still names new work and the durable journal.
     2. **`created a DETACHED worktree`** — the branch is checked out in the primary checkout, so git refuses a second checkout of it. Work detached and push with `git push origin HEAD:"$BR"` (Step 5i) — never `git push` bare from a detached HEAD.
     3. **`keeping <n> unpushed local commit(s)`** — a previous interrupted run committed without pushing, so the alias checked the branch out **as-is, no reset**. Reconcile forward with `git merge "origin/$BR" --no-edit`; those commits are recovered work and Step 5i pushes them. Never reset or drop them.
     4. **`created worktree on '<branch>'`** — a clean start from `origin/$BR`, nothing owed.
   - **If cwd is NOT the target repo** (typical when babysit was invoked with an explicit PR URL from elsewhere), clone the repository outside `$HOME/.worktrees/<owner>/<repo>/`, then run `worktree_create "$BR"` inside that clone. Do not assemble the path, create the container, or invent a temp dir.
   - **⚠️ Recover interrupted work BEFORE the clean guard — assume a previous pass was killed mid-flight.** This command sleeps between polls and polls CI inside a pass, so being terminated mid-run (Ctrl-C, session timeout, reboot, OOM, a fan-out job cancelled) is normal, not exceptional. A reused worktree is _expected_ to hold unfinished work of ours, and a deleted worktree is expected to have left commits on the local branch. In `$WT`, check all four in order and resolve each **before** merging:
     1. **In-progress git operation.** Read `git status`, or look in `$(git rev-parse --git-dir)` for `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `rebase-merge/`, `rebase-apply/`. A left-over `MERGE_HEAD` means the last run died mid-conflict-resolution: finish the resolution per Step 5e and `git commit --no-edit`. Do not `git merge --abort` a resolution that is already complete, and do not start a new merge on top (git refuses anyway). A left-over `rebase-*` is not ours — this command never rebases — so `git rebase --abort` and say so in the report.
     2. **Uncommitted / staged changes** (`git status --porcelain`). At the **canonical** path these are ours from an interrupted pass: read the diff, then either commit it (message describes the actual hunks — see the commit-message rule) if it is complete, or finish the half-edit and commit. At a **non-canonical** path — case 1, the user's own worktree — they are the user's: **STOP and ask.** Never stash, `reset`, `checkout --`, or merge on top of either.
     3. **Untracked files** — same canonical/non-canonical split, ignoring build artifacts and anything already `.gitignore`d.
     4. **Unpushed local commits** (`git log --oneline "origin/$BR..HEAD"`). A run that committed and died before pushing leaves these; a run whose worktree was deleted leaves them on the local branch. Never reset or drop them — they ride out through the normal pre-push gate at Step 5i.
        Report each recovery in the final report (`Recovered from interrupted run: <what>`), and account for it when scoping Steps 6–10 — do not redo work that is already committed in the worktree.
   - **Guard, after recovery: the workspace must be clean before the merge.** Re-run `git status --porcelain` — it must come back empty. If it is still dirty (the user's own worktree, or work you could not confidently finish), STOP and ask the user. Never stash, reset, or merge on top of in-progress work.
   - `cd "$WT"` and run **every subsequent git / `gh` command from there**. The user's primary checkout stays untouched — never `git checkout`, `git switch`, or `gh pr checkout` in it.
   - On final exit — **after the last pass (Step 12), not between passes** — clean up **only the workspace this run created**:
     - Worktree created by this run: `git worktree remove "$WT"`. Only pass `--force` after confirming no uncommitted work to preserve.
     - Clone created by this run: `rm -rf "$WT"` after the same confirmation.
     - **Pre-existing worktree (case 1) at a non-canonical path: leave it in place.** Report the path in the final report; do not remove it.
     - Anything left behind is still reachable via `ls "$HOME/.worktrees"` and reapable by the `git clean-worktree` alias (skips dirty worktrees; skips detached HEADs, so remove those explicitly).
       b. **Confirm the workspace is on the PR head.** `git rev-parse HEAD` should match `gh pr view <number> --repo <owner/repo> --json headRefOid --jq .headRefOid`; if not, fast-forward it (`git merge --ff-only "origin/$BR"`). Skip `gh pr checkout` in worktree mode — it can collide with the branch being checked out elsewhere.
       c. **Delegate the whole sync to `/sy-sync-pr-branch` — do not merge anything yourself.** Invoke it with the workspace already resolved, local-only, and machine-readable:

     `/sy-sync-pr-branch <PR-URL> workspace=$WT server-side=never report=structured`

   - `workspace=$WT` — the sync runs in babysit's worktree and never creates, cleans, or removes one; babysit owns its lifecycle across all passes.
   - `server-side=never` — `gh pr update-branch` would merge remotely, leaving the local worktree behind and useless for Steps 6–11.
   - Defaults carry the rest: it resolves the ancestor chain fresh, merges the floor then every ancestor root-most → immediate parent (one merge per source), resolves conflicts, runs the migration-head check, runs the pre-push gate, and pushes.
   - **Re-invoke it every pass.** The chain is re-resolved each time — parents push, merge, and get retargeted between passes.
     d. **Consume the sync result block** (`/sy-sync-pr-branch` Step 8) and act on it before continuing:
   - `flags: stopped-for-human` or `migrations: needs-human` → the branch is **not** synced. Do not proceed to Steps 6–11 as if it were: report what the sync asked for, end the pass, and fall through to the Step 12 loop gate.
   - `flags: orphaned-base <link>` (an ancestor PR closed without merging) or `retargeted` → carry it into the Step 13 report; the sync already handled the merge itself.
   - `stack`, `floor`, `sources`, `migrations`, `pushed` → quote them verbatim in the Step 13 report. Babysit does not re-derive the stack shape.
   - **`migrations: re-parented <what>` + a non-empty `pushed` → re-request review from everyone who already approved.** A re-parent is a new commit, so on any repo with "dismiss stale approvals" branch protection every existing approval just silently disappeared and the PR dropped out of `APPROVED` without anyone being told. Left alone, the PR sits green and unmergeable until a human notices — and the next pass's early-exit reads `reviewDecision != "APPROVED"` and reports it as simply not approved yet, hiding the cause.
     - Resolve the prior approvers from the Step 4 fetch: `reviews[]` entries with `state == "APPROVED"`, deduped by `user.login`, excluding yourself and bots. None → nothing to do.
     - Re-request them in one call: `gh pr edit <number> --repo <owner/repo> --add-reviewer <login>[,<login>...]`. If `gh` rejects a login (no longer a collaborator, or the API refuses to re-request an author), report that one and carry on with the rest — never let a single bad login skip the others.
     - Post one comment naming the change as mechanical, so re-approval is a glance and not a re-read: `"Re-parented this branch's migration onto <floor>'s current head (<old> → <new>) after merging <floor> in — no behavior change, no source edits. Re-requesting approval since the new commit dismissed the earlier one(s)."` Same body-file transport and journal entry as every other comment this command posts.
     - **Ping once per re-parent, not once per pass.** Record it in the `## State` block's `reping` marker keyed on the re-parent SHA (the same marker Step 7 uses for fix pings). A later pass re-pings only if it pushed a **further** re-parent; three passes must never produce three notifications for one push.
     - **Only for a re-parent this loop pushed.** `migrations: single-head` means nothing changed and nobody is pinged. `migrations: needs-human` already ended the pass above.
   - If the push changed what the PR does, re-check the PR body against the new diff and update it — see the _PR body tracks the branch_ rule.
   - Note: the sync creates regular merge commits on the PR branch. The eventual PR-level merge into the base must still be a **squash merge** per repo policy.

6. **Address all review comments — bot and human, in one pass.**
   - **There is no surface-only path for human comments. Bot and human comments are both auto-fixed by default.** Author identity changes how much weight a suggestion carries and how carefully you read it — never whether you act on it. A human comment is not "verified and parked for the user"; parking one without a posted reply is the failure mode this step exists to prevent. If a pass ends with a human comment neither fixed-and-replied nor declined-with-a-reason nor escalated as a named stop-and-ask, the pass did not do its job — say so in the report instead of counting it addressed.
   - **Fetch once:** review comments `gh api repos/<owner>/<repo>/pulls/<number>/comments` + issue comments `gh api repos/<owner>/<repo>/issues/<number>/comments`. Track each comment's `user.type` / `user.login` to tell bots (`user.type == "Bot"`, or a known pattern — `*[bot]`, `coderabbitai*`, `copilot*`, `dependabot*`, `sonarcloud*`, `github-actions*`, `renovate*`) from humans; that changes how much weight a suggestion carries, not whether you respond to it.
   - **Work every unresolved, substantive comment to a disposition — fix it and commit, or reply explaining why not.** Skip ones already resolved / outdated / on stale SHAs. Capture each fix SHA right after it lands: `SHA=$(git rev-parse --short HEAD)`. Bot suggestions are proposals, not orders: fix the clear ones (typos, lint nits, a real bug / missing edge case / security or data-loss risk it caught), but apply an architectural change, redesign, broad rename, new abstraction, speculative test, or perf rewrite only when it's clearly correct and in scope — otherwise reply with the concrete reason. Anything that would reshape the PR or is genuinely ambiguous is a **stop-and-ask**, never a silent skip. Human comments carry more weight, but the posture is identical: fix or reply-why-not, never ignore.
   - **Stop-and-ask is a narrow, enumerated exit — not the default disposition for anything hard.** It is available for exactly four cases: a split request that survived the reply (below), a stack request the reviewer repeated after being declined, a change that would alter the PR's stated scope or public contract, and a conflict / migration the sync flagged `needs-human`. **Everything else gets fixed this pass**, including comments that are large, tedious, opinion-shaped, or about code you did not write. "Needs human judgment" is a claim you must justify by naming which of the four cases applies and why — an unjustified one is a skipped comment wearing a label.
   - **A comment is dispositioned once, on the pass that first sees it.** Re-verifying the same comment on pass after pass and deferring it again each time is not diligence — it is nine rounds of no-ops. If you read it, you decide it: fix, decline with a reason, or escalate by name. Carry the disposition in the `## State` block so a later pass never re-litigates a settled one.
   - **Authorization is not required to fix a review comment.** A comment on the PR _is_ the request; babysit does not wait for the user to separately approve acting on it. The only work that waits on the user is the enumerated stop-and-ask list above and the split/stack restructuring below.
   - **After each applied fix: reply `Fixed — <one-line summary> (<sha>)` (include the short hash), then resolve the thread.** Line comments → reply via `gh api -X POST repos/<owner>/<repo>/pulls/<number>/comments/<comment-id>/replies --input <tmp-reply-file>`, then resolve with the `resolveReviewThread` GraphQL mutation (`gh api graphql -F threadId='<thread-id>' -f query='mutation($threadId:ID!){ resolveReviewThread(input:{threadId:$threadId}){ thread{ id isResolved } } }'`; get `<thread-id>` from the `reviewThreads(first:100)` query, matched on `comments.nodes[0].databaseId == <comment-id>`). Issue (top-level) comments → `gh pr comment <number> --repo <owner/repo> --body-file <tmp-comment-file>` (no thread to resolve). Write every body to a unique temp file, delete it after the request whether it succeeded or failed, then journal the action. A reply-without-fix (declining): post the reason, leave the thread open, **no SHA**.
   - **A request to stack this PR is declined, every time — a review comment does not override the branching policy.** "Rebase this onto my PR #N", "base this on `<branch>`", "stack this on top of that one", or any `--base` pointing somewhere other than `<default>` is the one review request babysit never complies with, regardless of who asked or how reasonable the framing. **Never run `gh pr edit <n> --base <sibling-branch>`, never re-cut this branch from a sibling, and never merge a sibling's branch into this one** (a sibling that already landed arrives through `git merge origin/<default>` — merging its branch directly is what manufactures the dependency). Reply in the thread and leave it open (this is the "explaining why not" path), and give the concrete reason rather than citing policy at them: a stacked child cannot merge until its parent lands, its diff carries the parent's commits so nobody can see what it actually changes, and a squash-merge or retarget under it breaks it. Offer the alternative in the same reply.
   - **A request to split is answered with independent slices, never with a stack.** "This is too big, break it up" is a legitimate ask; the _shape_ of the answer is not the reviewer's to choose. Propose slices that each branch off `<default>` and each merge into `<default>` on their own, **chosen so no two touch the same files** — that is what stops the split from turning into a merge conflict two days later, and it is the whole reason to slice vertically rather than by layer (schema → API → UI is the standard road to a stack, because each layer needs the one beneath it to compile). Disjointness is engineered, not promised: the techniques live in the "Make slices disjoint with new files, not with discipline" rule — most often a new spec file per slice instead of every slice appending to the shared one, EOF appends instead of sorted inserts in registries, regenerate-don't-merge for lockfiles and snapshots, and a tiny prep PR landed alone when every slice needs the same shared edit. **Give the slices no shared ancestor PR**: siblings sequenced onto disjoint files need only `git merge origin/<default>` to stay current, while siblings hanging off a common parent PR are a stack wearing a different name and inherit every one of its failure modes. If no split leaves every piece independently mergeable, say so and keep it as one PR — one larger standalone PR beats two stacked ones, and that is a complete answer to "split this", not a dodge.
   - **Babysit proposes a split; it never performs one.** Cutting branches, moving commits, and opening sibling PRs restructures work the user owns, so a split request that survives the reply above is a **stop-and-ask** (Step 12 terminate-early: a review comment needing human judgment). Post the proposed slice list in the thread, tell the user, end the pass — do not open PRs, do not re-cut branches, and do not close this PR in favor of the slices.
   - **Run the Pre-push gate before any push at the end of this step** (Rules section).

7. **Ping anyone who requested changes, once their comments are addressed — a `CHANGES_REQUESTED` review is a hard block.** A reviewer who requested changes blocks the merge until _they_ re-review, no matter how green CI is or how many threads you resolved; GitHub does not clear that block automatically. So, once Step 6 has addressed and **pushed** fixes for every one of a given reviewer's comments, tell them and ask for a fresh look.
   - **Identify the blockers.** `gh api repos/<owner>/<repo>/pulls/<number>/reviews` → take the **latest** review per `user.login`, keep only those whose latest `state == "CHANGES_REQUESTED"`, dropping yourself (`gh api user --jq .login`) and any bot (`user.type == "Bot"` or a known bot login pattern). If none remain, skip this step entirely.
   - **Re-request the review** for each such login so it re-appears in their queue: `gh api -X POST repos/<owner>/<repo>/pulls/<number>/requested_reviewers -f 'reviewers[]=<login>'` (a 422 "cannot request from the author / already requested" is fine — report and move on).
   - **Post ONE top-level comment @-mentioning all of them together**, after the fixes are pushed. Write it to a unique temporary Markdown file and post with `gh pr comment <number> --repo <owner/repo> --body-file <tmp-reping-file>`; capture the result, delete the file immediately whether it succeeded or failed, then append the action and result to the durable PR journal. Body (plain prose, never persona-styled — a human reads it):
     `@<login1> @<login2> — I've addressed your review comments (<comma-separated fix SHAs>); the threads are resolved and pushed. Since your review currently requests changes and blocks the merge, could you take another look and re-review when you get a chance? Thanks!`
   - **Net-new only — ping once per set of fixes, not once per pass.** Post it only for reviewers whose threads you actually resolved with a pushed fix _this pass_. Do not re-ping on a later pass unless you pushed further fixes for their comments since the last ping (see the _Every review comment must be net new_ rule). A reviewer you only replied "why not" to — no fix — is **not** pinged; leave their block in place so they can respond. In `pass=single` slot mode, carry a `reping` marker in the `## State` block (which reviewers were pinged at which SHA) so a later round does not re-ping without new fixes.

8. **Add / update tests to cover the changes from Steps 6 and 7:**
   - For every code change introduced while addressing bot comments (Step 6) and human comments (Step 7), check whether existing tests cover the new behavior. If not, **add a new test or extend an existing one**. This is language-agnostic — unit tests, integration tests, snapshot tests, table-driven tests, doctests, whatever the repo uses.
   - Look for gaps: new branches / conditions, new error paths, renamed / relocated APIs, edge cases the comment specifically called out, regression coverage for the bug a reviewer flagged.
   - Place tests in the repo's existing test folder / file convention (e.g. `software/tests/`, `__tests__/`, `tests/`, `*_test.go`, `spec/`, etc.). Don't invent a new test framework — reuse what's already there.
   - If a comment was a pure doc / typo fix with no behavior change, skip — no test needed.
   - Skip if the change is genuinely untestable (e.g. CI YAML, formatting-only). Note it in the final report.
   - Commit the new/updated tests.
   - **After adding tests, verify coverage didn't regress (best-effort, language-agnostic).** Detect the repo's coverage entrypoint in this order — use the first one that exists:
     1. Repo-defined Make targets: `make test_coverage`, `make coverage`, `make cover`.
     2. `package.json` scripts: `npm run coverage`, `npm test -- --coverage`, or a script literally named `coverage` / `test:coverage`.
     3. Python: `pytest --cov` if `.coveragerc` or `pyproject.toml` `[tool.coverage]` is present.
     4. Rust: `cargo llvm-cov` or `cargo tarpaulin` if either is configured.
     5. Go: `go test -cover ./...` (always available where Go is the language).
     6. README / CONTRIBUTING.md / DEV.md mention of a coverage command — honor that one.
   - If a coverage entrypoint is found, run it once. Most repos with a configured threshold (`vitest.config`, `.coveragerc`, `pyproject.toml`, `codecov.yml`, CI config) will fail the entrypoint on regression — surface the failure in the final report and fix before pushing.
   - If no coverage entrypoint is found, **skip silently** and note `"no coverage tooling detected"` in the final report. Do NOT block on a missing coverage entrypoint — coverage is best-effort; tests being added at all is the primary gate.
   - **Run the Pre-push gate before any push at the end of this step** (Rules section).

9. **Pull current CI state and pre-emptively fix any visible failures (language-agnostic):**
   - Before running local checks, fetch the latest CI status: `gh pr view <number> --repo <owner/repo> --json statusCheckRollup`.
   - For any check already failing (lint, test, type-check, build, config validation, security scan, custom step — any language), pull the logs: `gh run view <run-id> --repo <owner/repo> --log-failed`.
   - Fix what you can locally: lint / format violations, syntax errors, type errors, broken config (`tsconfig.json`, `pyproject.toml`, `Cargo.toml`, `.golangci.yml`, etc.), simple test failures. Same generic posture as Step 11 — diagnose by category, not by language.
   - If a failure is clearly infra / flaky / approval-gated (network timeout, missing secret, queued runner), note it for the final report and move on.
   - Commit any fixes here so they get re-validated by the local checks in the next step.
   - **Run the Pre-push gate before any push at the end of this step** (Rules section).

10. **Run local checks before pushing any new commit (language-agnostic):**

- Detect project type from repo files and run whatever the repo defines. Order of preference:
  1.  **Repo-defined entrypoints first** — `make validate` / `make test` / `make lint` / `make check` (Makefile), `just test`, `pre-commit run --all-files`, scripts in `package.json` / `pyproject.toml` / `Cargo.toml` / `go.mod`, or whatever `README` / `CLAUDE.md` / `CONTRIBUTING.md` says to run.
  2.  **Otherwise fall back to language-native tooling**, e.g.:
      - Node/TS: `npm test` (or `yarn`/`pnpm`), `npx tsc --noEmit`, `npx prettier --check .`, `npx eslint .`
      - Python: `pytest`, `ruff check .`, `ruff format --check .`, `mypy .`
      - Rust: `cargo test`, `cargo fmt --check`, `cargo clippy`
      - Go: `go test ./...`, `gofmt -l .`, `go vet ./...`
      - Shell: `shellcheck`, `shfmt -d`, `bash -n`
      - Config: `tsc --noEmit` for `tsconfig.json`, `yamllint`, `jsonlint`, `cargo check`, etc.
- If any fail, **fix them before pushing** — including lint/format violations, syntax errors, type errors, broken config (`tsconfig.json`, `pyproject.toml`, `Cargo.toml`, etc.), and unit/integration test failures. Re-run until green locally.
- **Run the Pre-push gate** (commit-author check + secret scan).
- Commit and push the fixes.

11. **Monitor CI and fix any failure (language-agnostic)** — poll every **15 minutes**, max **10 polls (~2.5 hours)**: `gh pr view <number> --repo <owner/repo> --json statusCheckRollup,reviews,reviewDecision,mergeable`.
    - **Track two counters across the loop:**
      - **Global poll counter**, hard-capped at 10.
      - **Per-check fix-attempt counter** — `attempts[<check-name>]`, hard-capped at **2 fix attempts per individual check name**. Same check failing → same fix tried twice with no result usually means more pushes just churn CI. Stop trying that one.
    - On poll 11: STOP and post the **resumable escalation comment** (template below). Exit.
    - If all checks pass: go back to **Step 4 (early-exit)** to confirm green + approved.
    - If checks are still pending: **re-apply Step 3's classification before spending a poll.** A still-running _blocking_ build → keep polling (counts toward the 10-poll cap). If the only pending entries are non-blocking (human gate or stalled past 60 min), **stop polling** — they will not resolve on a timer, and burning the remaining polls on them ends in a false `poll-cap` escalation 2.5 hours later. Treat CI as settled, name the gate(s), and go back to **Step 4**.
    - If any check is failing:
      a. Get failing run IDs from `statusCheckRollup`.
      b. Examine logs: `gh run view <run-id> --repo <owner/repo> --log-failed`.
      c. **Unfixable-base checks (do these BEFORE diagnosing as a PR-side bug).** Two situations make a red check something other than a defect in this PR, and both waste the whole attempt budget if you diagnose them as code bugs.
      - **Broken main.** Check whether the same check is also failing on `origin/<default>`'s latest commit: `gh run list --repo <owner/repo> --branch <default> --limit 1 --json conclusion,name,headSha`. If the same check name has `conclusion == "failure"` on the latest default-branch commit, this is broken main — **STOP babysit**. Post the escalation comment (template below) with `Stop reason: broken-main`, tell the user, and exit. Do not retry-fix-retry against an unfixable base.
      - **Wave-blocked.** If the PR body has a `## Blocked on` section naming a PR that is still open, this failure is caused by a dependency that has not merged yet, not by anything on this branch — editing code here cannot fix it. Step 4's wave check already ends the pass in that case, so reaching this point means the section appeared or changed mid-pass: re-run that check and end the pass rather than diagnosing. Never spend an attempt-counter slot on a wave-blocked failure.
        d. **Per-check attempt cap.** If `attempts[<check-name>] >= 2`, do NOT try to fix this check again. Mark it `UNFIXABLE_AFTER_2_ATTEMPTS` in state and continue polling other checks. **If ALL currently failing checks are at the cap, STOP** and post the escalation comment with `Stop reason: all-checks-at-attempt-cap`.
        e. Otherwise diagnose the failure regardless of category — could be a test failure, a lint/format violation, a syntax error, a type error, a misconfigured `tsconfig.json` / `pyproject.toml` / `Cargo.toml` / similar, a missing dependency, or a build error in any language. Read the relevant code/config, fix it, and re-run the matching local check from Step 10 to confirm. **Run the Pre-push gate** (Rules section). Commit and push. Increment `attempts[<check-name>]`.
        f. **Go back to Step 3** — re-run the full loop: skip-if-running → early-exit → merge → bot comments → human comments → tests → pre-emptive CI fix → local checks → CI monitor.

    **Escalation comment template (resumable state).** Write the rendered template to a unique temporary Markdown file and post via `gh pr comment <number> --repo <owner/repo> --body-file <tmp-escalation-file>`. Capture the result, delete the file immediately whether it succeeded or failed, then append the escalation and result to the durable PR journal. Used on: poll-11 cap, all-failing-checks-at-attempt-cap, or broken-main detection.

    ```
    Babysit handing off — PR needs hands-on attention.

    Stop reason: <poll-cap | all-checks-at-attempt-cap | broken-main>
    Passes used: <N> full passes, <M> probes (elapsed <H:MM> of the run budget)
    Watch ticks: <N> (blocked on <what>, or "none — watch never armed")
    Polls used: <N>/10 (in-pass CI polls)
    Per-check fix attempts:
      - <check-name-1>: <attempts> (status: FAILING | UNFIXABLE_AFTER_2_ATTEMPTS | PENDING)
      - <check-name-2>: ...

    Last failing logs:
      - <check-name>: <gh run view URL>

    Commits pushed this session: <comma-separated short SHAs>
    Worktree: <path> (<reused | created-this-run>)
    Recovered from interrupted run: <none | what was recovered>
    Human comments addressed: <N> threads resolved
    Bot comments addressed: <N> fixes applied, <M> declined with reason
    Outstanding human comments: <N> (require judgment)

    To resume: re-invoke `/sy-babysit-pr <PR-URL>`. Counters reset on re-invocation; the prior state above shows what was already tried.
    ```

    Include enough state that a re-invocation OR a human picking up the PR can see exactly what was tried and where the loop gave up.

12. **Loop gate — the run is bounded by a CLOCK, not by a pass count.** One pass only ever sees the PR as it was at that instant; reviewers, bots, and CI post asynchronously. So the loop keeps working for a fixed budget and reacts to what actually changes, instead of spending a fixed number of expensive passes on a PR nobody has touched.
    - **The run budget is `<SY_PR_RUN_BUDGET_SECONDS>` seconds.** Record `started_at` on the first pass and `deadline_at = started_at + <SY_PR_RUN_BUDGET_SECONDS>`. Everything below runs until that deadline, a terminal state, or an enumerated stop-and-ask. There is no pass quota: a busy PR may take dozens of passes and a quiet one two, and both are correct.
    - **Round 1 is always a full pass.** Sync, automerge gate, comment triage, and CI all happen there, so a run that starts by polling has done no work at all.
    - **Between passes the loop POLLS, it does not sleep out a fixed round.** Every `<SY_PR_POLL_INTERVAL_SECONDS>` seconds, run the Step 12a read-only probe. Fingerprint moved → run a full pass immediately, then resume polling. Fingerprint identical → the poll was the whole round; sleep and poll again. A poll is two `gh` calls, so a one-minute cadence is cheaper than a single pass was.
    - **A full pass runs on a keepalive even when nothing moved** — at least every `<SY_PR_KEEPALIVE_INTERVAL_SECONDS>` seconds, and always as the last thing before the deadline. The digest is a proxy, not a proof; the keepalive catches what it cannot see, and the final pass stops a run from ending on an unverified probe.
    - **Inbound work never interrupts a pass in flight.** A probe that fires while a full pass is running does not cancel it: set `dirty_after_pass = 1`, let the pass finish to its safe point (edits committed, targeted check run, nothing half-applied), then start the next pass **immediately** with no sleep. Several probes collapse into one follow-up pass, so a reviewer posting six comments costs one pass, not six. Debounce a burst by one poll interval rather than firing per comment.
    - **Your own writes are not inbound work.** Exclude comments, reactions, pushes, and status updates this run produced from the change decision, or the loop re-triggers itself forever.
    - **The sleep is a real blocking command, not a note in the report.** Run `sleep <SY_PR_POLL_INTERVAL_SECONDS>` in the shell — one foreground, self-terminating command — and let the turn block on it. Never substitute a shorter sleep and never claim elapsed time you did not wait out; if the harness kills the command early, re-issue it for the remainder.
    - **Never end the run because the harness has no detached timer.** "No background job outlives the turn", "no wall clock has elapsed", "two probes were byte-identical", "the PR is quiescent, re-invoke me later" are not terminal conditions — they are exactly what the poll sleep is for. Nothing-changed is the expected result of most polls. Never close a turn by asking whether to continue; the answer is yes until the deadline, `MERGED` / `CLOSED`, or an enumerated stop-and-ask.
    - **Terminate early ONLY on:** `state == "MERGED"` (report the merge and stop; no release is triggered), broken-main escalation, all-checks-at-attempt-cap escalation, poll-cap escalation, a stop-and-ask where a conflict / migration / review comment needs human judgment, or the unreachable-service stop below. Everything else loops.
    - **Stop when GitHub or the model service is unreachable, and only after retrying.** One flaky call is not an outage: retry up to `<SY_PR_RETRY_MAX_FAILURES>` consecutive times, sleeping `<SY_PR_RETRY_INTERVAL_SECONDS>` seconds between attempts. If every attempt fails, stop and report `"GitHub or model service unreachable — stopping with resumable state"`. Never name a local network cause you cannot verify. A single failure that recovers on retry resets the counter and the loop continues.
    - **Write the resumable state on every stop, whatever the reason** — `started_at`, `deadline_at`, `last_full_pass_at`, `last_poll_at`, the last fingerprint, `dirty_after_pass`, and the `## State` block below, into the durable PR journal. That is what lets a fresh invocation pick up instead of restarting from zero, and it is the only reason an interrupted run is not lost work.
    - The poll interval is between rounds and is independent of Step 11's in-pass CI polling — they nest, they don't replace each other.
    - **`pass=single` — one pass, no clock.** When the invocation carries `pass=single`, run exactly one pass **inline, in the calling job — never dispatch a background agent for a single pass** (see _A pass that runs inside a job runs in that job_); report it, and return without sleeping and without re-entering Step 3. This exists so a **slot driver** holding several PRs (`/sy-babysit-prs` Step 4) can own the cadence itself: it polls and calls each of its PRs when their state moves, under the same run budget. The budget is not waived — it moves up to the caller, which is responsible for honoring it. An agent never adds `pass=single` on its own initiative: a human asking "babysit this PR" gets the full budgeted run. If a human types it explicitly, honor it.

      **Argument grammar.** Trailing `key=value` tokens are parameters, the bare token is the PR ref — the same shape Step 5c already uses when delegating (`/sy-sync-pr-branch <PR-URL> workspace=$WT server-side=never report=structured`). Slot mode uses two: `pass=single` and `round=<n>`, plus optional `last=true` on the pass the driver knows is final. All are single whitespace-free tokens. **`pass=single` with no `round=` means `round=1` and `last=true`** — one round, and it is the last one, so cleanup runs normally. That is what a human typing `pass=single` by hand wants, and it keeps `completed_round` and the cleanup gate below well-defined instead of depending on an argument only a slot driver ever passes. Unrecognized `key=value` tokens are reported and ignored, never treated as a PR ref.

      **State handoff — the caller is the memory.** A fresh invocation has no memory of the last one, so the counters this loop depends on (`loop_count`, `attempts[<check-name>]`, the poll count, and what this command did to automerge in Step 2a) would reset every round and quietly defeat their own caps: a check capped at 2 fix attempts would be retried forever, and a `--auto` this command never enabled could be revoked. So `pass=single` **returns a state block and accepts it back**:
      - End every `pass=single` report with a `## State` block. **It is passed as a block inside the job's prompt, never as a `state=` argument token** — it is multi-line, so no argument grammar that splits on whitespace can carry it, and encoding it into one token would just invent a quoting scheme for no benefit. The caller pastes the previous round's block into the next round's prompt under a `## Prior state` heading; no prior-state block present means round 1, and say so rather than guessing.
      - Fields: `completed_round` (rounds fully finished, distinct from the `round=` currently being run — a job that dies mid-round must resume that round, not skip it), `attempts` per check name, `polls` used, any `UNFIXABLE_AFTER_2_ATTEMPTS` marks, `reping` (which reviewers were pinged at which SHA — both change-requesting reviewers pinged after a fix (Step 7) and prior approvers re-requested after a migration re-parent (Step 5d), so a later round does not re-ping without new work), `migration_head` (the floor head this branch's migration is parented on as of the last check, plus whether this loop re-parented it — without it every round re-probes from scratch and a re-parent already pushed reads as a fresh drift), **the Step 12a probe fields** (`started_at`, `deadline_at`, `last_full_pass_at`, `last_poll_at`, `watch_fingerprint`, `probe_count`, `consecutive_noops`, `dirty_after_pass`, `externally_blocked` — without them a job re-derives its whole clock every round and the cheap poll degrades back into a full pass), plus the two ownership records below.
      - **`automerge_decision` is an enum, not a boolean.** `false` cannot be acted on, because it conflates five outcomes that need opposite follow-ups: `enabled_by_me` (revocable by me, and the only value that permits revocation), `deferred_companion` (a companion PR is still open — **re-check every round**, since the block lifts the moment the last one lands), `ineligible` (not a standalone prose-only diff — settled, never reconsider), `failed` (the `--auto` call errored — do not retry), and `pre_existing` (the user enabled it — never touch). Store the value, not a bit.
      - **`workspace` records path _and_ kind** — `worktree` or `clone` — plus whether this run created it. Their teardowns differ (`git worktree remove "$WT"` vs `rm -rf "$WT"`), so a bare "I made it" boolean cannot pick the right one, and a `rm -rf` on a real worktree leaves a stale admin record behind.
      - **Checkpoint immediately after any ownership-changing action, not only at end of pass.** Enabling automerge, creating the workspace, and pushing a fix each change state that outlives the job; a job that dies after enabling automerge but before its end-of-pass report leaves nobody knowing it is revocable. Report those the moment they happen so the slot's ledger has them.
      - The durable backstop, if the slot itself dies and the block is lost, is the **resumable escalation comment** on the PR — but note it carries only the counters, is posted only on escalation paths, and has neither ownership record. It recovers a stalled loop, not ownership; that is why the ledger holds the block.
      - **Cleanup waits for the last round.** `last=true` tells you whether this is it. Do the Step 5a workspace teardown only when the caller marked this round last or the PR reached a terminal state; on any earlier round leave it exactly as it is, since the next round reuses it.

      **In slot mode the CI monitor observes and yields — it does not hold the lane.** Step 11's 10-poll / 2.5-hour budget assumes the job owns its own time. Under `pass=single` it does not: every minute spent polling is a minute the other PRs in the lane are not being serviced, and three poll-capped passes would push the third PR of a slot five hours out — head-of-line blocking, which is the same starvation this design removes. So with `pass=single`, take **at most one** CI observation and at most one fix attempt per pass, then return; carry the poll count forward in the `## State` block and let the slot's next round do the next observation. The caps still apply across rounds, they just accrue in the handed-back state instead of inside one long pass. A slot holding exactly one PR may poll normally — nothing is waiting behind it.

12a. **The read-only state probe — what a poll actually costs, and what counts as a change.** Between passes the loop is a cheap probe, not an agent: two `gh` calls, no worktree, no diff, no writes. This is what makes a one-minute cadence affordable, and it is what fires a full pass the instant a human, a bot, or CI moves the PR. **This is the canonical definition — `/sy-review-pr`, `/sy-babysit-prs`, and `/sy-review-prs` reference it rather than restating it.**

    - **A probe is read-only and capped at two `gh` calls for the PR**, plus one `gh pr view <link> --json state --jq .state` per named blocker (wave PR, companion, stacked parent). No worktree, no `gh pr diff`, no comment bodies, no clone, no sub-agent — and nothing that writes: a probe never pushes, posts, reacts, merges, or touches automerge.
    - **A PR is `externally blocked` when a pass ended with it waiting on a person or on another PR and left nothing behind** — (a) Step 3 ended it on a blocking build; (b) Step 4 wave-blocked on an open `## Blocked on` PR; (c) Step 4 green + approved with `autoMergeRequest == null`, waiting on a human click; (d) Step 4 stacked on an open parent; (e) Step 2a prose-only deferred on open companions; (f) the only thing holding the merge is a pending human review gate Step 3 classified non-blocking, and Steps 5–11 found nothing to do. Nothing else counts. The label changes nothing about the polling cadence — every PR is polled the same way — but a fan-out uses it to decide it need not hold a worker slot for this PR (`/sy-babysit-prs` Step 4b).
    - **Never treat a PR as externally blocked while anything is actionable** — an undispositioned comment, a failing check still under its attempt cap, `mergeable != "MERGEABLE"`, a stale migration head, unpushed commits or a dirty workspace, or an outstanding stop-and-ask. Being unsure means not applying the label.
    - **The fingerprint — two commands, compared as strings:**

      ```bash
      gh pr view <number> --repo <owner/repo> --json state,isDraft,title,reviewDecision,mergeable,mergeStateStatus,headRefOid,autoMergeRequest,baseRefName,updatedAt,statusCheckRollup,comments,reviews \
        --jq '[.state,(.isDraft|tostring),(.reviewDecision//"none"),.mergeable,.mergeStateStatus,.headRefOid[0:7],(if .autoMergeRequest then "auto" else "noauto" end),.baseRefName,.updatedAt,((.statusCheckRollup//[])|map((.name//.context)+"="+((.conclusion//.state//.status)//"?"))|sort|join(",")),((.comments//[])|length|tostring),((.reviews//[])|length|tostring)]|join("|")'

      gh api "repos/<owner>/<repo>/pulls/<number>/comments?per_page=1&sort=updated&direction=desc" \
        --jq 'if length == 0 then "none" else "\(.[0].id):\(.[0].updated_at)" end'
      ```

      `--jq` reduces locally, so the probe costs two short lines of output however large the PR is. The second call exists because **line comments are not in `comments`** — that field is issue comments only, and a new review thread is exactly what a watched PR is most likely to gain. Sorting by `updated` and taking one row makes it pagination-proof: a PR with 200 line comments still answers in one row, and an edited comment sorts back to the top. `gh pr view` has no `reviewThreads` field — do not look for one.

    - **Fingerprint changed → run a FULL pass immediately, in this same round.** Reset `consecutive_noops` to 0 and name the field that flipped (`probe: rollup changed — unit-tests SUCCESS→FAILURE — running a full pass`). A probe never judges a change uninteresting; judging is the pass's job.
    - **Fingerprint identical → the probe IS the round.** Report one line — `probe <N> — no change (<blocker>) · next check <ETA> · <HH:MM> left`, sleep `<SY_PR_POLL_INTERVAL_SECONDS>` seconds, and probe again.
    - **Probes never quietly replace passes.** Round 1 is always a full pass, the **last** round before the deadline is always a full pass, and a full pass runs at least every `<SY_PR_KEEPALIVE_INTERVAL_SECONDS>` seconds even while nothing changes. The fingerprint is a cheap proxy, not a proof.
    - **Report every probe — a silent probe is indistinguishable from a dropped round.** The probe line prints per round, and Step 13 carries `<N> passes, <M> probes over <elapsed> of <budget>`.
    - **State fields.** Carry `started_at`, `deadline_at`, `last_full_pass_at`, `last_poll_at`, `watch_fingerprint` (both digest strings, verbatim), `probe_count`, `consecutive_noops`, `dirty_after_pass`, and `externally_blocked` in the `## State` block beside the other counters. Without them a `pass=single` job re-derives its whole clock every round.
    - **Under `pass=single` the probe belongs to the caller** — the per-PR job runs its pass and returns the fingerprint in its state block; the slot driver owns the sleep and the comparison, so a slot whose PRs are all externally blocked costs a handful of `gh` calls per round and holds no worker (`/sy-babysit-prs` Step 4b).

13. **Final report:** Summarize what happened — workspace setup (worktree path, whether it was reused or created, anything recovered from an interrupted prior run, cleanup status), the Step 2a automerge decision (`enabled — standalone prose-only` / `deferred — prose-only, <n> companion PR(s) open: <links>` / `enabled on pass <N> — last companion landed` / `left off — <what the diff touches>` / `skipped — <draft | WIP | not yours | already enabled>` / `revoked — no longer prose-only` / `revoked — companion PR opened: <link>`), passes run (`<N> passes, <M> probes over <elapsed> of <budget>`, naming what the probes were waiting on, per Step 12a), **the sync result block from `/sy-sync-pr-branch`, quoted verbatim** (its `stack` / `floor` / `sources` / `migrations` / `pushed` / `flags` lines — do not re-derive or paraphrase them), **any check Step 3 classified non-blocking and stepped over** (`pending human gate: <names>` / `stalled check treated as non-blocking: <names>` — these still block the merge, so never report the PR as green while one is open), comments addressed (bot + human), **a per-author disposition count that adds up** (`human: <n> total — <f> fixed, <d> declined-with-reason, <e> escalated (<which stop-and-ask case>)`, same for bots; the three must sum to the total, and any remainder is reported as unaddressed with the reason, never rounded into "addressed"), **any change-requesting reviewer pinged for re-review** (`re-review requested from @<reviewer> (<fix SHAs>)` — a `CHANGES_REQUESTED` block the reviewer must clear), **the migration-head state** (`migration head current (<head>)` / `re-parented <old> → <new>, re-approval re-requested from @<a>, @<b>` / `no migrations in diff` — never report a migration PR as green without naming which head it sits on), **any stack or split request declined in Step 7** (`declined stack request from @<reviewer>: <link>` / `proposed <n> independent slices, stopped for human` — a decline the user never sees is not a stance), tests added / updated, coverage tooling detected (or `"no coverage tooling detected"`), pre-emptive CI fixes, local checks run, CI fixes applied, per-check fix-attempt counts, and merge outcome. **No release is triggered — `/sy-release` stays a manual user action.** **Wave state, when the PR has a `## Blocked on` section:** name every blocking PR and its state, say whether the pass was skipped as wave-blocked or the PR was promoted, and when promoted say the prefix was dropped (or why it was kept).

## Rules

- **Step 3 (skip if a build is running) is the first check that may touch the PR's content — nothing before it pushes, comments, or merges.** The only thing ahead of it is the Step 2a automerge gate, which queues an instruction rather than acting (`--auto` waits for the same CI). A **running build** ends the pass: never merge, comment, or push while a job is executing. A **pending human review gate is not a build** — an approval / sign-off / changes-resolution check reported by an app sits `IN_PROGRESS` by design until a person clicks, so counting it as "CI is running" makes every pass a no-op and leaves requested changes unaddressed for the entire run. Only self-resolving checks end the pass; human gates, and anything pending past 60 minutes, are named in the report and stepped over. Ending a pass ends the **pass**, not the babysit — fall through to the Step 12 loop gate, resume polling, and re-enter at Step 3 when the probe moves.
- The loop is: Step 2a prose-only automerge gate (first pass; the deferred-companion branch re-checks every pass) → Step 3 skip-if-running → Step 4 early-exit (or, when automerge is already on, wait-for-merge) → Step 5 worktree setup + delegated `/sy-sync-pr-branch` (ancestor chain, chain merge, conflicts, migration head, pre-push gate, push) → Step 6 bot comments → Step 7 human comments → Step 8 add/update tests + best-effort coverage check → Step 9 pre-emptive CI fix → Step 10 local checks → Step 11 CI monitor → (on failure) back to Step 3 → Step 12 loop gate (run budget + cheap poll), with Step 12a's read-only probe between passes. On `state == "MERGED"`: report the merge SHA and stop. **Do NOT trigger a release — `/sy-release` stays manual.**
- **The run is bounded by a clock, not a pass count (Step 12).** A single pass is never "done" unless the PR merged or babysit escalated. The run works for `<SY_PR_RUN_BUDGET_SECONDS>` seconds, probing every `<SY_PR_POLL_INTERVAL_SECONDS>` seconds and running a full pass whenever the probe moves, plus a keepalive pass at least every `<SY_PR_KEEPALIVE_INTERVAL_SECONDS>` seconds and one final pass before the deadline. In-pass CI polling (Step 11) nests inside a pass — it does not count as a round. The budget is waived only by `pass=single` (Step 12), which does not shorten it but **moves it to the caller**: a slot driver holding several PRs owns the clock itself.
- **A round with nothing to do costs two read-only `gh` calls, never a full pass (Step 12a).** Between passes the loop is a probe: any change in that fingerprint fires the real pass on the spot, and no change means the probe was the round. Never let a probe write to GitHub, never let your own writes count as inbound change, and always run a full pass on round 1, on the keepalive, and as the last thing before the deadline — the digest is a proxy, not a proof. This is the canonical definition; the other Sy PR commands reference it.
- **Inbound work never interrupts a pass in flight (Step 12).** A comment, review, or push landing mid-pass sets `dirty_after_pass`; the current pass finishes to its safe point and the next one starts immediately with no sleep. Several events collapse into one follow-up pass, so a reviewer posting six comments costs one pass, not six.
- **An unreachable GitHub or model service ends the run, but only after `<SY_PR_RETRY_MAX_FAILURES>` consecutive failed retries `<SY_PR_RETRY_INTERVAL_SECONDS>` seconds apart (Step 12).** One flaky call is not an outage. On the real stop, report `"GitHub or model service unreachable — stopping with resumable state"` and write the state block to the journal; never name a local network cause you cannot verify.
- **ALWAYS work in a git worktree — never the user's primary checkout** (see Never do PR-branch work in the primary checkout). One rigid path: **`$HOME/.worktrees/<owner>/<repo>/<sanitized-branch>`** (see One rigid worktree path). Step 5a never hand-rolls that path or `git worktree add` — `WT="$(worktree_create "$BR")"` does the resolution order itself, and it never returns the primary checkout. When cwd is not the target repo, clone outside the worktree container, then run `worktree_create` inside that clone. Never `git checkout` / `git switch` / `gh pr checkout` in the user's main checkout. Clean up only what this run created; a reused worktree at a non-canonical path is the user's — leave it. The worktree persists across all 10+ passes.
- **Always assume the last run was interrupted; resume its work, never discard it (Step 5a).** Termination mid-run is the normal case here — the loop sleeps between probes and polls CI inside a pass. Before merging anything, recover from the reused worktree, in order: an in-progress merge (`MERGE_HEAD` → finish the resolution and `git commit --no-edit`), uncommitted / staged edits at the canonical path (finish + commit; at a **non-canonical** path they are the user's — stop and ask), untracked files, and unpushed local commits (`origin/<branch>..HEAD` → push through the Step 5i pre-push gate). Two things make discarded work possible and both are banned: `git worktree add -B` onto a branch holding unpushed commits (it hard-resets), and `stash` / `reset` / `checkout --` to "clean up" a dirty worktree. Both are why Step 5a goes through `worktree_create`: it checks for unpushed commits before choosing `-B`, and prunes first so a deleted folder's orphan record cannot make `git worktree add` fail.
- **⚠️ NEVER REBASE.** Always use `git merge` to sync branches. Never use `git pull --rebase`, `git rebase`, `gh pr update-branch --rebase`, or interactive rebase on a PR branch. Rebasing rewrites pushed history and forces `--force-with-lease` on next push. Always merge.
- **Babysit never implements branch syncing — it delegates to `/sy-sync-pr-branch` (Step 5c).** The ancestor-chain walk, the merge order, the conflict resolver, the migration-head check, and the pre-push gate all live there, once, for every Sy command. Never hand-roll a `git merge origin/<base>` in this loop, never re-derive the stack shape, and never copy the sync algorithm back in here. Babysit's own contribution is the workspace (Step 5a–5b, reused across all passes) and reading the result block.
- **What the delegated sync guarantees, every pass:** the chain is re-resolved from scratch (parents push, merge, and get retargeted mid-run); the floor is merged first, then every ancestor root-most → immediate parent, one merge per source; conflicts are resolved between sources; merges flow downhill only, so no ancestor branch is ever pushed and no ancestor PR is ever merged or retargeted to unblock this one. Cross-stack ordering falls out of the polling loop — a parent that pushes after this pass read it is picked up on the next probe. Never wait on, message, or poll a sibling job.
- **Read the sync result block before continuing (Step 5d).** `flags: stopped-for-human` or `migrations: needs-human` means the branch is NOT synced: end the pass there rather than running Steps 6–11 on a half-merged tree. `orphaned-base` / `retargeted` flags and the `stack` / `floor` / `sources` / `migrations` / `pushed` lines are quoted verbatim in the Step 13 report.
- **A stacked PR that is green + approved is still not yours to merge (Step 4).** Its base is another open PR, so merging would land the work into the parent's branch. Report the blocking parent link, leave automerge alone, end the pass, and keep looping — the parent landing (and GitHub's automatic retarget) is what a later pass is there to catch.
- **No reviewer can authorize a stack (Step 6).** The canonical rules live in the global instructions — "Every PR branches off the default branch", "Split by slice, never by layer", "Overlap is resolved by ordering, never by stacking" — read them there; do not restate, re-derive, or renegotiate them here. Babysit's only job is to hold that line inside the review thread: decline the retarget, counter-offer slices that each stand alone against `<default>` with **no shared ancestor PR**, and stop-and-ask rather than restructuring. The right time to prevent a stack is while the split is still being _described_, not once two branches have diverged on the same files and the conflict is already real. Step 4's stacked-PR handling and the delegated ancestor-chain sync exist to keep an **already-stacked** PR from rotting; neither is permission to create one, and "the tooling supports stacks" is never read as "stacking is fine".
- **A green + approved migration PR is not done until its head is current (Step 4).** The migration-head override runs every pass, ahead of the early-exit, because this is the one state where every signal reads ready and merging still breaks the default branch: sibling revisions are separate files so `mergeable` stays `MERGEABLE`, and this branch's CI never ran against the head that landed while it sat. It matters most on a PR with `--auto` already on — that one merges unattended, so the head is re-checked on **every poll cycle** of the Step 4 wait, not once on entry. Babysit implements no part of the check or the fix: detection and re-parenting live in `/sy-sync-pr-branch` Step 7, and the override's only job is to refuse to early-exit so that sync actually runs. Never resolve drift by rebasing, and never `alembic merge` when re-parenting is available.
- **A re-parent dismisses approvals, so babysit re-requests them (Step 5d).** `migrations: re-parented` plus a push means every prior approval was silently dropped by branch protection and the PR left `APPROVED` with nobody told. Re-request each prior approver by login and post one comment saying the change was mechanical (`<old> → <new>`, no source edits). Once per re-parent SHA, tracked in `reping` — three passes never send three pings for one push.
- **A wave-blocked PR is a documented skip, never a build to fix (Step 4).** A later-wave branch is red because it does not contain the migration or field it needs, and that is the design working, not a defect — see the _Hard dependencies phase into waves, never into a stack_ rule. Skip the pass while its `## Blocked on` PRs are open, re-check every pass, and never resolve a wave block by rebasing this branch onto the blocking PR; that converts a clean wait into the stack the rules forbid.
- **A merged blocker is an event this command acts on, not one it reports (Step 4a).** GitHub does not undo a `WIP: DO NOT MERGE — ` prefix, a `## Blocked on` section, or draft state when the wave below lands, so a wave-2 PR left alone stays unmergeable forever while reading as green. Promotion runs every pass — even on a pass Step 4 ended early — and in a fixed order: sync, CI green, `gh pr ready`, drop the prefix, rewrite the body, then re-run the Step 2a automerge gate once. It is idempotent, it promotes **per reason** (a WIP kept alive by an open `TODO —` marker keeps its prefix), and it is reported action by action.
- **Pre-push gate runs before every `git push` in this command — no exceptions.** Two checks, both blocking:
  1. **Commit-author identity check.** Compare each pending commit's `author.email` and `author.name` to local config (`.gitconfig`): `git log @{u}..HEAD --format='%H %ae %an'` vs `git config --get user.email` / `user.name`. On mismatch, flag the SHA(s) + identities side-by-side and ask the user whether to proceed with the existing author. **Default = "no"** → run `git commit --amend --reset-author --no-edit` (single commit) or `git rebase <base> --exec 'git commit --amend --reset-author --no-edit'` (multiple). **Preserve `Co-Authored-By:` trailers** — `--reset-author` only touches the author field; trailers in the message body survive. Only push without `--reset-author` on explicit user "yes".
  2. **Secret scan.** Scan all unpushed changes — `git log @{u}..HEAD -p` plus `git diff --cached` (if anything staged). Check for:
     - **Filename allowlist** — flag staged paths matching: `.env*` (except `.example` / `.sample` / `.template`), `**/credential*`, `**/secret*`, `**/*.pem`, `**/*.key` (except `.pub.key`), `**/*.p12` / `.pfx` / `.keystore`, ssh keys (`id_rsa*` / `id_ed25519*` / `id_ecdsa*` / `id_dsa*`), `*.kdbx`, `service-account*.json`, `gha-creds-*.json`, `.npmrc` / `.pypirc` / `.netrc` with auth lines, `.aws/credentials`, `.kube/config`, `.docker/config.json`, `terraform.tfstate*`.
     - **Content patterns** — AWS (`AKIA|ASIA[0-9A-Z]{16}`, `aws_secret_access_key\s*=`), GitHub (`gh[pous]_[A-Za-z0-9]{36,}`, `github_pat_`), Anthropic/OpenAI (`sk-(ant-|proj-)?[A-Za-z0-9_-]{20,}`), Slack (`xox[abprs]-`), Google (`AIza[0-9A-Za-z_-]{35}`), private keys (`-----BEGIN .* PRIVATE KEY-----`), JWTs (`eyJ[A-Za-z0-9_-]+\.eyJ[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+`), assignments `(password|api[_-]?key|token|secret)\s*=\s*["'][^"']{6,}` — skip placeholders (`<...>` / `xxx` / `***` / `example`).
     - On hit: redact the value (e.g. `AKIA****REDACTED****`), show path + line + matched pattern, ask the user. **Default = "no"** → STOP, do not push, tell the user to remove the commit (`git reset HEAD~N` or rebase) and re-stage clean. Proceed only on explicit "yes" + user confirms false positive.
- Never skip local checks before pushing — it wastes CI cycles.
- **Bot comments: only trivial / minor fixes** (typos, single-line lint nits, doc wording). Never let a bot drive a refactor or redesign — skip anything non-trivial.
- **Every behavior-changing fix from Step 6 or 7 needs test coverage in Step 8.** Doc/typo/format-only changes are exempt. Coverage verification at the end of Step 8 is best-effort and language-agnostic — skip silently if no entrypoint is detected; do NOT block.
- Fix CI failures of every kind (tests, lint, type-check, build, config) regardless of language — do not assume JS/Node.
- **Broken-main detection runs before every fix attempt.** If the same check is failing on `origin/<default>`'s latest commit, the PR can't go green until default is fixed — stop, post the escalation comment, flag the user.
- Poll CI every 15 minutes; do not spam `gh` calls. Each wake runs the full loop (comments + CI) in one pass. Hard cap at 10 polls (~2.5 hours) — escalate via the resumable escalation comment after that.
- **Per-check fix-attempt cap = 2.** A single CI check failing twice with no result usually means the fix path needs human judgment. Don't churn CI with a third attempt — mark it `UNFIXABLE_AFTER_2_ATTEMPTS` and surface in the escalation comment.
- **After every applied fix: reply `Fixed — <one-liner> (<short-sha>)` and resolve the thread** (mechanics in Step 6). Reply-without-fix → post reply, leave thread open, no SHA.
- **Human comments are auto-fixed, exactly like bot comments (Step 6).** There is no "surface it to the user and move on" disposition — that is how a PR accumulates nine rounds of verified-but-untouched feedback while every report claims the pass ran clean. Every comment leaves the pass fixed-and-replied, declined-with-a-reason, or escalated under one of the four enumerated stop-and-ask cases, and the Step 13 counts must sum to the number of open comments.
- **A `CHANGES_REQUESTED` review is a hard block that only the reviewer clears — ping them once you've addressed it (Step 6).** Resolving threads and going green does not lift a requested-changes review; GitHub keeps the merge blocked until that reviewer re-reviews. After pushing fixes for all of a given blocker's comments this pass, re-request their review and post ONE top-level comment @-mentioning them, telling them their comments were addressed (with the fix SHAs) and asking for a re-review. Net-new only: ping a reviewer once per set of fixes, never once per pass, and never ping someone you only replied "why not" to. The comment body is human-facing prose — never persona-styled.
- **Release dispatch is NEVER automatic.** Releases are expensive and stay a manual `/sy-release` the user invokes deliberately. When babysit observes `state == "MERGED"`, report the merge and stop — do not dispatch a release, and do not offer to.
- **A merged PR is reaped, not left to rot (Step 4).** The terminal `MERGED` observation stops babysit before Step 5's per-run worktree teardown ever runs, so the dead branch and worktree must be cleaned up right there: `git clean-worktree` (removes worktrees whose branch is merged or gone, skips dirty ones and detached HEADs), then `git clean-stale-branches` (deletes the local branch whose upstream went `[gone]` on the squash-merge). Remove a skipped detached-HEAD worktree with `git worktree remove <path>` only after confirming it is clean. **Never `--force` past a dirty tree and never delete the durable journal** — a worktree with unpushed commits or uncommitted work means work never made it into the merged PR: report its path and leave it for the human (see the _A merged PR gets cleaned up_ global rule).
- **Never enable automerge on babysit's own behalf — with one carve-out: a STANDALONE prose-only diff (Step 2a).** Docs files, comments, docstrings, whitespace and nothing else, **and no companion PR still open** → babysit runs `gh pr merge <n> --squash --auto` on the first pass, before the CI check, and says so; CI and any required approval still gate the merge. Any executable line in the diff and automerge stays off until the user says otherwise. A prose-only PR that belongs to a set (batch siblings, a shared `<username>/<group-slug>/` branch prefix in any repo, an explicit reference to another open PR, or a stacked base) is **deferred, not enabled** — babysit re-checks each pass and flips `--auto` only once the last companion is merged or closed, so docs never land ahead of the code they describe. If babysit's own later commits make the PR non-prose-only, it runs `--disable-auto` and hands the merge back. Automerge the user or `/sy-create-pr` enabled is never touched — babysit observes it and waits (Step 4).
- **Migration head stays single — checked and fixed inside the delegated sync** (`/sy-sync-pr-branch` Step 7), once after the whole chain merges: exactly one head descending from the floor, re-parented rather than merge-revisioned, never re-parenting an ancestor PR's migration. `/sy-review-pr` warns about cross-PR migration conflicts; the sync fixes them. Babysit only reports the `migrations:` line it gets back.

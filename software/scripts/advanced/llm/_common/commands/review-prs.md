[Sy] Run `/sy-review-pr` on EVERY open PR in scope. Fan-out wrapper — finds matching open PRs, ranks them by how much work they are owed, and dispatches them **all at once, in parallel background jobs**, delegating the full per-PR review (skip checks, author flags, diff review, verdict, post) to `/sy-review-pr`. One job per PR while job slots last; past that, PRs are **assigned** to the running slots rather than queued behind them, so every resolved PR is reviewed in the same run. Every PR gets **at least 3 passes, 30 minutes apart**. Repo-, language-, and framework-agnostic.

**Recommended order.** Run `/sy-review-prs` first (verdict pass — no code changes), then `/sy-babysit-prs` (apply fixes, drive CI green). Reversing wastes babysit cycles on PRs that would otherwise be requested-changes and rewritten. Both commands now run the same 3-pass / 30-minute cadence, so both are hour-plus fan-outs by design.

Argument: $ARGUMENTS (optional — scope filter; see "Resolving scope" below). Defaults to **all open PRs in the current repo, authored by anyone**, when invoked from inside a git checkout — otherwise **all open PRs authored by me**.

## Steps

1. **Resolve scope.** Parse `$ARGUMENTS` and build the `gh search prs` call:
   - **Empty `$ARGUMENTS`** — if invoked from inside a git checkout, default to the current repo (resolve via `git remote get-url origin` → `<owner>/<repo>`) and ALL authors: `gh search prs --repo <owner>/<repo> --state=open`. If not inside a repo, default to `--author=@me`.
   - **`me` / `mine` / `self`** (case-insensitive) → `--author=@me`.
   - **`<github-handle>`** (single bare token, no spaces) → `--author=<handle>`.
   - **`<full name>`** (multiple tokens, no slashes) → resolve via `gh api "search/users?q=<name>" --jq '.items[0].login'`, confirm with the user, then `--author=<resolved-handle>`.
   - **`<owner>/<repo>`** (single token containing `/`) → `--repo <owner>/<repo>`. Multiple `<owner>/<repo>` tokens (comma- or space-separated) → fan out one `gh search prs` call per repo and union the results.
   - **`org:<org-name>`** → `gh search prs --owner=<org-name> --state=open`.
   - **Combined** — repo / author tokens compose: e.g. `acme/api,acme/web alice` → search both repos for PRs by `alice`.
   - **Repo list** (e.g. workspace bundles like `myapp-frontend`, `myapp-backend` or `myapp-lib`) — same as multiple `<owner>/<repo>` tokens; resolve each to its `<owner>/<repo>` (the user may pass bare repo names, in which case ask for the owner once and reuse it across the list).

2. **Fetch PRs:**
   `gh search prs <scope-flags> --state=open --limit 1000 --json number,title,repository,isDraft,url,createdAt,updatedAt,author`

   Then, for stack detection and worktree paths, one follow-up per PR: `gh pr view <url> --json headRefName,baseRefName`. **`gh search prs` has no `headRefName` / `baseRefName` field** and **`gh pr view` has no `repository` field** — see the `gh` field traps in `/sy-list-prs` (Fetch PR data). Without an explicit `--limit`, search returns only 30 and the tail is silently missing, which would strand PRs before slot assignment ever runs; if the count comes back exactly at the limit, report the set as possibly truncated.

3. **Announce:** Tell the user how many open PRs were found and list them (repo, PR number, title, author). When the set includes any author other than you (`gh api user --jq .login`), lead with a `Mixed authors: <handle> (N), …` line and keep the author on every row — reviewing your own PR and reviewing a teammate's are different acts, and the default scope here is "all authors in the current repo". Skip PRs already filtered out by `/sy-review-pr`'s own skip rules in the per-PR step — don't pre-filter here.

4. **Concurrent-migration cross-check (only when scope is multi-repo or covers a workspace bundle).** Run this BEFORE dispatching any review job — once the fan-out is in flight the jobs run concurrently and can't be handed shared context. Scan ALL open PRs in scope for ones that add a database migration file (same detection paths as `/sy-review-pr`'s Migration checks). If two or more PRs each add a migration: note the migration-conflict pairs upfront in the announcement, and pass the pairing to each affected job so it can flag its author symmetrically.

4a. **Open the ping-pong pulse — emit the FIRST one before dispatching anything.** Render `/sy-list-prs pingpong <same-scope-token>` with every Agent cell at `⚪ NOT STARTED`. Reviews post no code, but they still run 3 passes 30 minutes apart, so the same rule holds: never let the user stare at a silent terminal wondering whether anything is running. Layout lives in `/sy-list-prs` — do not hand-roll it.

Start the **agent ledger** here: one row per resolved PR holding job state, loop number, **slot number and position within that slot**, first dispatch time, last pass start / end, next pass ETA, **that PR's latest `## State` block verbatim** (round counter, what was already posted, current verdict, outstanding stop-and-ask — handed back by `/sy-review-pr` after every `pass=single` pass), and the **last rendered pulse snapshot** (Status color emoji, component lines, counters strip) that `/sy-list-prs pingpong` diffs to pick its change marker and `Δ` line — overwrite it after every pulse. The state block is the only copy of what a re-invoked per-PR job cannot remember: the next round's prompt is built from it, and a replacement job for a dead slot is seeded from it, so a ledger without it makes every round a first round and pass 2 restate pass 1. Record the slot number and position for every PR at assignment (Step 4b), position-2+ ones included; the pulse groups its board by feature set and prints `🌊 slot <N>` on every row. Record every timestamp the moment it happens (dispatch, pass start, pass end, next-pass ETA); the pulse's `started 17:12 · running 6m` clock is read from them and cannot be reconstructed later. Every PR gets ≥3 passes (`/sy-review-pr` Step 10, or the slot's own rounds when it holds several), so Agent cells carry the `(loop N/3)` counter — `🔄 IN PROGRESS`, `⏸️ WAITING`, `⏸️ WAITING_AFTER_SKIP`, `✅ COMPLETED`, `⏭️ SKIPPED`, `❌ FAILED`.

4b. **Rank every PR, then assign every PR to a slot — before anything launches.** The harness caps how many background jobs can run at once. With more PRs than slots, the naive fan-out reviews the first `S` and silently strands the rest; this step is what makes "EVERY open PR in scope" true rather than aspirational. Identical to `/sy-babysit-prs` Step 3b — same ranking, same dealing, same guarantee:

- **Resolve `S`, the concurrency cap.** Default to **8**. It is a property of the harness, not of this command, so treat it as a parameter: a `cap=<positive-int>` token in `$ARGUMENTS` wins over the default, as does the user naming a cap in prose. Reject anything that is not a positive integer — fall back to the default and say so, because `S = 0` makes `i mod slot_count` a division by zero. **Strip the `cap=` token from `$ARGUMENTS` before any scope parsing**, and never forward it to `/sy-list-prs`; left in place, Step 1 reads a bare token as an author and would search for author `cap=4`. Say which value you used and where it came from.
- **If the launch is partially rejected, cancel and relaunch — never inject the rejects into a running slot.** Slot prompts are immutable and self-contained by design (Step 5), which is why a live slot cannot be handed extra PRs; the dead-slot rule forbids the same mutation for the same reason. When only `k` of `slot_count` jobs actually start:
  - **`k == 0` is a launch failure, not a cap discovery.** Report it and stop — `S = 0` makes `i mod slot_count` a division by zero and would "recover" into launching nothing.
  - **Cancel the `k` that started and confirm each is terminated before relaunching**; two jobs reviewing one PR double-post.
  - **Seed the relaunched slots with each PR's `## State` block from the ledger**, so a review already posted by a cancelled job is not posted again.
  - Then set `S = k`, re-deal the **entire** ranked list round-robin into `k` slots, and launch that set in one message. These jobs are sleep-dominated, so cancelling a partial first pass costs almost nothing. Report the discovered cap and the re-deal, since the new slot map supersedes the one already announced.
- **Rank all `N` resolved PRs by the work-owed ranking, read through the REVIEWER lens** — the canonical tier list lives in `/sy-list-prs` (`## Work-owed ranking`), which defines one table and two lenses over it. Do not restate or re-derive the tiers here; read them there. Use the **reviewer lens**, not the default author lens: _awaiting first review_ is promoted to the top (it is this command's entire reason for existing, and the only tier where nobody has looked at the PR at all), and P1 `CHANGES_REQUESTED` drops to just above P6 (another reviewer already has an open block, so `/sy-review-pr` Step 3 skips it rather than piling on — servicing it early spends a round on a documented no-op). Say which lens you used when reporting the slot map. Ranking decides **order only** — it never removes a PR from the set, and it never substitutes for `/sy-review-pr`'s own skip rules.
- **Open `slot_count = min(N, S)` slots and deal the ranked list round-robin**, not in chunks: ranked PR `i` (0-based) goes to slot `i mod slot_count`. Dealing puts the top `slot_count` PRs each at the **head of their own slot**, so every one of them is reviewed in round 1; chunking would pile the most urgent PRs into one lane behind each other.
- **Every PR has a slot before the first job launches.** There is no queue and no "wave 2". A resolved PR with no slot assignment is a bug in this step, not a backlog — go back and assign it.
- **Report the slot map at dispatch** — one line per slot listing its PRs in service order with each one's tier. This is the artifact that proves nothing was stranded.
- **Warn — do not refuse — when a slot holds more than 3 PRs.** Say so, name the number, and carry on; reviewing all of them slowly beats reviewing `S` of them and abandoning the rest.

5. **Fan out one background job per SLOT — all at once, in parallel.** Do NOT walk the list sequentially. If one job fails, the others keep going — record it and move on.

   **Dispatch mechanics — this is the step agents get wrong.** "In parallel" is a hard requirement, not a hint:
   - **Emit every slot job in ONE assistant message with `slot_count` tool calls in that same message.** One sub-agent / Task / background-shell invocation per slot, all in a single block. A second message per slot is a sequential loop wearing a parallel costume — that is the failure mode this section exists to prevent.
   - **Never** `for pr in ...; do ...; done`, never "start job 1, wait, start job 2", never a staggered launch. Every slot starts at the same instant.
   - **One slot = one job = one lane. When `N ≤ S`, one slot holds exactly one PR** and this is the classic one-job-per-PR fan-out. A slot only holds several PRs because there were more PRs than slots — that is the carve-out to the "never a single job that iterates the PR list" rule, and it is the _only_ one: a slot iterates **its own assigned PRs**, never the whole list, and never a list it chose itself.
   - **Jobs share nothing** — no cwd, no state file, no conversation. A slot job must never read another slot's result or wait on it.
   - **Each slot job's prompt is self-contained.** Pass, explicitly: its **ordered list of assigned PRs** with each one's tier, and for every one of them the full PR URL, the resolved `<owner>/<repo>` (from `git remote get-url origin`, never the folder name), the PR number, and any migration-conflict pairing from Step 4. Sub-agents start with a fresh context — anything you don't pass, they don't have.
   - **Report the fan-out the moment it's launched** — the slot map from Step 4b — so the user can see the whole set covered, not a prefix of it.

   **What a slot job does — interleave rounds, never review one PR to completion first.** A slot that ran the full `/sy-review-pr` loop for PR A (≥3 passes, ~1.5h) before touching PR B has moved the starvation somewhere less visible. **The slot owns the cadence:**
   - **One round = one pass on each PR the slot holds, in its assigned order, then ONE shared 30-minute sleep.** Invoke `/sy-review-pr <PR-URL> pass=single round=<n>/<total>` per PR, **and paste that PR's `## State` block from the previous round into the job's prompt under a `## Prior state` heading** (omit it on round 1). `pass=single` makes the per-PR command run one pass and return instead of sleeping and looping itself; the prior-state block is what stops pass 2 from restating pass 1. Dropping either turns a 3-round slot into three disconnected first passes.
   - **Run at least 3 rounds**, so every PR in the slot still gets its ≥3 passes, 30 minutes apart — the floor from `/sy-review-pr` Step 10, honored by the slot instead of by the per-PR job. A slot holding one PR is behaviorally identical to plain `/sy-review-pr`.
   - **Re-rank the slot's own PRs at the top of every round**, so a PR that just picked up new commits or a new thread moves ahead of an idle one. **Re-ranking sets the order within the round — never whether a PR gets a pass in that round.** Every PR the slot still holds gets exactly one pass per round regardless of its tier, so a PR that ranks last forever is reviewed last forever, not skipped. Re-rank within the slot only — never steal a PR from another slot mid-run.
   - **A PR that reaches a terminal state drops out of the slot's rotation** (`MERGED` / `CLOSED`, or a stop-and-ask needing human judgment). Report it and stop passing it. A skipped pass is **not** terminal — draft, WIP, already-reviewed, and blocked-by-another-reviewer all get called again next round, because any of them can flip in 30 minutes.
   - **If a whole slot job dies, relaunch that slot — do not fold its PRs into a live one.** A dying slot frees exactly the capacity it was using, so a replacement fits without exceeding `S`, while pushing its PRs into a neighbour silently doubles that lane's round length and breaks the "a slot's assignment never changes mid-run" rule. Launch the replacement with the dead slot's **remaining** PRs plus a checkpoint from the ledger — each PR's last `## State` block. **Resume per PR from its own `completed_round + 1`**, never from one slot-wide round number: a slot dies mid-rotation, so a slot-wide restart either re-reviews a PR minutes after its last pass (breaking the 30-minute spacing) or skips the round another PR never got. The replacement services only the PRs still owing the interrupted round, sleeps once, then resumes the full rotation — the slot re-unifies once every PR is level. No capacity to relaunch into (the run is being torn down) means reporting those PRs with their per-PR round counts, never as reviewed.
   - The 30-minute sleep is per round, not per PR — that is what makes packing a slot nearly free. These jobs are sleep-dominated: a pass bursts a handful of `gh` calls and then waits, so three PRs in one lane cost three passes of work and **one** sleep.

   The per-PR skill owns the full behavior:
   - Skip drafts / WIP / DO NOT MERGE / already-reviewed-no-new-commits / blocked-by-other-reviewer.
   - Load repo rules and culture context (`CLAUDE.md` / `AGENTS.md` / `CONTRIBUTING.md` / `.cursorrules`).
   - Pre-flight author flags (diff-vs-description mismatch, merge conflict with base, failing CI with run-URL pinpoint, migration coordination) as PR comments.
   - De-dup against existing review threads and their reactions (human + bot + own past comments) — 👍 what's already covered, reply in-thread with the delta when a comment misses a case, new top-level comment only for genuinely new findings.
   - Read the diff (or just the new commits for stale-approval re-reviews).
   - Pick verdict — APPROVE / COMMENT (default bias) / REQUEST_CHANGES (show-stoppers only). Cap at COMMENT when another reviewer's `REQUEST_CHANGES` is open or CI is failing.
   - Post the review — or post nothing at all when a re-review turns up nothing new.
   - Terminate that PR early only on `MERGED` / `CLOSED` or a stop-and-ask.

   **Expect long runtimes.** Every PR gets at least 3 passes 30 minutes apart, so a run takes 1h+ by design, longer as slots fill. That is the point — do not shorten it, do not collapse a PR to a single round, and do not poll the jobs in a busy loop. Collect each result when its job reports back.

   Review is read-only — it works off `gh pr diff` / `gh api` and needs no checkout, so parallel jobs never collide. **If a review genuinely needs the code on disk** (building the branch, running a tool over the tree, reproducing a failure), that job checks out into a worktree at the canonical path — **`$HOME/.worktrees/<owner>/<repo>/<repo>__pr-<number>`** (see One rigid worktree path) — with `WT="$(git create-worktree "$BR" <number>)"`, which reuses a linked worktree already on that branch when one exists and creates it there otherwise; only when cwd is not the target repo does it `gh repo clone` into that same leaf. The PR number keys the path, so PRs never collide across slots or within one, and babysit shares the same worktree instead of making its own. Never `git checkout` / `git switch` / `gh pr checkout` in the user's primary checkout (see Never do PR-branch work in the primary checkout). The worktree persists across all 3 rounds; remove only worktrees the job created.

   Do NOT re-implement any of the per-PR logic here — if per-PR behavior needs to change, edit `/sy-review-pr`.

5a. **Ping-pong every 10 minutes until every job reports.** The fan-out runs an hour-plus by design (≥3 passes, 30 min apart), so the dispatcher's job while it waits is to keep a pulse on the wall — not to sit silent, and not to busy-poll the jobs.

- **Cadence: one pulse every 10 minutes**, from dispatch until the last verdict lands. Three pulses per review pass, so a sleeping job still shows a live heartbeat with its next-loop ETA. A packed slot outlives many pulses — keep pulsing until the board is fully terminal.
- **Render with `/sy-list-prs pingpong <same-scope-token>`, passing the current agent ledger.** Same scope token as Step 4a so every pulse covers exactly the dispatched set.
- **Refresh the Status column from GitHub, not from the jobs.** Re-run the cheap `gh pr view` status calls `/sy-list-prs` already uses. **Never message or interrupt a running job to ask its progress** — that wakes a sleeping pass and corrupts its 30-minute cadence. Read job state only from verdicts already reported. A PR sitting at position 2+ of a slot whose earlier PRs are still mid-pass stays `⚪ NOT STARTED — slot <N>, position <p> of <n> — behind <link>`, and keeps its slot number on the PR cell's group line so it still reads inside its feature set rather than in a queue bucket.
- **Update the ledger from reports as they land** — a job finishing pass N on a PR moves that row to `⏸️ WAITING (loop N/3)` with `next loop <ETA>`, or to `⏸️ WAITING_AFTER_SKIP` when that pass was skipped but passes remain; a job's final report for a PR moves it to `✅ COMPLETED` / `⏭️ SKIPPED` / `❌ FAILED`. Between reports, derive `IN PROGRESS` vs `WAITING` and the next-loop ETA from the known cadence (round end + 30 min) rather than leaving the cell blank.
- **A pulse is display-only.** It never dispatches, retries, posts a review, changes a verdict, or re-assigns a slot. A pulse that notices a **dead** slot reports it and nothing more — the relaunch is Step 5's job, taken outside the pulse, and it relaunches the dead slot rather than moving its PRs anywhere.
- Stop pulsing when every row is terminal (`✅ COMPLETED` / `⏭️ SKIPPED` / `❌ FAILED`), then go to Step 6. **`⏸️ WAITING_AFTER_SKIP` is not terminal** — that PR still has passes scheduled, so the pulse keeps running.

6. **Final report:** emit the **closing ping-pong** — one last `/sy-list-prs pingpong <same-scope-token>` with the final ledger and `Next ping-pong: — (final)` — then summarize per PR: author (when the set is mixed), slot, passes run (`<N>/3`), verdict (APPROVE / COMMENT / REQUEST_CHANGES / SKIPPED + reason), author flags posted, and any cross-PR migration coordination notes. **State explicitly that every resolved PR was reviewed** — count the rows and compare against the Step 3 announced count; a mismatch is the failure this command's slot assignment exists to prevent, so name any PR that got zero passes and why. The run therefore always brackets itself: pulse at the start (Step 4a), pulse every 10 min (Step 5a), pulse at the end.

## Rules

- **This command is a dispatcher. The per-PR logic lives in `/sy-review-pr` — do not re-implement it here.**
- **Every job writes to GitHub — there is no report-only mode** (see `/sy-review-pr` Output surface). Verdicts, author flags, line comments, threaded replies, and 👍 reactions land on the PRs themselves; the Step 6 summary reports what was posted, it does not replace posting. Never stop to ask the user whether to post or report, and never route findings to a `/sy-critique-*` command — no such command exists.
- **Parallel means one message, `slot_count` tool calls — not `N` (Step 5 Dispatch mechanics).** The job count is `min(N, S)`, never the PR count: launching one job per PR past the cap is what strands the tail. If the transcript shows slot jobs starting one message at a time, the fan-out was sequential and must be relaunched.
- **Every resolved PR is assigned before anything launches — never queue, never drop (Step 4b).** One job per PR while slots last; past the concurrency cap, the surplus PRs are dealt round-robin into the running slots and reviewed there. There is no "wave 2", nothing waits for a freed slot, and a PR that ends the run with zero passes is a bug in this command, not an acceptable outcome. Slots are **sleep-dominated** — a pass bursts a few `gh` calls and then waits 30 minutes — so packing a lane costs extra passes, not extra sleeps.
- **Order comes from the work-owed ranking, defined once in `/sy-list-prs`.** Do not restate the tiers here, do not invent a second ranking, and never use it to skip a PR — it sets service order only, and it never substitutes for `/sy-review-pr`'s own skip rules.
- **A slot with several PRs interleaves rounds — it never finishes one PR before starting the next (Step 5).** One pass per held PR, then one shared 30-minute sleep, at least 3 rounds, via `/sy-review-pr <url> pass=single`. Reviewing PR A's full 3-pass loop before touching PR B is the same starvation this design removes, just hidden inside a job.
- **Review all resolved PRs in parallel background jobs — never a sequential for-loop** (see Fan out multi-PR work in parallel). Collect verdicts as jobs finish and report once at the end.
- **Any job that needs the code on disk uses a worktree at the canonical path** — `$HOME/.worktrees/<owner>/<repo>/<repo>__pr-<number>`, always via `git create-worktree` (see One rigid worktree path) — never the user's primary checkout (see Never do PR-branch work in the primary checkout). Reviews are normally checkout-free; treat a checkout as the exception, not the default.
- **Show the author on every row when the set is mixed** (see Show PR authors). This command defaults to ALL authors in the current repo, so mixed sets are the norm, not the exception — the final report (Step 6) carries the author alongside each verdict too.
- **Honor `/sy-review-pr`'s skip rules** — never pre-filter drafts / WIP / already-reviewed PRs in this wrapper. Let the per-PR skill decide and report the skip reason so the audit trail is complete. A per-pass skip is not terminal there — a job that skips pass 1 on a draft still runs passes 2 and 3, so that row is `⏸️ WAITING_AFTER_SKIP`, not `⏭️ SKIPPED`; only an exhausted pass budget (or `MERGED` / `CLOSED`) settles it to terminal. **The announced count is the dispatched count**: 10 in-scope PRs of which 5 are drafts is 10 jobs, not 5. A draft that gets marked ready between passes is exactly what the later passes exist to catch.
- **Every PR gets ≥3 passes, 30 minutes apart** (`/sy-review-pr` Step 10, or the slot's own rounds when it holds several). Never treat the first verdict as a PR's final report, and never cancel a job because it went quiet — between passes it is asleep by design. `pass=single` is the one sanctioned way to run a lone pass, and only from a slot driver that is itself honoring the 3-round floor (Step 5).
- **Default bias inherits from `/sy-review-pr`**: APPROVE or COMMENT — REQUEST_CHANGES is reserved for show-stoppers only.
- **Silent jobs are a success, not a failure.** A job that posts nothing because the re-review turned up nothing new reports `NO-OP` in the final summary. Don't retry it and don't nudge it into commenting to prove it ran.
- **Ping-pong is mandatory, not optional (Steps 4a / 5a / 6).** Every run pulses before dispatch, every 10 minutes while jobs run, and once at the end. The pulse is read-only — it refreshes PR status from `gh` and reads already-reported verdicts; it never messages or interrupts a running job, and it never acts on what it finds.
- **Ping-pong layout is owned by `/sy-list-prs pingpong`.** This command owns the agent ledger (job state, loop number, dispatch / pass times, next-pass ETA, slot number and position, last rendered pulse snapshot) and passes it in; `/sy-list-prs` owns the three columns, the icons, the change marker, the feature-set grouping, and the sort. Every PR gets ≥3 passes, so Agent cells here carry the `(loop N/3)` counter — same form as `/sy-babysit-prs`.
- **Multi-repo workspaces** (e.g. a bundle like `myapp-frontend`, `myapp-backend` or `myapp-lib`): pass each repo as a `<owner>/<repo>` token. The cross-PR migration check (Step 4) runs across the full union **before** any job is dispatched, so coordination flags surface before any verdict is posted.
- **Always resolve `<owner>/<repo>` via `git remote get-url origin`, never from the folder name (see Repo Identification).**

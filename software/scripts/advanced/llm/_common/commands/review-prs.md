[Sy] Review OTHER PEOPLE'S open pull requests — you act as the **reviewer**, not the author. Runs `/sy-review-pr` on every open PR in scope: finds matching PRs, ranks them by how much attention they are owed, and dispatches them **all at once, in parallel background jobs**, delegating the full per-PR review (skip checks, author flags, diff review, verdict, post) to `/sy-review-pr`. One worker per PR while job slots last; past that, PRs are **enrolled and queued by rank** and take the next slot a worker releases, so every resolved PR is reviewed in the same run. The run works a fixed time budget, polling each PR cheaply and reviewing it whenever its state moves. Repo-, language-, and framework-agnostic.

**Whose PRs, and what this does to them — the one distinction to get right.** This command reviews **teammates' and bots' PRs**: it reads a diff someone else wrote and leaves a verdict (APPROVE / COMMENT / REQUEST_CHANGES) plus line comments. It **never pushes code, never syncs a branch, never fixes CI, and never merges** — everything it produces is feedback for that PR's author to act on. The sibling `/sy-babysit-prs` is the opposite in every one of those respects: it works **your own** PRs and changes them. If the ask is "get my PRs green / merged / caught up with main", that is `/sy-babysit-prs`, not this. Reviewing your own PR is a no-op worth refusing — you cannot approve it and there is nobody to hand the feedback to.

**Recommended order.** Run `/sy-review-prs` first (verdict pass — no code changes), then `/sy-babysit-prs` (apply fixes, drive CI green). Reversing wastes babysit cycles on PRs that would otherwise be requested-changes and rewritten. Both commands run the same budgeted polling cadence, so both are long-running fan-outs by design.

Argument: $ARGUMENTS (optional — scope filter; see "Resolving scope" below). Defaults to **all open PRs in the current repo authored by anyone EXCEPT me** when invoked from inside a git checkout — reviewing is something you do for other people, so your own PRs are excluded unless you ask for them by name (`me` / `mine` / `self`, or your handle). Outside a git checkout there is no repo to scope to, so the default falls back to `--author=@me`; say so, since that is the one default that hands you your own PRs.

## Execution mode

Background agents are default. Resolve, sort, announce, and assign the complete PR set first, then dispatch the existing slot jobs in parallel and return while they run. Explicit foreground signals are `foreground`, `fg`, `inline`, `blocking`, `synchronous`, `sync`, or `wait`; strip that token, keep the same reviewer-lens ranking and queue order, then execute enrolled PRs inline in that order without background agents. Never change scope, sorting, enrollment, worktree reuse, state checkpoints, or pass cadence based on mode.

## Steps

1. **Resolve scope.** Parse `$ARGUMENTS` and build the `gh search prs` call:
   - **Empty `$ARGUMENTS`** — if invoked from inside a git checkout, default to the current repo (resolve via `git remote get-url origin` → `<owner>/<repo>`) and **every author except you**: `gh search prs --repo <owner>/<repo> --state=open -- -author:@me`. Reviewing is work you do for other people, so your own PRs are out of scope unless asked for by name; say how many were excluded so the count is never silently short. If not inside a repo, there is no repo to scope to — fall back to `--author=@me` and **say that the default flipped to your own PRs**, since that is the one case where this command hands you your own work and `/sy-babysit-prs` is probably what was meant.
   - **`me` / `mine` / `self`** (case-insensitive) → `--author=@me`. Honor it — an explicit ask overrides the exclusion above — but note once that reviewing your own PRs produces no approval and no audience, and name `/sy-babysit-prs` as the command that acts on them.
   - **`<github-handle>`** (single bare token, no spaces) → `--author=<handle>`.
   - **`<full name>`** (multiple tokens, no slashes) → resolve via `gh api "search/users?q=<name>" --jq '.items[0].login'`, confirm with the user, then `--author=<resolved-handle>`.
   - **`<owner>/<repo>`** (single token containing `/`) → `--repo <owner>/<repo>`. Multiple `<owner>/<repo>` tokens (comma- or space-separated) → fan out one `gh search prs` call per repo and union the results.
   - **`org:<org-name>`** → `gh search prs --owner=<org-name> --state=open`.
   - **Combined** — repo / author tokens compose: e.g. `acme/api,acme/web alice` → search both repos for PRs by `alice`.
   - **Repo list** (e.g. workspace bundles like `myapp-frontend`, `myapp-backend` or `myapp-lib`) — same as multiple `<owner>/<repo>` tokens; resolve each to its `<owner>/<repo>` (the user may pass bare repo names, in which case ask for the owner once and reuse it across the list).

2. **Fetch PRs:**
   `gh search prs <scope-flags> --state=open --limit 1000 --json number,title,repository,isDraft,url,createdAt,updatedAt,author`

   Then, for stack detection and worktree paths, one follow-up per PR: `gh pr view <url> --json headRefName,baseRefName`. **`gh search prs` has no `headRefName` / `baseRefName` field** and **`gh pr view` has no `repository` field** — see the `gh` field traps in `/sy-list-prs` (Fetch PR data). Without an explicit `--limit`, search returns only 30 and the tail is silently missing, which would strand PRs before enrollment ever runs; if the count comes back exactly at the limit, report the set as possibly truncated.

3. **Announce:** Tell the user how many open PRs were found and list them (repo, PR number, title, author). When the set includes any author other than you (`gh api user --jq .login`), lead with a `Mixed authors: <handle> (N), …` line and keep the author on every row — reviewing your own PR and reviewing a teammate's are different acts, and the default scope here is "all authors in the current repo". Skip PRs already filtered out by `/sy-review-pr`'s own skip rules in the per-PR step — don't pre-filter here.

4. **Concurrent-migration cross-check — always, whatever the scope.** Run this BEFORE dispatching any review job — once the fan-out is in flight the jobs run concurrently and can't be handed shared context, and a per-PR job only ever sees its own branch. **There is no scope condition on this step:** same-repo PRs share one migration DAG, so a single-repo scope is the _most_ likely place two migrations collide, not the least.

- **Scan every open PR in each repo the scope touches — not just the PRs being reviewed.** `gh pr list --repo <owner/repo> --state open --json number,url,title,headRefName,author,autoMergeRequest --limit 100`, then `gh pr diff <n> --repo <owner/repo> --name-only` on each to spot migration files (detection paths: `/sy-sync-pr-branch` Step 7, as `/sy-review-pr`'s Migration checks defer to). A PR outside the review scope still collides with one inside it, and a PR with automerge already on can land mid-run with nobody watching.
- **Record each repo's current migration head at dispatch** and pass it to every affected job, so a job can tell "this branch was always stale" from "the head moved under it mid-run" without re-deriving it per pass.
- **Two or more open PRs adding a migration → note the conflict pairs upfront in the announcement, with each PR's automerge state,** and pass the pairing to each affected job so it can flag its author symmetrically (`/sy-review-pr` Check 2). Reviews never re-parent or reorder anything — this is coordination the authors act on.

4a. **Open the ping-pong pulse — emit the FIRST one before dispatching anything.** Render `/sy-list-prs pingpong <same-scope-token>` with every Agent cell at `⚪ NOT STARTED`. Reviews post no code, but they still run for the full budget, so the same rule holds: never let the user stare at a silent terminal wondering whether anything is running. Layout lives in `/sy-list-prs` — do not hand-roll it.

Start the **agent ledger** here: one row per resolved PR holding its **stable job key (`sy-review-pr:<owner>/<repo>#<number>`) and the handle of the live job that currently owns it** — the pair every later turn matches on before dispatching anything, so a re-invocation, a requeue, or a recovery adopts the running job instead of putting a second reviewer onto the same PR — plus its ledger state (`active` / `queued` / `watching` / `terminal`), pass count, **slot number when active and queue position when queued**, first dispatch time, last pass start / end, next pass ETA, **whether the PR has had a completed pass yet plus its `R0` / `R1` attention-key scores and `createdAt`** (what the reviewer lens's "new since the last round" key is read from — GitHub cannot answer "have I looked at this yet in this run"), **that PR's latest `## State` block verbatim** (round counter, what was already posted, current verdict, outstanding stop-and-ask — handed back by `/sy-review-pr` after every `pass=single` pass), and the **last rendered pulse snapshot** (Status color emoji, component lines, counters strip) that `/sy-list-prs pingpong` diffs to pick its change marker and `Δ` line — overwrite it after every pulse. The state block is the only copy of what a re-invoked per-PR job cannot remember: the next round's prompt is built from it, and a replacement job for a dead slot is seeded from it, so a ledger without it makes every pass a first pass and pass 2 restate pass 1. Record the ledger state and slot for every PR from enrollment onward (Step 4b), queued and watching ones included; the pulse groups its board by feature set and prints `🌊 slot <N>` on every active row. Record every timestamp the moment it happens (dispatch, pass start, pass end, next-pass ETA); the pulse's `started 17:12 · running 6m` clock is read from them and cannot be reconstructed later. Every PR is serviced for the whole run budget (`/sy-review-pr` Step 10, or the dispatcher's clock when it holds several), so Agent cells carry a `(pass N · <HH:MM> left)` counter — `🔄 IN PROGRESS`, `⏸️ WAITING`, `⏸️ WAITING_AFTER_SKIP`, `✅ COMPLETED`, `⏭️ SKIPPED`, `❌ FAILED`.

4b. **Enroll every PR, rank them, then fill the worker slots from the top of the queue — before anything launches.** The harness caps how many background jobs run **at once**; it does not cap how many PRs the run covers. Identical to `/sy-babysit-prs` Step 3b — same ranking, same four ledger states, same guarantee:

- **Resolve `S`, the concurrency cap.** It is a property of the harness, never of this command, so this command names no number. Resolve in this order: a `cap=<positive-int>` token in `$ARGUMENTS` or the user naming a cap in prose wins; otherwise the **harness concurrency cap** declared in your harness's own instructions, if it declares one; otherwise there is no cap and `S = N`, one job per PR. Reject anything that is not a positive integer — fall back to the next source down and say so, because `S = 0` leaves nothing able to run. **Strip the `cap=` token from `$ARGUMENTS` before any scope parsing**, and never forward it to `/sy-list-prs`; left in place, Step 1 reads a bare token as an author and would search for author `cap=4`. Say which value you used and where it came from.
- **If the launch is partially rejected, cancel and relaunch — never inject the rejects into a running slot.** Slot prompts are immutable and self-contained by design (Step 5), which is why a live slot cannot be handed extra PRs; the dead-slot rule forbids the same mutation for the same reason. When only `k` of `slot_count` jobs actually start:
  - **`k == 0` is a launch failure, not a cap discovery.** Report it and stop — `S = 0` would "recover" into launching nothing.
  - **Cancel the `k` that started and confirm each is terminated before relaunching**; two jobs reviewing one PR double-post.
  - **Seed the relaunched slots with each PR's `## State` block from the ledger**, so a review already posted by a cancelled job is not posted again.
  - Then set `S = k`, refill from the top of the ranked queue, and launch that set in one message. A cancelled first pass costs almost nothing. Report the discovered cap and the refill, since the new ledger supersedes the one already announced.
- **Rank all `N` resolved PRs by the work-owed ranking, read through the REVIEWER lens** — the canonical tier list lives in `/sy-list-prs` (`## Work-owed ranking`), which defines one table, two lenses over it, and the reviewer lens's attention keys and tiebreakers. Do not restate or re-derive any of it here; read it there. Use the **reviewer lens**, not the default author lens: the `R0` / `R1` attention keys sort ahead of the tiers, _awaiting first review_ is promoted to the top tier, and P1 `CHANGES_REQUESTED` drops to just above P6. Scoring `R1` needs one extra `gh pr view <url> --json body,comments,reviews,reviewRequests,latestReviews` per PR — fold it into the Step 2 follow-up call rather than making a second pass over the set. Say which lens you used, and name every PR that scored `R0` or `R1` **with the reason** (`R1: @-mentioned in review thread`), so a PR sitting above a red one reads as intentional. Ranking decides **order only** — it never removes a PR from the set, and it never substitutes for `/sy-review-pr`'s own skip rules.
- **Launch `min(N, S)` workers from the top of the ranked queue, all at once**, so the highest-ranked PRs each get their own worker immediately. When a worker returns, its PR moves to `watching` or back to `queued`, the slot frees, and the next PR by rank takes it.
- **Every PR is enrolled before the first job launches.** A resolved PR missing from the ledger is a bug in this step, not a backlog — go back and enroll it. `queued` is not stranded: it is next in line, and the ledger says so.
- **Report the ledger at dispatch** — every PR with its tier and starting state. This is the artifact that proves nothing was stranded.
- **Warn — do not refuse — when the queue is more than 3× the slot count.** Say so, name the number, and carry on; reviewing all of them slowly beats reviewing `S` of them and abandoning the rest.

5. **Fan out one background job per SLOT — all at once, in parallel.** Do NOT walk the list sequentially. If one job fails, the others keep going — record it and move on.

   **Dispatch mechanics — this is the step agents get wrong.** "In parallel" is a hard requirement, not a hint:
   - **Adopt before you dispatch — a slot is a long-lived job, not a per-round spawn.** Every slot job carries the stable key `sy-review-prs:slot<i>`, and every PR it holds carries `sy-review-pr:<owner>/<repo>#<number>` (see _A job is addressed by a stable key_). **Enumerate the jobs already running or idle before launching anything** and match on those keys: a slot whose key already has a live owner is **not** re-dispatched — a running owner is left alone, an idle one is handed its next round as a follow-up turn. Only a key with no live owner gets a new job. This is what makes re-invoking `/sy-review-prs` while a fan-out is still in flight safe: it re-attaches to the running slots rather than doubling every lane and posting every review twice. A PR found under two live jobs is resolved by keeping the older and cancelling the newer, reported explicitly.
   - **Emit every slot job in ONE assistant message with `slot_count` tool calls in that same message.** One sub-agent / Task / background-shell invocation per slot, all in a single block. A second message per slot is a sequential loop wearing a parallel costume — that is the failure mode this section exists to prevent.
   - **Never** `for pr in ...; do ...; done`, never "start job 1, wait, start job 2", never a staggered launch. Every slot starts at the same instant.
   - **One slot = one job = one lane. When `N ≤ S`, one slot holds exactly one PR** and this is the classic one-job-per-PR fan-out. A slot only holds several PRs because there were more PRs than slots — that is the carve-out to the "never a single job that iterates the PR list" rule, and it is the _only_ one: a slot iterates **its own assigned PRs**, never the whole list, and never a list it chose itself.
   - **Jobs share nothing** — no cwd, no state file, no conversation. A slot job must never read another slot's result or wait on it.
   - **Give every job an identifying label, and a PR-specialized worker when one exists.** Where the environment lets a dispatched job carry a short label, set it to `<PR number> - <head branch> - <author>` for the PR that job starts on. Where the environment offers a worker specialized for reviewing someone else's pull request, dispatch to that one rather than the generic default. Both are cosmetic-only: a run that can do neither is not degraded, and neither ever changes scope, ranking, assignment, or cadence. They exist because a board of identically-named workers is unreadable the moment a fan-out exceeds two slots — the operator cannot tell which lane stalled.
   - **Each slot job's prompt is self-contained.** Pass, explicitly: its **ordered list of assigned PRs** with each one's tier, and for every one of them the full PR URL, the resolved `<owner>/<repo>` (from `git remote get-url origin`, never the folder name), the PR number, and any migration-conflict pairing from Step 4. Sub-agents start with a fresh context — anything you don't pass, they don't have.
   - **Report the fan-out the moment it's launched** — the slot map from Step 4b — so the user can see the whole set covered, not a prefix of it.

   **What a worker does — one pass, then release the slot.** A worker is dispatched for a specific PR, runs exactly one pass, reports, and returns; it never sits on a slot waiting for a sleep to elapse, because that is the capacity another PR needs. **The dispatcher owns the cadence:**
   - **Invoke `/sy-review-pr <PR-URL> pass=single round=<n>` per pass**, adding `last=true` on the final one, **and paste that PR's `## State` block from the previous pass into the job's prompt under a `## Prior state` heading** (omit it on the first pass). `pass=single` makes the per-PR command run one pass and return instead of owning the clock itself; the prior-state block is what stops pass 2 from restating pass 1. Dropping either turns a long run into a series of disconnected first passes.
   - **Run every pass inside the slot job itself — never dispatch a sub-agent per pass.** `pass=single` forces `/sy-review-pr` inline (its Execution mode), and so does the fact that the slot job is already a dispatched job; either alone is sufficient. A slot that spawns a child agent per PR per round creates `PRs × rounds` agents — 30 for a 3-PR slot — each starting from an empty context, re-fetching the same diff and re-walking the same review threads it must de-duplicate against, and charging another job against the concurrency cap. **A worker is one pass, and the ledger is the long-lived thing.** The `## State` block a worker hands back is what seeds its next pass and any replacement, which is why it is never dropped.
   - **The dispatcher owns the clock — the run budget is `<SY_PR_RUN_BUDGET_SECONDS>` seconds** from launch, shared by the whole set. Within it, a PR gets a full pass when its fingerprint moves, when it has never had one, or on its keepalive (at least every `<SY_PR_KEEPALIVE_INTERVAL_SECONDS>` seconds), plus one final pass before the deadline. There is no per-PR pass quota.
   - **Re-rank the queue every pulse** — full reviewer lens, attention keys included — so a PR that just picked up new commits, a new thread, or a fresh `@`-mention of me jumps ahead of an idle one. `R0` stays live: a PR with no pass yet outranks one already passed on, newest `createdAt` first. **Ranking sets which queued PR takes the next free slot — never whether a PR is reviewed at all.** Age the queue so a permanently low-ranked PR is reviewed late, never never.
   - **A PR that reaches a terminal state leaves the rotation** (`MERGED` / `CLOSED`, or a stop-and-ask needing human judgment). Report it and stop scheduling it. A skipped pass is **not** terminal — draft, WIP, already-reviewed, and blocked-by-another-reviewer stay enrolled and are re-passed the moment their fingerprint moves.
   - **Never preempt a running pass.** New inbound work on an `active` PR marks it `dirty_after_pass` and re-queues it at the head the moment its worker returns.
   - **If a whole slot job dies, relaunch that slot — do not fold its PRs into a live one.** A dying slot frees exactly the capacity it was using, so a replacement fits without exceeding `S`, while pushing its PRs into a neighbour silently doubles that lane's round length and breaks the "a slot's assignment never changes mid-run" rule. **Confirm it is dead before replacing it** — a job that finished its turn is _idle_, not dead, and an idle slot is resumed with a follow-up turn carrying its next round, which keeps everything it has already read and posted (see _Resume an idle job; relaunch only a dead one_). Only a failed, cancelled, or gone job gets a replacement, launched with the dead slot's **remaining** PRs plus a checkpoint from the ledger — each PR's last `## State` block. **Resume per PR from its own `completed_round + 1`**, never from one run-wide round number: re-queue the PR its worker died on at the head with its last `## State` block, and leave every other PR's counter alone. No capacity to relaunch into (the run is being torn down) means reporting those PRs with their per-PR pass counts, never as reviewed.
   - **Report each PR's fingerprint and `externally_blocked` back with its `## State` block, every pass.** That is what lets the dispatcher move it to `watching` and stop paying a worker for it (Step 5b). A worker never decides to park itself — it reports state; the dispatcher schedules.

   The per-PR skill owns the full behavior:
   - Skip drafts / WIP / DO NOT MERGE / already-reviewed-no-new-commits / blocked-by-other-reviewer.
   - Load repo rules and culture context (`CLAUDE.md` / `AGENTS.md` / `CONTRIBUTING.md` / `.cursorrules`).
   - Pre-flight author flags (diff-vs-description mismatch, merge conflict with base, failing CI with run-URL pinpoint, migration coordination) as PR comments.
   - De-dup against existing review threads and their reactions (human + bot + own past comments) — 👍 what's already covered, reply in-thread with the delta when a comment misses a case, new top-level comment only for genuinely new findings.
   - Read the diff (or just the new commits for stale-approval re-reviews).
   - Pick verdict — APPROVE / COMMENT (default bias) / REQUEST_CHANGES (show-stoppers only). Cap at COMMENT when another reviewer's `REQUEST_CHANGES` is open or CI is failing.
   - Post the review — or post nothing at all when a re-review turns up nothing new.
   - Terminate that PR early only on `MERGED` / `CLOSED` or a stop-and-ask.

   **Expect long runtimes.** The run works its full `<SY_PR_RUN_BUDGET_SECONDS>`-second budget by design. That is the point — do not shorten it, do not collapse a PR to a single pass, and do not busy-poll the jobs. Collect each result when its job reports back.

   Review is read-only — it works off `gh pr diff` / `gh api` and needs no checkout, so parallel jobs never collide. **If a review genuinely needs the code on disk** (building the branch, running a tool over the tree, reproducing a failure), that job checks out into `$HOME/.worktrees/<owner>/<repo>/<sanitized-branch>` (see One rigid worktree path) with `WT="$(worktree_create "$BR")"`, which reuses a linked worktree already on that branch when one exists and creates it there otherwise. Never `git checkout` / `git switch` / `gh pr checkout` in the user's primary checkout (see Never do PR-branch work in the primary checkout). The worktree persists across the whole run; remove only worktrees the job created.

   Do NOT re-implement any of the per-PR logic here — if per-PR behavior needs to change, edit `/sy-review-pr`.

5a. **Ping-pong every 10 minutes until the run ends.** The fan-out works its full `<SY_PR_RUN_BUDGET_SECONDS>`-second budget by design, so the dispatcher's job while it waits is to keep a pulse on the wall — not to sit silent, and not to busy-poll the jobs. The Step 5b fingerprint probes ride on it, at the `<SY_PR_POLL_INTERVAL_SECONDS>`-second cadence.

- **Cadence: one pulse every 10 minutes**, from dispatch until the last verdict lands. A watched PR still shows a live heartbeat with its next-check ETA. Keep pulsing until the board is fully terminal or the budget expires.
- **Render with `/sy-list-prs pingpong <same-scope-token>`, passing the current agent ledger.** Same scope token as Step 4a so every pulse covers exactly the dispatched set.
- **Refresh the Status column from GitHub, not from the jobs.** Re-run the cheap `gh pr view` status calls `/sy-list-prs` already uses. **Never message or interrupt a running job to ask its progress** — that wakes a running pass and corrupts its cadence. Read job state only from verdicts already reported. A queued PR with no pass yet stays `⚪ NOT STARTED — queued, position <p> of <n>`, and keeps its feature-set grouping so it still reads inside its set rather than in a queue bucket.
- **Update the ledger from reports as they land** — a worker finishing pass N on a PR moves that row to `👁️ WATCHING` or back to `⏸️ WAITING` with its next-check ETA, or to `⏸️ WAITING_AFTER_SKIP` when that pass was skipped but the PR stays enrolled; a final report moves it to `✅ COMPLETED` / `⏭️ SKIPPED` / `❌ FAILED`. Between reports, derive `IN PROGRESS` vs `WAITING` and the next-check ETA from the poll cadence rather than leaving the cell blank.
- **A pulse is display-only.** It never dispatches, retries, posts a review, changes a verdict, or re-orders the queue on its own. A pulse that notices a **dead** slot reports it and nothing more — the relaunch is Step 5's job, taken outside the pulse, and it relaunches the dead slot rather than moving its PRs anywhere.
- Stop pulsing when every row is terminal (`✅ COMPLETED` / `⏭️ SKIPPED` / `❌ FAILED`), then go to Step 6. **`⏸️ WAITING_AFTER_SKIP` is not terminal** — that PR still has passes scheduled, so the pulse keeps running. **`👁️ WATCHING` is not terminal either** (Step 5b).

5b. **Watching — a PR with nothing left to review is polled by the dispatcher and holds no worker.** A review fan-out otherwise spends its back half paying a full agent per PR to re-read an unchanged diff and reach Step 9's stop-early gate again. Watching replaces those agents with two read-only `gh` calls per PR, folded into the pulse's existing fetch, and requeues the PR the moment its state moves. **Identical to `/sy-babysit-prs` Step 4b — same move-to-watching rule, same stand-down-with-state-capture, same requeue-on-change, same keepalive, same reporting. Read it there; do not restate or re-derive it here.** The fingerprint itself is defined once in `/sy-babysit-pr` Step 12a. Two review-specific notes:

- **A PR moves to `watching` when its `## State` block comes back `externally_blocked`** — `/sy-review-pr` Step 10a's set (stop-early no-op, draft / WIP skip, no new commits, blocked by another reviewer), decided by the per-PR job and never second-guessed here. Watching is per PR, so one blocked PR frees its slot immediately.
- **`headRefOid` is what requeues a watched review most often.** A push is the one event that makes a diff worth re-reading, so a watched PR is picked back up on a new commit exactly as fast as a live worker would have noticed it — the difference is that the rounds in between cost two `gh` calls instead of an agent.

5c. **The run ends when the rounds run out — never when the work does.** A review fan-out is sleep-dominated by design, so "nothing changed" is the normal shape of most rounds and is never a stopping condition.

- **Every wait is a real blocking `sleep` command.** The fingerprint poll is `sleep <SY_PR_POLL_INTERVAL_SECONDS>`; the dispatcher's pulse gap is `sleep 600`. One foreground, self-terminating command per wait — never a note in the report claiming time passed, never a shortened sleep, never a busy-poll. A harness timeout below the target re-issues `sleep` for the remainder until the full interval has actually elapsed.
- **A dispatcher with no detached-job facility runs the loop inline — it does not cancel it.** "Background jobs do not outlive the turn", "no wall clock has elapsed", "two probes were byte-identical", "the set is quiescent, re-invoke me later" are not terminal states; they describe a run that should be polling. Fall back to running the loop in the foreground with real sleeps, keeping the same ranking, enrollment, cadence, and ledger. Ending early with budget still left is the failure this command exists to prevent.
- **Stop the run on the deadline, on a fully terminal ledger, or on an unreachable service.** The budget is `<SY_PR_RUN_BUDGET_SECONDS>` seconds, after which every non-terminal PR gets one final full pass. GitHub or the model service staying unreachable for `<SY_PR_RETRY_MAX_FAILURES>` consecutive attempts `<SY_PR_RETRY_INTERVAL_SECONDS>` seconds apart also ends the run — report `"GitHub or model service unreachable — stopping with resumable state"`, never a local network cause you cannot verify. On every stop, write the ledger and each PR's `## State` block to the durable journals so a fresh invocation resumes instead of restarting.
- **Re-resolve the PR set at every pulse, with the same scope token.** The set is not frozen at dispatch: PRs open, merge, close, get marked ready, and pick up new commits mid-run. A newly opened in-scope PR is enrolled and ranked into the queue on the pulse that finds it; a `MERGED` / `CLOSED` one drops out. That is the whole reason an unchanged round is still worth running.
- **A worker's stop-and-ask is surfaced to the operator, and revalidated before it is repeated.** A PR handed back with `needs_user` in its `## State` block leaves the rotation for this run, and the operator is the one who has to see it — a sub-agent's report scrolls past. Carry the block into the ledger verbatim, mark that row `NEEDS_USER`, and repeat it in every pulse and in the final report: the reason, the exact message, and its `Next:` line. Never open a prompt, never block waiting on an answer, and never express it on GitHub. Other PRs keep running; when every enrolled PR is terminal or `NEEDS_USER`, print all the outstanding questions together and stop. A claim read out of a journal at startup is revalidated first — dispatch that PR's next pass with the block pasted in and render `/sy-review-pr` Step 2a's verdict, never the stale claim on its own.
- **Never close a turn by asking what to do next.** No "want me to continue?", no "re-invoke when time has passed", no handing the ledger back for the user to drive. The only terminal exits are: every PR terminal (`MERGED` / `CLOSED` / passes exhausted), or a stop-and-ask that names one of `/sy-review-pr` Step 10's three enumerated cases.

6. **Final report:** emit the **closing ping-pong** — one last `/sy-list-prs pingpong <same-scope-token>` with the final ledger and `Next ping-pong: — (final)` — then summarize per PR: author (when the set is mixed), final ledger state, passes run, verdict (APPROVE / COMMENT / REQUEST_CHANGES / SKIPPED + reason), author flags posted, **every PR that spent time watching** (`github.com/acme/api/pull/51 watched 2h40m — nothing new; 32 probes, 0 worker dispatches`), and any cross-PR migration coordination notes. **State explicitly that every resolved PR was reviewed** — count the rows and compare against the Step 3 announced count; a mismatch is the failure this command's enrollment rule exists to prevent, so name any PR that got zero passes and why. A watched PR is a serviced PR: report it as one, never as skipped or missing. The run therefore always brackets itself: pulse at the start (Step 4a), pulse every 10 min (Step 5a), pulse at the end.

## Rules

- **This command is a dispatcher. The per-PR logic lives in `/sy-review-pr` — do not re-implement it here.**
- **A live job is adopted and resumed, never doubled (Step 5).** Every slot and every PR carries a stable job key; enumerate live jobs and match on it before dispatching anything, so re-invoking this command mid-fan-out re-attaches to the running slots instead of doubling every lane — and two jobs reviewing one PR post the same review twice, which is the one failure this workflow cannot take back. A job that finished its turn is **idle, not dead**: resume it with a follow-up turn, replace it only when it is failed, cancelled, or gone. And a pass runs **inside** the job that owns it — `pass=single` and "already inside a dispatched job" each force `/sy-review-pr` inline, because a job that spawns a child agent per pass multiplies agents, every one of them re-fetching the diff and re-walking the threads the live job has already read. The canonical rules are _A job is addressed by a stable key_, _Resume an idle job; relaunch only a dead one_, and _A pass that runs inside a job runs in that job_.
- **Every job writes to GitHub — this bulk dispatcher has no report-only mode** (see `/sy-review-pr` Output surface). Verdicts, author flags, line comments, threaded replies, and 👍 reactions land on the PRs themselves; the Step 6 summary reports what was posted, it does not replace posting. Never stop to ask the user whether to post or report, and never route findings to a `/sy-critique-*` command — no such command exists. `/sy-review-pr`'s `dry-run` opt-out is a single-PR, foreground, human-in-the-loop review and is **never dispatched from this fan-out** — a batch runs unattended in the background, where there is no user to confirm each proposal.
- **The cross-PR migration check runs on every invocation, at any scope, over every open PR in the repos involved (Step 4).** It is not a multi-repo-only step and it is not limited to the PRs under review: same-repo PRs share one migration DAG, so a single-repo scope is where collisions are most likely, and a PR nobody asked you to review still breaks the default branch when it lands second. The dispatcher is the only thing that can see the whole set — once jobs are in flight they cannot be handed shared context. It coordinates and flags only; re-parenting belongs to the author, via `/sy-babysit-pr`.
- **Parallel means one message, `min(N, S)` tool calls (Step 5 Dispatch mechanics).** The job count is the free-slot count, never the PR count: launching one job per PR past the cap is what gets the launch rejected and strands the tail. If the transcript shows slot jobs starting one message at a time, the fan-out was sequential and must be relaunched.
- **Every resolved PR is enrolled before anything launches — never dropped (Step 4b).** One worker per PR while slots last; past the concurrency cap the surplus is `queued` by rank and takes the next slot a worker releases. A slot is held only by a pass actually running, so a `watching` or `queued` PR costs nothing. A PR that ends the run with zero passes is a bug in this command, not an acceptable outcome.
- **Order comes from the work-owed ranking, defined once in `/sy-list-prs`.** Do not restate the tiers, the reviewer lens's `R0` / `R1` attention keys, or its tiebreakers here, do not invent a second ranking, and never use any of it to skip a PR — it sets service order only, and it never substitutes for `/sy-review-pr`'s own skip rules.
- **Draft / `WIP` / `DO NOT MERGE` / `DNM` PRs rank dead last and no attention key lifts them (P6).** Newest arrival or a direct `@`-mention does not promote one — an author marking a PR not-ready outranks both. They are still dispatched and still get their passes, but every pass is a documented skip that **posts nothing to GitHub**, so "ignored" is true of the output while later rounds still catch a PR marked ready mid-run. Verify both halves in the Step 6 report: each such PR ends terminal as `⏭️ SKIPPED` with its marker as the reason (mid-run it is `⏸️ WAITING_AFTER_SKIP`, since the marker can drop between rounds), and zero posted artifacts.
- **A worker runs one pass and releases its slot (Step 5).** Every pass goes through `/sy-review-pr <url> pass=single` with the prior state block pasted in. A worker that sleeps out a cadence while holding a slot is the starvation this design removes, just hidden inside a job.
- **Review all resolved PRs in parallel background jobs — never a sequential for-loop** (see Fan out multi-PR work in parallel). Collect verdicts as jobs finish and report once at the end.
- **Any job that needs the code on disk uses a worktree at the canonical path** — `$HOME/.worktrees/<owner>/<repo>/<sanitized-branch>`, always via `worktree_create` (see One rigid worktree path) — never the user's primary checkout (see Never do PR-branch work in the primary checkout). Reviews are normally checkout-free; treat a checkout as the exception, not the default.
- **Show the author on every row when the set is mixed** (see Show PR authors). This command defaults to ALL authors in the current repo, so mixed sets are the norm, not the exception — the final report (Step 6) carries the author alongside each verdict too.
- **Honor `/sy-review-pr`'s skip rules** — never pre-filter drafts / WIP / already-reviewed PRs in this wrapper. Let the per-PR skill decide and report the skip reason so the audit trail is complete. A per-pass skip is not terminal there — a job that skips pass 1 on a draft still runs passes 2 and 3, so that row is `⏸️ WAITING_AFTER_SKIP`, not `⏭️ SKIPPED`; only an exhausted pass budget (or `MERGED` / `CLOSED`) settles it to terminal. **The announced count is the dispatched count**: 10 in-scope PRs of which 5 are drafts is 10 jobs, not 5. A draft that gets marked ready between passes is exactly what the later passes exist to catch.
- **Every PR is serviced for the whole run budget** (`/sy-review-pr` Step 10, or the dispatcher's clock when it holds several). Never treat the first verdict as a PR's final report, and never cancel a job because the board went quiet — between passes the run is polling by design. `pass=single` is the one sanctioned way to run a lone pass, and only from a driver that is itself honoring the budget (Step 5).
- **Default bias inherits from `/sy-review-pr`**: APPROVE or COMMENT — REQUEST_CHANGES is reserved for show-stoppers only.
- **Silent jobs are a success, not a failure.** A job that posts nothing because the re-review turned up nothing new reports `NO-OP` in the final summary. Don't retry it and don't nudge it into commenting to prove it ran.
- **A PR with nothing left to review is watched by the dispatcher and holds no worker (Step 5b).** Repeated no-op passes are the expected shape of a long review run, and paying a full agent to reproduce one is the waste this removes: watching costs two read-only `gh` calls per probe, folded into the pulse's existing fetch, and the PR is requeued the instant its fingerprint moves — a new commit above all — plus a keepalive pass at least every `<SY_PR_KEEPALIVE_INTERVAL_SECONDS>` seconds and one before the deadline. Never move a PR to watching mid-pass, and never report a watched PR as a missing one.
- **Ping-pong is mandatory, not optional (Steps 4a / 5a / 6).** Every run pulses before dispatch, every 10 minutes while jobs run, and once at the end. The pulse is read-only — it refreshes PR status from `gh` and reads already-reported verdicts; it never messages or interrupts a running job, and it never acts on what it finds.
- **Ping-pong layout is owned by `/sy-list-prs pingpong`.** This command owns the agent ledger (ledger state, pass count, dispatch / pass times, next-check ETA, slot or queue position, last rendered pulse snapshot) and passes it in; `/sy-list-prs` owns the three columns, the icons, the change marker, the feature-set grouping, and the sort. Agent cells here carry the `(pass N · <HH:MM> left)` counter — same form as `/sy-babysit-prs`.
- **Multi-repo workspaces** (e.g. a bundle like `myapp-frontend`, `myapp-backend` or `myapp-lib`): pass each repo as a `<owner>/<repo>` token. The cross-PR migration check (Step 4) runs across the full union **before** any job is dispatched, so coordination flags surface before any verdict is posted.
- **Always resolve `<owner>/<repo>` via `git remote get-url origin`, never from the folder name (see Repo Identification).**
- **An idle set is a reason to sleep, not to stop (Step 5c).** Every wait is a real `sleep` command, the PR set is re-resolved every round, and the run never ends with a question to the user. A run that stops with rounds still owed is reported as a failed run.

[Sy] Review OTHER PEOPLE'S open pull requests — you act as the **reviewer**, not the author. Runs `/sy-review-pr` on every open PR in scope: finds matching PRs, ranks them by how much attention they are owed, and dispatches them **all at once, in parallel background jobs**, delegating the full per-PR review (skip checks, author flags, diff review, verdict, post) to `/sy-review-pr`. One job per PR while job slots last; past that, PRs are **assigned** to the running slots rather than queued behind them, so every resolved PR is reviewed in the same run. Every PR gets **at least 10 passes, 25 minutes apart**. Repo-, language-, and framework-agnostic.

**Whose PRs, and what this does to them — the one distinction to get right.** This command reviews **teammates' and bots' PRs**: it reads a diff someone else wrote and leaves a verdict (APPROVE / COMMENT / REQUEST_CHANGES) plus line comments. It **never pushes code, never syncs a branch, never fixes CI, and never merges** — everything it produces is feedback for that PR's author to act on. The sibling `/sy-babysit-prs` is the opposite in every one of those respects: it works **your own** PRs and changes them. If the ask is "get my PRs green / merged / caught up with main", that is `/sy-babysit-prs`, not this. Reviewing your own PR is a no-op worth refusing — you cannot approve it and there is nobody to hand the feedback to.

**Recommended order.** Run `/sy-review-prs` first (verdict pass — no code changes), then `/sy-babysit-prs` (apply fixes, drive CI green). Reversing wastes babysit cycles on PRs that would otherwise be requested-changes and rewritten. Both commands run the same 10-pass / 25-minute cadence, so both are four-hours-plus fan-outs by design.

Argument: $ARGUMENTS (optional — scope filter; see "Resolving scope" below). Defaults to **all open PRs in the current repo authored by anyone EXCEPT me** when invoked from inside a git checkout — reviewing is something you do for other people, so your own PRs are excluded unless you ask for them by name (`me` / `mine` / `self`, or your handle). Outside a git checkout there is no repo to scope to, so the default falls back to `--author=@me`; say so, since that is the one default that hands you your own PRs.

## Execution mode

Background agents are default. Resolve, sort, announce, and assign the complete PR set first, then dispatch the existing slot jobs in parallel and return while they run. Explicit foreground signals are `foreground`, `fg`, `inline`, `blocking`, `synchronous`, `sync`, or `wait`; strip that token, keep the same reviewer-lens ranking and round-robin slot assignment, then execute assigned PRs inline in slot order without background agents. Never change scope, sorting, assignment, worktree reuse, state checkpoints, or pass cadence based on mode.

## Steps

1. **Resolve scope.** Parse `$ARGUMENTS` and build the `gh search prs` call:
   - **Empty `$ARGUMENTS`** — if invoked from inside a git checkout, default to the current repo (resolve via `git remote get-url origin` → `<owner>/<repo>`) and **every author except you**: `gh search prs --repo <owner>/<repo> --state=open -- -author:@me`. Reviewing is work you do for other people, so your own PRs are out of scope unless asked for by name; say how many were excluded so the count is never silently short. If not inside a repo, there is no repo to scope to — fall back to `--author=@me` and **say that the default flipped to your own PRs**, since that is the one case where this command hands you your own work and `/sy-babysit-prs` is probably what was meant.
   - **`me` / `mine` / `self`** (case-insensitive) → `--author=@me`. Honor it — an explicit ask overrides the exclusion above — but note once that reviewing your own PRs produces no approval and no audience, and name `/sy-babysit-prs` as the command that acts on them.
   - **`<github-handle>`** (single bare token, no spaces) → `--author=<handle>`.
   - **`<full name>`** (multiple tokens, no slashes) → resolve via `gh api "search/users?q=<name>" --jq '.items[0].login'`, confirm with the user, then `--author=<resolved-handle>`.
   - **`<owner>/<repo>`** (single token containing `/`) → `--repo <owner>/<repo>`. Multiple `<owner>/<repo>` tokens (comma- or space-separated) → fan out one `gh search prs` call per repo and union the results.
   - **`org:<org-name>`** → `gh search prs --owner=<org-name> --state=open`.
   - **Combined** — repo / author tokens compose: e.g. `acme/api,acme/web alice` → search both repos for PRs by `alice`.
   - **Repo list** (e.g. workspace bundles like `myapp-frontend`, `myapp-backend` or `myapp-lib`) — same as multiple `<owner>/<repo>` tokens; resolve each to its `<owner>/<repo>` (the user may pass bare repo names, in which case ask for the owner once and reuse it across the list).

2. **Fetch PRs:**
   `gh search prs <scope-flags> --state=open --limit 1000 --json number,title,repository,isDraft,url,createdAt,updatedAt,author`

   Then, for stack detection and worktree paths, one follow-up per PR: `gh pr view <url> --json headRefName,baseRefName`. **`gh search prs` has no `headRefName` / `baseRefName` field** and **`gh pr view` has no `repository` field** — see the `gh` field traps in `/sy-list-prs` (Fetch PR data). Without an explicit `--limit`, search returns only 30 and the tail is silently missing, which would strand PRs before slot assignment ever runs; if the count comes back exactly at the limit, report the set as possibly truncated.

3. **Announce:** Tell the user how many open PRs were found and list them (repo, PR number, title, author). When the set includes any author other than you (`gh api user --jq .login`), lead with a `Mixed authors: <handle> (N), …` line and keep the author on every row — reviewing your own PR and reviewing a teammate's are different acts, and the default scope here is "all authors in the current repo". Skip PRs already filtered out by `/sy-review-pr`'s own skip rules in the per-PR step — don't pre-filter here.

4. **Concurrent-migration cross-check — always, whatever the scope.** Run this BEFORE dispatching any review job — once the fan-out is in flight the jobs run concurrently and can't be handed shared context, and a per-PR job only ever sees its own branch. **There is no scope condition on this step:** same-repo PRs share one migration DAG, so a single-repo scope is the _most_ likely place two migrations collide, not the least.

- **Scan every open PR in each repo the scope touches — not just the PRs being reviewed.** `gh pr list --repo <owner/repo> --state open --json number,url,title,headRefName,author,autoMergeRequest --limit 100`, then `gh pr diff <n> --repo <owner/repo> --name-only` on each to spot migration files (detection paths: `/sy-sync-pr-branch` Step 7, as `/sy-review-pr`'s Migration checks defer to). A PR outside the review scope still collides with one inside it, and a PR with automerge already on can land mid-run with nobody watching.
- **Record each repo's current migration head at dispatch** and pass it to every affected job, so a job can tell "this branch was always stale" from "the head moved under it mid-run" without re-deriving it per pass.
- **Two or more open PRs adding a migration → note the conflict pairs upfront in the announcement, with each PR's automerge state,** and pass the pairing to each affected job so it can flag its author symmetrically (`/sy-review-pr` Check 2). Reviews never re-parent or reorder anything — this is coordination the authors act on.

4a. **Open the ping-pong pulse — emit the FIRST one before dispatching anything.** Render `/sy-list-prs pingpong <same-scope-token>` with every Agent cell at `⚪ NOT STARTED`. Reviews post no code, but they still run 10 passes 25 minutes apart, so the same rule holds: never let the user stare at a silent terminal wondering whether anything is running. Layout lives in `/sy-list-prs` — do not hand-roll it.

Start the **agent ledger** here: one row per resolved PR holding job state, loop number, **slot number and position within that slot**, first dispatch time, last pass start / end, next pass ETA, **whether the PR has had a completed pass yet plus its `R0` / `R1` attention-key scores and `createdAt`** (what the reviewer lens's "new since the last round" key is read from — GitHub cannot answer "have I looked at this yet in this run"), **that PR's latest `## State` block verbatim** (round counter, what was already posted, current verdict, outstanding stop-and-ask — handed back by `/sy-review-pr` after every `pass=single` pass), and the **last rendered pulse snapshot** (Status color emoji, component lines, counters strip) that `/sy-list-prs pingpong` diffs to pick its change marker and `Δ` line — overwrite it after every pulse. The state block is the only copy of what a re-invoked per-PR job cannot remember: the next round's prompt is built from it, and a replacement job for a dead slot is seeded from it, so a ledger without it makes every round a first round and pass 2 restate pass 1. Record the slot number and position for every PR at assignment (Step 4b), position-2+ ones included; the pulse groups its board by feature set and prints `🌊 slot <N>` on every row. Record every timestamp the moment it happens (dispatch, pass start, pass end, next-pass ETA); the pulse's `started 17:12 · running 6m` clock is read from them and cannot be reconstructed later. Every PR gets ≥10 passes (`/sy-review-pr` Step 10, or the slot's own rounds when it holds several), so Agent cells carry the `(loop N/10)` counter — `🔄 IN PROGRESS`, `⏸️ WAITING`, `⏸️ WAITING_AFTER_SKIP`, `✅ COMPLETED`, `⏭️ SKIPPED`, `❌ FAILED`.

4b. **Rank every PR, then assign every PR to a slot — before anything launches.** The harness caps how many background jobs can run at once. With more PRs than slots, the naive fan-out reviews the first `S` and silently strands the rest; this step is what makes "EVERY open PR in scope" true rather than aspirational. Identical to `/sy-babysit-prs` Step 3b — same ranking, same dealing, same guarantee:

- **Resolve `S`, the concurrency cap.** It is a property of the harness, never of this command, so this command names no number. Resolve in this order: a `cap=<positive-int>` token in `$ARGUMENTS` or the user naming a cap in prose wins; otherwise the **harness concurrency cap** declared in your harness's own instructions, if it declares one; otherwise there is no cap and `S = N`, one job per PR. Reject anything that is not a positive integer — fall back to the next source down and say so, because `S = 0` makes `i mod slot_count` a division by zero. **Strip the `cap=` token from `$ARGUMENTS` before any scope parsing**, and never forward it to `/sy-list-prs`; left in place, Step 1 reads a bare token as an author and would search for author `cap=4`. Say which value you used and where it came from.
- **If the launch is partially rejected, cancel and relaunch — never inject the rejects into a running slot.** Slot prompts are immutable and self-contained by design (Step 5), which is why a live slot cannot be handed extra PRs; the dead-slot rule forbids the same mutation for the same reason. When only `k` of `slot_count` jobs actually start:
  - **`k == 0` is a launch failure, not a cap discovery.** Report it and stop — `S = 0` makes `i mod slot_count` a division by zero and would "recover" into launching nothing.
  - **Cancel the `k` that started and confirm each is terminated before relaunching**; two jobs reviewing one PR double-post.
  - **Seed the relaunched slots with each PR's `## State` block from the ledger**, so a review already posted by a cancelled job is not posted again.
  - Then set `S = k`, re-deal the **entire** ranked list round-robin into `k` slots, and launch that set in one message. These jobs are sleep-dominated, so cancelling a partial first pass costs almost nothing. Report the discovered cap and the re-deal, since the new slot map supersedes the one already announced.
- **Rank all `N` resolved PRs by the work-owed ranking, read through the REVIEWER lens** — the canonical tier list lives in `/sy-list-prs` (`## Work-owed ranking`), which defines one table, two lenses over it, and the reviewer lens's attention keys and tiebreakers. Do not restate or re-derive any of it here; read it there. Use the **reviewer lens**, not the default author lens: the `R0` / `R1` attention keys sort ahead of the tiers, _awaiting first review_ is promoted to the top tier, and P1 `CHANGES_REQUESTED` drops to just above P6. Scoring `R1` needs one extra `gh pr view <url> --json body,comments,reviews,reviewRequests,latestReviews` per PR — fold it into the Step 2 follow-up call rather than making a second pass over the set. Say which lens you used, and name every PR that scored `R0` or `R1` **with the reason** (`R1: @-mentioned in review thread`), so a PR sitting above a red one reads as intentional. Ranking decides **order only** — it never removes a PR from the set, and it never substitutes for `/sy-review-pr`'s own skip rules.
- **Open `slot_count = min(N, S)` slots and deal the ranked list round-robin**, not in chunks: ranked PR `i` (0-based) goes to slot `i mod slot_count`. Dealing puts the top `slot_count` PRs each at the **head of their own slot**, so every one of them is reviewed in round 1; chunking would pile the most urgent PRs into one lane behind each other.
- **Every PR has a slot before the first job launches.** There is no queue and no "wave 2". A resolved PR with no slot assignment is a bug in this step, not a backlog — go back and assign it.
- **Report the slot map at dispatch** — one line per slot listing its PRs in service order with each one's tier. This is the artifact that proves nothing was stranded.
- **Warn — do not refuse — when a slot holds more than 3 PRs.** Say so, name the number, and carry on; reviewing all of them slowly beats reviewing `S` of them and abandoning the rest.

5. **Fan out one background job per SLOT — all at once, in parallel.** Do NOT walk the list sequentially. If one job fails, the others keep going — record it and move on.

   **Dispatch mechanics — this is the step agents get wrong.** "In parallel" is a hard requirement, not a hint:
   - **Emit every slot job in ONE assistant message with `slot_count` tool calls in that same message.** One sub-agent / Task / background-shell invocation per slot, all in a single block. A second message per slot is a sequential loop wearing a parallel costume — that is the failure mode this section exists to prevent.
   - **Never** `for pr in ...; do ...; done`, never "start job 1, wait, start job 2", never a staggered launch. Every slot starts at the same instant.
   - **One slot = one job = one lane. When `N ≤ S`, one slot holds exactly one PR** and this is the classic one-job-per-PR fan-out. A slot only holds several PRs because there were more PRs than slots — that is the carve-out to the "never a single job that iterates the PR list" rule, and it is the _only_ one: a slot iterates **its own assigned PRs**, never the whole list, and never a list it chose itself.
   - **Jobs share nothing** — no cwd, no state file, no conversation. A slot job must never read another slot's result or wait on it.
   - **Each slot job's prompt is self-contained.** Pass, explicitly: its **ordered list of assigned PRs** with each one's tier, and for every one of them the full PR URL, the resolved `<owner>/<repo>` (from `git remote get-url origin`, never the folder name), the PR number, and any migration-conflict pairing from Step 4. Sub-agents start with a fresh context — anything you don't pass, they don't have.
   - **Report the fan-out the moment it's launched** — the slot map from Step 4b — so the user can see the whole set covered, not a prefix of it.

   **What a slot job does — interleave rounds, never review one PR to completion first.** A slot that ran the full `/sy-review-pr` loop for PR A (≥10 passes, ~4h) before touching PR B has moved the starvation somewhere less visible. **The slot owns the cadence:**
   - **One round = one pass on each PR the slot holds, in its assigned order, then ONE shared 25-minute sleep.** Invoke `/sy-review-pr <PR-URL> pass=single round=<n>/<total>` per PR, **and paste that PR's `## State` block from the previous round into the job's prompt under a `## Prior state` heading** (omit it on round 1). `pass=single` makes the per-PR command run one pass and return instead of sleeping and looping itself; the prior-state block is what stops pass 2 from restating pass 1. Dropping either turns a 10-round slot into ten disconnected first passes.
   - **Run at least 10 rounds**, so every PR in the slot still gets its ≥10 passes, 25 minutes apart — the floor from `/sy-review-pr` Step 10, honored by the slot instead of by the per-PR job. A slot holding one PR is behaviorally identical to plain `/sy-review-pr`.
   - **Re-rank the slot's own PRs at the top of every round** — full reviewer lens, attention keys included — so a PR that just picked up new commits, a new thread, or a fresh `@`-mention of me moves ahead of an idle one. From round 2 on, `R0` is live: a PR the slot has not yet passed on outranks one it has, newest `createdAt` first. **Re-ranking sets the order within the round — never whether a PR gets a pass in that round.** Every PR the slot still holds gets exactly one pass per round regardless of its tier, so a PR that ranks last forever is reviewed last forever, not skipped. Re-rank within the slot only — never steal a PR from another slot mid-run.
   - **A PR that reaches a terminal state drops out of the slot's rotation** (`MERGED` / `CLOSED`, or a stop-and-ask needing human judgment). Report it and stop passing it. A skipped pass is **not** terminal — draft, WIP, already-reviewed, and blocked-by-another-reviewer all get called again next round, because any of them can flip in 25 minutes.
   - **If a whole slot job dies, relaunch that slot — do not fold its PRs into a live one.** A dying slot frees exactly the capacity it was using, so a replacement fits without exceeding `S`, while pushing its PRs into a neighbour silently doubles that lane's round length and breaks the "a slot's assignment never changes mid-run" rule. Launch the replacement with the dead slot's **remaining** PRs plus a checkpoint from the ledger — each PR's last `## State` block. **Resume per PR from its own `completed_round + 1`**, never from one slot-wide round number: a slot dies mid-rotation, so a slot-wide restart either re-reviews a PR minutes after its last pass (breaking the 25-minute spacing) or skips the round another PR never got. The replacement services only the PRs still owing the interrupted round, sleeps once, then resumes the full rotation — the slot re-unifies once every PR is level. No capacity to relaunch into (the run is being torn down) means reporting those PRs with their per-PR round counts, never as reviewed.
   - The 25-minute sleep is per round, not per PR — that is what makes packing a slot nearly free. These jobs are sleep-dominated: a pass bursts a handful of `gh` calls and then waits, so three PRs in one lane cost three passes of work and **one** sleep.
   - **Report each PR's `watch` field back with its `## State` block, every round.** When every PR in the slot comes back `watch: armed`, the dispatcher parks the whole slot and watches it for two `gh` calls per PR instead of dispatching this job at all (Step 5b). The slot job never decides to park itself and never skips a round to save cost — it reports state; the dispatcher acts on it.

   The per-PR skill owns the full behavior:
   - Skip drafts / WIP / DO NOT MERGE / already-reviewed-no-new-commits / blocked-by-other-reviewer.
   - Load repo rules and culture context (`CLAUDE.md` / `AGENTS.md` / `CONTRIBUTING.md` / `.cursorrules`).
   - Pre-flight author flags (diff-vs-description mismatch, merge conflict with base, failing CI with run-URL pinpoint, migration coordination) as PR comments.
   - De-dup against existing review threads and their reactions (human + bot + own past comments) — 👍 what's already covered, reply in-thread with the delta when a comment misses a case, new top-level comment only for genuinely new findings.
   - Read the diff (or just the new commits for stale-approval re-reviews).
   - Pick verdict — APPROVE / COMMENT (default bias) / REQUEST_CHANGES (show-stoppers only). Cap at COMMENT when another reviewer's `REQUEST_CHANGES` is open or CI is failing.
   - Post the review — or post nothing at all when a re-review turns up nothing new.
   - Terminate that PR early only on `MERGED` / `CLOSED` or a stop-and-ask.

   **Expect long runtimes.** Every PR gets at least 10 passes 25 minutes apart, so a run takes 4h+ by design, longer as slots fill. That is the point — do not shorten it, do not collapse a PR to a single round, and do not poll the jobs in a busy loop. Collect each result when its job reports back.

   Review is read-only — it works off `gh pr diff` / `gh api` and needs no checkout, so parallel jobs never collide. **If a review genuinely needs the code on disk** (building the branch, running a tool over the tree, reproducing a failure), that job checks out into `$HOME/.worktrees/<owner>/<repo>/<sanitized-branch>` (see One rigid worktree path) with `WT="$(worktree_create "$BR")"`, which reuses a linked worktree already on that branch when one exists and creates it there otherwise. Never `git checkout` / `git switch` / `gh pr checkout` in the user's primary checkout (see Never do PR-branch work in the primary checkout). The worktree persists across all 10 rounds; remove only worktrees the job created.

   Do NOT re-implement any of the per-PR logic here — if per-PR behavior needs to change, edit `/sy-review-pr`.

5a. **Ping-pong every 10 minutes until every job reports.** The fan-out runs four-hours-plus by design (≥10 passes, 25 min apart), so the dispatcher's job while it waits is to keep a pulse on the wall — not to sit silent, and not to busy-poll the jobs.

- **Cadence: one pulse every 10 minutes**, from dispatch until the last verdict lands. Three pulses per review pass, so a sleeping job still shows a live heartbeat with its next-loop ETA. A packed slot outlives many pulses — keep pulsing until the board is fully terminal.
- **Render with `/sy-list-prs pingpong <same-scope-token>`, passing the current agent ledger.** Same scope token as Step 4a so every pulse covers exactly the dispatched set.
- **Refresh the Status column from GitHub, not from the jobs.** Re-run the cheap `gh pr view` status calls `/sy-list-prs` already uses. **Never message or interrupt a running job to ask its progress** — that wakes a sleeping pass and corrupts its 25-minute cadence. Read job state only from verdicts already reported. A PR sitting at position 2+ of a slot whose earlier PRs are still mid-pass stays `⚪ NOT STARTED — slot <N>, position <p> of <n> — behind <link>`, and keeps its slot number on the PR cell's group line so it still reads inside its feature set rather than in a queue bucket.
- **Update the ledger from reports as they land** — a job finishing pass N on a PR moves that row to `⏸️ WAITING (loop N/10)` with `next loop <ETA>`, or to `⏸️ WAITING_AFTER_SKIP` when that pass was skipped but passes remain; a job's final report for a PR moves it to `✅ COMPLETED` / `⏭️ SKIPPED` / `❌ FAILED`. Between reports, derive `IN PROGRESS` vs `WAITING` and the next-loop ETA from the known cadence (round end + 25 min) rather than leaving the cell blank.
- **A pulse is display-only.** It never dispatches, retries, posts a review, changes a verdict, or re-assigns a slot. A pulse that notices a **dead** slot reports it and nothing more — the relaunch is Step 5's job, taken outside the pulse, and it relaunches the dead slot rather than moving its PRs anywhere.
- Stop pulsing when every row is terminal (`✅ COMPLETED` / `⏭️ SKIPPED` / `❌ FAILED`), then go to Step 6. **`⏸️ WAITING_AFTER_SKIP` is not terminal** — that PR still has passes scheduled, so the pulse keeps running. **`👁️ WATCHING` is not terminal either** (Step 5b).

5b. **Cheap watch mode — park a fully-blocked slot and watch it from the dispatcher, with no agent at all.** A review fan-out spends its back half re-reading unchanged diffs to re-derive the same "nothing new": every round dispatches a full agent per PR, and every one of them reaches Step 9's stop-early gate and posts nothing. Parking replaces those agents with two read-only `gh` calls per PR, folded into the pulse's existing fetch, and relaunches the moment the state moves. **Identical to `/sy-babysit-prs` Step 4b — same parking rule, same stand-down-with-state-capture, same un-park-on-change, same keepalive, same reporting. Read it there; do not restate or re-derive it here.** The fingerprint itself is defined once in `/sy-babysit-pr` Step 12a. Two review-specific notes:

- **A PR is armed when its `## State` block comes back `watch: armed`** — `/sy-review-pr` Step 10a's arming set (stop-early no-op, draft / WIP skip, no new commits, blocked by another reviewer), decided by the per-PR job and never second-guessed here. A slot is parked only when every PR it holds is armed.
- **`headRefOid` is what un-parks a review slot most often.** A push is the one event that makes a diff worth re-reading, so a parked review slot relaunches on a new commit exactly as fast as a live one would have noticed it — the difference is that the rounds in between cost two `gh` calls instead of an agent.

5c. **The run ends when the rounds run out — never when the work does.** A review fan-out is sleep-dominated by design, so "nothing changed" is the normal shape of most rounds and is never a stopping condition.

- **Every wait is a real blocking `sleep` command.** A slot's shared round sleep is `sleep 1500`; the dispatcher's pulse gap is `sleep 600`. One foreground, self-terminating command per wait — never a note in the report claiming time passed, never a shortened sleep, never a busy-poll. A harness timeout below the target re-issues `sleep` for the remainder until the full interval has actually elapsed.
- **A dispatcher with no detached-job facility runs the loop inline — it does not cancel it.** "Background jobs do not outlive the turn", "no wall clock has elapsed", "two ticks were byte-identical", "the set is quiescent, re-invoke me later" are not terminal states; they describe a slot that should be sleeping. Fall back to running the rounds in the foreground with real sleeps, keeping the same ranking, slot assignment, cadence, and ledger. Explicitly ending early with rounds still owed is the failure this command exists to prevent.
- **Re-resolve the PR set at the top of every round, with the same scope token.** The set is not frozen at dispatch: PRs open, merge, close, get marked ready, and pick up new commits mid-run. A newly opened in-scope PR is ranked and dealt into a slot on the round that finds it; a `MERGED` / `CLOSED` one drops out. That is the whole reason an unchanged round is still worth running.
- **Never close a turn by asking what to do next.** No "want me to continue?", no "re-invoke when time has passed", no handing the ledger back for the user to drive. The only terminal exits are: every PR terminal (`MERGED` / `CLOSED` / passes exhausted), or a stop-and-ask that names one of `/sy-review-pr` Step 10's three enumerated cases.

6. **Final report:** emit the **closing ping-pong** — one last `/sy-list-prs pingpong <same-scope-token>` with the final ledger and `Next ping-pong: — (final)` — then summarize per PR: author (when the set is mixed), slot, passes run (`<N>/3`), verdict (APPROVE / COMMENT / REQUEST_CHANGES / SKIPPED + reason), author flags posted, **any slot parked under watch mode** (`slot 1 parked rounds 4–10 — nothing new on either PR; 14 watch ticks, 0 agent dispatches`), and any cross-PR migration coordination notes. **State explicitly that every resolved PR was reviewed** — count the rows and compare against the Step 3 announced count; a mismatch is the failure this command's slot assignment exists to prevent, so name any PR that got zero passes and why. A watched round is a serviced round: report it as one, never as a skipped or missing round. The run therefore always brackets itself: pulse at the start (Step 4a), pulse every 10 min (Step 5a), pulse at the end.

## Rules

- **This command is a dispatcher. The per-PR logic lives in `/sy-review-pr` — do not re-implement it here.**
- **Every job writes to GitHub — this bulk dispatcher has no report-only mode** (see `/sy-review-pr` Output surface). Verdicts, author flags, line comments, threaded replies, and 👍 reactions land on the PRs themselves; the Step 6 summary reports what was posted, it does not replace posting. Never stop to ask the user whether to post or report, and never route findings to a `/sy-critique-*` command — no such command exists. `/sy-review-pr`'s `dry-run` opt-out is a single-PR, foreground, human-in-the-loop review and is **never dispatched from this fan-out** — a batch runs unattended in the background, where there is no user to confirm each proposal.
- **The cross-PR migration check runs on every invocation, at any scope, over every open PR in the repos involved (Step 4).** It is not a multi-repo-only step and it is not limited to the PRs under review: same-repo PRs share one migration DAG, so a single-repo scope is where collisions are most likely, and a PR nobody asked you to review still breaks the default branch when it lands second. The dispatcher is the only thing that can see the whole set — once jobs are in flight they cannot be handed shared context. It coordinates and flags only; re-parenting belongs to the author, via `/sy-babysit-pr`.
- **Parallel means one message, `slot_count` tool calls — not `N` (Step 5 Dispatch mechanics).** The job count is `min(N, S)`, never the PR count: launching one job per PR past the cap is what strands the tail. If the transcript shows slot jobs starting one message at a time, the fan-out was sequential and must be relaunched.
- **Every resolved PR is assigned before anything launches — never queue, never drop (Step 4b).** One job per PR while slots last; past the concurrency cap, the surplus PRs are dealt round-robin into the running slots and reviewed there. There is no "wave 2", nothing waits for a freed slot, and a PR that ends the run with zero passes is a bug in this command, not an acceptable outcome. Slots are **sleep-dominated** — a pass bursts a few `gh` calls and then waits 25 minutes — so packing a lane costs extra passes, not extra sleeps.
- **Order comes from the work-owed ranking, defined once in `/sy-list-prs`.** Do not restate the tiers, the reviewer lens's `R0` / `R1` attention keys, or its tiebreakers here, do not invent a second ranking, and never use any of it to skip a PR — it sets service order only, and it never substitutes for `/sy-review-pr`'s own skip rules.
- **Draft / `WIP` / `DO NOT MERGE` / `DNM` PRs rank dead last and no attention key lifts them (P6).** Newest arrival or a direct `@`-mention does not promote one — an author marking a PR not-ready outranks both. They are still dispatched and still get their passes, but every pass is a documented skip that **posts nothing to GitHub**, so "ignored" is true of the output while later rounds still catch a PR marked ready mid-run. Verify both halves in the Step 6 report: each such PR ends terminal as `⏭️ SKIPPED` with its marker as the reason (mid-run it is `⏸️ WAITING_AFTER_SKIP`, since the marker can drop between rounds), and zero posted artifacts.
- **A slot with several PRs interleaves rounds — it never finishes one PR before starting the next (Step 5).** One pass per held PR, then one shared 25-minute sleep, at least 10 rounds, via `/sy-review-pr <url> pass=single`. Reviewing PR A's full 10-pass loop before touching PR B is the same starvation this design removes, just hidden inside a job.
- **Review all resolved PRs in parallel background jobs — never a sequential for-loop** (see Fan out multi-PR work in parallel). Collect verdicts as jobs finish and report once at the end.
- **Any job that needs the code on disk uses a worktree at the canonical path** — `$HOME/.worktrees/<owner>/<repo>/<sanitized-branch>`, always via `worktree_create` (see One rigid worktree path) — never the user's primary checkout (see Never do PR-branch work in the primary checkout). Reviews are normally checkout-free; treat a checkout as the exception, not the default.
- **Show the author on every row when the set is mixed** (see Show PR authors). This command defaults to ALL authors in the current repo, so mixed sets are the norm, not the exception — the final report (Step 6) carries the author alongside each verdict too.
- **Honor `/sy-review-pr`'s skip rules** — never pre-filter drafts / WIP / already-reviewed PRs in this wrapper. Let the per-PR skill decide and report the skip reason so the audit trail is complete. A per-pass skip is not terminal there — a job that skips pass 1 on a draft still runs passes 2 and 3, so that row is `⏸️ WAITING_AFTER_SKIP`, not `⏭️ SKIPPED`; only an exhausted pass budget (or `MERGED` / `CLOSED`) settles it to terminal. **The announced count is the dispatched count**: 10 in-scope PRs of which 5 are drafts is 10 jobs, not 5. A draft that gets marked ready between passes is exactly what the later passes exist to catch.
- **Every PR gets ≥10 passes, 25 minutes apart** (`/sy-review-pr` Step 10, or the slot's own rounds when it holds several). Never treat the first verdict as a PR's final report, and never cancel a job because it went quiet — between passes it is asleep by design. `pass=single` is the one sanctioned way to run a lone pass, and only from a slot driver that is itself honoring the 10-round floor (Step 5).
- **Default bias inherits from `/sy-review-pr`**: APPROVE or COMMENT — REQUEST_CHANGES is reserved for show-stoppers only.
- **Silent jobs are a success, not a failure.** A job that posts nothing because the re-review turned up nothing new reports `NO-OP` in the final summary. Don't retry it and don't nudge it into commenting to prove it ran.
- **A slot whose every PR has nothing left to review gets parked and watched, not dispatched (Step 5b).** Repeated no-op rounds are the expected shape of a long review run, and paying a full agent per PR to reproduce one is the waste this removes: parking costs two read-only `gh` calls per PR, folded into the pulse's existing fetch, and the slot relaunches the instant a fingerprint moves — a new commit above all — plus at least every 4th round and always for the last. Never park a mixed slot, never park mid-round, and never report a watched round as a missing one.
- **Ping-pong is mandatory, not optional (Steps 4a / 5a / 6).** Every run pulses before dispatch, every 10 minutes while jobs run, and once at the end. The pulse is read-only — it refreshes PR status from `gh` and reads already-reported verdicts; it never messages or interrupts a running job, and it never acts on what it finds.
- **Ping-pong layout is owned by `/sy-list-prs pingpong`.** This command owns the agent ledger (job state, loop number, dispatch / pass times, next-pass ETA, slot number and position, last rendered pulse snapshot) and passes it in; `/sy-list-prs` owns the three columns, the icons, the change marker, the feature-set grouping, and the sort. Every PR gets ≥10 passes, so Agent cells here carry the `(loop N/10)` counter — same form as `/sy-babysit-prs`.
- **Multi-repo workspaces** (e.g. a bundle like `myapp-frontend`, `myapp-backend` or `myapp-lib`): pass each repo as a `<owner>/<repo>` token. The cross-PR migration check (Step 4) runs across the full union **before** any job is dispatched, so coordination flags surface before any verdict is posted.
- **Always resolve `<owner>/<repo>` via `git remote get-url origin`, never from the folder name (see Repo Identification).**
- **An idle set is a reason to sleep, not to stop (Step 5c).** Every wait is a real `sleep` command, the PR set is re-resolved every round, and the run never ends with a question to the user. A run that stops with rounds still owed is reported as a failed run.

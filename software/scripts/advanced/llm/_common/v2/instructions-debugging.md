# Debugging Discipline

Read before the first fix attempt on broken behavior. Use this file for diagnosis and proof; use Validation Cadence for check scope and Test Quality for regression-test design. Epistemic Honesty and the safety gates in the main instructions remain binding. Rules are named, not numbered.

## Reproduce before you theorize

- **No fix without a reproduction.** Establish expected behavior from the request, issue discussion, acceptance criteria, and owning contract. Run a deterministic pass/fail check that produces the reported failure before proposing a patch. Prefer a focused test, then an integration seam, CLI fixture, replay, or bounded interactive procedure. A different failure is a separate finding, not a substitute reproduction.
- **Make the loop cheap.** Reduce the failing input, setup, and execution path until another reduction removes the failure. Preserve the original command and triggering conditions; the reduced case accelerates investigation but does not replace final proof.
- **First failure first.** Read the first causal error and its complete relevant stack, not the downstream cascade. Quote the shortest decisive error verbatim after redacting secrets and identifiers. Search public sources using the error category, not raw private traces, hostnames, SQL, or customer data.
- **Intermittence needs a baseline.** Record failures over attempts, the seed, timing, concurrency, environment, and state. Stabilize controllable clocks, ports, data, and randomness; use bounded repetition or stress to raise the reproduction rate. Do not call a single green rerun a fix.
- **An unavailable repro is the result.** Compare environments, inspect recent changes and prior fixes, and try the smallest alternate seam. If the reported failure still cannot be reproduced, report the attempts and missing evidence; stop before a speculative patch. Read-only investigation does not authorize production experiments or data repair.

## Isolate one variable at a time

- **One hypothesis, one change, one observation.** Write a ranked set of plausible causes with a predicted observation and a disproof for each. Test one candidate at a time with the smallest probe; remove only your disproven experimental change before the next. Never erase unrelated work.
- **Bisect; don't stare.** Search the cheapest discriminating axis: history with the minimal reproducer, input, configuration, dependency, test order, or execution path. Identify an expected value at a named boundary and narrow to the adjacent observations where it becomes wrong. A probe must change the next action depending on its result.
- **Compare a working path.** Read the complete local pattern, callers, dependencies, and paired operation. List the differences between working and failing cases. A missing await, stale cache, encode/decode mismatch, or configuration drift is a hypothesis until the real path confirms it.
- **Verify the running artifact.** Before trusting live observations, prove the process runs the build and checkout under investigation using a version/SHA or start time after the build. Check imported module and executable paths; stale servers and shadowed modules invalidate the experiment.
- **Instrument the boundary, not everything.** Prefer a breakpoint or one value observation over broad logs. Add bounded, redacted diagnostics before the suspect operation; give temporary logs a unique searchable tag and remove every tag before completion. Never capture credentials or entire authenticated payloads for convenience.
- **Reconsider a failed model.** After three consecutive ruled-out hypotheses, stop generating more of the same. Recheck the artifact, baseline, test meaning, state ownership, and unobserved boundary. If repeated fix attempts expose architectural coupling, discuss the revised model before a fourth patch.
- **Performance has its own evidence.** For latency, throughput, memory, or scaling symptoms, load Measure Before Optimizing, capture the baseline/profile, and bisect measured behavior. Diagnostic logs alone do not prove the bottleneck.

## Fix the cause, then prove it

- **Repair the owning invariant.** Trace the bad value to its origin and fix the responsible layer, including sibling callers with the same demonstrated defect. Do not mask it with a catch-all, crash-site null check, unbounded retry, sleep, weakened assertion, or unrelated refactor. Ask why the defect escaped the existing check.
- **Prove the fix is load-bearing.** All three checks are required: the original failing command now passes; removing only the fix makes the regression fail for the intended reason and reapplying it restores green; the targeted collateral suite passes. Preserve concurrent work during the negative control. If a safe negative control cannot run, report the gap rather than claiming both directions.
- **Prove the real surface.** UI: perform the interaction and inspect console/network results. Persistence: write and read back through the owner's normal read path or reload. Races: run concurrent attempts and assert the permitted success count plus final invariant. Intermittent failures: compare a documented repeated run against the original failure rate. Name any unavailable surface check explicitly.
- **Audit consequences separately.** Search changed callers and partner operations; apply Risky Changes when a contract changes. Existing corrupt data and production remediation require separate approval, not an implicit cleanup inside the code fix.
- **Never round an unexplained remainder up to fixed.** Account for every reported symptom. Record a separate warning or failure as a separate finding, or admit the cause is incomplete. Disappearance without an understood cause is not proof of repair.
- **Close with reproducible evidence.** Report symptom, relevant environment, cause and code location, changed behavior, original/regression check commands and results, negative-control evidence, and remaining gaps. Distinguish executed evidence from supplied logs. A blocked report names the smallest action needed to resume; a completed report includes the regression test and removes all temporary diagnostics.

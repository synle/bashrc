# PR & Source Control Workflow

Companion to the always-loaded engineering principles. Read before any branch,
commit, PR, review, worktree, or GitHub action. Rules are named — quote the name
when referencing one. Epistemic Honesty from the main instructions governs here too.

## Branches, titles, commits

- **Documentation PR independence** — Open completed documentation-only PRs early as regular PRs, without `WIP`, `Placeholder`, `DO NOT MERGE`, or draft status. Docs and companion code may merge in either order, without waiting for the other to merge or deploy. Keep unfinished docs and failing CI visible; required checks and human approvals still apply. This overrides status and companion holds in creation, milestones, prose-only automerge, babysitting, and batch workflows, not dependencies between executable changes.
- **Branch naming** — `<username>/<feature>`, or `<username>/<group-slug>/<feature>` when 2+ branches share a feature, plan, or agent fan-out. Resolve `<username>` from `git config --get user.email | cut -d@ -f1`, else `gh api user --jq .login`. Segments kebab-case. Pick the group slug once (from the plan file's `<feature>`, parent agent group, or umbrella feature) and reuse on every sibling. Never an unprefixed branch, a group of one, a fourth segment, or a slug reused across unrelated work.
- **PR titles** — `[<repo>] <description>`, org dropped (`gh repo view --json name -q .name`). Status prefixes stay outermost (`WIP: DO NOT MERGE — [repo] ...`); a revert wraps the whole original title (`Revert "[repo] ..."`) and gets no second prefix. Strip `[<repo>] ` when the renderer already prints the repo.
- **Commit messages** — read the diff first (`git status`, `git diff --staged`, `git show`); base the message on what the hunks do, never on intent or a patch/branch/issue name. Inspect hunks file-by-file when the change is not your own edits (`git apply`, `am`, cherry-pick, stash pop, generated diff). Subject = imperative one-line behavior change; body = why. Never `apply patch` / `fix stuff` / a bare file list. Split unrelated concerns.
- **Commit/push** — stage and commit only task hunks; never `git add -A` over someone else's dirty files. Run the repository's validation before final commits; **PR publication milestones** defines the narrow early-checkpoint exception. Pushing, amending, and opening PRs require explicit authorization. Authorization to publish this task's PR covers its milestone pushes without another prompt; an existing PR alone grants no authority. Local-only requests remain local.
- **Non-trivial branch work starts with a placeholder PR, before implementation.** For authorized PR work, follow the shared **Placeholder checkpoint** and share the real PR URL before implementation. Reuse that same PR through later milestones; no separate creation skill owns this lifecycle.
- **Placeholder drafts are parked, not babysat.** A pre-implementation PR with `isDraft == true` and a title containing `Placeholder` remains outside babysit flows. Single/batch babysit and pending-PR helpers skip it. The **Implementation checkpoint** marks it ready for review, drops only `Placeholder`, and keeps WIP; non-draft WIP does not exclude explicitly requested babysitting.
- **Commit identity from history** — before the first commit in a repo, pin `user.email` to the address you actually commit with there, never the global default. Run `git fix-identity` when the alias exists: it skips repos that already pin a local email, collects every `user.email` on file (`~/.gitconfig`, `~/.gitconfig-personal`), walks the last 50 commit authors newest-first, and sets the first match with `git config --local user.email`. No alias → do the same by hand. No match → leave config untouched and say so; never invent an address or copy one from a non-you author.
- **Commit-author check** — every commit and push. Compare, don't eyeball:

  ```bash
  git config --get user.name && git config --get user.email
  git --no-pager log --format='%h %an <%ae>' @{upstream}..HEAD 2>/dev/null \
    || git --no-pager log --format='%h %an <%ae>' origin/HEAD..HEAD
  ```

  On mismatch: flag SHA + both identities side by side and ask. Default "no" repairs with `git commit --amend --reset-author --no-edit` (or `git rebase <base> --exec '...'` for a run); proceed unchanged only on explicit "yes". `--reset-author` preserves `Co-Authored-By:` trailers — keep intentional LLM ones.

- **Sync** — `git merge origin/<default>`; never rebase or force-push a shared feature branch. Resolve default, don't assume `main`:

  ```bash
  DEF=$(git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null | sed 's#^origin/##')
  DEF=${DEF:-$(gh repo view --json defaultBranchRef -q .defaultBranchRef.name)}
  git fetch origin "$DEF" && git merge "origin/$DEF"
  ```

  Exception: pushing to default itself always `git pull --rebase` then fast-forward push — never a merge commit on default from local work.

- **Plain-English "pull latest code" means the merge workflow, not a rebase.** On a non-default working branch, route those requests through `/sy-sync-pr-branch`, not a separate merge skill.
  - Sync floor/default first, then ancestor wave or feature branches from root-most to immediate parent. Preserve a non-default release/integration floor instead of forcing main.
  - Read the sync result. Stop for `stopped-for-human` or migration `needs-human`; do not continue to a fork merge after an incomplete sync.
  - When `upstream` points at a different repository than `origin`, resolve its actual default branch and merge that upstream default branch last.
  - Use the verified target checkout under shared Worktrees rules; finish any existing merge before starting another. Never merge upward into ancestors or push their branches.
  - Without a distinct upstream repository, skip that step. Report the sync result and upstream outcome, including an explicit no-op when nothing changed.
  - On the default branch itself, the existing fast-forward exception above still wins.

- **Solo repos** — if `git log --format='%ae' -200 | sort -u` is only you plus known bots (`*[bot]@*`, the LLM noreply addresses), push straight to default; say so. An explicit "open a PR" overrides.

## Execution routing

Apply these defaults to implementation, review, and babysitting, including batch skills. They override skill-specific placement defaults and fan-out instructions, not explicit user mode choices or repository rules.

- **Foreground by default** — Keep a single repository's task in the foreground; do not delegate it merely because workers are available.
- **One code repository plus docs/context companions** — Keep the main code task in the foreground and background each separate docs/context repository's work. Skip companion environment setup unless a concrete writing or generation step needs it.
- **Multiple code repositories** — When two or more repositories require non-docs/context changes, background each repository's work in parallel, including companion docs/context work. Group same-repository PRs under one owner; preserve dependency ordering and avoid concurrent writers.
- **Urgent work stays foreground** — Reverts, emergency fixes, and hotfixes default to foreground even across repositories; parallelize only when explicitly requested.
- **Placement is not another workflow** — Invoke shared skills inline for foreground work, including sync; invoking a skill does not require another agent. Apply **Parallel fan-out** only to the background subset. If delegation is unavailable or explicitly denied, move those assignments to the main agent and run them inline; preserve scope, ownership, state, and cadence, and report reduced parallelism.

## Fast-track PRs

- **Eligibility** — Simple docs-only, context-only, version/dependency changes, reverts, emergency fixes, and hotfixes may skip a dedicated worktree, background worker, and environment setup. Optional worktree bypass does not remove isolation requirements for concurrent writers.
- **Existing-checkout safety** — Before bypassing a worktree, verify repository, branch, pending Git operations, dirty files, and ownership. Use a task branch without moving unrelated work. If safe reuse is impossible, use a worktree; never reset, stash, overwrite, or claim unrelated changes.
- **Publish first** — For authorized fast-track PR work, make the smallest reviewable change, commit task hunks, sync, push, and create the PR immediately. Skip optional local validation before creation: formatting, lint, syntax checks, tests, coverage, builds, and runtime setup. This overrides skill baselines, placeholder requirements, dependency pre-push test ordering, and implementation-checkpoint title sequencing.
- **Finish after publication** — Share the returned PR URL, then complete applicable formatting, validation, feedback repair, and wrap-up through **PR publication milestones**. Record unrun checks and known failures in the PR body. Do not equate early publication with completion or merge readiness.
- **Status and safety** — Completed docs follow **Documentation PR independence**; other fast-track PRs keep unfinished work visible without requiring a placeholder draft. **Checkpoint safety**, publication authorization, required sync, repository-required gates, hooks, secret handling, downstream audits, and migration safety still apply. Required CI and human approval still gate merging.

## PR publication milestones

The shared workflow owns creation and all three author states. Ready for review is not ready to merge, and removing markers never grants merge authority.
Remove pipeline status markers only; preserve substantive title text.

| Author stage                                 | GitHub state                                         | Title markers               |
| -------------------------------------------- | ---------------------------------------------------- | --------------------------- |
| 1. Placeholder                               | Draft                                                | WIP + Placeholder           |
| 2. Implementation published                  | Ready for review / non-draft                         | WIP only                    |
| 3. Validation and current feedback published | Ready for merge subject to required CI and approvals | Neither WIP nor Placeholder |

Existing **Fast-track PRs**, **Documentation PR independence**, repository gates, publication authority, and local-only restrictions remain applicable.

- **Milestone sequencing** — For authorized implementation work on your own PR, publish at implementation, validation, and feedback/CI checkpoints. Continue the task after each push. Include reviewer-comment resolution and CI-error repair in progress steps and durable milestone state. These checkpoints override completion-only task-skill ordering, not repository-required gates or Secret Handling. A placeholder or early PR does not end implementation.
- **Placeholder checkpoint** — For authorized new implementation work, resolve the real repository/default branch, inspect commits/diff, apply no-stack and sibling-overlap checks, and reuse the task's owned PR when present. If no branch divergence exists, one empty placeholder commit is allowed. Create a true draft against default with both `WIP` and `Placeholder` in the title, using `WIP: DO NOT MERGE — [<repo>] Placeholder <summary>`. Follow the repository template and file-backed Payloads, seed or reuse owned-PR memory, and share the returned full URL before coding. If the host rejects an empty PR, report the blocker; never invent a URL or edit unrelated files to force creation. Do not replay placeholder creation for a PR already past this stage.
- **Implementation checkpoint** — Once real implementation is reviewable, commit task hunks, run shared sync in the selected execution mode, and push immediately for early feedback. Do not delay for formatting, lint, syntax checks, test writing/execution, coverage, or the full gate unless repository rules require them before publication. Report known failures and unrun checks. Checkpoint safety and required sync still apply; never bypass hooks. After this push, mark the same PR non-draft/ready for review if still draft, remove only `Placeholder`, and retain `WIP` in the title. Update its real summary and pending test plan, then continue stage 3 without another push prompt. Ready for review does not mean merge-ready, approved, or permission to enable automerge.
- **Checkpoint safety** — Verify commit authors and scan pending commits for secrets before every push. Preserve downstream audits, migration checks, and repository-required pre-push gates. If repository rules require full validation before any commit or push, they override early publication. Never hide failures or bypass hooks.
- **Sync before publication** — Before every implementation, validation, or repair push, invoke `/sy-sync-pr-branch` with `workspace=<selected-checkout> push=defer server-side=never`. Run it inline for foreground work. Resolve the actual default branch and ancestor chain; never assume `master` or `main`. Resolve conflicts before publishing; never rebase or force-push a shared PR branch. A sync failure blocks publication.
- **Validation checkpoint** — Continue test writing, validation, and current-comment repair after implementation publication. Refresh current actionable PR feedback and latest-head checks; apply authorized fixes or evidence-based dispositions, then format and run required tests, coverage, and the repository gate. Unresolved code or validation blockers keep WIP. Commit validation/feedback changes, sync, rerun checks affected by sync, and push again. After successful validation publication, remove `WIP` and any remaining `Placeholder`; keep the PR non-draft and update actual results and remaining human/CI gates. With no new changes, record the verified no-change checkpoint instead of an empty commit or pretend push. Later CI reconciliation does not restore title markers, but unresolved required checks still block merging.
- **Feedback/CI reconciliation checkpoint** — After the validation push, start a run with a total budget of `<<SY_CI_RECONCILIATION_BUDGET_MINUTES>>` minutes. Each cycle waits up to `<<SY_CI_WAIT_MINUTES>>` minutes for blocking CI checks, or proceeds sooner when they finish. At timeout, fetch fresh, fully paginated feedback and latest-head checks. Handle actionable human/bot findings and completed CI failures through `/sy-pr-reconciliation-pass` with `scope=all-actionable`. That pass batches fixes, validates once, syncs before one repair push, and reruns only checks affected by sync. After each repair push, restart the cycle on the new head. Continue while actionable findings, failed checks, or blocking checks remain pending. Do not wait on human gates; report them separately. Stop early for an external blocker or required human decision. Step 4 never changes WIP or `Placeholder`. At the total limit, report remaining work directly to the user and update PR memory; never claim completion.
- **Checkpoint evidence** — Update the PR body and durable PR memory with the phase, pushed head SHA, actual check results, remaining work, and feedback snapshot time. Preserve unfinished `TODO —` items. Verify remote head and title state after publication. Record a no-change milestone without an empty push.
- **Completion boundary** — Complete the task only when latest-head required blocking CI passes, all actionable findings have dispositions, and no code or CI blockers remain. Step 3 removes WIP; Step 4 never restores it. Report pending human approval separately; it is not CI success and may still block merging. If the Step 4 budget expires first, report pending work to the user and stop without claiming completion. Milestone pushes never authorize merging or release.

## PR bodies and payloads

- **PR prose component** — Repository templates remain authoritative. When available, read `<<LLM_ROOT_FOLDER>>/upstream/ADAPTERS.md` and the installed `<<UPSTREAM_ARJUN>>/skills/docs/pr-descriptions/SKILL.md` for what/why/risk/verification writing only. This component grants no branch, push, creation, readiness, review-posting, merge, or automerge authority. If unavailable, explicitly report that optional dependency and use the repository template or the shared default: `## Summary` and `## Test plan`. Placeholder content may be minimal; unfinished implementation/validation items stay visibly `TODO —`, and unrun checks are never checked off.

- **PR body follows the repo's template** — before every `gh pr create` (and before rewriting a body with `gh pr edit`), check for a template; `--body`/`--body-file` overrides GitHub's prefill, so skipping the check silently drops it (`git ls-files | grep -i pull_request_template`). Precedence: `.github/PULL_REQUEST_TEMPLATE.md` → root → `docs/` → `.github/PULL_REQUEST_TEMPLATE/*.md` (multi-template: pick best fit, say which, ask if two are equal). When found, the body **is** that template filled — every heading reproduced in order/wording/level, nothing dropped or invented, `<!-- -->` placeholders answered and deleted. Inapplicable section → `N/A` + half-line why (WIP → `TODO — <what's left>`), never deleted.
- **Payloads** — every GitHub body goes through a temporary file: Markdown + `--body-file` for `gh pr create`/`edit`/`comment`/`review`; JSON + `gh api --input` for REST comments, replies, reactions, reviews. Never `--body`, `-f body=`, a shell var, `echo`/`printf`, command substitution, or an inline heredoc — backticks, quotes, and `$` stay out of the shell. Delete each temp file after capturing the result, success or failure.
- **Human-readable GitHub text** — every user-facing GitHub body must be plain human-readable Markdown or prose: PR bodies, issue comments, review summaries, line-comment text, replies, author flags, and coordination messages. JSON is transport-only for the REST envelope; never paste a serialized request object or fields such as `event`, `body`, `comments`, `path`, or `line` into GitHub-visible text. Before posting, inspect the body file; if it starts like a JSON object or contains an API request wrapper, rewrite it as Markdown and keep any JSON only in the separate `gh api --input` file.
- **PR memory is the durable journal** — stable identity is `<owner>/<repo>#<number>`. Reviews of other people's PRs keep `<<LLM_ROOT_FOLDER>>/pr_reviews/<repo-name>_<number>_<author>_<slug>.md`; babysits of your own PRs keep `<<LLM_ROOT_FOLDER>>/pr_babysits/<repo-name>_<number>_<slug>.md`. Resolve `<owner>/<repo>` and `<repo-name>` from GitHub, preserve punctuation in the repository name, lowercase `<author>`, and derive a short lowercase snake_case `<slug>` from the title after stripping status / repo prefixes. Before creating a file, search the target folder for the stable identity in a heading or full PR URL and for historical filename aliases; one match is reused without renaming. Multiple same-kind matches create no new file: report the conflict and use the newest verified snapshot until a content-preserving consolidation is explicitly approved. One file is the latest verified snapshot: `## TLDR`, `## Context`, `## Relevant Rules`, `## Progress`, `## Open Items`, `## State`, `## Final Snapshot`. Rewrite sections in place after meaningful actions, findings, verdict/state changes, stop-and-ask, and terminal state; do not append polls, routine commands, raw logs, temporary payloads, or facts obvious from PR comments. Preserve resume-critical counters and ownership in `## State`, keep every memory after merge/close, and revalidate saved claims before acting. An old worktree-adjacent `pr<number>-<branch>.md` may seed the current memory once, but never write both.
- **Understand before acting** — before review findings or babysit edits, read the title, body, commits, changed-file list, and diff; write a private 2–3 sentence feature TLDR covering goal, implementation, affected contracts, and main risk. Then scan root and changed-path rules plus architecture/developer docs and docs linked from them; widen to related repos only when the PR or architecture names a concrete consumer. Record only applicable hard rules and non-obvious context in PR memory. Description claims remain hypotheses and the diff wins when they disagree.
- **Checklists** — tick only what the diff proves; call out gaps in the summary.
- **Body drift** — re-read the body after any push that changes what the PR does; diff it against `git diff <base>...HEAD`. Amend only drifted parts through the reviewed body file (`gh pr edit <n> --body-file <tmp>`). During draft/placeholder promotion, replace placeholder prose with the implemented diff and tick only proven boxes. Clear only completed `TODO —` items; **PR publication milestones** governs WIP retention and removal.

## No stacked PRs

- **Every PR branches off the default branch and targets it — no stacked PRs, ever.** Pass `--base <default>` explicitly; cut the branch from an up-to-date default. Pre-flight: `git log --oneline origin/<default>..HEAD` must list only this PR's commits. If it lists a sibling's, re-cut from default and re-apply only this branch's work — never point `--base` at the sibling. A stacked child is unmergeable until its parent lands, shows a polluted diff, and breaks when the parent squash-merges under it.
- **Split by slice, never by layer.** Each PR is one self-contained slice standing against default, touching the fewest files siblings also touch. Bundle tightly-coupled changes (API + schema + models) into one PR. If no split leaves every piece independently mergeable, ship one PR — a bigger standalone beats two stacked.
- **Independence is the test, not slice count — do not over-split.** A split earns its keep only when each slice truly stands alone. Two "independent" slices that both edit the same file — worse, the same line: a shared constant, a budget assertion, a registry, a barrel — are not independent, and splitting them rewrites that line per slice, re-derives the baseline on every rebase, and forces a merge order on peers meant to have none. That is _more_ churn than one PR, not less — consolidate them. Price the split before making it: shared-line edits × slices = guaranteed conflicts, forced order = serialized review; when that cost outweighs the isolation, ship one standalone PR. "A bigger standalone beats two stacked" extends to "beats N churning peers".
- **Hard caps per round: at most 3 waves, at most 7 PRs.** Hitting either ceiling is the signal the split is too fine — not a licence to open a fourth wave or an eighth PR. Merge the cheapest-to-combine slices until under both. A genuinely larger change that cannot fit is phased across separate rounds, never fanned wider within one.
- **Overlap is resolved by ordering, not stacking** — land one, `git merge origin/<default>` into the other.
- **Make slices disjoint with new files, but check the discovery mechanism first.** A runner globbing `**/*.spec.ts` picks up a new file free; a barrel, registry, or manifest does not — there the conflict just moved.
  - Tests — one new spec per slice, named for the behavior, matching repo convention; duplicate a few setup lines rather than extract a shared helper.
  - Fixtures/factories — a new file per slice, never new keys in a shared one.
  - Genuinely unsplittable files (barrels, registries, enum blocks) — append at EOF, never in sorted position.
  - Lockfiles/snapshots/generated code — regenerate, never hand-merge; better, let one slice own the dependency change.
  - One migration per slice, uniquely named; never renumber a sibling's.
  - Shared edit every slice needs — land it alone and first as a tiny prep PR to default; siblings pick it up by merge. Not a stack: it targets default and merges before anything depends on it.
  - Assign every file to exactly one slice, said out loud in the plan/body. Verify: `git diff --name-only "origin/<default>...HEAD"` per branch, intersect — non-empty outside regenerable classes means redo the split.
- **Hard dependencies phase into waves, never a stack. A wave is a merge barrier, not a branch parent** — every PR in every wave is cut from and targets default; wave N+1's branch does not yet contain wave N's code.
  - Wave 1 depends on nothing (migration, schema, shared interface, config key). Within a wave, PRs are disjoint and merge in any order; waves are ordered, the PRs inside one are not.
  - Later waves open WIP (`WIP: DO NOT MERGE — ...`) with a `## Blocked on` section linking every PR they wait for. Reuse one group slug across waves.
  - A title number is MERGE order, never creation order: `wave <W> - pr <i>/<N>`, `<i>` monotonic against `<W>` (every wave-2 PR numbers above every wave-1 PR), `<N>` the whole set across all waves. Within a wave, any stable order (alphabetical by slug reads best).
  - Renumber the whole set whenever the graph changes, and say you did — a title edit per affected PR plus an announcement line naming old→new. A newcomer takes the wave its dependencies put it in and triggers a full re-derive, never appends to the end. Fix the prose too: `## Blocked on` sections, the thread reply that asked for the follow-up, the announcement.
  - A later-wave PR is expected red until its dependency lands — say so in the body (`"CI stays red until <link> lands"`); never spend a fix loop on it.
  - Promotion: blocker merged → `git merge origin/<default>` → CI green → drop WIP prefix, in that order, only when the blocked-on section was the sole WIP reason and no `TODO —` remains.
  - Migrations phase expand → migrate → contract, and **wave 1 must be backward compatible** (adds only — nullable column, new table/index — leaving deployed code untouched). Wave 2 backfills/dual-writes; wave 3 drops the old thing once wave 2 is fully deployed. A rename is never one PR: add-new → dual-write → backfill → read-new → drop-old. If wave 1 can't be backward compatible, the waves are wrong — one atomic PR or redesign.
- **An existing stack is damage to contain, not a pattern to follow.** Don't rewrite pushed history; sync it downhill and land bottom-up. Say out loud it's stacked and unintended. Sync the whole ancestor chain floor-first, immediate parent last: walk up to the floor (default, or a long-lived non-default release/integration line with no PR — then default is _not_ merged in), merge the floor, then each ancestor root-most down, one `git merge` each with conflicts resolved between them. No octopus, no rebase, max 10 hops, stop on repeat. **Merges flow downhill only** — never push an ancestor, merge child→parent, or retarget an ancestor's PR to unblock a child. A green+approved stacked PR is still blocked on its parent landing — report the link, don't merge. Where `/sy-sync-pr-branch` exists, delegate the sync to it.

## Worktrees and fan-out

- **Worktrees** — use a dedicated worktree for PR-branch work unless **Fast-track PRs** permits safe existing-checkout reuse. `worktree_create <branch>` is the only creator (`WT="$(worktree_create "$BR")"`): it fetches, reuses a linked worktree already on the branch, preserves unpushed commits, refuses the primary checkout, and falls back detached. Never hand-roll `git worktree add`, the path, or `mkdir`. Remove only worktrees you created. cwd not the target repo → clone it outside the container first, run `worktree_create` inside. Interactive: `git_create_worktree` adds a `cd`.
- **Canonical path** — `worktree_create --path-only <branch>` prints `$HOME/.worktrees/<owner>/<repo>/<sanitized-branch>` and touches nothing. Owner/repo from origin, never the folder name. Leaf keeps `[A-Za-z0-9._-]`, every other run → `_`, leading/trailing `._-` trimmed. An already-linked worktree may carry an older noncanonical leaf — reuse it without moving, report the legacy path, use `--path-only` as canonical for new work.
- **Parallel fan-out** — Dispatch the background subset selected by **Execution routing** together, subject to **Capacity**. Each repository owner isolates concurrent PR branches in worktrees unless **Fast-track PRs** permits safe reuse. Each handoff identifies the task or verified PR URL/number, resolved `owner/repo`, workspace policy, and full sibling list. Workers own their workspaces; the foreground owner may work on its assigned main repository. Report once after awaiting all jobs. Repo-wide cleanup stays sequential in one shared checkout.
- **Capacity** — enroll every PR before launching; never drop scope. A declared harness concurrency cap is `S` (read by name, never hardcoded); no declaration means no cap. Rank by work owed: unshipped local work (only tier that can lose data) → awaiting reply → broken-and-ours → stale → bot nits → waiting-on-someone-else → drafts, ties to oldest untouched. Launch `min(N, S)` from the top; a finishing worker hands its slot to the next PR by rank. Age the queue so a low-ranked PR is serviced late, never never.
- **Stable job key** — derived from the work, not launch time: `<command>:slot<i>` or `<per-PR-command>:<owner>/<repo>#<number>`. Store it in the prompt, PR memory, and the dispatcher's ledger beside the resume handle the dispatch returned (record it immediately — it's the only address for the job later). Before dispatching, match the key against live jobs: running owner left alone, idle owner resumed, only an unowned key gets a new job. A duplicate on one PR double-pushes and double-comments — keep the older, cancel the newer, report it.
- **Resume idle, relaunch only dead.** A job that finished its turn is idle, not dead — it holds its worktrees, read threads, counters, context; resume it with a follow-up turn (one cheap turn, warm context). Relaunch only failed/cancelled/gone, confirmed first, seeded from the ledger's last state block, taking only the dead job's remaining PRs. Never fold a dead job's PRs into a live neighbour.
- **A pass runs inside its job.** A round is one pass, not a reason for a new worker; the per-PR command runs inline once inside a dispatched job. Spawning a child per PR per round makes `PRs × rounds` cold agents where one job would do. The job and ledger are long-lived; the pass is not.
- **Never end a turn with a dispatched job in flight** — a parent that stops first freezes the child's status at "running" forever. Await every job dispatched in a turn, land the final report, close each round before the next. A run hitting its deadline finishes its last round rather than issuing one it can't await.
- **Watch/review is clock-bounded, not pass-counted** — a fixed budget, read-only probes on a short interval, a full pass whenever the fingerprint moves, a periodic keepalive pass, and one final pass before the deadline. Inbound work never interrupts a pass in flight (mark dirty, finish to the safe point, re-run at the head of the queue); never count your own writes. Ends on deadline, all-PRs-merged/closed (explicit PR refs only — a search scope re-resolves and sleeps through an empty round), or GitHub/model service unreachable across a short retry window — a stop-and-ask parks its PR and keeps probing, so an answer posted on GitHub is seen. Every stop writes resumable PR-memory state. Intervals live in the command sources — never restate a number here.

## Worktree dependencies

Share caches and runtimes, isolate environments and output. Apply these three layers across ecosystems:

| Layer               | Examples                                                                                                     | Rule                                                                  |
| ------------------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| 1. Global cache     | `~/.cache/uv`, `uv python` installs, pnpm store, `~/.cargo/registry`, `GOMODCACHE`, `~/.gradle/caches`, gems | Share — content-addressed, concurrency-safe; most tools do by default |
| 2. Per-worktree env | `node_modules`, `.venv`, `vendor/bundle`                                                                     | Own copy per worktree — cache-backed install from the lockfile        |
| 3. Build output     | `target/`, `dist/`, `build/`, `.next/`, project `.gradle/`, test caches                                      | Never shared — speed up with a compiler/build cache instead           |

- **Never symlink a layer-2 or layer-3 folder between worktrees.** Bundlers and Node resolve the real path, so imports escape into another checkout; an install in one worktree rewrites every other one's tree; an editable Python install points at whichever worktree built the venv, so tests silently import another branch's code; concurrent builds corrupt a shared `target/` or `dist/`.
- **Keep package caches outside the worktree.** Confirm the store/cache path resolves outside the checkout (e.g. a repo-local `.yarn/cache`, `.pnpm-store`, or project `.gradle` is per-worktree and starts cold every time); a repo-local cache defeats every other rule here.
- **Reinstall only when the lockfile changed.** After a successful install, record a hash of every lockfile in that worktree; skip the next install when the hash matches and the env folder exists. Safe because the env was still built by this worktree — never by a clone.
- **Turn on the build tool's content-keyed cache** (Gradle build cache, `sccache` / `ccache`, turbo/nx local cache) so rebuilds across worktrees reuse compiled work without sharing build output.
- **Give each worktree its own ports.** Derive dev-server, debugger, and test-service ports per worktree, never the tool default — two agents on one default port collide, or one silently talks to the other's server.
- **Install only when the task runs code.** Docs, context, review, and source reading require no environment bootstrap by default. When execution is necessary, provision only dependencies, configuration, or services needed by that specific check; do not bootstrap the full application without need.
- **Install from the warm cache; don't clone by default.** Reconcile layer-2 environments against this worktree's lockfile using cache-first installs. Clone only when a repo-specific before/after measurement proves a win and reconciliation still runs; never fully copy a large tree. Copy-on-write still pays per-file metadata cost.
- **Never clone an env holding absolute paths.** A Python venv (shebangs, `pyvenv.cfg`, editable `.pth`) and any tool-managed venv point back at the worktree that built them — a clone imports the other checkout's code and tests pass against the wrong source. Build it fresh per worktree; ruled out on correctness, not speed.
- **Expect a cold first run.** The first install in a fresh worktree can pay a one-off cost (build daemon start, first cache fill) several times the steady state; judge an approach on the second fresh worktree, not the first.
- **Prove isolation after install.** Resolve one project import or binary and confirm it points inside this worktree, not the primary checkout.
- **Install commands by ecosystem** (prefer offline/cache-first forms):

  | Lockfile            | Reconcile                                                      | Build-cache speedup               |
  | ------------------- | -------------------------------------------------------------- | --------------------------------- |
  | `pnpm-lock.yaml`    | `pnpm install --frozen-lockfile --prefer-offline`              | the repo's task cache (turbo, nx) |
  | `package-lock.json` | `npm ci --prefer-offline` (wipes `node_modules` — no seed)     | —                                 |
  | `yarn.lock`         | `yarn install --frozen-lockfile --prefer-offline`              | —                                 |
  | `uv.lock`           | `uv sync --frozen`                                             | —                                 |
  | `requirements*.txt` | `uv venv` + `uv pip sync <file>`                               | —                                 |
  | `Cargo.lock`        | `cargo fetch --locked`                                         | `RUSTC_WRAPPER=sccache`           |
  | `go.sum`            | `go mod download` (module + build caches already global)       | —                                 |
  | `Gemfile.lock`      | `bundle install`                                               | —                                 |
  | Gradle wrapper      | the repo's own Gradle task; venvs it manages stay per worktree | `org.gradle.caching=true`         |
  | C/C++               | —                                                              | `ccache`                          |

- **Reuse the runtime, never rebuild it.** Python interpreters come from `uv python install <ver>` (once per machine); Node from the version manager already present (corepack, volta, nvm, fnm); Rust toolchains from `rustup`. Never compile or download an interpreter per worktree.
- **Never point several worktrees at one `CARGO_TARGET_DIR`** (or any shared build output) — they serialize on its lock and invalidate each other's fingerprints. Share compiled work through `sccache` / `ccache` / the build tool's cache, which key by content.
- **Monorepos reconcile at every lockfile root**, not just the worktree root.
- **A repo or machine helper wins.** When setup is necessary, use the repository's or machine's supported helper for the required scope instead of hand-rolling it. A helper's existence does not require setup.
- **Diagnose by path.** An import, binary, or stack frame resolving into another worktree's path means a shared or stale env — delete that env folder **in this worktree only** and re-run the seed/reconcile; never patch paths by hand, never delete the primary checkout's copy.

## Merging and cleanup

- **Release is never automatic.** PR creation, validation, and merging do not authorize the agent to dispatch a release. Release work requires a separate explicit request and a verified repository-documented process; do not trigger or offer one after a merge.

- **Squash merge only** — `gh pr merge --squash`, one PR / one commit. Never merge commits or rebase merges; never squash local dev history.
- **Automerge is opt-in except a standalone prose-only diff, which enables itself.** Prose-only = every changed line is docs (`*.md/.mdx/.rst/.txt`, `docs/**`, `README*`, `CHANGELOG*`, `LICENSE*`), a comment, a docstring, or whitespace; one executable line (code/config/schema/lockfile/CI/test) disqualifies it. On a standalone prose-only diff, `gh pr merge <n> --squash --auto` the moment it exists, say so, don't ask. Elsewhere `--auto` is never yours on your own initiative — offer once for a tests-only/dependency-only/trivial diff and enable only on explicit "yes". Never on a WIP/`DO NOT MERGE`/draft/someone-else's PR; leave a pre-enabled one alone. Safe because `--auto` still waits for CI and required approval.
- **Prose-only self-merge requires the PR to be standalone.** Documentation-only PRs count as standalone under **Documentation PR independence**. Other prose-only PRs are not standalone (and `--auto` not yours) when: part of a multi-PR batch with any sibling open; sharing a `<group-slug>/` prefix with another open PR in any repo; referencing another open PR (link, "depends on", "part of", shared plan slug); or based on another open PR's head. Re-check every pass — enable `--auto` the moment the last companion merges/closes, naming which released it; while deferred, report the blocking links.
- **Clean up the moment a PR reaches `MERGED`** (you merged it, `--auto` landed it, or a poll saw it). Don't hand-roll `git branch -D` / `git worktree remove`; the aliases encode the safety checks:
  - `git clean-worktree` — prunes stale records, removes worktrees whose branch is merged/gone, skips dirty and detached-HEAD ones.
  - `git clean-stale-branches` — deletes locals whose upstream is `[gone]` (what squash-merge leaves); never the default or current branch.
  - A detached-HEAD worktree: `git worktree remove <path>` only after confirming no uncommitted work — never `--force` past a dirty one.
  - Never delete PR memory — it's durable provenance. Remove the worktree, keep the memory.
  - A worktree with unpushed commits or a dirty tree is not reaped silently — work never reached the PR. Report the path and contents, leave it for the human.

## Stuck PRs — retrigger a frozen pipeline

- **Green Actions but a blocked merge is usually a missing check, not a failing one.** Approval, policy, lock, description, and custom-validation gates are check runs posted by org apps; a dropped webhook means the check is never _created_ on the head SHA — not red, not pending, absent — so the branch rule never satisfies and `mergeStateStatus` stays `BLOCKED`. Nothing to `rerequest`; a check never created can't be re-run.
- **Diagnose before touching the branch** — diff required contexts against what posted on the head SHA. Missing = dropped webhook; posted-and-failed = an ordinary red build:

  ```bash
  REPO=<owner>/<repo>; N=<number>
  DEF=$(gh repo view "$REPO" --json defaultBranchRef -q .defaultBranchRef.name)
  SHA=$(gh pr view "$N" --repo "$REPO" --json headRefOid --jq .headRefOid)
  gh api "repos/$REPO/rules/branches/$DEF" \
    --jq '[.[] | select(.type=="required_status_checks")] | .[].parameters.required_status_checks[].context' \
    | sort -u > /tmp/required.txt
  gh api "repos/$REPO/commits/$SHA/check-runs?per_page=100" --jq '.check_runs[].name' | sort -u > /tmp/posted.txt
  comm -23 /tmp/required.txt /tmp/posted.txt   # required but never posted → dropped webhook
  ```

- **The fix is an empty commit on the PR branch** — a new head SHA is what makes the apps re-evaluate. "Retrigger the PR build/checks/stats" means exactly this. Allow a full pipeline duration (~20 min) before judging it failed.

  ```bash
  git commit --allow-empty -m "Retrigger CI checks"
  git push
  ```

- **Empty means empty** — no whitespace tweak, bumped comment, or touch-and-revert; a dummy edit pollutes review/blame and can trip path filters. Say what it is in the subject so a scanner sees it changes nothing. **Confirm the branch first** — this runs on the PR's own branch, never default (an empty commit on default is noise no squash collapses).
- **Approval after an empty push is repository-policy-specific.** Read the repository's rules and re-fetch the review state after the push; do not predict whether approval survives. A real diff can invalidate approval even when an empty commit would not, so never use a content change merely to retrigger checks.
- **A genuinely red Actions job is a different problem** — `gh run rerun <id> --failed` re-runs only the failed jobs, far cheaper than a push.

## Links and references

- **Never hand-build a PR/issue URL** — emit the `url`/`.html_url` field verbatim. Web path is singular `/pull/<n>`; `/pulls/<n>` is REST and 404s on github.com. Issues are `/issues/<n>` on both.
- **A link is four independent facts — owner, repo, `pull` vs `issues`, number — each verified.** Well-formed ≠ correct. Never derive `<repo>` from a folder basename, product name, ticket text, or a sibling repo (`-ui`/`-api`/`-service`/`-web` are _different_ repos with independent numbering) — resolve per Repo Identification. Never guess type; numbering is shared, so `<n>` is at most one of the two. One probe checks all four, and its output is what you print:

  ```bash
  gh api "repos/<owner>/<repo>/issues/<n>" --jq '{url: .html_url, is_pr: (.pull_request != null), state, title}'
  ```

  `.pull_request` is the type discriminator, `.html_url` the canonical path. A `404` means a wrong segment — try the sibling repo, say which candidates you tried, never print an unresolved link. Re-probe any link from memory, a paste, an earlier turn, a ticket, or a commit message — someone else's link is a hypothesis.

- **A bare `#<number>` is a rendering bug, not shorthand.** Clients and GitHub auto-link it relative to the repo in context — for an agent, the cwd, routinely an unrelated workspace repo. This applies to every word you emit, not just link lists: the common slip is a careful list of full URLs then "fixed in #1731". If a number sits next to `#`, write the full path instead, or name the PR with no number. Scan for `#`+digits before sending.
- **Render every reference with its full verified URL.** Follow Link Display for Markdown-capable agent replies and OSC 8 terminal programs. Plain-text clients receive full scheme-prefixed URLs, never backticks or abbreviated targets. Keep URLs first and one per line in lists; trailing context may follow. Preserve each skill's documented machine-readable format; shorthand remains allowed only in prose written into GitHub itself.
- **Show authors when a list isn't all yours** — request `author` in the `gh --json` fields. All yours → omit as noise. Even one different → label the author on every row and say who in the summary. Machine-parseable bare-URL output stays untouched; put the breakdown in surrounding prose.

## Reviewing and babysitting

- **Review setup is evidence-driven** — Review the PR diff, relevant existing local source, callers, tests, and CI evidence before provisioning anything. Verify local source matches the reviewed head; fetch missing source without installing dependencies. Trivial logic often needs no execution. When a concrete uncertainty requires testing, run the smallest useful check with minimal setup under **Worktree dependencies**. Use an isolated worktree if checking out the reviewed head would disturb existing work. Report unrun checks and evidence limits; never claim an unexecuted test passed.
- **Babysitting is opt-in; creating the PR ends the task.** For creation-only requests, create the PR, report the full link, then stop. For implementation requests, share the early link and continue through **PR publication milestones**; early publication is not task completion. Do not poll CI, sleep-and-recheck, start a pass loop, fix an unrequested build, or enable automerge outside the prose-only carve-out. An unrequested watch loop burns unbudgeted hours and acts on the branch while the user's away.
- **Only an explicit instruction starts a watch loop** — `/sy-babysit-pr(s)`, `/sy-review-pr(s)`, or a plain ask that plainly means it ("keep an eye on it", "see it through", "watch CI until green", "babysit this"). "Fix the tests" or a follow-up after the PR exists is a fresh task, not a subscription. Unsure → finish, hand back the link, offer the loop in one sentence; never assume yes.
- **Every review comment is net new** — fetch all review threads, issue comments, and reactions from every author (humans, bots, your own past reviews) first. Route each finding: covered → post nothing, react `+1`; covered-but-missing-a-case → reply in that thread with only the delta (`-F in_reply_to=<id>`, opening "Adding to the above") and 👍 the original; genuinely new → top-level comment. A prior 👎 means already-rejected — don't resurrect without a concrete new reason, stated. A reworded duplicate is still a duplicate.
- **"Already addressed" is proven by the diff** — reply that a thread is handled only after reading `git show <sha> -- <path>` for the cited commit; a commit message saying so is a claim, not evidence.
- **Verify load-bearing claims yourself.** "Unused", "no consumers", "behavior unchanged", "tests cover it", "CI is green", "I audited the callers" are hypotheses — grep the name (string _and_ symbol), open the cited test and read its asserts, fetch the check run, read the call site. What you can't verify from here (another repo, a runtime consumer, manual QA) is asked for by name, never granted. Applies to bot summaries and your own earlier passes.
- **Act on feedback — author identity sets weight, never whether you act.** Every actionable human/bot finding gets a disposition on the pass that first reads it: fixed and replied, declined with a concrete reason, or escalated as a named stop-and-ask. No "surface to the user and move on", no waiting for separate authorization, no deferring the same comment pass after pass. On your own PR, resolve the review thread right after the reply posts when it is fixed (fix pushed, reply cites the SHA) or clearly declined (final reason, reply asks nothing) — no asking first; leave it open only for a question, an alternative awaiting the reviewer's pick, or a stop-and-ask. Your own findings likewise land on the PR (comment, thread, or 👍); one that ends up only in the user's terminal is reported as dropped.
- **Stop-and-ask is surfaced, never prompted** — it pauses that PR for you, not on GitHub. Record `needs_user` in PR memory with the reason, the exact human message, the source (comment/review/thread/check id + its timestamp + the head SHA it was raised against), and the next step. Print that block, keep working the other PRs; never open an interactive prompt, block waiting, or express it on GitHub (no label, status, review, or comment for scheduler state). It's a narrow enumerated exit: restructuring the user's work (splitting, re-cutting branches, changing a base), a change to stated scope or public contract, a `needs-human` conflict/migration, or input you can't obtain. Size, tedium, opinion-shaped feedback, harsh tone, and code you didn't write don't qualify. End-of-run disposition counts sum to the number of open items.
- **Revalidate a prior `needs_user`** against live state before displaying or scheduling it — a fresh session remembers nothing and the thing may have resolved hours ago. Re-fetch the source by id, re-read current reviews/threads/checks/head SHA/body and everything posted since the recorded timestamp. Classify: current, cleared, changed, conflicted (show both), or stale-unknown. Print the prior claim and verdict together, always with a `Next:` line. A cleared claim re-queues the PR and says which comment cleared it.
- **A re-review with nothing new posts nothing** — no verdict, no "still looks good", no re-approval; reactions are the whole output and the no-op is reported to the user, not the PR. One exception: a state flip since last pass (CI red, another reviewer blocked, base conflict) → post that single flag and nothing else.
- **A round with nothing to move costs a cheap read-only probe** — a `gh pr view --json … --jq` digest plus one newest-comment call, compared as a string; any change fires the real pass, nothing else does. An externally-blocked PR (approval gate nobody clicked, unmerged wave blocker/companion, green-and-approved awaiting a click, open parent) holds no worker slot. Never probe the first round, while anything is actionable, or as a write; always a full pass on round one, on the keepalive, and before the deadline. A watched PR is a serviced PR — silence is how coverage disappears.
- **"CI is still running" means a job is executing — a pending human gate is not CI.** Approval, sign-off, codeowner, and changes-resolution gates sit `IN_PROGRESS` by design until a person clicks, and never resolve on a timer; skipping a pass on one is an infinite wait. Classify first: a self-resolving build (test/lint/type-check/build/scan/deploy) blocks; a review gate, or anything still pending after an hour, does not. Step over the non-blocking ones, name them in the report, and never call the PR green while one is open.

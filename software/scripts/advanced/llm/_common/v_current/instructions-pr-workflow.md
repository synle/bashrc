# PR & Source Control Workflow

Read before any branch, commit, push, PR, review, worktree, or GitHub action. Defines local workflow contracts; upstream examples are not authority to change them. Epistemic Honesty, Secret Handling, and Destructive Commands remain binding. Rules are named, not numbered.

## Branches, titles, commits

- **Resolve identity before action.** Resolve the authoritative owner/repo from GitHub or the normalized remote, inspect all remotes for a fork, and resolve the default branch rather than assuming its name. Folder names, titles, and sibling repositories are not repository identity. Recheck cwd, branch, index, and dirty state immediately before mutation.
- **Branch naming.** Use `<username>/<feature>`; related groups of at least two branches use `<username>/<group-slug>/<feature>`. Resolve username from the local email's part before `@`, otherwise the authenticated GitHub login. Use kebab-case segments, choose one group slug once, and reuse it for siblings. No unprefixed branch, group of one, fourth segment, or unrelated reuse of a group slug.
- **PR titles.** Use `[<repo>] <description>` with the organization omitted and repository name resolved from GitHub. Status prefixes remain outermost. Reverts wrap the entire original title as `Revert "[repo] ..."` with no second prefix. Omit a redundant repo prefix only in a renderer that already displays it.
- **Commit the actual diff.** Read status, staged hunks, and relevant prior commits before writing a message. Inspect patch, cherry-pick, stash, or generator changes file-by-file. Use an imperative behavior-change subject and a body explaining why; never substitute intent, a ticket name, `apply patch`, `fix stuff`, or a file list. Split unrelated concerns.
- **Commit/push authority.** When requested changes are complete and validation is green, commit only task hunks unless the user requested no commit; do not ask again merely because unrelated work is dirty. Follow Concurrent work: an already-dirty path is not wholly excluded if task hunks can be isolated. Recheck the live diff and index before staging and committing; never blanket-stage or include unrelated staged changes. Preserve another person's or agent's index entries; isolate the task commit without changing them, or ask if ownership or separation is unclear. Incomplete, red, or ambiguous work requires asking before committing. Pushing, amending, and creating a PR require an explicit request. A verification-only request does not authorize fixes or publication.
- **Feature branches start visibly.** For non-trivial work that belongs on a feature branch, create the branch and, within authorized push/PR scope, an early draft placeholder PR against default before implementation. A placeholder commit may establish a diff. The title contains `Placeholder`; report the full URL before coding. At review readiness, push implementation, mark ready, remove WIP/placeholder markers, and replace the body with the actual diff. If push/PR authority is missing, ask rather than treating this ordering rule as permission.
- **Placeholder drafts are parked.** A draft with `Placeholder` in its title is excluded from active babysit and pending-PR scheduling. A single-PR flow reports it skipped. Implementation plus removal of placeholder state makes it eligible; drafting alone does not start monitoring.
- **Commit identity from history.** Before the first commit, use `git fix-identity` if available to pin the repository-local email from your configured addresses matched against the newest 50 commit authors. It leaves an existing local email alone. Without the helper, perform the same comparison; no match means leave configuration unchanged and report it. Never borrow another author's address.
- **Compare authors before every commit/push.** Compare configured name/email with authors of the outgoing upstream range, falling back to origin's default reference when necessary. Report mismatched SHAs and both identities side by side and ask. The default answer is no: repair authorship only with authorized scoped history editing; explicit yes permits proceeding unchanged. Preserve intentional co-author trailers when resetting authorship.
- **Merge shared branches, never rewrite them.** Resolve/fetch the remote default and merge it into a working branch; no rebase or force-push on shared feature history. The exception is pushing local work to default itself: pull with rebase, then fast-forward push, never add a local merge commit on default. Preserve dirty and unpushed work before synchronization.
- **Plain-English pull means the merge workflow.** On a non-default branch, first synchronize the repository floor/default and all ancestor feature/wave branches root-most to immediate parent, then merge the fork's upstream default last. Use the existing branch-sync workflow when available. The default-branch exception above still wins; never assume a requested `main` or `master` is the actual floor.
- **Solo repositories.** If the newest 200 author emails contain only you and recognized bots/LLM noreply identities, use default directly for an authorized push and say so. An explicit PR request overrides this preference.

## PR bodies and payloads

- **Honor the template.** Before creating or rewriting a body, search tracked pull-request templates. Precedence: `.github/PULL_REQUEST_TEMPLATE.md`, root, `docs/`, then the multi-template folder. Pick the best fit and name it; ask if equally applicable choices change the result. Preserve every heading's order, wording, and level. Replace/delete comment placeholders; mark inapplicable sections `N/A` with a reason and unfinished WIP sections `TODO — <remaining work>`, never drop them.
- **Payload files, not shell strings.** Use Markdown files with `--body-file` for PR create/edit/comment/review and JSON files with API `--input` for REST bodies. Never put body text in a command argument, shell variable, echo/printf, substitution, or inline heredoc. Inspect the human-visible body before posting and delete temporary payload files after capturing success or failure. JSON is transport only, never a serialized request envelope posted as prose.
- **One durable PR memory.** Stable identity is `<owner>/<repo>#<number>`. Other authors' reviews live in `<<LLM_ROOT_FOLDER>>/pr_reviews/<repo-name>_<number>_<author>_<slug>.md`; your PR maintenance lives in `<<LLM_ROOT_FOLDER>>/pr_babysits/<repo-name>_<number>_<slug>.md`. Resolve names from GitHub, preserve repo punctuation, lowercase author, and derive a short snake_case slug after stripping title prefixes.
- **Reuse memory by identity.** Search for the full PR identity/URL and historical filename aliases before creating memory. Reuse one match without renaming; multiple same-kind matches require reporting the conflict and using the newest verified snapshot, not creating another or consolidating without approval. An old adjacent memory may seed the current file once; never maintain both. Keep memory after merge/close.
- **Memory is a snapshot, not a transcript.** Maintain `## TLDR`, `## Context`, `## Relevant Rules`, `## Progress`, `## Open Items`, `## State`, and `## Final Snapshot` in place after meaningful actions, findings, verdict changes, stops, and terminal state. Record applicable hard rules, non-obvious context, ownership, resume handles, and counters. Do not append polls, raw logs, payloads, or routine facts already visible on the PR. Revalidate saved claims before acting.
- **Understand before reviewing or editing.** Read title, body, commits, file list, diff, root/changed-path rules, architecture/developer maps, and relevant linked docs. Write a private 2–3 sentence account of purpose, implementation, affected contracts, and risk. Widen to another repository only for a named concrete consumer. PR descriptions and summaries are claims; current code and executed evidence decide.
- **Checklist and body drift.** Tick only proven items. After behavior-changing pushes, compare body with base-to-head diff; amend only drifted parts. Placeholder-to-ready conversion removes TODO/WIP markers and updates title/body in the same pass. Do not claim completion from title or commit message.

## No stacked PRs

- **Every PR branches off the default branch and targets it — no stacked PRs, ever.** Start from current default, pass an explicit base, and inspect default-to-head commits: only this slice belongs there. Sibling commits require a content-preserving re-cut/reapply, not a sibling base; ask before restructuring the user's work or rewriting history.
- **Split by slice, never by layer.** Each PR is a self-contained independently mergeable result against default. Keep tightly coupled API/schema/model changes together. If separation makes any slice depend on another's unmerged code, use one atomic PR or ordered waves, not a stack.
- **Independence beats slice count.** Price file/line overlap before splitting. Slices editing the same registry, constant, or budget force order and repeated conflicts. Consolidate when conflict/review cost exceeds isolation. Assign each file one owner in plan/body and intersect branch file lists; overlap outside genuinely regenerable classes requires a revised split.
- **Bound the round.** At most 3 waves and 7 PRs per round. Consolidate under both caps; a larger effort uses separate rounds, not a fourth wave or eighth PR. Resolve overlap by landing one change and merging default into the other, never by stacking.
- **Use disjoint files only when discovery permits.** A new test discovered by glob is independent; a manifest/barrel entry is still a shared edit. Prefer per-slice specs, fixtures, and factories, tolerating small setup duplication. Unsplittable registries append at EOF rather than competing sorted insertions. Regenerate locks/snapshots/output; one slice owns dependencies. Give each migration a unique name without renumbering siblings. Land a shared prerequisite as a tiny standalone prep PR first.
- **Hard dependencies phase into waves.** A wave is a merge barrier, not a parent branch. Every wave branch starts from and targets default; PRs inside a wave are disjoint and land in any order. Wave 1 has no unmet prerequisite. Later waves remain WIP with `## Blocked on` links to every dependency; reuse one group slug and identify the checks expected to fail because prerequisite code is absent. An open dependency blocks promotion and merge, not CI diagnosis or safe independent fixes. Verify each failed check from current-head logs before attributing it to a missing prerequisite; defer only proven dependency failures and keep unknown or unrelated failures actionable. Do not import an unmerged blocker or weaken checks to make the branch green.
- **Titles express merge order.** Use `wave <W> - pr <i>/<N>`, numbering across the entire set so later-wave numbers exceed earlier ones. Choose a stable order within a wave. Any dependency-graph change re-derives and renumbers the whole set, including blocked-on prose, requesting threads, and an old-to-new announcement; a newcomer never simply appends by creation time.
- **Promote only after the barrier.** Blocker merged, merge default, CI green, then remove WIP, in that order, and only if dependency blocking was the sole WIP reason and no TODO remains.
- **Migrations preserve deployment compatibility.** Wave 1 expands compatibly, wave 2 backfills/dual-writes, wave 3 contracts only after full deployment. Renames follow add-new, dual-write, backfill, read-new, drop-old; never a single destructive rename PR. If the first wave cannot remain backward compatible, redesign or ship one atomic change with approved recovery.
- **Existing stacks are containment work.** Name the unintended stack; do not copy the pattern, rewrite pushed history, retarget ancestors, or merge children upward. Walk at most 10 unique ancestor hops to the floor, stop on repeats, and merge floor then root-most ancestor through immediate parent with conflicts resolved between merges. A long-lived non-default release/integration floor without a PR is not silently replaced by default. Never push ancestors. Green and approved children remain blocked until the parent's merge; report that link and use the existing sync workflow when available.

## Worktrees and fan-out

- **Use the sanctioned creator.** PR-branch work never runs in the primary checkout. Use `worktree_create` unless repository rules name their own helper; never hand-roll its path, mkdir, or `git worktree add`. The helper fetches, reuses existing links, preserves unpushed commits, refuses primary reuse, and may fall back detached. Outside the target repository, clone outside the container first and invoke the helper there. Remove only worktrees you created.
- **Canonical paths are helper output.** `worktree_create --path-only <branch>` is read-only and derives `$HOME/.worktrees/<owner>/<repo>/<sanitized-branch>` from origin. The leaf keeps `[A-Za-z0-9._-]`, collapses other runs to `_`, and trims leading/trailing `._-`. Reuse an existing legacy linked path without moving it; report it and use canonical output for new work.
- **Dispatch a batch in parallel.** One worktree/job per PR, launched together rather than one assistant turn per job. Each assignment includes full URL, resolved owner/repo, PR number, worktree, and sibling list. The dispatcher does not enter worktrees or alter primary; report once at the end. Repository-wide cleanup is the explicit sequential shared-checkout exception.
- **Enroll all work before capacity scheduling.** Read a declared concurrency cap by name; absent declaration means no assumed cap. Rank unshipped local work, awaiting replies, broken-and-ours, stale, bot nits, external waits, then drafts, oldest untouched first within a tier. Launch up to capacity and hand each freed slot to the next item. Age the queue; never silently drop low-ranked scope.
- **One stable job owner.** Key jobs by work, such as `<command>:slot<i>` or `<command>:<owner>/<repo>#<number>`, and record key plus returned resume handle immediately in the assignment, memory, and ledger. Match live jobs before dispatch: leave running owners alone, resume idle ones, and create only unowned jobs. Duplicate owners risk double-push/comments; keep the older, cancel only the duplicate you launched, and report it.
- **Resume idle; relaunch only dead.** A finished turn does not destroy a job's context. Resume it cheaply; relaunch only confirmed failed/cancelled/gone jobs from verified ledger state with their remaining work. Never merge a dead job's queue into a live neighbor. One long-lived job runs its own per-PR passes; do not spawn a cold child each round.
- **Await every dispatched job.** Never end a turn while its jobs remain in flight. Complete the round and final report before another; a deadline does not permit dispatching work that cannot be awaited.
- **Watch budgets are clocks, not pass counts.** Use the command's configured budget/intervals, cheap read-only probes between full passes, keepalive passes, and a final pass before deadline. Do not duplicate numeric intervals here. Finish an in-flight pass to a safe point, mark inbound changes dirty, then requeue; your own writes do not count as external activity. Explicit PR scopes stop when all close/merge; search scopes re-resolve and wait through empty rounds. Persistent service unreachability ends after a bounded retry window. Stop-and-ask parks that PR but keeps probing for a reply; every stop saves resumable memory.

## Worktree dependencies

- **Share caches, isolate environments/output.** Machine-wide content-addressed package/runtime/compiler caches may be shared. Every worktree owns `node_modules`, `.venv`, and other installed environments; `dist`, `target`, build folders, and test caches are never shared. Never symlink environment or output folders across worktrees: real-path resolution, editable installs, and concurrent writes silently cross branches.
- **Cache location matters.** Verify caches resolve outside checkout; a repo-local package/cache folder stays per-worktree. Use the build tool's content-keyed cache instead of shared output, and assign unique server/debug/test ports per worktree.
- **Install only for execution.** Docs/read-only review needs no install. At first code/test/build need, prefer the repo/machine bootstrap helper; otherwise use cache-first locked installs from this worktree's lockfiles. Honor secret/destructive gates; disable lifecycle scripts until each required script is read and approved.
- **Reuse a verified environment only.** After success, record hashes of every lockfile root. Skip reinstall only when hashes match and this worktree's own environment exists. Monorepos reconcile at each lockfile root. Do not clone large dependency trees by default; an exception requires measured benefit and reconciliation. Never clone absolute-path-bearing environments such as Python venvs or editable installs.
- **Reuse the runtime, not another checkout.** Use existing machine-managed interpreters/toolchains and shared content-addressed build caches; never download/compile a runtime per worktree or point several worktrees at one build-output location. Expect the first fresh environment to pay startup/cache-fill cost; compare subsequent fresh worktrees for performance claims.
- **Prove isolation.** Resolve an actual project import/binary after install and confirm this worktree owns it. A stack frame/import into another checkout is evidence of stale/shared state. Recreate only the verified disposable environment in the affected worktree, with destructive approval when unrecoverable files may be present; never patch absolute paths or delete the primary environment.

## Merging and cleanup

- **Squash merge only.** One PR becomes one commit. Never merge commits or rebase-merge; never squash local development history as incidental cleanup.
- **Automerge has a narrow exception.** A standalone prose-only PR enables squash auto-merge as soon as it exists, with a user report. Every changed line must be docs, comments, docstrings, or whitespace; any executable code/config/schema/lock/CI/test line disqualifies it. Otherwise offer auto-merge once only for tests-only/dependency-only/trivial work and enable only after explicit yes. Never enable it on WIP, DO NOT MERGE, drafts, or another author's PR; do not alter a pre-enabled setting.
- **Prose-only self-merge requires the PR to be standalone.** Defer while any sibling in the batch is open, an open PR shares its group prefix in any repository, it references an open dependency/companion/shared plan, or its base is an open PR head. Recheck every pass, report blocking links, and enable only after the last companion merges/closes, naming what released it. Docs never land ahead of code they describe.
- **Clean up at merge, without losing work.** Use `git clean-worktree` and `git clean-stale-branches` when available; do not hand-roll forced branch/worktree deletion. Helpers skip dirty/detached worktrees and default/current branches. A detached worktree can be removed only after verifying no uncommitted work, never with force. Dirty or unpushed work is reported and preserved. Keep durable PR memory permanently.

## Stuck PRs — retrigger a frozen pipeline

- **Diagnose missing versus failed checks.** Green Actions plus a blocked merge can mean an organization/app-required check was never posted to the current head. Compare all required contexts with paginated check runs/statuses on that exact SHA; absent, failed, running, and human-gated are different states. An absent webhook/check cannot be rerequested as if it existed. Do not assert the cause solely from a blocked merge label.
- **A requested retrigger is an empty commit.** Once missing check creation is confirmed, a request to retrigger PR builds/checks means an empty `Retrigger CI checks` commit and push on that PR branch only, within commit/push authority. Never use whitespace, comment churn, touch-and-revert, or default-branch noise. Allow the full pipeline duration, approximately 20 minutes where applicable, before judging it failed.
- **Read policy after the push.** Approval survival is repository-specific; reread rules/reviews on the new head rather than predicting it. Real content edits can invalidate approval even when an empty push would not. A genuinely red Actions job is separate: use the failed-job rerun when authorized instead of a new content/empty push.

## Links and references

- **PR tooling discovery.** Before listing PRs or declaring collection/rendering unavailable, read the `sy-list-prs` skill's **Fetch PR data** and requested **Output format** sections. Check the canonical `list_prs` executable, not only optional `pr_list_*` shell wrappers; collection and Markdown rendering have separate availability checks.

- **API-returned links only.** Emit the verified `url`/`html_url` rather than constructing it. Verify owner, repository, issue-versus-pull-request type, and number independently; the issues endpoint's pull-request discriminator distinguishes the shared numbering space. A 404 is unresolved identity/access, not license to invent a sibling link. State candidates actually tried and never print an unresolved link. Re-probe remembered, pasted, ticket, or commit-message references before acting.
- **A bare `#<number>` is a rendering bug.** Outside GitHub-authored prose, use the full verified reference or omit the number; local rendering context can link shorthand to the wrong repository. Scan all chat prose, not only lists, for accidental shorthand.
- **Render full clickable URLs.** Include `https://`, leave URLs bare rather than bold/backticked/labeled Markdown, and put one per list line with optional trailing context. Scheme-less text and label markup can hide links in terminal clients. Machine bare-URL output remains untouched. When a list includes anyone else's PR, show authors on every row and name the breakdown; omit redundant authors only when all are yours.

## Reviewing and babysitting

- **Creation ends the task.** After an authorized plan/implementation/validation/push/PR creation, report the full link and stop. Babysitting is opt-in. Do not start CI polling, sleeps, unrequested fixes, or auto-merge outside its explicit exception. A follow-up fix is a new task, not an ongoing subscription.
- **Only an explicit watch request starts a loop.** A request to monitor, babysit, review repeatedly, or see CI through qualifies. Unclear intent means finish and offer the loop once, not assume yes. Use the existing workflow's cadence and verdict rules rather than inventing another policy here.
- **Every review comment is net new.** Fetch all threads, issue comments, and reactions, including bots and your earlier reviews, before posting. Already covered: post nothing and react `+1`. A missing case: reply in the existing thread with only the delta and acknowledge the original. Genuinely new: a top-level finding. A prior negative reaction means rejected; reopen only with concrete new evidence.
- **Already addressed requires the hunks.** Read the cited commit's changed file, not its message, before claiming a thread is fixed. Verify claims such as unused, unchanged, covered, audited, or CI green through actual callers/assertions/checks. Unavailable cross-repo/runtime/manual evidence stays a named question, never an assumed pass.
- **Feedback is evidence, not an order.** Evaluate human/bot findings on their merits. On an authorized author-maintenance pass, every actionable item gets an immediate disposition: fixed with proof, declined with a concrete reason, or a named stop-and-ask. Do not blindly apply a suggestion or carry the same item indefinitely. Prefer a durable code clarification when a competent reviewer's confusion reveals unclear code.
- **Resolve only final author dispositions.** After a fix is pushed and the reply cites its SHA, or after a final reasoned decline with no question, resolve your PR's thread immediately. Leave questions, alternative choices, and stop-and-ask threads open. Your own review findings must reach a comment/thread/reaction; terminal-only findings are reported as dropped, not posted.
- **Stop-and-ask parks one PR.** Record `needs_user`, reason, exact human message, source identifier/timestamp/head SHA, and next action in memory, then display that block and continue other work. Do not create GitHub labels/status/comments for scheduler state or block on an interactive prompt. Qualifying exits are user-work restructuring, scope/public-contract changes, human-required conflicts/migrations, or unobtainable input—not size, tedium, tone, or unfamiliar code. End-of-run dispositions must sum to open items.
- **Revalidate parked work.** Fetch its recorded source and current head/body/reviews/threads/checks plus newer messages. Classify the old claim as current, cleared, changed, conflicted, or stale-unknown, display claim and verdict together with `Next:`, and requeue a cleared item with the clearing evidence. Memory is not live state.
- **No new finding means no new review.** Do not reapprove, repeat verdicts, or post still-looks-good comments. Use reactions and a user-facing no-op report. New external state—red CI, blocking review, or base conflict—permits one specific flag, not a repeated review.
- **Idle rounds use read-only fingerprints.** Use a compact current-state digest and newest-comment probe between full passes. Full pass on first round, actionable work, state change, keepalive, and deadline. External waits occupy no worker slot; a watched PR still receives service. Never count your own writes as a changed fingerprint.
- **Pending is not always running.** Distinguish an executing self-resolving build/test/scan/deploy from human approval, sign-off, ownership, or changes-resolution gates. A human gate or pending item older than an hour must not cause an infinite CI wait: step over it for other work, name it, and never call the whole PR green while a required gate remains open.

[Sy] Babysit your own open pull requests with the single-PR readiness contract: bot clearance, CI, mergeability, and migration validation. Preserve approval unless verified blockers require repair. Enroll every selected PR, rank work owed, and service it in isolated worktrees through reusable background jobs.

**Whose PRs, and what this does to them — the one distinction to get right.** This command works on **PRs you authored**, and it **changes them**: it pushes commits, merges the base branch in, replies to review threads, and can enable automerge. That is why the default scope is `@me` and why it must never be pointed at a teammate's PR — pushing to someone else's branch rewrites work you do not own, and answering their reviewers speaks for them. The sibling `/sy-review-prs` is the opposite: it reviews **other people's** PRs and only ever leaves feedback. If the ask is "review the team's PRs / give a verdict / leave comments", that is `/sy-review-prs`, not this. Someone else's PR belongs here only when they explicitly hand it over — say whose it is and what you pushed.

**This is the command for "sync all my PRs with main, preserve approval, and fix only blocking failures — all at once, in the background, with worktrees."** Every part of that ask is already in scope: the branch sync is `/sy-babysit-pr` Step 5, which delegates to `/sy-sync-pr-branch` (default branch + the whole ancestor chain on a stack); comment remediation is conditional in Steps 6–7 and activates only for failed CI, a base merge conflict, a stale migration head, an active `CHANGES_REQUESTED` review or one verified major finding, regardless of comment count; background + worktree + all-at-once is Step 4 below. Route any plain-English phrasing of that request here — do not hand-roll a loop, and do not call `/sy-sync-pr-branch` yourself first; every job already runs it.

**Recommended order.** Run `/sy-review-prs` first (verdict pass), then `/sy-babysit-prs` (this command). Reversing wastes babysit cycles on PRs that would be requested-changes anyway.

Argument: $ARGUMENTS (optional — selects scope; the first token decides the mode, no mixing). Every mode below stays scoped to **your own** PRs unless a PR is named explicitly.

- **Empty** — babysit every open PR authored by `@me` for git repos at or below cwd, two levels deep (see Repo discovery). (Default behavior.)
- **PWD keyword** — first token (case-insensitive, trimmed) is one of the PWD keyword set defined in `/sy-list-prs`. Scan repos up to 2 child levels below cwd and babysit `@me` open PRs in those repos only.
- **Explicit PR refs** — one or more whitespace-separated PR refs. Each ref is one of:
  - full URL: `http://github.com/<owner>/<repo>/pull/<n>` or the HTTPS equivalent
  - shorthand: `<owner>/<repo>#<n>`
  - bare `#<n>` or bare digits `<n>` — only valid when the current working directory is a git repo with a GitHub `origin`; resolve `<owner>/<repo>` via `git remote get-url origin`, never from the folder name (see Repo Identification).

## Readiness goal

Batch default: `goal=watch`; explicit `goal=ready` selects the single-PR readiness exit. Strip this token before scope parsing and rendering.
Strip `feedback=blockers` or `feedback=all` before scope parsing/rendering; default to blockers unless an explicit caller or saved state selects otherwise. Reject unknown modes before dispatch.
Pass the selected `goal`, `feedback`, caller `automerge_policy`, and all readiness provenance to every worker. Preserve explicit `observe_only` across the ledger and handoffs; never infer normal policy from a missing token. Apply the single-PR **Readiness contract**; never implement another bot-clearance or migration policy here.
A verified `READY` row is terminal only under `goal=ready`, after final verification, the selected feedback gate, and owned-workspace cleanup. Strict rows require verified zero unresolved review threads and zero unaddressed actionable top-level comments; the read-only driver never resolves them itself. `NEEDS_USER` remains parked, never successful.
In explicit-ref scope, all rows verified ready/merged/closed ends a readiness run. Search scopes still re-resolve through their deadline; a changed head/base invalidates a saved ready result.
Read-only drivers may collect readiness evidence; required actions and cleanup resume the existing owner. Preserve gate evidence, bot policy, reviewed SHAs, and repair counters in the ledger.

## Execution mode

Background agents are default. Resolve, sort, announce, and enroll the complete PR set first, then dispatch the existing slot jobs in parallel and await every dispatched or resumed job before the turn ends. Explicit foreground signals are `foreground`, `fg`, `inline`, `blocking`, `synchronous`, `sync`, or `wait`; strip that token, keep the same author-lens ranking and queue order, then execute enrolled PRs inline in that order without background agents. Never change scope, sorting, enrollment, worktree reuse, state checkpoints, or pass cadence based on mode.

## Steps

1. **Resolve target PR list from `$ARGUMENTS`.** Pick exactly one branch:

1p. **Drop placeholder drafts before ranking or dispatch.** For every resolved PR URL, fetch `gh pr view <url> --json isDraft,title,url`. If `isDraft` is true **and** the title contains `Placeholder` (case-insensitive), remove it from the babysit set and report it as `skipped placeholder draft pending implementation`. These PRs are intentionally parked before implementation starts and should not consume a slot, probe loop, or watch budget. They re-enter scope only after code lands, the PR is marked ready, and the placeholder markers are gone.

a. **Empty `$ARGUMENTS` or PWD keyword** — delegate to `/sy-list-prs short pwd` (scope = pwd, format = short). Parse the emitted URLs (one full PR URL per line, grouped under `##` headings). **Do not pre-filter the READY TO MERGE group, or any other group** — a green PR still gets a slot and still gets its passes, and `/sy-babysit-pr` Step 4's early exit is what turns each of those passes into a cheap documented no-op. Pre-filtering here is how a PR ends the run with zero passes, which is exactly what Step 3b exists to make impossible; it also assumes "green right now" means "green in 90 minutes", which a fan-out this long routinely disproves. If zero PRs resolved, report it and run idle rounds (see _An empty or fully terminal ledger_ below) — a search scope is re-resolved every round, never ended because it is empty right now.

b. **Explicit PR refs** (any other `$ARGUMENTS` — treat as whitespace-separated tokens):

- For each token, normalize to a full PR URL:
  - Full URL → accept HTTP or HTTPS; normalize to HTTPS before requests and de-duplication.
  - `<owner>/<repo>#<n>` → expand to `https://github.com/<owner>/<repo>/pull/<n>`.
  - `#<n>` or bare digits → require cwd to be a git repo; resolve `<owner>/<repo>` via `git remote get-url origin` (never from the folder name), then expand. If cwd is not a git repo, error out naming the unresolvable token and ask the user to use a fully-qualified ref.
  - Anything else (not a URL, shorthand, `#<n>`, or digits) → error out, name the bad token, do NOT silently skip.
- For each resolved URL, fetch metadata to match the search-result shape used downstream:
  `gh pr view <url> --json number,title,headRefName,baseRefName,isDraft,url,createdAt,updatedAt,author`. **`gh pr view` has no `repository` field** (see the `gh` field traps in `/sy-list-prs`) — the owning `<owner>/<repo>` is the one you already resolved from the ref itself.
- De-duplicate by URL.

2. **Announce:** Tell the user which scope mode was resolved (`pwd scan of <N> repos` for empty/PWD args, or `explicit list of <N> PRs`), how many PRs were resolved, how many placeholder drafts were dropped, and list the PRs that remain (repo, PR number, title). If any resolved PR is authored by someone other than you (`gh api user --jq .login`), include the author on every listed PR and call the split out explicitly — explicit-ref mode does not filter by author, so babysitting someone else's PR is easy to do by accident.

   **Also announce the stacks.** Stack detection needs `headRefName` + `baseRefName`, and **the PWD path does not have them yet** — `/sy-list-prs short` deliberately skips the per-PR branch fetch (see its Fetch PR data notes), so only the explicit-refs path of Step 1b has them already. Fill the gap the same way `/sy-review-prs` does: one `gh pr view <url> --json headRefName,baseRefName` per resolved PR, which is also the call whose result the worktree path depends on. Then detect stacks from the set itself: any PR whose `baseRefName` equals another PR's `headRefName` is stacked on it. Chain those links and print each stack bottom-up (`<root link> ← <child link> ← <grandchild link>`), noting that they merge in that order. This is display only — it does not change dispatch (Step 3b still assigns every PR before anything launches) and it never makes one job wait on another.

   **Also announce the waves.** A wave is a merge barrier, not a branch parent (see the _Hard dependencies phase into waves_ rule), so it is invisible to the stack detection above — every wave PR targets the default branch. Read each resolved PR's body (`gh pr view <url> --json body,isDraft,title`) for a `## Blocked on` section or dependency prose (`depends on <link>`, `blocked by <link>`, `part of <link>`), and resolve each named blocker's real state. Print the waves in merge order with each blocked PR's parked shape (`wave 2: http://github.com/acme/web/pull/7 (draft, WIP prefix) — blocked on http://github.com/acme/api/pull/40`). **When the set carries `wave <W> - pr <i>/<N>` titles, check `<i>` against the wave graph you just resolved and report any that disagree** — a number below a lower wave's, a duplicate, or a stale `<N>` means the titles encode creation order rather than merge order (see the _A sequence number in a title is MERGE order_ rule). Report the corrected positions; the retitle itself is the per-PR job's, on its own pass. **Re-run this check on every pulse, not only at dispatch** — the set is re-resolved each time, and a PR that appeared mid-run (a new slice, or a follow-up a reviewer asked for) changes the ordering and `<N>` for everyone. Place it by its dependencies rather than at the end, re-derive the whole order, and name every PR whose position moved. **Hand every blocked PR's blocker links down to its worker** (Step 4) — that context is what `/sy-babysit-pr` Step 4a promotes on, and a job that was never told cannot see a wave from its own branch. The dispatcher itself never edits a title, never undrafts, and never rewrites a body: promotion is the per-PR job's, on its own pass.

3. **Render the resolved PR set as a table** so the user sees exactly what is about to be babysat. Delegate to `/sy-list-prs table <same-scope-token>` — `/sy-list-prs` accepts the same scope vocabulary as this command (empty / PWD keyword / explicit refs), so pass the same scope `$ARGUMENTS` (prefixed with `table`) and let it render. Single source of truth for the table layout lives in `/sy-list-prs`.

3a. **Open the ping-pong pulse — emit the FIRST one before dispatching anything.** Render `/sy-list-prs pingpong <same-scope-token>` with every Agent cell at `⚪ NOT STARTED`. This is the baseline the user compares every later pulse against; a fan-out that goes quiet for an hour before its first status line is the exact failure this exists to prevent. Layout lives in `/sy-list-prs` — do not hand-roll it. **This includes the baseline.** Emit the full four-column board (`PR | Description | Status | Agent`) — the PR cell carrying one bare `http://github.com/<owner>/<repo>/pull/<number>` URL, the Description cell carrying author, head branch, title, creation date, and auto-merge state `·`-separated in the documented spans, exactly as `/sy-list-prs pingpong` specifies — never a condensed stand-in with elided paths, invented columns, or a bespoke header, and never `<br>` inside a cell. A baseline in a different shape than the pulses that follow it cannot be diffed against them, which is the only reason it is printed first.

Start the **agent ledger** here: one row per resolved PR holding its **stable job key (`sy-babysit-pr:<owner>/<repo>#<number>`) and the handle of the live job that currently owns it** — the pair every later turn matches on before it dispatches anything, so a re-invocation, a requeue, or a recovery adopts the running job instead of spawning a second one onto the same PR — plus its ledger state (`active` / `queued` / `watching` / `terminal`), pass count, **slot number when active and queue position when queued**, first dispatch time, last pass start / end, next pass ETA, **that PR's latest `## State` block verbatim** (the round counter, per-check attempt counters, `automerge_decision`, and workspace path + kind + ownership that `/sy-babysit-pr` hands back after every `pass=single` pass), and its `activityAt`, activity band (`active` / `stale`), queue-aging count, plus the **last rendered pulse snapshot** (Status change marker, color emoji, and fragments, plus the Agent counters). The state block is not bookkeeping trivia — it is the only copy of what a re-invoked per-PR job cannot remember, so the next round's prompt is built from it and a replacement job for a dead slot is seeded from it. A ledger without it makes every pass a first pass. The snapshot is what `/sy-list-prs pingpong` diffs to pick the `Δ` / `▫️` / `🆕` change marker and write the `Δ` line — overwrite it with what was just printed after every pulse, so each pulse compares against the one immediately before it. Record the ledger state and slot for every PR from enrollment onward (Step 3b), queued and watching ones included: the pulse groups its board by feature set and prints `🌊 slot <N>` on every active row, and a missing state silently degrades that row to an ungrouped one. Record every timestamp the moment it happens (dispatch, pass start, pass end, next-pass ETA) — the pulse's `started 17:12 · running 22m` clock is read straight from this ledger and cannot be reconstructed after the fact. Never snapshot the elapsed duration itself; it is recomputed at render time and is deliberately excluded from the diff. The ledger is this command's bookkeeping; `/sy-list-prs` only renders it.

3b. **Enroll every PR, rank them, then fill the worker slots from the top of the queue.** The harness caps how many background jobs can run **at once**; it does not cap how many PRs the run covers. Every resolved PR is enrolled in the ledger before anything launches, and `S` limits only how many are being **actively worked** at the same moment — a PR that is merely being polled holds no slot. This is what makes "EVERY open PR in scope" true rather than aspirational, without stranding anything behind a lane.

- **Resolve `S`, the concurrency cap.** It is a property of the harness, never of this command, so this command names no number. Resolve in this order: a `cap=<positive-int>` token in `$ARGUMENTS` or the user naming a cap in prose wins; otherwise the **harness concurrency cap** declared in your harness's own instructions, if it declares one; otherwise there is no cap and `S = N`, one job per PR. Reject anything that is not a positive integer — fall back to the next source down and say so, because `S = 0` makes `i mod slot_count` a division by zero and `S < 0` makes the whole assignment meaningless. **Strip the `cap=` token from `$ARGUMENTS` before any scope parsing**, and never forward it to `/sy-list-prs`; left in place it is read as a PR ref by Step 1 and as a scope token by every delegated render. Say which value you used and where it came from.
- **If the launch is partially rejected, cancel and relaunch — never inject the rejects into a running slot.** Slot prompts are immutable and self-contained by design (Step 4), which is exactly why a live slot cannot be handed extra PRs; the dead-slot rule forbids the same mutation for the same reason. When only `k` of `slot_count` jobs actually start:
  - **`k == 0` is a launch failure, not a cap discovery.** Report it and stop — do not set `S = 0`, which makes `i mod slot_count` a division by zero and would "recover" into launching nothing at all.
  - **Cancel the `k` that started and confirm each one is actually terminated before relaunching.** Two jobs on one PR is worse than a stranded PR: they push over each other, double-comment, and race on the same worktree.
  - **Collect what the cancelled jobs already did.** A first pass is short but not empty — a job may already have pushed a fix, posted a comment, or enabled automerge. Take each PR's `## State` block from the ledger (jobs report ownership changes the moment they happen, precisely for this) and seed the relaunched slots with it, so previously-enabled automerge is not misread as `pre_existing` and already-done work is not repeated.
  - Then set `S = k`, refill from the top of the ranked queue, and launch that set in one message. A cancelled first pass costs almost nothing. Report the discovered cap and the refill, since the new ledger supersedes the one already announced.
- **Rank all `N` resolved PRs by the work-owed ranking, read through the AUTHOR lens** (the default) — the canonical ranking lives in `/sy-list-prs` (`## Work-owed ranking`), including P0–P6, activity bands, queue aging, and tiebreakers. Request scheduler data with `pr_list --json --activity`; do not change ordinary `pr_list` calls. Use author tier order, then active before stale and newest `activityAt` first within equal urgency. A stale PR waiting through `3` queue selections, or `1` full run without a pass, receives an aging promotion within its current band and tier. Do not restate or re-derive the ranking here; read it there. Say which lens you used, the activity band, `activityAt`, and aging count when reporting the ledger. Ranking decides **order only** — it never removes a PR from the set.
- **Every enrolled PR is in exactly one of four states, and only one of them costs a slot:** `active` (a worker is running a full pass on it — consumes a slot), `queued` (owed a full pass, waiting for a free slot — costs nothing), `watching` (nothing actionable; the dispatcher polls its fingerprint from the pulse — costs nothing), `terminal` (GitHub merged/closed, verified explicit ready-goal completion, or a workflow-defined final escalation; never a parked decision). A PR moves between them freely; nothing is ever dropped from the ledger.
- **Launch `min(N, S)` workers from the top of the ranked queue, all at once.** The highest-ranked PRs each get their own worker, so every one of them is serviced immediately. When a worker finishes a pass, its PR moves to `watching` or back to `queued`, the slot frees, and the next PR by rank takes it.
- **Every PR is enrolled before the first job launches.** A resolved PR missing from the ledger is a bug in this step, not a backlog — go back and enroll it. `queued` is not stranded: it is next in line, and the ledger says so.
- **Report the ledger at dispatch** — every PR with its tier and starting state (`http://github.com/acme/api/pull/51 (P1) active — slot 1`, `http://github.com/acme/web/pull/7 (P5) queued`). This is the artifact that proves nothing was stranded, and it is the first thing to check when a PR looks ignored.
- **Warn — do not refuse — when the queue is more than 3× the slot count.** `N > 3 × S` means a PR can wait through several passes before its first, so the run stretches. Say so, name the number, and carry on; servicing all of them slowly beats servicing `S` of them and abandoning the rest.

3c. **Concurrent-migration cross-check — run it BEFORE dispatching anything, over EVERY open PR in each repo, not just the ones being babysat.** Once the fan-out is in flight the jobs run concurrently and cannot be handed shared context, and a per-PR job only ever sees its own branch. Merge ordering across a shared migration DAG is a property of the whole set, so the dispatcher is the only thing positioned to compute it.

- **Scope is every open PR in every repo the resolved set touches** — `gh pr list --repo <owner/repo> --state open --json number,url,title,headRefName,author,autoMergeRequest --limit 100` per repo. Deliberately wider than the babysit set: a migration PR nobody asked you to babysit still collides with one you are, and a PR with automerge already on can land mid-run without any job watching. Filtering to babysat PRs, or to automerge-on PRs, would hide exactly the collisions that break the default branch.
- **Keep the ones that add a migration file** (detection table: `/sy-sync-pr-branch` Step 7 — do not restate it). `gh pr diff <n> --repo <owner/repo> --name-only` per candidate. Zero or one hit across the repo → nothing to coordinate; say so in one line and move on.
- **Record the floor head once, at dispatch,** and hand it to every job: the current migration head on each repo's default branch. A job that knows the head as of dispatch can tell "I was always stale" from "the head moved under me mid-run", which is the difference between re-parenting once and re-parenting every pass.
- **Two or more migration PRs in one repo → compute a merge order and pass it down.** Rank them by whichever must land first (ready-to-merge and automerge-on first — those land without a human), then hand each job its position plus the full pairing. Whichever lands second re-parents; that is the job's own Step 4 override doing the work, not something the dispatcher fixes. **Never re-parent, push, or reorder anything from here** — the dispatcher coordinates and never touches a branch.
- **Name the pairs in the announcement and in the Step 5 final report,** with each PR's automerge state. An unattended `--auto` PR sitting behind another migration is the single highest-risk row in the set, and the user should see it before an hour of passes starts, not after.

4. **Fan out one background job per SLOT — all at once, in parallel.** Do NOT walk the list sequentially.

   **Dispatch mechanics — this is the step agents get wrong.** "In parallel" is a hard requirement, not a hint:
   - **Emit every slot job in ONE assistant message with `slot_count` tool calls in that same message.** One sub-agent / Task / background-shell invocation per slot, all in a single block. A second message per slot is a sequential loop wearing a parallel costume — that is the failure mode this section exists to prevent.
   - **Never** `for pr in ...; do ...; done`, never "start job 1, wait, start job 2", never a staggered launch. Every slot starts at the same instant.
   - **One slot = one job = one lane. When `N ≤ S`, one slot holds exactly one PR** and this is the classic one-job-per-PR fan-out. A slot only holds several PRs because there were more PRs than slots — that is the carve-out to the "never a single job that iterates the PR list" rule, and it is the _only_ one: a slot iterates **its own assigned PRs**, never the whole list, and never a list it chose itself.
   - **Jobs share nothing** — no cwd, no branch, no state file, no conversation. A slot job must never read another slot's result or wait on it. Within a slot, each PR still gets its own worktree; the slot switches between them, it does not merge them.
   - **Give every job an identifying label, and a PR-specialized worker when one exists.** Where the environment lets a dispatched job carry a short label, set it to `<PR number> - <head branch> - <author>` for the PR that job starts on (drop the author when every PR in the set is yours). Where the environment offers a worker specialized for babysitting a pull request, dispatch to that one rather than the generic default. Both are cosmetic-only: a run that can do neither is not degraded, and neither ever changes scope, ranking, assignment, or cadence. They exist because a board of identically-named workers is unreadable the moment a fan-out exceeds two slots — the operator cannot tell which lane stalled.
   - **Each slot job's prompt is self-contained.** Pass, explicitly: its **ordered list of assigned PRs** with each one's tier, and for every one of them the full PR URL, the resolved `<owner>/<repo>` (from `git remote get-url origin`, never the folder name), the PR number, the head branch, the canonical worktree path `$HOME/.worktrees/<owner>/<repo>/<sanitized-branch>` (what `worktree_create "$BR"` produces), **the full list of every other PR URL in the whole dispatched set** — all slots, not just this one (its batch siblings, needed by `/sy-babysit-pr` Step 2c's companion check so a docs PR does not merge ahead of the code), and **the stack position from Step 2 when that PR is in one** (its ancestor PR links bottom-up and its children, so the job knows it must not merge before its parent), and **its migration coordination context from Step 3c when that PR adds a migration** (the floor's migration head as of dispatch, the other open migration PRs in that repo with their automerge state, and this PR's position in the computed merge order — a job cannot see any of that from its own branch). Sub-agents start with a fresh context — anything you don't pass, they don't have.
   - **Do not pre-create worktrees from the dispatcher.** Each job owns the worktree lifecycle of every PR it holds (`/sy-babysit-pr` Step 5a create/reuse and cleanup). The dispatcher never runs `git worktree add`, never `cd`s anywhere, and never touches the user's primary checkout.
   - **A cancelled fan-out leaves live worktrees — re-running resumes them, it does not start over.** Jobs killed mid-flight (session ended, run cancelled, machine slept) leave dirty worktrees and unpushed commits at the canonical paths. That is recoverable state, not garbage: `/sy-babysit-pr` Step 5a picks each one back up, and the Step 3b ranking scores exactly that state as **P0**, so a resumed run services it first. Never pre-clean `$HOME/.worktrees` before a fan-out, and never pass jobs an instruction to reset or re-clone.
   - **Report the fan-out the moment it's launched** — the ledger from Step 3b, with every PR's state, job, and worktree path — so the user can see the whole set covered, not a prefix of it.

   **Adopt before dispatch.** Follow the shared PR-loop owner contract with stable slot key `sy-babysit-prs:slot<i>` and per-PR key `sy-babysit-pr:<owner>/<repo>#<number>`. Record handles immediately; never create another owner for the same PR.

   **What a worker does — one pass per round, inside the job that already owns the slot.** A slot job is dispatched **once** and then resumed for each subsequent round; the **PR assignment** rotates through it, the job itself does not end and is not re-spawned (see _A pass that runs inside a job runs in that job_). A worker still runs exactly one pass per PR per round and reports, so it never sits on a slot waiting for a sleep to elapse — the dispatcher owns the sleeping.
   - **Run every round inside the slot job it belongs to — never dispatch a fresh agent per PR per round.** Resuming a slot for round N+1 is a follow-up turn against a warm context that still holds its worktrees, the comment threads it has read, and its counters. Re-dispatching instead produces `PRs × rounds` agents — 10 PRs over 3 rounds is 30 cold agents rather than 10 warm ones, each re-fetching the same diff and re-walking the same threads. A round number in a job's label (`3217 r2`, `3217 r3`) beside a fresh session is the visible symptom that this rule was skipped.
   - **Invoke `/sy-babysit-pr <PR-URL> goal=<selected-goal> feedback=<selected-feedback> pass=single round=<n>` per pass**, adding `last=true` on the pass you know is the final one for that PR, **and paste that PR's `## State` block from the previous pass into the job's prompt under a `## Prior state` heading** (omit the heading entirely on the first pass; a resumed job that still holds the prior round in its own context needs it only as a cross-check). `pass=single` makes the per-PR command run one pass and return instead of owning the clock itself; `last=true` is what releases workspace cleanup; the prior-state block is what keeps its counters, automerge decision, workspace ownership, and fingerprint from resetting to zero. Dropping any of the three silently turns a long run into a series of disconnected first passes.
   - **Await every job dispatched or resumed in a turn before that turn ends** (see _Never end a turn with a dispatched job still in flight_). A child's completion status is written by this dispatcher when the child returns, so a round left open when the turn stops freezes those jobs at "running" permanently — the workers exited, the board just cannot say so. Never issue a round the run has no time left to await: on the deadline, finish the round in flight and report, rather than starting one more.
   - **The dispatcher owns the clock.** Apply the shared PR-loop lifecycle and this workflow's selected ready/watch goal. Single-pass workers return state; they never restart the budget.
   - **Re-rank the queue every pulse** using the same author lens, activity band, and queue-aging rule, so a PR with a fresh commit, comment, review, CI transition, or approval change jumps ahead of an idle peer in the same urgency tier. Active PRs precede stale PRs; newest `activityAt` goes first within the band. A stale PR waiting through `3` queue selections, or `1` full run without a pass, receives an aging promotion within its current band and tier. **Ranking sets which queued PR takes the next free slot — never whether a PR is serviced at all.** Report every promotion.
   - **A PR that reaches a terminal state leaves the ledger's rotation** (merged, closed, or handed to the human). Report it and stop scheduling it.
   - **Never preempt or blindly requeue an active pass.** Apply `/sy-babysit-pr` Step 12b before setting `dirty_after_pass`. Harmless CI progress updates watch state only. Persist actionable or uncertain events in `pending_wake_events` with head/source versions; let the owner finish safely. Reconcile those events against the worker's returned snapshot and dispositions. Drop only events proven consumed or no longer actionable; never overwrite newer driver observations with a late snapshot. Clear dirty state when nothing remains, otherwise requeue once at the head with the unresolved wake reason and existing handle. Carry pending events through ledger checkpoints and prior-state handoffs. Never cancel a pass mid-edit.
   - **Report each PR's fingerprint and `externally_blocked` back with its `## State` block, every pass.** That is what lets the dispatcher move it to `watching` and stop paying a worker for it (Step 4b). A worker never decides to park itself — it reports state; the dispatcher schedules.

   - Expect long runtimes: the run works its full budget by design. That is the point — do not shorten it, and do not busy-poll the jobs. Collect each result when its job reports back.
   - If one job fails or escalates, the others keep running; never abort the whole fan-out for a single PR. **If a whole slot job dies, relaunch that slot — do not fold its PRs into a live one.** A dying slot frees exactly the capacity it was using, so a replacement job fits without exceeding `S`, and pushing its PRs into a neighbour would both silently double that lane's round length and violate the "a slot's assignment never changes mid-run" rule. **Confirm it is dead before replacing it** — a job that finished its turn is _idle_, not dead, and an idle slot is resumed with a follow-up turn carrying its next round, which keeps its worktrees, its read comment history, and its counters intact (see _Resume an idle job; relaunch only a dead one_). Only a job that is failed, cancelled, or gone gets a replacement, launched with the dead slot's **remaining** PRs (drop the ones that already reached a terminal state) plus a checkpoint of what it got through — each PR's last `## State` block from the dispatcher's ledger, which exists precisely because a replacement cannot inherit what the live job still held.
   - **Resume per PR from its own `completed_round + 1`.** A worker that died mid-pass leaves that PR owing the pass it was on, not the next one; re-queue it at the head with its last `## State` block, and let every other PR keep its own counter. This is exactly why the state block carries `completed_round` per PR rather than a single run-wide round number.
   - If the slot died with no capacity to relaunch into (the whole run is being torn down), report its PRs as partially serviced with their per-PR round counts, so the next invocation picks them up as P0.
   - **Parallelism is safe because every PR gets its own git worktree** at a rigid path — **`$HOME/.worktrees/<owner>/<repo>/<sanitized-branch>`**, created by `worktree_create` (see One rigid worktree path). The sanitized branch key keeps branches separated, and none of them touch your primary checkout. Never let a job `git checkout` in the main repo.
   - The per-PR command owns the pass. This wrapper owns only which PRs run in which lane and when — if the per-PR flow needs to change, edit `/sy-babysit-pr`.

4a. **Ping-pong — use the shared PR-loop batch pulse contract.** Keep the opening, periodic, and closing board, rendered through the existing list workflow with this driver's ledger and unchanged scope.
Reuse probe snapshots for live status. Read only worker results already returned; never message or interrupt an owner for progress.
Keep workflow-specific row states and counters. A watched or non-terminal skipped PR remains enrolled; a dead owner is reported here and recovered only by the scheduling step.

4b. **Watching — a PR with nothing actionable is polled by the dispatcher and holds no worker.** This is the fan-out's biggest waste: three PRs all sitting on a human approval gate means three workers waking worktrees, re-reading diffs, re-walking the same comments, and reporting the same no-op — while a fourth PR with a fresh review comment waits for a slot. Nothing an agent can do moves any of them; only a person clicking, or another PR merging, does. So the dispatcher stops paying workers it does not need and pays two `gh` calls per PR instead — and the freed slot goes to the PR that actually has work.

- **Move a PR to `watching` when its last `## State` block came back `externally_blocked`** — the enumerated set in `/sy-babysit-pr` Step 12a, which the per-PR job decides and this command never second-guesses. Watching is per PR, not per lane: one blocked PR frees its slot immediately, whatever the rest of the set is doing.
- **Never move a PR to `watching` mid-pass, and never one whose state records unpushed commits or a dirty workspace** — that PR has work outstanding and cannot be externally blocked in the first place. Let its worker finish and report first.
- **Prefer an idle, addressable job over a terminated one.** An idle job still holds its worktrees, the comment threads it has read, and its counters, so resuming it is a follow-up turn rather than a fresh agent re-deriving all of it from a pasted summary (see _Resume an idle job; relaunch only a dead one_). An idle job holds no slot. Terminate only when the harness cannot hold an idle job, and say so when you do — the ledger requirement (Step 3a) is what makes that fallback safe.
- **The watch runs inside the pulse's existing fetch.** Step 4a already re-runs the cheap `gh pr view` status calls for every row, so the fingerprint costs one extra `gh api .../pulls/<n>/comments?per_page=1&sort=updated&direction=desc` line per watched PR and nothing else. Compute the digest exactly as the shared PR-loop Read-only probe defines it — same two commands, same string comparison. Do not invent a second fingerprint here.
- **The pulse itself stays display-only.** It renders; it never dispatches. This step schedules, it happens to reuse the pulse's fetch, and the only thing it may launch is a worker for a PR **it moved to `watching` itself**. It never relaunches a dead job (Step 4 owns that) and never merges, comments, or pushes.
- **Classify before requeueing.** Apply `/sy-babysit-pr` Step 12b in the driver, not a new classifier worker. Harmless build progress updates the fingerprint, snapshot, and short status without dispatch. Actionable/uncertain changes requeue the PR with a named wake reason. Resume its idle handle; replace only a confirmed dead/gone owner. Never turn an unchanged blocked PR into another no-op worker pass.
- **A merged wave blocker is a fingerprint change, and the requeued pass is what promotes.** The probe already checks every named blocker's state (`/sy-babysit-pr` Step 12a), so `OPEN → MERGED` on a blocker fires a full pass, and that pass runs `/sy-babysit-pr` Step 4a: sync, CI green, `gh pr ready`, drop the `WIP: DO NOT MERGE — ` prefix, rewrite the `## Blocked on` section. This is the whole reason a wave-blocked PR stays enrolled instead of being written off — a watched wave-2 PR that never wakes ends the run unpromoted, which is the failure the fingerprint exists to prevent. The dispatcher notices; it never promotes anything itself.
- **A watched PR still owes verification, not automatic worker dispatch.** The driver performs Step 12b's bounded read-only keepalive/final verification. Preserve `last_full_pass_at`, `last_watch_verification_at`, `probe_snapshot`, `wake_reason`, and driver-owned probe counters in the ledger and handoff. Harmless progress never postpones verification. Actionable or uncertain results resume the owner; quiet results checkpoint state and keep watching.
- **Say what it saved.** The pulse shows watched rows as `🔍 WATCHING` with the blocker and the next check time, and the Step 5 report names every watched PR, how long it spent watching, what it was waiting on, and how many worker dispatches that avoided. Watching is a reported state, never silence.

4d. **A worker's stop-and-ask is surfaced to the operator, and revalidated before it is repeated.** A PR handed back with `needs_user` in its `## State` block is parked in `watching` — no fix work on the blocked decision, but it keeps its probe and keepalive — and the operator is the one who has to see it, since a sub-agent's report scrolls past. Carry the block into the ledger verbatim, mark that row `NEEDS_USER`, and print the full question on first validation, changed/conflicted verdict, and final report. Unchanged pulses show only `NEEDS_USER — unchanged; <next step>`; complete state stays in memory and internal handoffs. Never open a prompt, never block the run waiting on an answer, and never express it on GitHub — no label, no status, no review, no comment posted purely to record it. **Every PR being terminal or `NEEDS_USER` is not a stop condition** — print the outstanding questions together, then keep sleeping and probing to the deadline. Relevant source changes and read-only keepalive/final verification revalidate through `/sy-babysit-pr` Step 2b. Step 12b decides whether the result warrants resuming a worker; an unchanged parked question never does. `cleared` returns the PR to normal scheduling. The run ends only on the deadline, every PR `MERGED` / `CLOSED` in explicit-ref scope, or the unreachable-service stop.

- **Revalidate before repeating a claim from an earlier run.** A `needs_user` block read out of babysit memory at startup is a hypothesis: dispatch that PR's next pass with the block pasted in, let `/sy-babysit-pr` Step 2b re-fetch the source and resolve `current` / `cleared` / `changed` / `conflicted` / `stale_unknown`, and render that verdict — never the stale claim on its own. A `cleared` verdict re-queues the PR normally and names the comment that cleared it.
- **`NEEDS_USER` is a local pause, not a GitHub state.** The PR may be green, approved, and mergeable to everyone else; only this run is holding off on it. Render it distinctly from `⚠️ ESCALATED` (a job that stopped on its own error) and never as `⏭️ SKIPPED`.

4c. **Stop through the shared PR-loop lifecycle contract.** Keep this driver's Readiness goal outcomes: explicit-ref `goal=ready` may finish after every row is freshly ready/merged/closed and cleanup is complete. A parked `NEEDS_USER` is not success or terminal escalation. Search scopes keep re-resolving until the shared deadline. Persist the complete ledger and every PR's state to owned-PR memory on every exit.

5. **Final report:** emit the **closing ping-pong** — one last `/sy-list-prs pingpong <same-scope-token>` with the final ledger and `Next ping-pong: — (final)` — followed by one `/sy-list-prs table <same-scope-token>` render and a short summary of which PRs were skipped (already green), which were processed, and which need human attention. Include each PR's pass count, its final ledger state, its worktree path (reused vs created), and **every PR that spent time watching** (`http://github.com/acme/api/pull/51 watched 3h12m — blocked on a human approval gate; 41 probes, 0 worker dispatches, requeued once when <link> merged`), and note any worktrees left behind because they pre-existed. **Name every wave promotion** (`http://github.com/acme/web/pull/7 promoted on round 6 — blocker http://github.com/acme/api/pull/40 merged → synced, undrafted, WIP prefix dropped`) and every wave PR still watching, with the blocker it is still waiting on — a run that left a promotable PR unpromoted is a reportable miss, not a silent one. **Report agent reuse too**: which jobs were adopted or resumed rather than freshly dispatched, and any duplicate job cancelled. **State explicitly that every resolved PR was serviced** — count the rows and compare against the Step 1 resolved count; a mismatch is the failure this command's enrollment rule exists to prevent, so name any PR that got zero passes and why. A watched PR is a serviced PR: report it as one, never as skipped or missing. The run therefore always brackets itself: pulse at the start (Step 3a), periodic pulse through the shared contract (Step 4a), pulse at the end.

## Rules

- This command is a dispatcher. The per-PR loop lives in `/sy-babysit-pr` — do not re-implement it here.
- **A slot is a long-lived job that is adopted, resumed, and reused — never re-spawned per round (Step 4).** Follow the shared PR-loop ownership/handoff contract; preserve existing stable keys, per-PR state, concurrency, and safe workspace recovery.
- **Wave promotion is detected here and performed there.** The dispatcher sees the whole set, so it resolves the wave graph at announce time (Step 2) and hands every blocked PR its blocker links down to its slot job; the fingerprint then makes a blocker's `OPEN → MERGED` flip requeue that PR on the next probe (Step 4b). The promotion itself — sync, CI green, `gh pr ready`, drop the `WIP: DO NOT MERGE — ` prefix, rewrite `## Blocked on` — is `/sy-babysit-pr` Step 4a, on that PR's own pass. **The dispatcher never edits a title, never undrafts, and never rewrites a body.** A wave-2 PR that ends the run unpromoted while its wave-1 blocker merged hours earlier is the failure both halves of this exist to prevent.
- **Prose-only PRs in a fan-out do NOT self-merge — they wait for their batch.** `/sy-babysit-pr` Step 2c only enables `--auto` on a _standalone_ docs / comment / whitespace PR, and every PR in this dispatched set counts as a companion of every other. So a docs PR inside a fan-out is deferred until its siblings merge or close, then self-merges on a later pass. That is what keeps documentation from landing ahead of the code it describes. A fan-out of exactly one PR still checks other companion signals and Readiness before automerge; one batch row alone proves neither. Say which docs PRs are deferred in the Step 2 announce; the dispatcher itself never enables or disables automerge.
- **Migration collisions are the dispatcher's to see and the jobs' to fix (Step 3c).** Scan **every** open PR in each repo — not just the babysat set, not just the automerge-on ones — because a per-PR job only ever sees its own branch, and the PR that breaks the default branch is routinely one nobody asked you to babysit. Compute the merge order, record the floor's migration head at dispatch, and hand both to every affected job. The dispatcher never re-parents, never pushes, and never reorders a merge itself: whichever PR lands second re-parents via its own `/sy-babysit-pr` Step 4 override.
- **Base-branch sync eligibility belongs to the worker.** Each job applies `/sy-babysit-pr` Step 5c before delegating sync. Any current approval vetoes sync except for a confirmed merge conflict or migration-head conflict. Ordinary unapproved sync follows its configured cooldown, including on quiet keepalive and final passes. Preserve `last_sync_at`, `last_sync_sources`, `last_sync_check_at`, and `sync_decision` verbatim in the ledger and every prior-state handoff. Never call `/sy-sync-pr-branch` from the dispatcher or add a separate sync pass.
- **Preserve approval by default.** New-code comment remediation follows the blocker gate in the per-PR workflow's Step 6. Read-only classification and **Review-thread closeout** for already-pushed fixes remain required under Step 2d, even during CI or after approval. Keep the driver read-only: missing evidence or resolution wakes the existing owner through Step 12b. Do not mark closeout complete from a worker summary alone; carry verified thread state and unresolved counts into the ledger. Other feedback remains subject to Step 6; this exception authorizes no edits, pushes, sync, or review requests.
- **Parallel means one message, `slot_count` tool calls — not `N` (Step 4 Dispatch mechanics).** The job count is `min(N, S)`, never the PR count: launching one job per PR past the cap is what strands the tail. If the transcript shows the slot jobs starting one message at a time, the fan-out was sequential and must be relaunched. Self-contained prompt per slot, no shared state.
- **An empty or fully terminal ledger ends the run only in explicit-ref scope.** Use the shared lifecycle and this driver's Readiness goal. A `READY` result completes only an explicit ready goal; parked decisions never count. Search scopes remain enrolled through the deadline.
- **An idle set is a reason to sleep, not to stop.** Apply shared deadline-bounded waits and search-scope re-resolution. Preserve the selected readiness goal; no second timer or invented early watch exit.
- **Every non-placeholder PR resolved for babysitting is enrolled before anything launches — never dropped (Steps 1p / 3b).** One worker per PR while slots last; past the concurrency cap the surplus is `queued` by rank and takes the next slot a worker releases. A slot is held only by a pass actually running: a `watching` or `queued` PR costs nothing, which is what makes covering the whole set affordable. A PR that ends the run with zero passes is a bug in this command, not an acceptable outcome. Placeholder drafts dropped by Step 1p are the one intentional exclusion, and they must be named in the announce and final report.
- **Order comes from the work-owed ranking, defined once in `/sy-list-prs`.** Do not restate the tiers here, do not invent a second ranking, and never use it to skip a PR — it sets service order only. Re-rank inside a slot each round; never move a PR between slots mid-run.
- **A worker runs one pass per round and hands the slot to the next PR — the job it runs in is not re-spawned (Step 4).** Every pass goes through `/sy-babysit-pr <url> pass=single` with the prior state block pasted in, run **inside** the slot job that already owns that lane; round N+1 resumes that job rather than dispatching a new one. A worker that sleeps out a cadence while holding a slot is the starvation this design removes, just hidden inside a job — and a fresh agent per PR per round is the agent explosion it removes, just hidden behind a round number in the label.
- **Babysit all resolved PRs in parallel background jobs — never a sequential for-loop** (see Fan out multi-PR work in parallel). One worktree per branch at `$HOME/.worktrees/<owner>/<repo>/<sanitized-branch>` via `worktree_create` (`/sy-babysit-pr` Step 5a) is what makes this safe: the sanitized branch key keeps PRs from colliding across slots or within one, nothing is shared, and the user's primary checkout is never touched.
- **A fan-out run is long by design.** Honor the shared watch budget or the selected ready-goal completion rule. Never truncate active owners, busy-poll them, or declare completion before every enrolled PR reports.
- **An externally blocked PR is watched by the dispatcher and holds no worker (Step 4b).** A PR waiting on a human approval click costs two read-only `gh` calls per probe, folded into the pulse's existing fetch, and its slot goes to a PR that actually has work. It is requeued only when `/sy-babysit-pr` Step 12b identifies actionable or uncertain state. The driver still performs read-only keepalive/final verification for verified quiet PRs; no worker wakes merely to repeat build progress or a parked question. Never move a PR to watching mid-pass, and never report a watched PR as skipped. The mechanism and fingerprint live in the shared PR-loop contract; Step 12a retains only babysit's wait classification; the externally-blocked call belongs to the per-PR job, the scheduling to this one.
- **Ping-pong is mandatory, not optional (Steps 3a / 4a / 5).** Apply the shared PR-loop Batch pulse timing and opening/periodic/closing requirement. A long async fan-out with no heartbeat is indistinguishable from a hung one. The pulse is read-only — it refreshes PR status from `gh` and reads already-reported job results; it never messages, wakes, or interrupts a running job, and it never acts on what it finds.
- **Ping-pong layout is owned by `/sy-list-prs pingpong`.** This command owns the agent ledger (job state, loop number, slot number and position, pass timestamps, next-loop ETA, last rendered pulse snapshot) and passes it in; `/sy-list-prs` owns the four columns, the icons, the change marker, the feature-set grouping, and the sort. Do not hand-roll a different board.
- **Table output is owned by `/sy-list-prs`.** Both the pre-flight render (Step 3) and the final report (Step 5) reuse its `table` format. Pass the same scope `$ARGUMENTS` to `/sy-list-prs table` so the rendered set matches the resolved PR set exactly. Do not hand-roll a different table layout.
- **First token of `$ARGUMENTS` decides the mode — no mixing.** PWD-keyword + explicit refs in the same call is an error; pick one. Empty and PWD-keyword modes both scan cwd + nested repos; explicit-list mode does not filter by author (you asked for those specific PRs).
- **Surface authors when the resolved set isn't all yours** (see Show PR authors). Explicit-ref mode is author-agnostic, so it can silently pull in someone else's PR — name the author on every row and in the summary whenever the set is mixed. The `/sy-list-prs table` renders (Steps 3 and 5) already add an `Author` column in that case.
- **Always resolve `<owner>/<repo>` via `git remote get-url origin`, never from the folder name (see Repo Identification).** Applies to PWD scan (delegated to `/sy-list-prs`) and to bare-`#<n>` ref expansion.
- **Stacked PRs still fan out in parallel — do NOT serialize them, and do NOT sync them from the dispatcher.** This contains existing stacks; it does not authorize new ones. An eligible worker syncs floor-then-ancestors downhill into only its own branch, so workers never write the same ref. Approval veto and cooldown still apply. Later probes pick up parent pushes. Never wait on or message a parent job, or merge/retarget an ancestor from the dispatcher.
- **Stacks land bottom-up, and only the human lands them.** A stacked PR that goes green + approved is reported as blocked on its parent (`/sy-babysit-pr` Step 4) — no job merges it, and no job enables automerge on it. When a parent does merge, GitHub retargets its children automatically and the children's next pass re-resolves the chain. Say which dispatched PRs are stacked, and on what, in the Step 2 announce so the merge order is visible before the run starts.

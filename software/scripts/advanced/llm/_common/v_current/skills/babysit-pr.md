[Sy] Babysit a pull request you authored until bot review, CI, mergeability, and migration checks prove readiness. Preserve approval unless a verified blocker needs repair. Work in a dedicated worktree, validate fixes, and keep resumable state. Use an explicit watch goal for continued monitoring; readiness never grants merge or release permission.

**Scope.** This command **changes the PR** — it pushes commits, merges the base in, replies to review threads, and can arm automerge. That is why it belongs to PRs you own: pushing to someone else's branch rewrites work that is not yours, and answering their reviewers speaks for them. To leave a verdict on **someone else's** PR without touching it, use `/sy-review-pr`. Take a PR authored by someone else only when it is explicitly handed to you — then say whose it is and exactly what you pushed.

Argument: $ARGUMENTS (optional — a PR URL or PR number. If empty, use the current branch's PR. A caller dispatching a batch, e.g. `/sy-babysit-prs`, may also pass the full list of sibling PR URLs in that batch; Step 2a's companion check treats them as companions. A slot driver holding several PRs may pass `pass=single` — see the Step 12 loop gate.)

## Readiness contract

Standalone default: `goal=ready`; `goal=watch` preserves deadline-driven monitoring even after readiness. Strip the goal token before resolving the PR.
Reject unknown goal values without starting work. A caller's explicit goal wins over saved state; a driver passes its selected goal to each single pass.

Evaluate these four gates for one published head and current base. Each gate records `pass`, `waiting`, `failed`, `unknown`, or evidence-backed `not_applicable`.

| Gate          | Required evidence                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Bot clearance | Every required bot completed review of the current head, explicitly cleared major concerns, and has no outstanding major findings.                                                                                                                                                                                                                                                                                                                             |
| CI            | Verify required contexts against checks posted for the current head. Missing, pending, stalled, failing, or unreadable required checks never pass. Other relevant failing builds also block readiness. Unrelated failures and explicitly optional skipped checks need repository-policy evidence; no required checks also needs policy evidence.                                                                                                               |
| Mergeability  | GitHub confirms mergeability against the current base. Unknown mergeability never passes; open parent/wave dependencies still block readiness.                                                                                                                                                                                                                                                                                                                 |
| Migrations    | Run repository-defined migration validation against the current base in a non-production environment. Validate lineage/order and expected heads through the sync workflow's framework rules. No migration changes records `not_applicable` from the diff; unavailable validation records `unknown`. Missing local evidence with a known safe command is actionable work for Step 10, even when sync is vetoed; unknown validation policy records `NEEDS_USER`. |

- **Bot policy and trust:** resolve required bot identities and accepted signals from repository rules/configuration or explicit user instructions. Unknown bot policy records `NEEDS_USER`. Explicitly no required bot records `not_applicable` with policy evidence.
- **Bot evidence:** record required bot identity, source ID/URL, reviewed head SHA, and observation time. Prefer structured results. A documented LGTM/no-major-concerns signal counts only when that bot's latest completed review covers this head and has no contradictory major findings.
- A thumbs-up counts only from a required bot on an artifact proven to review the current head. Reaction time or a recent issue comment alone does not prove revision coverage. Silence, stale LGTM, arbitrary reactions, and author-resolved threads never prove clearance.
- **Freshness:** Every push invalidates head-bound bot and CI evidence. A changed base invalidates mergeability and migration evidence; re-evaluate repository policy for other gates. Never carry clearance forward by timestamp alone.
- **Bot re-review:** use only a repository-documented, verified request mechanism, at most once per required bot and published head. No known mechanism means waiting, not invented commands or repeated pings. Track at most 2 repair attempts per finding across this run's pushed heads. Never reset repair counters merely because a fix created a new SHA.
- **Required approvals:** Bot clearance never replaces required human approval. Re-fetch live approval/policy gates; an active blocking review, draft/WIP reason, unresolved dependency, closeout debt, or parked decision prevents `READY`. The approval veto still governs sync; verified blocker remediation follows Step 6.
- **Final verification:** apply the selected feedback gate, then re-fetch head/base after collecting evidence, required approvals, and every review-thread page. If either SHA changed, discard the candidate result and reconcile again. Pending events, incomplete closeout, dirty work, or unpushed commits prevent completion.
- **Outcomes:** `READY` is terminal only for `goal=ready`, after final verification and owned-workspace cleanup. `WAITING`, `NEEDS_USER`, and `EXHAUSTED` are never readiness success. Deadline/repair-cap exits save unresolved gates and exact next actions. `MERGED` and `CLOSED` reflect GitHub state, never inferred success.
- **Authority:** Readiness grants no merge or release permission. Never run production migrations, modify branch protections, or bypass required approval. Polling cannot enforce merge safety atomically; gates that must prevent merging need repository-required checks or an appropriate merge queue.
- **State:** carry `goal`, `feedback`, `automerge_policy`, `readiness`, `readiness_head_sha`, `readiness_base_sha`, gate results and evidence, `bot_policy`, `bot_evidence`, `bot_reping`, `finding_attempts`, and `readiness_verified_at` in memory and every `## State` handoff. A saved `READY` is reverified on a new invocation.

## Feedback and automerge policy

Strip `feedback=blockers` or `feedback=all` before PR resolution. Default to `feedback=blockers`; reject unknown values before starting work.
An explicit caller selection wins over saved state; otherwise preserve the prior mode across resumed passes.

- `feedback=blockers` keeps the existing severity-based remediation and optional-minor-deferral behavior.
- `feedback=all` authorizes every verified actionable in-scope human/bot request, including minor requests, without a severity/count trigger. Approval does not veto this explicitly requested remediation; Step 5c still independently governs sync.
- Strict readiness additionally requires all review-thread pages fetched, zero live unresolved threads, and zero unaddressed actionable top-level comments. Optional deferrals cannot satisfy it.
- Use the latest shared Review-thread closeout rule unchanged. Wrong suggestions receive justified final dispositions, not fabricated fixes; questions, pending choices, and stop-and-ask threads remain open.
- An otherwise harmless unresolved thread still needs a truthful final disposition before strict completion. Never bulk-resolve, delete comments, or claim a bot accepted an author-side decline.
- Carry `feedback`, `unresolved_review_threads`, `unaddressed_top_level_comments`, and observation evidence through memory, quiet verification, every handoff, and final reporting.

Caller contract `automerge_policy` accepts `normal` or `observe_only`. Default to `normal` only when neither caller nor saved state supplies it.
`observe_only` forbids new enablement, re-enablement, and offers to enable automerge, even for prose-only PRs. Preserve pre-existing decisions and existing ownership-based protection rules.
A new explicit user instruction may change policy; a resumed worker may not silently weaken it. Unknown policy fails closed without changing automerge.
Persist this policy in PR memory and every state handoff. Classify/reply/resolve/fix work retains its own guards; this policy grants no other permission.

## Execution mode

Top-level default: one self-contained background worker owning workspace recovery, cadence, pushes, and reporting. Match stable key `sy-babysit-pr:<owner>/<repo>#<number>` against live jobs first: retain running owner, resume idle owner, create only when unowned; cancel a confirmed duplicate, keeping the older. Record the handle and await the dispatched work before ending the turn, per shared PR instructions. Run inline when already dispatched, when `pass=single` is present, or when explicitly given `foreground`, `fg`, `inline`, `blocking`, `synchronous`, `sync`, or `wait`; strip mode tokens. Placement changes no scope, ownership, recovery, sync, checks, or pass order.

## Steps

1. **Determine which PR to babysit:**
   - If `$ARGUMENTS` is provided (a PR URL like `https://github.com/org/repo/pull/123` or a PR number), use that. Accept both HTTP and HTTPS URLs; normalize to HTTPS before requests and identity comparisons.
   - If `$ARGUMENTS` is empty, detect from the current working directory:
     - `git remote get-url origin` to determine the repo.
     - `git branch --show-current` to get the current branch.
     - `gh pr view --json number,title,url,headRefName,baseRefName` to find the PR for the current branch.
     - If no PR exists for the current branch, tell the user and stop.

2. **Announce:** Tell the user which repo and PR you are babysitting (repo name, PR number, title, URL).

2a. **Placeholder-draft skip gate — before memory, worktree, or sync.** Fetch `gh pr view <number> --repo <owner/repo> --json isDraft,title,url`. If `isDraft` is true **and** the title contains `Placeholder` (case-insensitive), this is still the pre-implementation placeholder PR. Report `"placeholder draft pending implementation — skipping babysit until code lands and the PR is marked ready"` with the full URL and stop immediately. Do not create babysit memory, do not allocate a worktree, do not sync, and do not consume a watch-loop budget on it. Once the placeholder markers are removed and the PR is readied, a later invocation babysits it normally.

2c. **Create or resume babysit memory before changing the PR.** Stable identity is `<owner>/<repo>#<number>`. Under `<<LLM_ROOT_FOLDER>>/pr_babysits/`, find an existing file by that identity in its heading or full PR URL and by historical filename aliases; otherwise create `<repo-name>_<number>_<slug>.md`, resolving `<owner>/<repo>` and `<repo-name>` from GitHub, preserving repository-name punctuation, and deriving a short lowercase snake_case slug from the title after stripping status / repo prefixes. One same-kind match is reused without renaming; multiple matches create no new file, so report the conflict and use the newest verified snapshot until consolidation is approved. Read title, body, commits, changed files, and full diff; write a 2–3 sentence `## TLDR` covering feature goal, implementation, affected contracts, and main risk. Scan root and changed-path `AGENTS.md` / `CLAUDE.md`, `CONTRIBUTING.md`, `ARCHITECTURE.md`, `DEV.md`, `.cursorrules`, and relevant linked/component docs; widen to another repo only when those sources identify a concrete consumer. Put only applicable hard rules and non-obvious context in `## Relevant Rules`. Initialize/update `## Context` with URL, owner/repo identity, head SHA, status, last-verified time, and stable job key. The diff wins over title/body; saved context and author claims remain hypotheses. If an old worktree journal exists, distill any still-current resume state once, then leave it untouched.

2b. **Replay and revalidate any `needs_user` claim left by an earlier run — before deciding anything else.** A fresh invocation remembers nothing, so the only record that this PR was handed to the human is the `needs_user` block in babysit memory. Read it on every first pass of a run, and treat it as a hypothesis rather than a fact: the comment that raised it may have been withdrawn, answered, or overtaken by a push hours ago.

    - **Re-fetch the source, do not trust the summary.** The block records `needs_user_source_id` (the comment / review / thread / check it came from), `needs_user_source_updated_at`, and `needs_user_head_sha`. Re-read that item by id, re-read the PR's current reviews, review threads, checks, head SHA, and body, and read everything posted since that timestamp.
    - **Resolve to exactly one verdict:** `current` (the thing still stands), `cleared` (it does not), `changed` (a human is still needed, for a different reason), `conflicted` (later comments disagree with each other), or `stale_unknown` (the source is gone or unreadable, so it cannot be verified either way).
    - **Print the prior claim and verdict together on first validation, changed/conflicted verdict, and final report, always with a `Next:` line.** Unchanged watch updates use Step 12b's short status; retain the complete record in memory and internal handoffs. `Prior:` what the last run asked, `Current:` the verdict and the evidence that produced it (quote the comment and its timestamp), `Next:` the concrete step — the decision the human owes when it stands, what this run resumes doing when it clears, which two comments disagree when it conflicts, or which check to run when it cannot be verified.
    - **`cleared` resumes the PR normally** — drop `needs_user` from babysit memory, name the comment that cleared it, and carry on into Step 3. `current`, `changed`, and `conflicted` keep it, refreshed with the new source id and timestamp. `stale_unknown` keeps it and says plainly that it could not be verified.
    - **This is display, never a prompt.** Print it and keep working: no interactive question, no blocking wait for an answer, and nothing written to GitHub to record it — no label, no status, no review, no comment posted purely to mark scheduler state. The PR stays exactly as mergeable to everyone else as it was.

2a. **Prose-only automerge gate — classify on the first pass, before the CI check.** Apply the caller's automerge policy first, then **Readiness before automerge** from shared PR instructions before enabling anything. Eligible prose-only PRs wait in `deferred_readiness` until fresh readiness is verified, unless server-side rules demonstrably enforce all readiness gates. Recheck readiness and companion deferrals on later passes. This classification never grants broader merge permission.

    Fetch: `gh pr view <number> --repo <owner/repo> --json state,isDraft,title,body,author,autoMergeRequest,headRefName,baseRefName`.

    - **Skip the gate entirely** (report why once, never re-check) when any of: `state != "OPEN"`; `isDraft` is true; the title contains `WIP` or `DO NOT MERGE` (case-insensitive); `author.login` is not you (`gh api user --jq .login`); or `autoMergeRequest != null` (already enabled — someone else's call, leave it alone). **"Never re-check" has exactly one exception: a Step 4a wave promotion.** Draft state and a WIP title are the two skip reasons promotion actively removes, so a promoted PR gets this gate re-run once, on the pass that promoted it — otherwise a wave-2 prose-only PR is disqualified by a condition that stopped being true hours earlier and is never reconsidered.
    - **Classify the diff** — `gh pr diff <number> --repo <owner/repo>`, and read every changed line, not just the file list. **Prose-only** means every `+`/`-` line is a line in a docs file (`*.md`, `*.mdx`, `*.rst`, `*.txt`, `docs/**`, `README*`, `CHANGELOG*`, `LICENSE*`), a comment line in a source file, a docstring / JSDoc block, or pure whitespace (see the Automerge is opt-in rule). A single executable line — code, config, schema, lockfile, CI workflow, test — disqualifies the whole PR, however small. A file-name check alone is not enough in either direction: a `.md` file can hold an executed snippet the repo tests, and a `.py` file can hold a comment-only fix.
    - **Companion check — only a STANDALONE prose-only PR self-merges.** Merging docs before the code they describe is the failure this prevents, so a prose-only PR that belongs to a set waits for that set. Gather companions from all four signals, then keep only those still `OPEN`:
      - **Batch siblings** — if the dispatcher passed a sibling PR list (`/sy-babysit-prs` Step 4 hands each job the full dispatched set), every other PR in it is a companion. This is the strongest signal and needs no API call.
      - **Branch group** — read `headRefName`. If it has three or more segments (`<username>/<group-slug>/<feature>`), the group prefix is the first two. Same repo: `gh pr list --repo <owner/repo> --state open --json number,url,title,headRefName,author --limit 100`, keep rows whose `headRefName` starts with `<username>/<group-slug>/`. Other repos (best effort — `gh search prs --json` exposes no `headRefName`, so match on text): `gh search prs --author @me --state open --json number,repository,url,title --limit 50 "<group-slug>"`.
      - **Explicit references** — read the title and body for another PR path (`.../pull/<n>`), or the words "depends on", "part of", "stacked on", or a shared plan slug. Resolve each and keep the open ones.
      - **Stacked** — `baseRefName` is another open PR's head branch.
    - **Prose-only AND standalone → apply Readiness before automerge, then enable only when permitted:** `gh pr merge <number> --squash --auto`, then report `"Standalone prose-only diff (<n> files, docs/comments only) — automerge enabled; CI and any required approval still gate the merge."` Then continue the normal loop at Step 3 — babysit still syncs and handles active blockers; ordinary review comments remain untouched unless the remediation gate activates.
    - **Prose-only but NOT standalone → defer, and re-check every later pass.** Leave `--auto` off and report `"Prose-only diff, but <n> companion PR(s) still open — automerge deferred so the docs don't land before the code: <full PR links>."` Companion and readiness deferrals are rechecked, not final: what blocks is a companion still being open, not the PR being grouped. On every later pass, re-resolve the companion list; the moment all of them are `MERGED` or `CLOSED`, re-evaluate Readiness before automerge and enable `--auto` only when permitted and report `"Last companion (<link>) landed — automerge enabled on the prose-only PR."` If any companion is still open when babysit finishes its passes, say so in the Step 13 report and leave the merge to the human.
    - **Not prose-only → leave it off,** report `"Diff touches <what> — automerge stays off until you say otherwise."`, and do not reconsider on later passes. Automerge is opt-in everywhere except a standalone prose-only diff.
    - **If `gh` rejects `--auto`** (repo has auto-merge disabled, squash not an allowed method, branch protection missing a required check), report the exact error once and carry on with the loop. Never fall back to a bare `gh pr merge` without `--auto` — that would merge on the spot — and never retry on later passes.
    - **Revoke it if the PR stops qualifying.** Babysit pushes its own commits (Steps 5–10), and a CI fix or a new test turns a docs PR into a code PR; separately, a companion PR can open after this gate already enabled `--auto`. On every later pass, if automerge is on **because this gate enabled it**, re-check both conditions:
      - The diff now contains an executable line → `gh pr merge <number> --disable-auto`, report `"PR is no longer prose-only (<what changed>) — automerge disabled; merge is yours again."`, and treat it as opt-in from then on.
      - A companion PR has since opened (re-run the companion check) → `gh pr merge <number> --disable-auto`, report `"A companion PR opened since automerge was enabled (<link>) — automerge revoked so the docs don't land first; it will be re-enabled once that PR merges or closes."`, and fall back to the deferred branch above.

      Never revoke automerge the user or `/sy-create-pr` enabled — only what this gate turned on.

2d. **Close out already-pushed fixes before build, approval, and blocker skip gates.** Run before Step 3 on every full pass, including resumed passes that otherwise re-enter at Step 3. Apply **Review-thread closeout** in the shared PR instructions. Fetch every review-thread page and inspect unresolved threads for verified fixes already present in the published head, including fixes from merged dependencies. Complete missing evidence replies and resolutions without duplicate replies. No new code, push, sync, or review request is authorized by this step. Preserve questions, pending choices, stop-and-ask threads, and unverified findings. Record incomplete closeout for recovery; do not report it as addressed. This step also runs when remediation is gated off. Step 12b verification detects remaining closeout work before quiet mode.

3. **Skip if a BUILD is currently running — a pending human review gate is not a build.** Before any other check, fetch state:
   `gh pr view <number> --repo <owner/repo> --json statusCheckRollup`

- **Classify every non-`COMPLETED` entry before deciding anything.** A pending entry is a `CheckRun` whose `status` is `IN_PROGRESS` / `QUEUED` / `WAITING` / `PENDING` / `REQUESTED`, or a `StatusContext` whose `state` is `PENDING` / `EXPECTED`. Sort each one into exactly one bucket:
  - **Blocking — a self-resolving build.** A job is executing and will reach a conclusion on its own: test, lint, type-check, build, scan, deploy. Pushing into it wastes CI cycles and merging into it is unsafe, so it ends the pass.
  - **Non-blocking — a human gate, or a stalled entry.** A check that cannot finish without a person clicking something never resolves on a timer, so "wait for CI" means wait forever. Mark an entry non-blocking when ANY of:
    1.  Its display name matches a review-gate pattern, case-insensitive: `approv`, `review`, `sign-?off`, `codeowner`, `resolution`, `ack`, `attestation`, `waiver`. The name is `name` (+ `workflowName`) on a `CheckRun` and `context` on a `StatusContext` — `gh pr view --json statusCheckRollup` emits those two and no `description`, so match on what it actually returns. Apps report approval gates as checks that sit `IN_PROGRESS` **by design** until a human acts.
    2.  It is a `StatusContext` in `PENDING` with no `targetUrl` — nothing is executing behind it.
    3.  **Staleness backstop** — it has been pending longer than **60 minutes**. Age comes from `startedAt`, which `gh` emits for **both** node types (the underlying GraphQL field on a `StatusContext` is `createdAt`; `gh` renames it — do not look for `createdAt` in `gh` output). Babysit's whole window is one bounded run, so a check that has not moved in an hour cannot be waited out; treating it as blocking makes every remaining round a no-op. Name it in the report as `"stalled check treated as non-blocking"` so a genuinely slow build is visible rather than silently stepped over.
- **End the pass ONLY if the blocking bucket is non-empty.** Report `"PR build is currently running (<blocking check names>) — skipping this pass"` and take no other action: do not merge, do not address comments, do not push. Then fall through to the **Step 12 loop gate** (use the shared probe cadence; re-enter at Step 3 when scheduled) instead of exiting babysit.
- **If every pending entry is non-blocking, DO NOT end the pass.** Report `"<n> check(s) pending on a human gate (<names>) — not a build; continuing the pass"` and go to Step 4. A review gate blocks the _merge_, not status polling or required blocker handling. Do not activate comment remediation for a human gate alone; ordinary code edits remain gated unless Step 6's selected feedback policy authorizes them. `feedback=all` still requires an actionable in-scope request; a human gate alone never authorizes edits.
- Carry the non-blocking list forward for the rest of the pass: Step 4 reads "all CI checks passing" as _all blocking checks passing_, Step 11 stops polling once only non-blocking entries remain, and Step 13 names every gate still pending.
- CI is fully idle only when every entry is `COMPLETED` (or there are no checks). A non-blocking gate means "proceed", never "green".

4. **Early-exit check.** Fetch state:
   `gh pr view <number> --repo <owner/repo> --json statusCheckRollup,reviews,reviewDecision,mergeable,state,autoMergeRequest,baseRefName,headRefName`
   - If `state == "MERGED"`: PR already landed — report the merge SHA, **reap the leftovers** (the merged branch and its worktree are now dead: run `git clean-worktree` then `git clean-stale-branches`, remove a skipped detached-HEAD worktree with `git worktree remove <path>` after confirming it is clean, and **keep babysit memory** — see the _A merged PR gets cleaned up_ rule). **Do NOT trigger a release** — release is expensive and stays a manual `/sy-release` the user invokes; never auto-dispatch it after a merge. Stop babysit entirely — merged is the one terminal state that skips the remaining Step 12 passes. A worktree carrying unpushed commits or a dirty tree is never reaped silently: report the path and leave it for the human.
   - **Merge-conflict override — check `mergeable` BEFORE either early-exit branch below.** A PR with conflicts against its base branch is NEVER "done", even when CI is green and reviewers have approved.
     - If `mergeable == "CONFLICTING"` (or any non-`MERGEABLE`, non-`UNKNOWN` value indicating a base-branch conflict): report `"PR is green + approved BUT conflicts with <baseRefName> — falling through to Step 5 to resolve"` and continue to **Step 5**. Step 5 will perform the actual merge + conflict resolution; the rest of the loop (tests, local checks, CI monitor) handles the rebuild.
     - If `mergeable == "UNKNOWN"`: wait 5s and re-fetch, capped at 6 retries (~30s total). Still unknown → report uncertainty, skip sync, and keep polling. Unknown mergeability never proves a conflict or bypasses approval.
   - **Migration-head override — check this BEFORE the green + approved early-exit below, and re-check it EVERY pass.** Same shape as the merge-conflict override above and for the same reason: a PR whose migration is parented on a superseded head is NEVER "done", however green CI is and however many reviewers approved. This is the one failure mode where every signal the early-exit reads says "ready" and merging still breaks the default branch — the migration DAG is not a git conflict (sibling revisions are different files, so `mergeable` stays `MERGEABLE`), and CI on this branch never ran against the head that landed while the PR sat.
     - **Applies to any PR whose diff touches a migration path** (detection table: `/sy-sync-pr-branch` Step 7 — do not restate it here). No migration in the diff → skip this bullet entirely, no API calls.
     - **Cheap read-only probe first.** Compare the branch's migration parent against the current head on the floor branch without checking anything out: for Alembic, read the new revision's `down_revision` from `gh pr diff <number> --repo <owner/repo>` and the floor's head from `gh api repos/<owner>/<repo>/contents/<versions-path>?ref=<floor>`; for the rest, apply the framework's equivalent ordering check. In doubt, fall back to **"is there a migration on the floor branch that is not in this PR's history?"** — if yes, treat it as stale.
     - **Stale → do NOT early-exit.** Report `"PR is green + approved BUT its migration is parented on <old-head> and <floor> is now at <new-head> — falling through to Step 5 to re-parent"` and continue to **Step 5**. The fix is the delegated sync's Step 7 (merge the floor in, re-stamp onto its head — **never `alembic merge`**, never a rebase), exactly as the merge-conflict override delegates the merge itself. Babysit implements neither.
     - **Single head → carry on** to the wave-block check and the early-exit below, and say `migration head current (<head>)` in the report so a pass that skipped is auditable.
     - **Never re-parent an ancestor PR's migration** — the sync enforces downhill-only; on a stack, this branch's revision re-parents onto the ancestor's.

   - **Wave-block check — do this before judging CI, and do it every pass.** Read the PR body for a `## Blocked on` section (see the _Hard dependencies phase into waves_ rule). It names the PRs this later-wave branch waits on, so it decides whether this pass has any work in it at all. Resolve each named PR's real state with `gh pr view <link> --json state` rather than trusting the section, which goes stale by design.
     - **Any named PR still `OPEN`** → this branch legitimately does not contain the migration / column / field it needs, so red CI here is expected and is not yours to fix. Report `"PR is wave-blocked on <link> — CI stays red until it merges; skipping this pass"` and **end the pass** (skip Steps 5–11), exactly as a running build does. Do not push, do not attempt fixes, do not touch the Step 11 attempt counters, and do not escalate — this is a documented skip, not a terminal state, and the next pass exists precisely to catch the blocker landing.
     - **Every named PR `MERGED`** → the block is over and this pass has real work in it. Do not end the pass; carry on to **Step 4a**, which owns the promotion end to end. Do not drop the title prefix, undraft, or rewrite the body from here — one implementation, and it is Step 4a's.
     - **A named PR is `CLOSED` without merging** → stop and ask. The dependency this branch was built on is not coming, so the wave plan itself is wrong and no amount of syncing fixes it.
     - **No `## Blocked on` section** → not a wave PR; skip this bullet entirely and carry on. Most PRs are wave 1 and never mention it.
   - **Stacked-parent check — every PR, not just prose-only.** Run `gh pr list --repo <owner/repo> --head <baseRefName> --state open --json number,url,title`. An open parent blocks readiness and merging; report it and continue watching. Never enable automerge into a parent branch.
   - **Readiness decision — apply the Readiness contract, not aggregate approval alone.** Evaluate bot clearance even when `reviewDecision` is `APPROVED`; one major finding prevents readiness.
     - All four gates pass or are evidence-backed not applicable, required human approvals are satisfied, no pending gate/dependency/WIP reason remains, and closeout is complete → run final verification.
     - Final verification succeeds → record `READY` with head/base SHAs and evidence. Re-evaluate any deferred prose-only automerge through Step 2a. With `goal=ready`, clean up only owned safe workspace state, report, and stop. With `goal=watch`, end the pass and keep probing through Step 12.
     - Otherwise record the exact waiting, failed, or unknown gate. A bot still reviewing is `WAITING`, not a reason to run tests or push again.
     - Actionable failure → continue to Step 5 under its approval/sync gate, then remediate through Step 6. Pure external waiting with no local work → end the pass and use Step 12.
     - Existing automerge never bypasses readiness checks. Never revoke user-enabled or create-enabled automerge; report any unenforced gate. While watching, recheck migration freshness against the current base on each poll when automerge is enabled. If drift is confirmed, schedule Step 5 without rewriting another actor's merge decision.

4a. **Wave promotion — when the wave below lands, make THIS PR mergeable.** A later-wave PR is parked in a deliberately unmergeable shape: a `WIP: DO NOT MERGE — ` title prefix, a `## Blocked on` section, often draft state. **Nothing in GitHub undoes any of that when the blocker merges** — so without this step a wave-2 PR ends the run green, unblocked, and still unmergeable, waiting on a human to notice a state change that happened hours ago. This step is what turns "wave 1 merged" into "wave 2 is ready". Run it **every pass**, and run it **even when Step 4 ended the pass early** — "skip Steps 5–11" never skips this one, because a green + approved PR still titled `WIP` is precisely the PR that needs promoting.

- **Resolve the blocker set from all three signals**, then keep only the ones still open:
  - the `## Blocked on` section in the body — the canonical signal (see the _Hard dependencies phase into waves_ rule);
  - **wave context handed down by the dispatcher** — `/sy-babysit-prs` Step 4 passes each job the blocking PR links for every PR it holds. No API call, and it is the only signal available when the body was never annotated;
  - dependency prose in the body: `depends on <link>`, `part of <link>`, `blocked by <link>`, a shared plan slug.

  Resolve every candidate's **real** state with `gh pr view <link> --json state --jq .state`. The body goes stale by design and is never trusted — that staleness is the whole reason this step re-checks instead of reading a flag.

- **Any blocker still `OPEN` → not promotable.** Say which one and leave the PR exactly as it is: prefix, section, and draft state all stay. Same documented skip as Step 4's wave-block check.
- **A blocker `CLOSED` without merging → stop and ask** (Step 12 terminate-early). The dependency is not coming, so the wave plan itself is wrong; no promotion and no sync fixes that.
- **Every blocker `MERGED` → promote, in this order, never out of it:**
  1.  **Sync when eligible** — Step 5c applies the approval veto and cooldown before calling `/sy-sync-pr-branch`. Neither wave promotion nor a final round overrides that gate. If required floor commits are already verified included, continue without syncing; otherwise leave promotion pending until sync is permitted. Nothing below runs before the required code is present.
  2.  **CI green** — let the loop re-run checks. A red branch is never promoted; the next pass resumes the promotion where this one left off.
  3.  **Undraft** — `gh pr ready <number> --repo <owner/repo>` when `isDraft` is true. Third and not first on purpose: readying requests reviewers, and pinging a team onto a red branch is exactly what draft state existed to prevent.
  4.  **Drop the WIP prefix** — `gh pr edit <number> --repo <owner/repo> --title "<new>"`, stripping only a leading `WIP` / `DO NOT MERGE` prefix and preserving the `[<repo>] ` prefix and everything after it.
  5.  **Rewrite the body** — replace the `## Blocked on` section with a one-line note that it landed (`Blocked on <link> — merged`), and clear any `TODO —` marker that blocker owned. Every other section is left alone (_PR body tracks the branch_), and the payload goes through `--body-file` (_Every GitHub body payload uses a temporary file_).
- **A wrong sequence number in the title is corrected here, and only here.** When the title carries `wave <W> - pr <i>/<N>` and the dispatcher reported `<i>` as out of order, duplicated, or stale against `<N>`, fix it in the same `gh pr edit --title` call that drops the prefix — or on its own when there is no prefix to drop. `<i>` is merge order and monotonic against the wave (see the _A sequence number in a title is MERGE order_ rule); a number that reads as a merge instruction and points the wrong way is worse than none. Never renumber from `createdAt` or the PR number, and never touch a branch to do it.
- **A follow-up PR cut from a review comment joins the wave set, and the set is reassessed before it is announced.** When Step 7 answers a reviewer by opening a separate PR, that PR is placed in the wave its dependencies put it in — usually the same wave as this one — never appended as the last position because it was written last. Re-derive the ordering, retitle whatever moved, update the `## Blocked on` sections the newcomer changed on both sides, and reply in the thread that asked for it with the new PR's link **and** its position, so the reviewer is not reading a number that was already superseded. See the _A PR joining the set mid-flight_ rule.
- **Promote per reason — the other reasons are the author's call.** When the WIP prefix or the draft state has a stated reason _besides_ the wave block (an open `TODO —` marker, unfinished work named in the body, an explicit "keep this draft"), apply Step 5c's sync gate, report that the blocker landed, and **leave the prefix and the draft state alone**. Promoting past a reason you did not resolve ships work its author called unfinished.
- **Idempotent and re-entrant.** Each pass completes only what is still outstanding, so a promotion interrupted between steps 3 and 5 finishes next pass instead of starting over — and nothing runs twice: a title with no prefix is left alone, an already-ready PR is not re-readied, a body with no `## Blocked on` section is not rewritten.
- **Re-run the Step 2a automerge gate once, on the pass that promotes.** Draft state and a WIP title are two of Step 2a's skip reasons, and promotion is the one event that makes them false — without this, a promoted prose-only PR stays disqualified by a condition that expired hours ago.
- **Report it explicitly** — which blocker landed, which of the five actions ran, and which did not and why: `promoted: blocked-on http://github.com/acme/api/pull/40 merged → synced, CI green, undrafted, prefix dropped, body updated`, or `blocker landed, WIP kept — 2 open TODO markers`.

5. **Set up the workspace, then DELEGATE an eligible sync to `/sy-sync-pr-branch`.** Babysit does not implement branch syncing — the ancestor walk, the merge order, the conflict resolver, the migration-head check, and the pre-push gate all live in `/sy-sync-pr-branch`, which is the single implementation every Sy command shares. Babysit owns the workspace (Steps 6–11 keep using it) and consumes the sync's result block.
   **⚠️ MERGE ONLY — NEVER REBASE**, in this step and every later one. `git pull --rebase`, `git rebase`, and `--squash` rewrite pushed history and force `--force-with-lease` on the next push.
   a. **Resolve an isolated worktree for this PR — ALWAYS a worktree, NEVER the user's primary checkout** (see Never do PR-branch work in the primary checkout). Resolve the PR head branch first: `BR="$(gh pr view <number> --repo <owner/repo> --json headRefName --jq .headRefName)"`.
   - **Create or reuse it with one command: `WT="$(worktree_create "$BR")"; cd "$WT"`** (see One rigid worktree path). The command prints the folder on stdout and diagnostics on stderr, so that line is the entire setup. Do not hand-roll `git worktree add`, do not assemble the path yourself, do not `mkdir` anything: `worktree_create` already prunes stale admin records, reuses a linked worktree already on `$BR`, refuses to hand back the primary checkout, preserves unpushed commits, and falls back to a detached worktree when the branch is checked out in the primary checkout.
   - **Update babysit memory immediately after resolving the workspace.** Record the workspace path/kind and pass number in `## State`; never create a worktree-adjacent journal. Memory persists across passes and re-invocations and is not a temporary API payload.
   - **Check which case you landed in — the alias reports it on stderr — and pay what each one owes:**
     1. **`reusing worktree already on '<branch>'`** — a worktree from an earlier run (or the user's own). `git fetch origin`, then go straight to the recovery pass below. Compare the path against `worktree_create --path-only "$BR"`: if it is not that canonical path, treat it as a pre-existing noncanonical worktree (possibly user-owned or created by an older helper), report it, never migrate or delete it automatically, and stop for human input if it is dirty. The canonical `--path-only` output still names new work; babysit memory remains under the shared LLM root.
     2. **`created a DETACHED worktree`** — the branch is checked out in the primary checkout, so git refuses a second checkout of it. Work detached and push with `git push origin HEAD:"$BR"` (Step 5i) — never `git push` bare from a detached HEAD.
     3. **`keeping <n> unpushed local commit(s)`** — a previous interrupted run committed without pushing, so the alias checked the branch out **as-is, no reset**. Reconcile forward with `git merge "origin/$BR" --no-edit`; those commits are recovered work and Step 5i pushes them. Never reset or drop them.
     4. **`created worktree on '<branch>'`** — a clean start from `origin/$BR`, nothing owed.
   - **If cwd is NOT the target repo** (typical when babysit was invoked with an explicit PR URL from elsewhere), clone the repository outside `$HOME/.worktrees/<owner>/<repo>/`, then run `worktree_create "$BR"` inside that clone. Do not assemble the path, create the container, or invent a temp dir.
   - **⚠️ Recover interrupted work BEFORE the clean guard — assume a previous pass was killed mid-flight.** This command sleeps between polls and polls CI inside a pass, so being terminated mid-run (Ctrl-C, session timeout, reboot, OOM, a fan-out job cancelled) is normal, not exceptional. A reused worktree is _expected_ to hold unfinished work of ours, and a deleted worktree is expected to have left commits on the local branch. In `$WT`, check all four in order and resolve each **before** merging:
     1. **In-progress git operation.** Read `git status`, or look in `$(git rev-parse --git-dir)` for `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `rebase-merge/`, `rebase-apply/`. A left-over `MERGE_HEAD` means the last run died mid-conflict-resolution: finish the resolution per Step 5e and `git commit --no-edit`. Do not `git merge --abort` a resolution that is already complete, and do not start a new merge on top (git refuses anyway). A left-over `rebase-*` is not ours — this command never rebases — so `git rebase --abort` and say so in the report.
     2. **Uncommitted / staged changes** (`git status --porcelain`). At the **canonical** path these are ours from an interrupted pass: read the diff, then either commit it (message describes the actual hunks — see the commit-message rule) if it is complete, or finish the half-edit and commit. At a **non-canonical** path — case 1, the user's own worktree — they are the user's: **STOP and ask.** Never stash, `reset`, `checkout --`, or merge on top of either.
     3. **Untracked files** — same canonical/non-canonical split, ignoring build artifacts and anything already `.gitignore`d.
     4. **Unpushed local commits** (`git log --oneline "origin/$BR..HEAD"`). A run that committed and died before pushing leaves these; a run whose worktree was deleted leaves them on the local branch. Never reset or drop them — they ride out through the normal pre-push gate at Step 5i.
        Report each recovery in the final report (`Recovered from interrupted run: <what>`), and account for it when scoping Steps 6–10 — do not redo work that is already committed in the worktree.
   - **Guard, after recovery: the workspace must be clean before the merge.** Re-run `git status --porcelain` — it must come back empty. If it is still dirty (the user's own worktree, or work you could not confidently finish), STOP and ask the user. Never stash, reset, or merge on top of in-progress work.
   - `cd "$WT"` and run **every subsequent git / `gh` command from there**. The user's primary checkout stays untouched — never `git checkout`, `git switch`, or `gh pr checkout` in it.
   - On final exit — **after the last pass (Step 12), not between passes** — clean up **only the workspace this run created**:
     - Worktree created by this run: `git worktree remove "$WT"`. Only pass `--force` after confirming no uncommitted work to preserve.
     - Clone created by this run: `rm -rf "$WT"` after the same confirmation.
     - **Pre-existing worktree (case 1) at a non-canonical path: leave it in place.** Report the path in the final report; do not remove it.
     - Anything left behind is still reachable via `ls "$HOME/.worktrees"` and reapable by the `git clean-worktree` alias (skips dirty worktrees; skips detached HEADs, so remove those explicitly).
       b. **Confirm the workspace is on the PR head.** `git rev-parse HEAD` should match `gh pr view <number> --repo <owner/repo> --json headRefOid --jq .headRefOid`; if not, fast-forward it (`git merge --ff-only "origin/$BR"`). Skip `gh pr checkout` in worktree mode — it can collide with the branch being checked out elsewhere.
       c. **Apply the sync eligibility gate before every delegation, including resumed work and wave promotion.** Evaluate on full passes, including keepalive and final passes; read-only polls never sync. This gate affects sync only: skipped sync still allows Steps 6–11 when their own gates permit.
   - **Approval veto first.** Refresh reviews and `reviewDecision` immediately before delegation. Any current, non-dismissed approval vetoes sync, even if aggregate review is not `APPROVED`. Use each reviewer's latest decisive review; a later comment alone does not cancel an approval. Record `sync_decision: approval-veto` when approval blocks sync. Unreadable approval state records `sync_decision: unknown` and vetoes ordinary sync too.
   - **Only two exceptions:** a confirmed base-branch merge conflict or a confirmed migration-head conflict permits sync despite approval and bypasses the cooldown. Record the evidence. CI failure, requested changes, comment count, elapsed time, commit distance, overlapping files, wave promotion, and the final round never override approval. `UNKNOWN` mergeability is not a confirmed conflict.
   - **Ordinary sync cooldown:** without approval or either conflict, sync is eligible only when at least `<<SY_PR_SYNC_INTERVAL_SECONDS>>` seconds have elapsed since `last_sync_at`. Before expiry, record `sync_decision: cooldown` and continue without delegating. The interval is a minimum, not a deadline; running-build, wave-block, and parked-decision gates still apply. No special final-round sync.
   - **Missing or invalid history:** when unapproved, perform one read-only comparison on the first eligible full pass. Missing, malformed, or future-dated timestamps require a fresh comparison, never an approval bypass. A changed source chain is compared when the cooldown expires; it does not shorten a valid interval. Resolve the current floor and ancestor sources using the sync skill's chain definition; compare their remote tips against PR head ancestry without merging. Do not implement another merge algorithm.
   - **Behind check:** after the cooldown, compare every current source tip against PR head. No missing commits → record `sync_decision: up-to-date`, current UTC time as `last_sync_at`, and the verified branch/SHA pairs as `last_sync_sources`; do not delegate or push. Missing commits → delegate below. Record each comparison attempt's UTC time as `last_sync_check_at`. A failed comparison records `sync_decision: unknown`; it never advances `last_sync_at` or starts a merge.
   - **Durable bookkeeping:** keep `last_sync_at` (UTC ISO 8601), `last_sync_sources` (branch/SHA pairs), `last_sync_check_at`, and `sync_decision` in babysit memory's `## State`. Carry them through every `pass=single` handoff and reuse them on later invocations. Read the current record before updating it. A verified successful sync, including a verified no-op, resets the interval; a failed, partial, deferred, approval-vetoed, or cooldown-skipped sync never does. No GitHub bookkeeping comments or repository files.
   - **Delegate only when eligible — never merge around the veto.** Invoke `/sy-sync-pr-branch` with the workspace already resolved, local-only, and machine-readable:

     `/sy-sync-pr-branch <PR-URL> workspace=$WT server-side=never report=structured`

   - `workspace=$WT` — the sync runs in babysit's worktree and never creates, cleans, or removes one; babysit owns its lifecycle across all passes.
   - `server-side=never` — `gh pr update-branch` would merge remotely, leaving the local worktree behind and useless for Steps 6–11.
   - Defaults carry the rest: it resolves the ancestor chain fresh, merges the floor then every ancestor root-most → immediate parent (one merge per source), resolves conflicts, runs the migration-head check, runs the pre-push gate, and pushes.
   - **Re-evaluate eligibility every full pass reaching this step, not unconditional sync.** Re-resolve the chain on each eligible comparison and delegation.
     d. **Consume the sync result block** (`/sy-sync-pr-branch` Step 8) when delegation ran. Otherwise continue with the recorded skip decision. Act on a returned result before continuing:
   - `flags: stopped-for-human` or `migrations: needs-human` → the branch is **not** synced. Do not proceed to Steps 6–11 as if it were: report what the sync asked for, end the pass, and fall through to the Step 12 loop gate.
   - `flags: orphaned-base <link>` (an ancestor PR closed without merging) or `retargeted` → carry it into the Step 13 report; the sync already handled the merge itself.
   - `stack`, `floor`, `sources`, `migrations`, `pushed` → quote them verbatim in the Step 13 report. Babysit does not re-derive the stack shape. After verified completion, record `sync_decision: synced` and checkpoint `last_sync_at` and the included source SHAs immediately. A generic `skipped` result alone does not prove current ancestry or reset the interval.
   - **`migrations: re-parented <what>` + a non-empty `pushed` → re-request review from everyone who already approved.** A re-parent is a new commit, so on any repo with "dismiss stale approvals" branch protection every existing approval just silently disappeared and the PR dropped out of `APPROVED` without anyone being told. Left alone, the PR sits green and unmergeable until a human notices — and the next pass's early-exit reads `reviewDecision != "APPROVED"` and reports it as simply not approved yet, hiding the cause.
     - Resolve the prior approvers from the Step 4 fetch: `reviews[]` entries with `state == "APPROVED"`, deduped by `user.login`, excluding yourself and bots. None → nothing to do.
     - Re-request them in one call: `gh pr edit <number> --repo <owner/repo> --add-reviewer <login>[,<login>...]`. If `gh` rejects a login (no longer a collaborator, or the API refuses to re-request an author), report that one and carry on with the rest — never let a single bad login skip the others.
     - Post one comment naming the change as mechanical, so re-approval is a glance and not a re-read: `"Re-parented this branch's migration onto <floor>'s current head (<old> → <new>) after merging <floor> in — no behavior change, no source edits. Re-requesting approval since the new commit dismissed the earlier one(s)."` Same body-file transport and memory update as every other comment this command posts.
     - **Ping once per re-parent, not once per pass.** Record it in the `## State` block's `reping` marker keyed on the re-parent SHA (the same marker Step 7 uses for fix pings). A later pass re-pings only if it pushed a **further** re-parent; three passes must never produce three notifications for one push.
     - **Only for a re-parent this loop pushed.** `migrations: single-head` means nothing changed and nobody is pinged. `migrations: needs-human` already ended the pass above.
   - If the push changed what the PR does, re-check the PR body against the new diff and update it — see the _PR body tracks the branch_ rule.
   - Note: the sync creates regular merge commits on the PR branch. The eventual PR-level merge into the base must still be a **squash merge** per repo policy.

6. **Remediate verified feedback under the selected policy.**
   - **Preserve approval by default.** One verified major finding activates remediation regardless of comment count or existing approval. Major means a reproducible correctness, security, data-integrity, compatibility, or merge-readiness defect; bot labels alone are hypotheses.
   - Set `comment_remediation_required=1` for a completed CI failure, confirmed base conflict, stale migration head, active non-self `CHANGES_REQUESTED` review, or a verified major finding. Under `feedback=all`, any verified unaddressed actionable in-scope request also activates remediation. Read all feedback before classifying; exclude praise, duplicates, unsupported bot noise, and your own findings already dispositioned.
   - Under `feedback=blockers`, minor suggestions receive a recorded disposition without mandatory code churn. Under `feedback=all`, fix verified in-scope requests or give a justified final disposition; no optional deferral satisfies readiness. Fix only within scope when justified, decline with a reason, or record an explicitly optional deferral. Optional deferrals are not addressed fixes; report their count separately. Required reviewer changes remain blockers regardless of severity labels.
   - When remediation is gated off, allow read-only classification, non-code dispositions, and Step 2d closeout of already-pushed fixes. Do not push ordinary polish or re-request review merely to chase a cosmetic LGTM.
   - When remediation is active, `feedback=blockers` fixes only the verified blocker and directly related feedback; `feedback=all` covers every verified actionable request within the PR's approved scope. Preserve unrelated approval and scope. Re-read declined findings if new evidence changes the conclusion; never claim the bot accepted an author-side decline.
   - **Fetch once:** review comments `gh api repos/<owner>/<repo>/pulls/<number>/comments` + issue comments `gh api repos/<owner>/<repo>/issues/<number>/comments`. Track each comment's `user.type` / `user.login` to tell bots (`user.type == "Bot"`, or a known pattern — `*[bot]`, `coderabbitai*`, `copilot*`, `dependabot*`, `sonarcloud*`, `github-actions*`, `renovate*`) from humans; that changes how much weight a suggestion carries, not whether you respond to it.
   - **Disposition only the relevant unresolved comments.** Skip only verified dispositions or feedback proven outside the selected policy's scope. Under `feedback=all`, lack of an active blocker never excludes an in-scope request. An outdated marker or stale SHA never proves a major finding was fixed; verify the current diff before excluding it. Capture each fix SHA right after it lands: `SHA=$(git rev-parse --short HEAD)`. Bot suggestions remain proposals, not orders; apply only a verified fix eligible under the selected policy, otherwise reply with the concrete reason. Anything that would reshape the PR or is genuinely ambiguous is a **stop-and-ask**.
   - **Stop-and-ask remains narrow for active blocker work.** It is available for a split request, a repeated stack request, a change that alters the PR's stated scope or public contract, or a conflict / migration the sync flagged `needs-human`. The blockers profile does not authorize general cleanup; the all-feedback profile never authorizes expanding the PR's approved scope.
   - **A comment is dispositioned once, on the pass that first sees it.** Re-verifying the same comment on pass after pass and deferring it again each time is not diligence — it is nine rounds of no-ops. If you read it, you decide it: fix, decline with a reason, or escalate by name. Carry the disposition in the `## State` block so a later pass never re-litigates a settled one.
   - **Eligible remediation needs no separate permission.** Once the selected policy's remediation gate is active, a relevant comment on the PR is the request; babysit does not wait for separate approval. Outside that gate, preserve approval and do not act on ordinary comments.
   - **After each applied fix, follow Review-thread closeout in the shared PR instructions.** Use its required fix-reply format with the verified fix SHA URL and a short solution sentence. Always resolve the addressed review thread immediately after confirming the reply posted; a reply alone does not complete closeout. Re-fetch all review-thread pages before reporting completion; record the live unresolved count and reasons for remaining threads. Failed resolution or verification is incomplete closeout, not an addressed comment. **Transport mechanics:** Line comments → reply via `gh api -X POST repos/<owner>/<repo>/pulls/<number>/comments/<comment-id>/replies --input <tmp-reply-file>`, then resolve with the `resolveReviewThread` GraphQL mutation (`gh api graphql -F threadId='<thread-id>' -f query='mutation($threadId:ID!){ resolveReviewThread(input:{threadId:$threadId}){ thread{ id isResolved } } }'`; get `<thread-id>` from the `reviewThreads(first:100)` query, matched on `comments.nodes[0].databaseId == <comment-id>`). Issue (top-level) comments → `gh pr comment <number> --repo <owner/repo> --body-file <tmp-comment-file>` (no thread to resolve). Write every body to a unique temp file, delete it after the request whether it succeeded or failed, then update memory only when the result matters beyond the thread itself. A reply-without-fix (declining): post the concrete reason, **no SHA**, then **resolve the thread too when the decline is clear** — the reason is final (out of scope, contradicts the contract, already handled elsewhere, the suggestion is wrong) and the reply asks the reviewer nothing. Leave it open only when the reply poses a question, offers alternatives awaiting the reviewer's pick (split / stack counter-offers), or is a stop-and-ask. Resolve right after the reply posts — and for a fix, only after the fix commit is pushed — never batch resolutions to the end of the pass or ask the user first; a reviewer who disagrees can unresolve.
   - **A request to stack this PR is declined, every time — a review comment does not override the branching policy.** "Rebase this onto my PR #N", "base this on `<branch>`", "stack this on top of that one", or any `--base` pointing somewhere other than `<default>` is the one review request babysit never complies with, regardless of who asked or how reasonable the framing. **Never run `gh pr edit <n> --base <sibling-branch>`, never re-cut this branch from a sibling, and never merge a sibling's branch into this one** (a sibling that already landed arrives through `git merge origin/<default>` — merging its branch directly is what manufactures the dependency). Reply in the thread and leave it open (this is the "explaining why not" path), and give the concrete reason rather than citing policy at them: a stacked child cannot merge until its parent lands, its diff carries the parent's commits so nobody can see what it actually changes, and a squash-merge or retarget under it breaks it. Offer the alternative in the same reply.
   - **A request to split is answered with independent slices, never with a stack.** "This is too big, break it up" is a legitimate ask; the _shape_ of the answer is not the reviewer's to choose. Propose slices that each branch off `<default>` and each merge into `<default>` on their own, **chosen so no two touch the same files** — that is what stops the split from turning into a merge conflict two days later, and it is the whole reason to slice vertically rather than by layer (schema → API → UI is the standard road to a stack, because each layer needs the one beneath it to compile). Disjointness is engineered, not promised: the techniques live in the "Make slices disjoint with new files, not with discipline" rule — most often a new spec file per slice instead of every slice appending to the shared one, EOF appends instead of sorted inserts in registries, regenerate-don't-merge for lockfiles and snapshots, and a tiny prep PR landed alone when every slice needs the same shared edit. **Give the slices no shared ancestor PR**: siblings sequenced onto disjoint files need only `git merge origin/<default>` to stay current, while siblings hanging off a common parent PR are a stack wearing a different name and inherit every one of its failure modes. If no split leaves every piece independently mergeable, say so and keep it as one PR — one larger standalone PR beats two stacked ones, and that is a complete answer to "split this", not a dodge.
   - **Babysit proposes a split; it never performs one.** Cutting branches, moving commits, and opening sibling PRs restructures work the user owns, so a split request that survives the reply above is a **stop-and-ask** (Step 12 terminate-early: a review comment needing human judgment). Post the proposed slice list in the thread, tell the user, end the pass — do not open PRs, do not re-cut branches, and do not close this PR in favor of the slices.
   - **Run the Pre-push gate before any push at the end of this step** (Rules section).

7. **Ping anyone who requested changes only after eligible Step 6 fixes — a `CHANGES_REQUESTED` review is a hard block.** A reviewer who requested changes blocks the merge until _they_ re-review, no matter how green CI is or how many threads you resolved; GitHub does not clear that block automatically. So, once Step 6 has addressed and **pushed** fixes for every one of a given reviewer's comments, tell them and ask for a fresh look.
   - **Identify the blockers.** `gh api repos/<owner>/<repo>/pulls/<number>/reviews` → take the **latest** review per `user.login`, keep only those whose latest `state == "CHANGES_REQUESTED"`, dropping yourself (`gh api user --jq .login`) and any bot (`user.type == "Bot"` or a known bot login pattern). If none remain, skip this step entirely.
   - **Re-request the review** for each such login so it re-appears in their queue: `gh api -X POST repos/<owner>/<repo>/pulls/<number>/requested_reviewers -f 'reviewers[]=<login>'` (a 422 "cannot request from the author / already requested" is fine — report and move on).
   - **Post ONE top-level comment @-mentioning all of them together**, after the fixes are pushed. Write it to a unique temporary Markdown file and post with `gh pr comment <number> --repo <owner/repo> --body-file <tmp-reping-file>`; capture the result, delete the file immediately whether it succeeded or failed, then update babysit memory with the re-review state. Body (plain prose, never persona-styled — a human reads it):
     `@<login1> @<login2> — I've addressed your review comments (<comma-separated fix SHAs>); the threads are resolved and pushed. Since your review currently requests changes and blocks the merge, could you take another look and re-review when you get a chance? Thanks!`
   - **Net-new only — ping once per set of fixes, not once per pass.** Post it only for reviewers whose threads you actually resolved with a pushed fix _this pass_. Do not re-ping on a later pass unless you pushed further fixes for their comments since the last ping (see the _Every review comment must be net new_ rule). A reviewer you only replied "why not" to — no fix — is **not** pinged; leave their block in place so they can respond. In `pass=single` slot mode, carry a `reping` marker in the `## State` block (which reviewers were pinged at which SHA) so a later round does not re-ping without new fixes.

8. **Add / update tests for eligible changes from Steps 6 and 7:**
   - For every code change introduced while addressing bot comments (Step 6) and human comments (Step 7), check whether existing tests cover the new behavior. If not, **add a new test or extend an existing one**. This is language-agnostic — unit tests, integration tests, snapshot tests, table-driven tests, doctests, whatever the repo uses.
   - Look for gaps: new branches / conditions, new error paths, renamed / relocated APIs, edge cases the comment specifically called out, regression coverage for the bug a reviewer flagged.
   - **If this PR's diff removes or renames anything a caller reads — an API, endpoint, response field, event, prop, config key, env var, exported symbol, or column — run the downstream audit before you push, and never treat a green suite as having done it.** Tests only cover the callers someone wrote a test for, inside the repos they run in, so a UI, another service, a job, or a script reading that name is invisible to them; the usual result is silent degradation (a UI dropping to read-only, a control disabling itself, a blank panel, a permission check reading `undefined`), which turns no check red. Grep every layer you can reach for the removed name **as a string** as well as a symbol — `obj["field"]`, serializer allowlists, GraphQL queries, schema / type / spec files, fixtures, templates. Then, in the PR body, list each consumer with its verdict (`updated in <link>` / `unaffected because <reason>` / `unreachable — deprecated instead`). Where a consumer cannot be reached or enumerated, **keep serving the old shape and deprecate it** rather than deleting; a removal that came in as a side effect of an optimization or refactor is the one most likely to skip this. Add a test asserting the consumer-visible shape you kept. Full rules: the Risky Changes section of the always-loaded instructions.
   - Place tests in the repo's existing test folder / file convention (e.g. `software/tests/`, `__tests__/`, `tests/`, `*_test.go`, `spec/`, etc.). Don't invent a new test framework — reuse what's already there.
   - If a comment was a pure doc / typo fix with no behavior change, skip — no test needed.
   - Skip if the change is genuinely untestable (e.g. CI YAML, formatting-only). Note it in the final report.
   - Commit the new/updated tests.
   - **After adding tests, verify coverage didn't regress (best-effort, language-agnostic).** Detect the repo's coverage entrypoint in this order — use the first one that exists:
     1. Repo-defined Make targets: `make test_coverage`, `make coverage`, `make cover`.
     2. `package.json` scripts: `npm run coverage`, `npm test -- --coverage`, or a script literally named `coverage` / `test:coverage`.
     3. Python: `pytest --cov` if `.coveragerc` or `pyproject.toml` `[tool.coverage]` is present.
     4. Rust: `cargo llvm-cov` or `cargo tarpaulin` if either is configured.
     5. Go: `go test -cover ./...` (always available where Go is the language).
     6. README / CONTRIBUTING.md / DEV.md mention of a coverage command — honor that one.
   - If a coverage entrypoint is found, run it once. Most repos with a configured threshold (`vitest.config`, `.coveragerc`, `pyproject.toml`, `codecov.yml`, CI config) will fail the entrypoint on regression — surface the failure in the final report and fix before pushing.
   - If no coverage entrypoint is found, **skip silently** and note `"no coverage tooling detected"` in the final report. Do NOT block on a missing coverage entrypoint — coverage is best-effort; tests being added at all is the primary gate.
   - **Run the Pre-push gate before any push at the end of this step** (Rules section).

9. **Pull current CI state and pre-emptively fix any visible failures (language-agnostic):**
   - Before running local checks, fetch the latest CI status: `gh pr view <number> --repo <owner/repo> --json statusCheckRollup`.
   - For any check already failing (lint, test, type-check, build, config validation, security scan, custom step — any language), pull the logs: `gh run view <run-id> --repo <owner/repo> --log-failed`.
   - Fix what you can locally: lint / format violations, syntax errors, type errors, broken config (`tsconfig.json`, `pyproject.toml`, `Cargo.toml`, `.golangci.yml`, etc.), simple test failures. Same generic posture as Step 11 — diagnose by category, not by language.
   - If a failure is clearly infra / flaky / approval-gated (network timeout, missing secret, queued runner), note it for the final report and move on.
   - Commit any fixes here so they get re-validated by the local checks in the next step.
   - **Run the Pre-push gate before any push at the end of this step** (Rules section).

10. **Run local checks before pushing any new commit (language-agnostic):**

- Detect project type from repo files and run whatever the repo defines. Order of preference:
  1.  **Repo-defined entrypoints first** — `make validate` / `make test` / `make lint` / `make check` (Makefile), `just test`, `pre-commit run --all-files`, scripts in `package.json` / `pyproject.toml` / `Cargo.toml` / `go.mod`, or whatever `README` / `CLAUDE.md` / `CONTRIBUTING.md` says to run.
  2.  **Otherwise fall back to language-native tooling**, e.g.:
      - Node/TS: `npm test` (or `yarn`/`pnpm`), `npx tsc --noEmit`, `npx prettier --check .`, `npx eslint .`
      - Python: `pytest`, `ruff check .`, `ruff format --check .`, `mypy .`
      - Rust: `cargo test`, `cargo fmt --check`, `cargo clippy`
      - Go: `go test ./...`, `gofmt -l .`, `go vet ./...`
      - Shell: `shellcheck`, `shfmt -d`, `bash -n`
      - Config: `tsc --noEmit` for `tsconfig.json`, `yamllint`, `jsonlint`, `cargo check`, etc.
- If any fail, **fix them before pushing** — including lint/format violations, syntax errors, type errors, broken config (`tsconfig.json`, `pyproject.toml`, `Cargo.toml`, etc.), and unit/integration test failures. Re-run until green locally.
- **Self-review your own diff before the pre-push gate — one pass, four lenses.** Read `git diff origin/<base>...HEAD` as if someone else wrote it, through the same lenses `/sy-review-pr` Step 7 uses: **correctness & logic** (off-by-one, unhandled boundary, race, null deref, falsy-vs-absent, an assumption the code cannot guarantee), **security & data integrity** (interpolated query or command, unvalidated trust-boundary input, a permission check that moved or fails open, a credential reaching a log), **performance & regressions** (query in a loop, unbounded fetch, grown complexity class, work added to a hot path), **testing** (a new path with no test, a regression test that would pass against the unfixed code). Linters and type checkers catch none of these, which is exactly why this runs after them and not instead of them.
  - Fix what you find, then re-run the checks above — a self-review fix is a code change like any other.
  - **Anything you find and deliberately do not fix is named in the final report**, with the reason. A known defect pushed silently is worse than one nobody looked for, because the PR now carries an implicit "I read this and it is fine".
  - This is one pass on your own diff, not a review loop, and it never posts anything to the PR.
- **Run the Pre-push gate** (commit-author check + secret scan).
- Commit and push the fixes.

11. **Monitor CI and fix any failure (language-agnostic)** — poll every **15 minutes**, max **10 polls (~2.5 hours)**: `gh pr view <number> --repo <owner/repo> --json statusCheckRollup,reviews,reviewDecision,mergeable`.
    - **Track two counters across the loop:**
      - **Global poll counter**, hard-capped at 10.
      - **Per-check fix-attempt counter** — `attempts[<check-name>]`, hard-capped at **2 fix attempts per individual check name**. Same check failing → same fix tried twice with no result usually means more pushes just churn CI. Stop trying that one.
    - On poll 11: STOP and post the **resumable escalation comment** (template below). Exit.
    - If all checks pass: go back to **Step 4 (early-exit)** to confirm green + approved.
    - If checks are still pending: **re-apply Step 3's classification before spending a poll.** A still-running _blocking_ build → keep polling (counts toward the 10-poll cap). If the only pending entries are non-blocking (human gate or stalled past 60 min), **stop polling** — they will not resolve on a timer, and burning the remaining polls on them ends in a false `poll-cap` escalation 2.5 hours later. Treat CI as settled, name the gate(s), and go back to **Step 4**.
    - If any check is failing:
      a. Get failing run IDs from `statusCheckRollup`.
      b. Examine logs: `gh run view <run-id> --repo <owner/repo> --log-failed`.
      c. **Unfixable-base checks (do these BEFORE diagnosing as a PR-side bug).** Two situations make a red check something other than a defect in this PR, and both waste the whole attempt budget if you diagnose them as code bugs.
      - **Broken main.** Check whether the same check is also failing on `origin/<default>`'s latest commit: `gh run list --repo <owner/repo> --branch <default> --limit 1 --json conclusion,name,headSha`. If the same check name has `conclusion == "failure"` on the latest default-branch commit, this is broken main — **STOP babysit**. Post the escalation comment (template below) with `Stop reason: broken-main`, tell the user, and exit. Do not retry-fix-retry against an unfixable base.
      - **Wave-blocked.** If the PR body has a `## Blocked on` section naming a PR that is still open, this failure is caused by a dependency that has not merged yet, not by anything on this branch — editing code here cannot fix it. Step 4's wave check already ends the pass in that case, so reaching this point means the section appeared or changed mid-pass: re-run that check and end the pass rather than diagnosing. Never spend an attempt-counter slot on a wave-blocked failure.
        d. **Per-check attempt cap.** If `attempts[<check-name>] >= 2`, do NOT try to fix this check again. Mark it `UNFIXABLE_AFTER_2_ATTEMPTS` in state and continue polling other checks. **If ALL currently failing checks are at the cap, STOP** and post the escalation comment with `Stop reason: all-checks-at-attempt-cap`.
        e. Otherwise diagnose the failure regardless of category — could be a test failure, a lint/format violation, a syntax error, a type error, a misconfigured `tsconfig.json` / `pyproject.toml` / `Cargo.toml` / similar, a missing dependency, or a build error in any language. Read the relevant code/config, fix it, and re-run the matching local check from Step 10 to confirm. **Run the Pre-push gate** (Rules section). Commit and push. Increment `attempts[<check-name>]`.
        f. **Go back to Step 3** — re-run the full loop: skip-if-running → early-exit → merge → bot comments → human comments → tests → pre-emptive CI fix → local checks → CI monitor.

    **Escalation comment template (resumable state).** Write the rendered template to a unique temporary Markdown file and post via `gh pr comment <number> --repo <owner/repo> --body-file <tmp-escalation-file>`. Capture the result, delete the file immediately whether it succeeded or failed, then update babysit memory with the escalation and result. Used on: poll-11 cap, all-failing-checks-at-attempt-cap, or broken-main detection.

    ```
    Babysit handing off — PR needs hands-on attention.

    Stop reason: <poll-cap | all-checks-at-attempt-cap | broken-main>
    Passes used: <N> full passes, <M> probes (elapsed <H:MM> of the run budget)
    Watch ticks: <N> (blocked on <what>, or "none — watch never armed")
    Polls used: <N>/10 (in-pass CI polls)
    Per-check fix attempts:
      - <check-name-1>: <attempts> (status: FAILING | UNFIXABLE_AFTER_2_ATTEMPTS | PENDING)
      - <check-name-2>: ...

    Last failing logs:
      - <check-name>: <gh run view URL>

    Commits pushed this session: <comma-separated short SHAs>
    Worktree: <path> (<reused | created-this-run>)
    Recovered from interrupted run: <none | what was recovered>
    Human comments addressed: <N> threads resolved
    Bot comments addressed: <N> fixes applied, <M> declined with reason
    Outstanding human comments: <N> (require judgment)

    To resume: re-invoke `/sy-babysit-pr <PR-URL>`. Restore the saved state and counters; re-invocation alone never resets attempt caps.
    ```

    Include enough state that a re-invocation OR a human picking up the PR can see exactly what was tried and where the loop gave up.

12. **Loop gate — use the shared PR-loop protocol.** Read **Lifecycle and termination** and **Owner and single-pass handoff** in `<<LLM_ROOT_FOLDER>>/skills/sy-pr-loop/SKILL.md`.
    - Keep this workflow's Readiness contract and Step 12b classifier. `goal=ready` exits only after fresh final verification and safe owned-workspace cleanup; `goal=watch` keeps the deadline-driven watch.
    - First pass is full. Later actionable or uncertain events use guarded full passes; verified quiet PRs use Step 12b read-only keepalive/final verification.
    - Early escalation remains bounded by Step 11's broken-main, poll, and per-check caps, plus the Readiness contract's finding cap. Exhaustion is never readiness success.
    - Every in-pass CI wait follows the shared deadline. Under `pass=single`, return after one observation/repair opportunity; only a driver with no waiting peer may permit normal monitoring.
    - **Babysit state:** preserve `attempts`, `polls`, `UNFIXABLE_AFTER_2_ATTEMPTS`, `reping`, `migration_head`, every readiness field, and Step 5c's `last_sync_at`, `last_sync_sources`, `last_sync_check_at`, and `sync_decision`.
    - **Automerge ownership:** keep `automerge_decision` as `enabled_by_me`, `deferred_readiness`, `deferred_companion`, `ineligible`, `failed`, or `pre_existing`. Only `enabled_by_me` permits revocation. Deferred states are rechecked; a failed enablement is not retried.
    - **Workspace ownership:** preserve path, `worktree`/`clone` kind, created-by-this-run flag, and recovery state. Checkpoint allocation, enablement, and pushes immediately. A PR escalation comment cannot reconstruct missing ownership.
    - **Cleanup:** Step 5a teardown waits for `last=true`, a verified ready-goal exit, or GitHub terminal state. Never delete reused user-owned workspaces or dirty/unpushed work. Keep PR memory.

12a. **Read-only probe compatibility anchor.** The canonical fingerprint, two-call cap, timers, and shared state now live under **Read-only probe** in `<<LLM_ROOT_FOLDER>>/skills/sy-pr-loop/SKILL.md`. Read that section; never reconstruct another probe here.
Babysit owns only its external-wait classification: - **A PR is `externally blocked` when a pass ended with it waiting on a person or on another PR and left nothing behind** — (a) Step 3 ended it on a blocking build; (b) Step 4 wave-blocked on an open `## Blocked on` PR; (c) Step 4 green + approved with `autoMergeRequest == null`, waiting on a human click; (d) Step 4 stacked on an open parent; (e) Step 2c prose-only deferred on open companions; (f) the only thing holding the merge is a pending human review gate Step 3 classified non-blocking, and Steps 5–11 found nothing to do; (g) the only outstanding item is a parked Step 2b `needs_user` question already printed for the operator; (h) only a required bot remains pending after all current feedback is dispositioned and no repair remains. Nothing else counts. The label changes nothing about the polling cadence — every PR is polled the same way — but a fan-out uses it to decide it need not hold a worker slot for this PR (`/sy-babysit-prs` Step 4b). - **Never treat a PR as externally blocked while anything is actionable** — an undispositioned comment, a failing check still under its attempt cap, `mergeable != "MERGEABLE"`, a stale migration head, unpushed commits or a dirty workspace, or a stop-and-ask not yet written to memory and printed. Being unsure means not applying the label.
Under `pass=single`, the driver probes and schedules; the worker returns complete state and never starts another clock.

12b. **Babysit wake policy — one classifier for standalone and batch runs.** This section changes babysit scheduling only; review commands retain their existing cadence. The standalone owner or batch driver classifies events locally, without spawning a classifier agent.

    - **Quiet eligibility:** the previous pass verified `externally_blocked`, a clean workspace, and no unpushed work. Missing evidence, unprocessed feedback, or an unfinished operation forbids quiet mode. Approval alone is not proof that nothing remains actionable.
    - **Wake for actionable work:** a new failure or a changed result on a different head; a changed head/base; a confirmed merge or migration-head conflict; relevant review/comment changes; a resolved dependency/rollout decision that permits the next action; or changed eligibility for babysit-owned or companion-deferred automerge. Repeated observations of the same failure never create another fix attempt. Existing attempt caps, running-build guards, and parked-decision restrictions still govern what the pass may do.
    - **Closeout debt is actionable even without new-code remediation authority.** Missing evidence replies or unresolved threads for already-pushed fixes wake the existing owner for Step 2d, even during CI or after approval. Read-only verification never posts or resolves anything itself.
    - **Triage new feedback read-only first.** A new or edited comment/review is a candidate, not automatic remediation permission. Read the changed item and apply Steps 2b and 6. Bounded read-only classification follow-ups are separate from the ordinary two-call probe; they never allocate a worker or workspace. A rollout answer, blocking review, or relevant actionable feedback under the selected policy wakes the owner. Under `feedback=all`, unresolved threads needing an eligible final disposition are actionable too. Other praise, own writes, and already-dispositioned duplicates do not wake it. Required-bot clearance and finding changes are readiness events, even when phrased as praise; verify revision provenance. Uncertain classification gets a guarded full pass.
    - **Harmless CI progress stays read-only:** queued/running changes, successful checks while another blocking build executes, and unchanged pending human gates update status only. When all blocking builds settle, wake only if a next action exists. A green approved PR awaiting a human merge click, or an unchanged rollout decision, remains watched. `MERGED`/`CLOSED` ends watching and invokes only required owner cleanup, never another review/fix pass.
    - **Do not ignore hidden edits.** On every changed snapshot, compare current title/body and issue-comment/review metadata before declaring harmless progress; simultaneous CI movement must not hide an edit. `updatedAt` alone never proves actionability. Fetch only changed bodies needed for classification. If unexplained movement remains, run a guarded full pass. Update the raw fingerprint after every successful classification, including harmless progress, so the same event cannot trigger repeatedly.
    - **Read-only keepalive/final verification:** refresh head/base, approval/review state, check results, all review-thread pages, changed comment/thread sources, and named dependencies. Check Step 2d closeout debt even when the fingerprint is unchanged; unresolved or unverified closeout forbids quiet eligibility. Reapply Step 3's pending/stalled classification even without fingerprint movement. Revalidate any `needs_user` source through Step 2b and all Readiness contract gates, including required bot coverage and migration freshness. A candidate `READY` under `goal=ready` owes final verification; resume the owner only for actions or cleanup the read-only driver cannot perform. The driver may exceed the ordinary two-call probe cap for these bounded checks. No worktree, bulk logs, tests, sync, replies, pushes, or automerge changes. Quiet eligibility must still hold. Actionable/uncertain results wake the existing owner; otherwise checkpoint verification and keep watching. An expired ordinary sync cooldown wakes an unapproved PR only when existing guards permit sync; approval always retains Step 5c's veto.
    - **Rediscover companions, not just known dependencies.** On every read-only keepalive/final verification, rerun Step 2a's complete companion discovery when `automerge_decision` is `enabled_by_me`, `deferred_readiness`, or `deferred_companion`. Refresh batch siblings, branch-group matches, explicit references, and stacked-parent relationships even when this PR's fingerprint is unchanged or its known companion set was empty. A new open companion that invalidates babysit-enabled automerge, or removal of the last companion blocking eligibility, is actionable: wake the existing owner to revalidate Step 2a and change automerge there. For `enabled_by_me`, run its ongoing revocation branch; the initial non-null-automerge skip must not suppress that protection. Driver verification remains read-only. Running CI does not suppress that wake: Step 2a's automerge protection precedes Step 3's build guard. Never revoke user-enabled automerge. Incomplete discovery records uncertainty and schedules guarded owner verification; it never proves eligibility. Store the verified companion set and observation time in `probe_snapshot`.
    - **Reconcile active-worker events.** Classify inbound events through this section before setting `dirty_after_pass`, whether the PR is watched or already active. Harmless CI progress only advances watch state; it never queues another pass. Retain actionable or uncertain event identities and their observed head/source versions in `pending_wake_events`, without interrupting the owner. When the worker returns, compare those events with its returned snapshot and disposition evidence. Drop only events proven consumed or no longer actionable; retain later or unverified events. Requeue once only if actionable or uncertain events remain. A late worker snapshot must not overwrite a newer driver observation. Persist the pending events in memory and state handoffs until reconciliation completes.
    - **Timers and ownership:** preserve `last_full_pass_at`; harmless progress never resets the keepalive. Record `last_watch_verification_at` after a completed read-only verification, and schedule the next keepalive from the latest completed full pass or verification. Carry `probe_snapshot` (field-level state, known feedback/source versions), `wake_reason`, and these timestamps in memory and every state handoff. The driver owns probe counters while watching; no-op worker passes must not substitute for its polls. Unknown legacy state requires verification, not guessed defaults.
    - **Resume, never multiply jobs.** A `watching` PR consumes no worker. On a real wake, match the PR's stable key and resume its idle handle; leave a running owner alone. Replace only a confirmed dead/gone owner, with its latest durable state. Log the wake reason and whether the handle was resumed or replaced. If final verification owes owned-workspace teardown, resume that owner for cleanup only, not a new full pass.
    - **Quiet output:** print one short probe/status line with blocker, next check, and remaining budget. Print a parked question in full on first validation, changed/conflicted verdict, or final report; unchanged pulses show only `NEEDS_USER — unchanged; <next step>`. Retain complete state in memory and the internal handoff, not repeated user-facing dumps. A returning `pass=single` worker reports `yielding to driver`, not `stopping babysit`.

    **Acceptance scenarios:** approved unchanged head + Validations becomes SUCCESS + another build runs → update baseline/status, zero worker wakeups. The same snapshot next poll → one probe, zero wakeups. A new failing check, changed head, confirmed conflict, or actionable rollout answer → resume the existing owner once, subject to guards. Keepalive/final verification with an unchanged parked question → read-only verification and short status, not another no-op worker. Unchanged watched PR + new same-group companion + babysit-enabled automerge → rediscovery wakes the owner for Step 2a revocation, even during CI. The same companion under user-enabled automerge never grants revocation authority. Harmless CI success during an active pass → no dirty mark or follow-up pass. Actionable event already handled by the returning worker → no follow-up; a newer unresolved event → one resumed pass.

13. **Final report:** Lead with `READY`, `WAITING`, `NEEDS_USER`, `EXHAUSTED`, `MERGED`, or `CLOSED`, the selected goal, verified head/base SHAs, and every readiness gate's evidence or blocker. Name bot identities, reviewed SHAs, re-review state, and optional deferrals separately from addressed findings. Include the latest sync decision, last verified sync time, and next ordinary eligibility time. An approval veto remains effective after that time. Quote a sync result only if delegation actually ran; never invent one for a skipped sync. Summarize what happened — workspace setup (worktree path, whether it was reused or created, anything recovered from an interrupted prior run, cleanup status), the Step 2c automerge decision (`enabled — standalone prose-only` / `deferred — readiness evidence missing` / `deferred — prose-only, <n> companion PR(s) open: <links>` / `enabled on pass <N> — last companion landed` / `left off — <what the diff touches>` / `skipped — <draft | WIP | not yours | already enabled>` / `revoked — no longer prose-only` / `revoked — companion PR opened: <link>`), passes run (`<N> passes, <M> probes over <elapsed> of <budget>`, naming what the probes were waiting on, per Step 12a), **the sync result block from `/sy-sync-pr-branch`, quoted verbatim** (its `stack` / `floor` / `sources` / `migrations` / `pushed` / `flags` lines — do not re-derive or paraphrase them), **any check Step 3 classified non-blocking and stepped over** (`pending human gate: <names>` / `stalled check treated as non-blocking: <names>` — these still block the merge, so never report the PR as green while one is open), comments addressed (bot + human), **a per-author disposition count that adds up** (`human: <n> total — <f> fixed, <d> declined-with-reason, <e> escalated (<which stop-and-ask case>)`, same for bots; include optional deferrals as a fourth bucket; the buckets must sum to the total, and any remainder is reported as unaddressed with the reason, never rounded into "addressed"), **any change-requesting reviewer pinged for re-review** (`re-review requested from @<reviewer> (<fix SHAs>)` — a `CHANGES_REQUESTED` block the reviewer must clear), **the migration-head state** (`migration head current (<head>)` / `re-parented <old> → <new>, re-approval re-requested from @<a>, @<b>` / `no migrations in diff` — never report a migration PR as green without naming which head it sits on), **any stack or split request declined in Step 7** (`declined stack request from @<reviewer>: <link>` / `proposed <n> independent slices, stopped for human` — a decline the user never sees is not a stance), tests added / updated, coverage tooling detected (or `"no coverage tooling detected"`), pre-emptive CI fixes, local checks run, **the Step 10 self-review result** (`self-review: 1 correctness fix, 1 perf finding left — <reason>` / `self-review: clean`; a finding found and not fixed is named here, never omitted), CI fixes applied, per-check fix-attempt counts, and merge outcome. **No release is triggered — `/sy-release` stays a manual user action.** **Wave state, when the PR has a `## Blocked on` section:** name every blocking PR and its state, say whether the pass was skipped as wave-blocked or the PR was promoted, and when promoted say the prefix was dropped (or why it was kept).

After producing the report, rewrite babysit memory as the last verified snapshot. `## Progress` keeps only meaningful fixes, pushed SHAs, sync/migration decisions, and CI root causes not obvious from PR comments; `## Open Items` holds unresolved ownership or `None`; `## State` keeps exact resume fields; `## Final Snapshot` records latest verified status, head SHA, validation, and remaining owner. Omit unchanged polls, routine commands, raw logs, and self-explanatory thread text.

## Rules

- **A fix that removes or renames something owes a downstream audit, and local green never discharges it (Step 8).** Addressing a review comment routinely means deleting a field, trimming a payload, or renaming a key — the consumers of that name live in the UI and in other services, break by degrading rather than failing, and no local suite or CI run in this repo can see them. Audit the consumers, record them in the PR body, and deprecate instead of deleting when the search is inconclusive.

- **Step 2d closeout is the narrow exception to the running-build guard below.** It completes evidence replies and resolution for already-pushed fixes under **Review-thread closeout**; it never authorizes branch changes. **Step 3 otherwise remains the first check after the Step 2c automerge gate that may touch the PR — Step 2a/2b only read and persist local memory.** The automerge gate follows Readiness before automerge; queuing alone does not prove bot or migration protection. A **running build** ends the pass after Step 2d: never merge, post other comments, or push while a job is executing. A **pending human review gate is not a build** — an approval / sign-off / changes-resolution check reported by an app sits `IN_PROGRESS` by design until a person clicks, so counting it as "CI is running" makes every pass a no-op and leaves requested changes unaddressed for the entire run. Only self-resolving checks end the pass; human gates, and anything pending past 60 minutes, are named in the report and stepped over. Ending a pass ends the **pass**, not the babysit — fall through to the Step 12 loop gate, resume polling, and re-enter at Step 3 only when Step 12b schedules a full pass.
- The loop is: Step 2a memory/context → Step 2b prior stop revalidation → Step 2c prose-only automerge gate (deferred readiness and companions recheck every pass) → Step 2d already-pushed-fix closeout → Step 3 skip-if-running → Step 4 readiness/terminal-state decision → Step 5 worktree setup + delegated `/sy-sync-pr-branch` (ancestor chain, chain merge, conflicts, migration head, pre-push gate, push) → Step 6 bot comments → Step 7 human comments → Step 8 add/update tests + best-effort coverage check → Step 9 pre-emptive CI fix → Step 10 local checks → Step 11 CI monitor → (on failure) back to Step 3 → Step 12 loop gate (run budget + cheap poll), with Step 12a's read-only probe between passes. On `state == "MERGED"`: report the merge SHA and stop. **Do NOT trigger a release — `/sy-release` stays manual.**
- **The run is bounded by a clock, not a pass count (Step 12).** The shared PR-loop contract owns scheduling. Keep this workflow's ready/watch exits, attempt caps, single-pass handoff, and Step 12b verification policy; no second clock or nested loop.
- **A round with nothing to do costs two read-only `gh` calls, never a full pass (Step 12a).** The shared PR-loop contract owns the probe. Step 12b alone decides whether babysit wakes, including bot-clearance changes and closeout debt; reviews keep their own full-pass policy.
- **A stop-and-ask is surfaced, never prompted (Step 2b).** It pauses this PR for the operator, not on GitHub: the `needs_user` block goes into babysit memory and onto the terminal, with the reason, the exact message, the source it came from, and the next step. No interactive question, no blocking wait, no label / status / review / comment posted to record it — the PR stays as mergeable to everyone else as it was.
- **A `needs_user` claim from a previous run is revalidated before it is shown again (Step 2b).** Re-fetch the source by id, read everything posted since, and resolve to `current` / `cleared` / `changed` / `conflicted` / `stale_unknown`. Use Step 2b's full first/changed/final report and Step 12b's short unchanged-watch status. A cleared claim names the comment that cleared it and the PR resumes normally.
- **Inbound work never interrupts a pass in flight (Step 12).** Apply shared event reconciliation through Step 12b; resume once only when actionable or uncertain events remain unconsumed.
- **An unreachable GitHub or model service ends the run, but only after bounded retries (Step 12).** Apply the shared PR-loop retry/deadline contract and preserve resumable PR memory.
- **ALWAYS work in a git worktree — never the user's primary checkout** (see Never do PR-branch work in the primary checkout). One rigid path: **`$HOME/.worktrees/<owner>/<repo>/<sanitized-branch>`** (see One rigid worktree path). Step 5a never hand-rolls that path or `git worktree add` — `WT="$(worktree_create "$BR")"` does the resolution order itself, and it never returns the primary checkout. When cwd is not the target repo, clone outside the worktree container, then run `worktree_create` inside that clone. Never `git checkout` / `git switch` / `gh pr checkout` in the user's main checkout. Clean up only what this run created; a reused worktree at a non-canonical path is the user's — leave it. The worktree persists across all 10+ passes.
- **Always assume the last run was interrupted; resume its work, never discard it (Step 5a).** Termination mid-run is the normal case here — the loop sleeps between probes and polls CI inside a pass. Before merging anything, recover from the reused worktree, in order: an in-progress merge (`MERGE_HEAD` → finish the resolution and `git commit --no-edit`), uncommitted / staged edits at the canonical path (finish + commit; at a **non-canonical** path they are the user's — stop and ask), untracked files, and unpushed local commits (`origin/<branch>..HEAD` → push through the Step 5i pre-push gate). Two things make discarded work possible and both are banned: `git worktree add -B` onto a branch holding unpushed commits (it hard-resets), and `stash` / `reset` / `checkout --` to "clean up" a dirty worktree. Both are why Step 5a goes through `worktree_create`: it checks for unpushed commits before choosing `-B`, and prunes first so a deleted folder's orphan record cannot make `git worktree add` fail.
- **⚠️ NEVER REBASE.** Always use `git merge` to sync branches. Never use `git pull --rebase`, `git rebase`, `gh pr update-branch --rebase`, or interactive rebase on a PR branch. Rebasing rewrites pushed history and forces `--force-with-lease` on next push. Always merge.
- **Babysit never implements branch syncing — it delegates to `/sy-sync-pr-branch` (Step 5c).** The ancestor-chain walk, the merge order, the conflict resolver, the migration-head check, and the pre-push gate all live there, once, for every Sy command. Never hand-roll a `git merge origin/<base>` in this loop, never re-derive the stack shape, and never copy the sync algorithm back in here. Babysit's own contribution is the workspace (Step 5a–5b, reused across all passes) and reading the result block.
- **Approval veto and timed sync are owned by Step 5c.** Never invoke `/sy-sync-pr-branch` while any current approval exists unless a confirmed merge conflict or migration-head conflict requires it. Cooldown expiry and final rounds never override this veto. Keepalive passes evaluate the same gate on quiet PRs.
- **What an eligible delegated sync guarantees:** the chain is re-resolved from scratch (parents push, merge, and get retargeted mid-run); the floor is merged first, then every ancestor root-most → immediate parent, one merge per source; conflicts are resolved between sources; merges flow downhill only, so no ancestor branch is ever pushed and no ancestor PR is ever merged or retargeted to unblock this one. Cross-stack ordering falls out of the polling loop — a parent that pushes after this pass read it is picked up on the next probe. Never wait on, message, or poll a sibling job.
- **Read the sync result block before continuing (Step 5d).** `flags: stopped-for-human` or `migrations: needs-human` means the branch is NOT synced: end the pass there rather than running Steps 6–11 on a half-merged tree. `orphaned-base` / `retargeted` flags and the `stack` / `floor` / `sources` / `migrations` / `pushed` lines are quoted verbatim in the Step 13 report.
- **A stacked PR that is green + approved is still not yours to merge (Step 4).** Its base is another open PR, so merging would land the work into the parent's branch. Report the blocking parent link, leave automerge alone, end the pass, and keep looping — the parent landing (and GitHub's automatic retarget) is what a later pass is there to catch.
- **No reviewer can authorize a stack (Step 6).** The canonical rules live in the global instructions — "Every PR branches off the default branch", "Split by slice, never by layer", "Overlap is resolved by ordering, never by stacking" — read them there; do not restate, re-derive, or renegotiate them here. Babysit's only job is to hold that line inside the review thread: decline the retarget, counter-offer slices that each stand alone against `<default>` with **no shared ancestor PR**, and stop-and-ask rather than restructuring. The right time to prevent a stack is while the split is still being _described_, not once two branches have diverged on the same files and the conflict is already real. Step 4's stacked-PR handling and the delegated ancestor-chain sync exist to keep an **already-stacked** PR from rotting; neither is permission to create one, and "the tooling supports stacks" is never read as "stacking is fine".
- **A green + approved migration PR is not done until its head is current (Step 4).** The migration-head override runs every pass, ahead of the early-exit, because this is the one state where every signal reads ready and merging still breaks the default branch: sibling revisions are separate files so `mergeable` stays `MERGEABLE`, and this branch's CI never ran against the head that landed while it sat. It matters most on a PR with `--auto` already on — that one merges unattended, so the head is re-checked on **every watch poll** while automerge is enabled, not once on entry. Babysit's read-only override delegates framework-specific detection and re-parenting, which live in `/sy-sync-pr-branch` Step 7, and the override's only job is to refuse to early-exit so that sync actually runs. Never resolve drift by rebasing, and never `alembic merge` when re-parenting is available.
- **A re-parent dismisses approvals, so babysit re-requests them (Step 5d).** `migrations: re-parented` plus a push means every prior approval was silently dropped by branch protection and the PR left `APPROVED` with nobody told. Re-request each prior approver by login and post one comment saying the change was mechanical (`<old> → <new>`, no source edits). Once per re-parent SHA, tracked in `reping` — three passes never send three pings for one push.
- **A wave-blocked PR is a documented skip, never a build to fix (Step 4).** A later-wave branch is red because it does not contain the migration or field it needs, and that is the design working, not a defect — see the _Hard dependencies phase into waves, never into a stack_ rule. Skip the pass while its `## Blocked on` PRs are open, re-check every pass, and never resolve a wave block by rebasing this branch onto the blocking PR; that converts a clean wait into the stack the rules forbid.
- **A merged blocker is an event this command acts on, not one it reports (Step 4a).** GitHub does not undo a `WIP: DO NOT MERGE — ` prefix, a `## Blocked on` section, or draft state when the wave below lands, so a wave-2 PR left alone stays unmergeable forever while reading as green. Promotion runs every pass — even on a pass Step 4 ended early — and in a fixed order: sync, CI green, `gh pr ready`, drop the prefix, rewrite the body, then re-run the Step 2c automerge gate once. It is idempotent, it promotes **per reason** (a WIP kept alive by an open `TODO —` marker keeps its prefix), and it is reported action by action.
- **Pre-push gate runs before every `git push` in this command — no exceptions.** Two checks, both blocking:
  1. **Commit-author identity check.** Compare each pending commit's `author.email` and `author.name` to local config (`.gitconfig`): `git log @{u}..HEAD --format='%H %ae %an'` vs `git config --get user.email` / `user.name`. On mismatch, flag the SHA(s) + identities side-by-side and ask the user whether to proceed with the existing author. **Default = "no"** → run `git commit --amend --reset-author --no-edit` (single commit) or `git rebase <base> --exec 'git commit --amend --reset-author --no-edit'` (multiple). **Preserve `Co-Authored-By:` trailers** — `--reset-author` only touches the author field; trailers in the message body survive. Only push without `--reset-author` on explicit user "yes".
  2. **Secret scan.** Scan all unpushed changes — `git log @{u}..HEAD -p` plus `git diff --cached` (if anything staged). Check for:
     - **Filename allowlist** — flag staged paths matching: `.env*` (except `.example` / `.sample` / `.template`), `**/credential*`, `**/secret*`, `**/*.pem`, `**/*.key` (except `.pub.key`), `**/*.p12` / `.pfx` / `.keystore`, ssh keys (`id_rsa*` / `id_ed25519*` / `id_ecdsa*` / `id_dsa*`), `*.kdbx`, `service-account*.json`, `gha-creds-*.json`, `.npmrc` / `.pypirc` / `.netrc` with auth lines, `.aws/credentials`, `.kube/config`, `.docker/config.json`, `terraform.tfstate*`.
     - **Content patterns** — AWS (`AKIA|ASIA[0-9A-Z]{16}`, `aws_secret_access_key\s*=`), GitHub (`gh[pous]_[A-Za-z0-9]{36,}`, `github_pat_`), Anthropic/OpenAI (`sk-(ant-|proj-)?[A-Za-z0-9_-]{20,}`), Slack (`xox[abprs]-`), Google (`AIza[0-9A-Za-z_-]{35}`), private keys (`-----BEGIN .* PRIVATE KEY-----`), JWTs (`eyJ[A-Za-z0-9_-]+\.eyJ[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+`), assignments `(password|api[_-]?key|token|secret)\s*=\s*["'][^"']{6,}` — skip placeholders (`<...>` / `xxx` / `***` / `example`).
     - On hit: redact the value (e.g. `AKIA****REDACTED****`), show path + line + matched pattern, ask the user. **Default = "no"** → STOP, do not push, tell the user to remove the commit (`git reset HEAD~N` or rebase) and re-stage clean. Proceed only on explicit "yes" + user confirms false positive.
- Never skip local checks before pushing — it wastes CI cycles.
- **Bot comments follow Step 6.** Fix verified, in-scope defects regardless of author; decline unsupported redesigns with a concrete reason, and escalate only the enumerated stop-and-ask cases. Non-trivial does not mean skippable.
- **Every behavior-changing fix from Step 6 or 7 needs test coverage in Step 8.** Doc/typo/format-only changes are exempt. Coverage verification at the end of Step 8 is best-effort and language-agnostic — skip silently if no entrypoint is detected; do NOT block.
- Fix CI failures of every kind (tests, lint, type-check, build, config) regardless of language — do not assume JS/Node.
- **Broken-main detection runs before every fix attempt.** If the same check is failing on `origin/<default>`'s latest commit, the PR can't go green until default is fixed — stop, post the escalation comment, flag the user.
- Poll CI every 15 minutes; do not spam `gh` calls. Each wake runs the full loop (comments + CI) in one pass. Hard cap at 10 polls (~2.5 hours) — escalate via the resumable escalation comment after that.
- **Per-check fix-attempt cap = 2.** A single CI check failing twice with no result usually means the fix path needs human judgment. Don't churn CI with a third attempt — mark it `UNFIXABLE_AFTER_2_ATTEMPTS` and surface in the escalation comment.
- **After every applied fix, enforce Review-thread closeout** in the shared PR instructions (transport in Step 6). Already-pushed fixes bypass only reply/resolution skip gates through Step 2d; new edits, pushes, sync, and review requests retain their existing guards.
- **Human comments are auto-fixed, exactly like bot comments (Step 6).** There is no "surface it to the user and move on" disposition — that is how a PR accumulates nine rounds of verified-but-untouched feedback while every report claims the pass ran clean. Every comment leaves the pass fixed-and-replied, declined-with-a-reason, or escalated under one of the four enumerated stop-and-ask cases, and the Step 13 counts must sum to the number of open comments.
- **A `CHANGES_REQUESTED` review is a hard block that only the reviewer clears — ping them once you've addressed it (Step 6).** Resolving threads and going green does not lift a requested-changes review; GitHub keeps the merge blocked until that reviewer re-reviews. After pushing fixes for all of a given blocker's comments this pass, re-request their review and post ONE top-level comment @-mentioning them, telling them their comments were addressed (with the fix SHAs) and asking for a re-review. Net-new only: ping a reviewer once per set of fixes, never once per pass, and never ping someone you only replied "why not" to. The comment body is human-facing prose — never persona-styled.
- **Release dispatch is NEVER automatic.** Releases are expensive and stay a manual `/sy-release` the user invokes deliberately. When babysit observes `state == "MERGED"`, report the merge and stop — do not dispatch a release, and do not offer to.
- **A merged PR is reaped, not left to rot (Step 4).** The terminal `MERGED` observation stops babysit before Step 5's per-run worktree teardown ever runs, so the dead branch and worktree must be cleaned up right there: `git clean-worktree` (removes worktrees whose branch is merged or gone, skips dirty ones and detached HEADs), then `git clean-stale-branches` (deletes the local branch whose upstream went `[gone]` on the squash-merge). Remove a skipped detached-HEAD worktree with `git worktree remove <path>` only after confirming it is clean. **Never `--force` past a dirty tree and never delete babysit memory** — a worktree with unpushed commits or uncommitted work means work never made it into the merged PR: report its path and leave it for the human (see the _A merged PR gets cleaned up_ global rule).
- **Never enable automerge on babysit's own behalf — with one carve-out: a STANDALONE prose-only diff (Step 2c).** Docs files, comments, docstrings, whitespace and nothing else, **and no companion PR still open** → babysit applies Readiness before automerge and runs `gh pr merge <n> --squash --auto` only when permitted, then says so. Any executable line in the diff and automerge stays off until the user says otherwise. A prose-only PR that belongs to a set (batch siblings, a shared `<username>/<group-slug>/` branch prefix in any repo, an explicit reference to another open PR, or a stacked base) is **deferred, not enabled** — babysit re-checks each pass and flips `--auto` only once the last companion is merged or closed, so docs never land ahead of the code they describe. If babysit's own later commits make the PR non-prose-only, it runs `--disable-auto` and hands the merge back. Automerge the user or `/sy-create-pr` enabled is never touched — babysit observes it and waits (Step 4).
- **Migration head stays single — checked and fixed inside the delegated sync** (`/sy-sync-pr-branch` Step 7), once after the whole chain merges: exactly one head descending from the floor, re-parented rather than merge-revisioned, never re-parenting an ancestor PR's migration. `/sy-review-pr` warns about cross-PR migration conflicts; the sync fixes them. Babysit only reports the `migrations:` line it gets back.
